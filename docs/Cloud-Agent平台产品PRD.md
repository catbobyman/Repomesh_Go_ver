# Cloud Agent 平台产品需求文档（PRD）

版本：v0.1 · 待评审  
日期：2026-09-07  
产品对象：面向个人开发者与研发团队的云端智能体工程平台  
参考范围：本次会话已阅读的 Cursor 2026 年 1–9 月更新日志

## 1. 文档定位

本 PRD 将 Cursor Cloud Agents 的能力演进转化为一套可讨论、可分期实施的产品需求，覆盖任务入口、自主执行、自动化、开发环境、基础设施、软件交付、扩展与治理。

本文是独立的平台产品设计稿，不代表 Cursor 官方 PRD，也不表示当前 RepoMesh 项目已经实现或承诺实现这些功能。是否落入现有项目、技术选型、人员投入、排期和商业定价，需在本稿评审后确定。

区分两类内容：

- **参考事实**：来源于已阅读的 Cursor 更新日志，来源索引见第 15 节；相关发布时期仅用于说明参考产品的演进。
- **设计要求**：本文提出的交互、状态、权限、资源边界、交付规则与验收标准；属于拟建产品的方案，不作为 Cursor 现有行为的事实陈述。

路线分为四个阶段：远程执行、Agent 平台、工程系统、自治基础设施。各阶段以验收门槛推进，不直接照搬 Cursor 的发布时间作为本产品排期。

## 2. 背景与问题

开发者将任务交给智能体后，仍需要处理环境安装、上下文补充、运行中断、测试验证、代码审查和部署等工作。任务越长、涉及的仓库越多，人工协调成本越高。

团队规模化使用智能体时，会进一步遇到环境不可复现、多个任务互相影响、凭证和权限分散、无法追踪费用，以及内网资源无法接入等问题。

本产品提供统一的任务与运行管理界面，将目标、代码、执行环境、外部事件和交付物关联起来，使智能体能够在明确的权限、资源和验收边界内持续完成软件工程任务。

## 3. 用户与核心场景

| 用户 | 主要诉求 | 典型场景 |
|---|---|---|
| 个人开发者 | 离开电脑后任务继续运行，随时跟进结果 | 将本地完成规划的功能开发交给云端，在手机上查看结果 |
| 全栈及跨仓库开发者 | 在隔离环境内处理多个仓库与并行任务 | 同时修改前端、后端和共享 SDK |
| 代码审查者 / 技术负责人 | 快速理解变化、验证质量、推动 PR 完成 | 查看测试与演示证据，要求 Agent 处理审查意见 |
| 团队管理员 | 统一管理环境、工具、权限和费用 | 配置团队开发环境、MCP、预算与网络策略 |
| 平台工程师 | 将 Agent 接入现有基础设施和 CI | 部署自托管 Worker，处理 CI 失败和工单事件 |

### 3.1 首要用户故事

1. 作为开发者，我希望将一个目标交给云端任务后关闭本地电脑，并在恢复查看时找到运行记录、验证结果和可审查的代码。
2. 作为开发者，我希望把长任务派给云端子智能体，同时继续本地工作，并在完成后审查和接收其结果。
3. 作为负责人，我希望 PR 的 CI 失败或新审查意见能够唤醒原任务，继续修复而无需重新解释背景。
4. 作为团队管理员，我希望开发环境可复用、可回滚，任务只能使用获授权的仓库、密钥和外部工具。
5. 作为平台工程师，我希望在自有机器上执行任务，并通过同一界面监控和接管。

### 3.2 核心端到端流程

选择仓库与环境 → 描述目标及验收条件 → 确认计划和资源范围 → 云端执行 → 测试与证据生成 → 人工审查或自动反馈 → 提交 / 更新 PR → 合并与发布。

在阶段二以后，外部事件可代替人工启动任务；在阶段四以后，已有任务可订阅后续事件并恢复运行。

## 4. 产品目标与范围

### 4.1 产品目标

- 开发者离线时，云端任务仍可执行并可靠保存进度。
- 每项任务获得隔离、可复用、可追踪版本的开发环境。
- 交付物同时包含代码变化、验证结果、剩余问题与必要的运行证据。
- 团队可从单个任务逐步扩展到并行子任务、定时自动化和事件驱动任务。
- 管理员可控制工具、仓库、网络、资源预算和执行基础设施。

### 4.2 本路线的边界

范围内：云端任务生命周期、运行环境、多 Agent 协作、外部事件、PR 交付、远程控制、自托管、API 与团队治理。

暂不单独建设：通用 IDE、基础模型训练、完整项目管理系统、完整 CI 引擎、通用办公套件。优先通过现有代码托管、协作工具和 CI/CD 集成完成流程。原生代码托管列入阶段四扩展范围，需单独满足实施门槛。

## 5. 核心对象与状态

### 5.1 领域对象

| 对象 | 定义 | 关键关系 |
|---|---|---|
| 项目 Project | 用户组织仓库、环境和任务的工作范围 | 包含一个或多个仓库和环境 |
| 任务 Agent Task | 持久保存目标、对话、上下文与交付记录的工作单元 | 包含多次 Run，可具有父任务和子任务 |
| 运行 Run | 一次提示或一次事件触发的执行过程 | 属于一个任务，记录环境、状态、用量和结果 |
| 执行环境 Environment | 仓库、工具链、安装步骤、启动步骤、凭证引用和网络配置的组合 | 配置可版本化，供多次运行复用 |
| 环境构建 Build | 根据环境配置生成的可启动产物 | 记录配置版本、提交、状态、日志及生成时间 |
| 自动化 Automation | 可反复触发新工作的规则 | 定义触发器、指令、范围、环境与预算 |
| 订阅 Subscription | 已有任务对特定事件源的持续关注 | 事件到达后恢复原任务，保留目标与上下文 |
| Worker / Pool | 实际执行工具调用的机器及可领取任务的机器集合 | 绑定能力、组织和可执行范围 |
| 交付物 Artifact | diff、测试报告、截图、视频、日志、预览或部署结果 | 关联具体 Run 和代码版本 |

自动化与订阅必须在产品上区分：自动化默认发起一项新任务；订阅默认恢复同一项任务。两者都需要去重、预算、终止条件和可审计的触发记录。

### 5.2 状态设计

运行状态：排队中 → 准备环境 → 执行中 → 成功 / 失败 / 已取消。执行中可进入“等待用户”，收到输入后继续；等待期间不计入活跃执行时长。

任务状态：进行中、等待输入、等待外部事件、待审查、已完成、已停止。任务归档是可恢复的组织操作，不等同于运行取消或目标完成。

交付状态：无变更、待审查、有待解决问题、可合并、已合并、已发布。运行成功表示本轮正常结束，不自动表示代码正确、PR 可合并或目标完成。

界面同时展示任务状态、运行状态和交付状态，避免单一“完成”标签混淆不同含义。

## 6. 功能需求

优先级定义：P0 为对应阶段上线必需；P1 为对应阶段增强项；P2 为满足验证门槛后进入的扩展项。优先级不代表所有阶段同时建设。

### 6.1 任务入口与控制面

| 编号 | 功能与需求 | 阶段 / 优先级 | 验收标准 |
|---|---|---|---|
| ENT-01 | Web 创建任务，选择项目、仓库、起始分支、环境、模型和目标 | 一 / P0 | 创建后显示唯一任务、环境版本与起始提交；错误配置可定位 |
| ENT-02 | CLI 云端接力，传递对话、计划和选定代码状态；支持“云端执行计划” | 一 / P0 | 本地退出后云端继续；用户可通过返回的任务链接跟进 |
| ENT-03 | 统一任务列表，展示状态、项目、运行位置、用量、最近活动和待处理项 | 一 / P0 | 可按状态与项目筛选；同一任务各入口显示一致结果 |
| ENT-04 | 运行中追加消息，支持排队与下一安全边界引导；单独提供立即停止 | 二 / P0 | 消息不丢失、状态可见；发送引导不会伪装成已取消当前工具 |
| ENT-05 | 本地与云端双向交接，预览迁移代码、上下文、分支和环境差异 | 三 / P0 | 目标端确认接收后才结束源端执行；失败可继续在源端工作 |
| ENT-06 | 移动端启动、跟进、输入、审查和合并；完成或需输入时通知 | 三 / P1 | 无需桌面端可完成一次任务审查；通知可直达关联任务 |
| ENT-07 | 平板多任务、分屏审查、收件箱和截图标注 | 三 / P1 | 可区分进行中、需关注、待审查任务；标注关联具体图像 |

交接时，未提交改动采用显式选择；用户能预览将传递的文件。凭证不随对话复制，目标环境通过已有授权独立获取。正在执行且无法安全迁移的工具需等待结束或明确停止。

### 6.2 自主运行与任务编排

| 编号 | 功能与需求 | 阶段 / 优先级 | 验收标准 |
|---|---|---|---|
| ORC-01 | 长任务先形成计划，持续执行并定期保存进度 | 一 / P0 | 客户端断开不影响运行；恢复查看后可识别已完成步骤和剩余问题 |
| ORC-02 | 支持异步子任务；父任务继续执行或等待指定子任务 | 二 / P0 | 父子关系、状态与结果可追踪；子任务失败不误报整体成功 |
| ORC-03 | 将计划拆成独立步骤和依赖步骤，并行执行独立工作 | 二 / P1 | 有依赖的步骤等待前置结果；并发不超过任务与组织上限 |
| ORC-04 | 云端子任务在独立 VM 和分支运行，支持 /in-cloud 类入口 | 三 / P0 | 子任务不直接污染父任务工作区；结果通过可审查的提交或补丁交付 |
| ORC-05 | 照看 PR，处理 CI 失败与审查意见，达到条件后进入待审查 | 三 / P0 | 每次修复关联触发事件和验证结果；不会绕过分支保护 |
| ORC-06 | 长期目标模式，定义完成条件、预算、期限和停止条件 | 四 / P0 | 达到条件后停止；预算耗尽或条件无法满足时明确暂停并报告 |
| ORC-07 | 任务订阅 PR、线程与时间事件，有进展时恢复执行 | 四 / P0 | 重复事件不重复执行；目标完成或用户停止后不再唤醒 |
| ORC-08 | 固定技能作为自定义模式；允许范围受控的跨运行记忆 | 四 / P1 | 可查看、修改和清除记忆；记忆及模式不扩大任务权限 |

父任务需审查子任务结果再整合；发生代码冲突时显示冲突及相关任务。任务树共享总预算，并设置最大并发与嵌套深度。预算不足时不再派生子任务。

### 6.3 自动化与外部事件

| 编号 | 功能与需求 | 阶段 / 优先级 | 验收标准 |
|---|---|---|---|
| AUT-01 | 定时与 Webhook 自动化，可配置环境、指令、模型和预算 | 二 / P0 | 显示时区、下一次执行时间、触发记录和执行结果；支持启停 |
| AUT-02 | GitHub / GitLab 类代码事件：Issue、PR、评论、Review、CI 结果 | 二 / P0 | 事件关联仓库和代码版本；重复投递不会创建重复工作 |
| AUT-03 | Slack 消息、提及与表情触发；读取获授权线程上下文 | 三 / P0 | 可从源消息追踪任务；失败原因回传到配置的通知位置 |
| AUT-04 | Jira、Linear、Teams、PagerDuty 等协作入口 | 三 / P1 | 工单或线程内容映射到任务；结果包含状态与交付链接 |
| AUT-05 | 多仓库自动化和无仓库自动化 | 三 / P0 | 任务可访问全部授权仓库；无仓库任务无需虚构代码项目 |
| AUT-06 | 自然语言创建自动化，提供可编辑配置预览和试运行 | 三 / P1 | 展示解析出的触发器、范围、执行身份和预算后才能启用 |
| AUT-07 | 跨频道获取上下文和回传结果 | 三 / P1 | 只能访问执行身份有权限的频道；敏感输出遵循目标频道权限 |

每条自动化配置执行身份、并发限制、失败重试次数和自触发策略。Agent 自己产生的评论或提交默认不能无限触发自身。连续失败达到阈值后暂停，保留失败原因并通知负责人。

### 6.4 云端开发环境与验证

| 编号 | 功能与需求 | 阶段 / 优先级 | 验收标准 |
|---|---|---|---|
| ENV-01 | 为任务提供隔离 VM，克隆仓库、安装依赖、执行启动命令 | 一 / P0 | 同时运行的任务互不共享可写工作区；启动失败有阶段日志 |
| ENV-02 | 自动环境配置助手，发现缺失依赖与凭证，执行验证 | 一 / P1 | 保存前展示配置与验证结果；缺失条件明确呈现 |
| ENV-03 | Dockerfile / 配置文件定义环境；区分安装和会话启动步骤 | 二 / P0 | 同一配置可复用；环境可追溯到配置版本 |
| ENV-04 | 多仓库环境，为各仓库定义分支、路径和权限 | 三 / P0 | 一个任务可跨仓库修改；分别记录代码版本和交付物 |
| ENV-05 | 构建密钥、运行密钥分别注入；构建密钥不进入最终镜像 | 三 / P0 | 非授权环境不能获取密钥；日志不输出密钥原文 |
| ENV-06 | 镜像层缓存、快照和版本管理，支持回滚 | 三 / P0 | 可识别缓存命中和实际版本；回滚不改写历史运行记录 |
| ENV-07 | Builds 预构建、预热、刷新和手动重建，保留最后可用构建 | 四 / P0 | 坏构建不替代成功构建；每次运行显示使用的构建及新旧差异 |
| ENV-08 | Computer Use 操作浏览器和桌面，运行软件并验证 UI | 一 / P0 | 示例任务可实际执行 UI 流程，保存可回放证据和失败步骤 |
| ENV-09 | 保存截图、视频、日志和测试报告 | 一 / P0 | 证据关联 Run、提交和时间；失败任务的证据仍可审查 |
| ENV-10 | 端口转发、实时预览和基于画面的修改反馈 | 三 / P1 | 用户可访问授权预览；环境结束后链接明确提示失效 |

环境回退必须可见。如果回退导致缺少测试工具或启动服务，任务只能报告“验证受阻”，不得将未执行的检查记为通过。预热和缓存不得跨租户共享密钥或私有可写数据。

### 6.5 基础设施与部署形态

| 编号 | 功能与需求 | 阶段 / 优先级 | 验收标准 |
|---|---|---|---|
| INF-01 | 平台托管计算资源，调度云端运行并显示容量等待状态 | 一 / P0 | 无可用容量时明确排队；取消排队不再分配机器 |
| INF-02 | 自托管 Worker 接入，工具在用户网络内执行 | 二 / P1 | 可查看在线状态、能力、归属和任务；只能领取获授权工作 |
| INF-03 | 个人机器作为运行目标，支持远程跟进和接管 | 三 / P1 | 机器离线时明确提示；无法接管时保留会话与结果 |
| INF-04 | 团队 Worker 池，按能力和权限调度，支持容量扩缩 | 四 / P0 | 空闲兼容 Worker 能领取任务；单个任务不会被并发重复领取 |
| INF-05 | 闲置休眠、事件唤醒和重连恢复 | 四 / P0 | 重连期限内恢复上下文；超时后呈现恢复结果或清晰失败原因 |
| INF-06 | 对接第三方沙箱及计算服务 | 四 / P1 | 先验证一种提供商的创建、运行、取消、回收，再扩展适配 |
| INF-07 | Linux / Mac 自托管 Computer Use、桌面观看与人工接管 | 四 / P1 | 用户与 Agent 的输入控制权明确切换，避免同时操作 |

自托管需明确控制面与执行面的数据边界，列出仍需传给模型或控制服务的数据。不得仅因工具本地执行就宣称全部数据不出内网。

### 6.6 代码审查与交付闭环

| 编号 | 功能与需求 | 阶段 / 优先级 | 验收标准 |
|---|---|---|---|
| DEL-01 | 生成交付包：变化摘要、diff、验证结果、证据和剩余问题 | 一 / P0 | 审查者无需阅读全文即可判断改了什么、测了什么、还缺什么 |
| DEL-02 | 创建和更新 PR，保留任务、运行与提交关联 | 一 / P0 | 同一任务后续修复更新目标 PR，重复请求不创建多余 PR |
| DEL-03 | 根据 Bugbot 类检查结果启动修复任务，验证后提交方案 | 二 / P1 | 发现项、修复提交和测试结果可对应；自动推送需受策略控制 |
| DEL-04 | 集中查看评论、检查、审批、提交和 diff，并推动修复 | 三 / P0 | PR 状态与代码托管平台同步；权限不足时不显示虚假成功 |
| DEL-05 | 按逻辑将变更拆分多个 PR，表达仓库和分支依赖 | 三 / P1 | 执行前有拆分方案与恢复点；每个 PR 可追踪到原任务 |
| DEL-06 | 移动端审查与合并 | 三 / P1 | 与 Web 使用相同权限和分支保护约束 |
| DEL-07 | 无仓库从零构建，成熟后保存为正式仓库 | 四 / P1 | 草稿项目内容可恢复；建库时配置名称、可见性与归属 |
| DEL-08 | 接入托管平台进行预览和发布，关联部署结果 | 四 / P1 | 预览与生产环境明确区分；发布失败保留日志和上一版本信息 |
| DEL-09 | 原生代码托管与外部仓库同步 | 四 / P2 | 明确权威仓库、推送路径、同步延迟、冲突规则和访问权限 |

默认由用户或已有仓库规则决定合并与生产发布。持续推进 PR 的目标不会自动授予合并、绕过审批或生产发布权限。

## 8. 典型流程与异常处理

### 8.1 本地规划后交给云端

1. 用户在本地完成规划，选择“云端执行”。
2. 展示将传递的仓库、分支、提交、未提交改动和上下文，以及目标环境。
3. 云端准备环境；失败则保留本地状态并展示原因。
4. 云端确认接收后启动运行，本地可退出。
5. Agent 执行、测试、生成交付包和 PR，用户在任一授权入口审查。

验收：关闭本地客户端不影响任务；重复交接不会创建重复工作；环境差异和遗漏的文件可定位。

### 8.2 跨仓库并行开发

1. 用户选择包含前端、后端和共享库的环境，描述目标与接口约束。
2. 主任务确定共享接口和依赖关系，给独立工作派生子任务。
3. 子任务在隔离环境及分支中执行，分别提交验证结果。
4. 主任务审查结果、处理冲突并执行集成验证。
5. 输出按仓库划分的 PR 和合并顺序。

验收：独立测试通过不能替代集成验证；任何仓库无写权限时应提示受阻，不得声称全部交付。

### 8.3 PR 持续推进

1. 用户为任务设置“处理反馈直至具备合并条件”，并配置预算和期限。
2. 任务订阅 PR 的 CI、审查和评论事件；等待时释放不需要的计算资源。
3. 收到有效新事件后恢复，先确认当前提交，再修复和验证。
4. 满足配置条件后进入待审查；如获独立授权则执行后续合并流程。

验收：过时提交的 CI 结果不会错误唤醒修复；重复事件去重；失败循环触及阈值后停止并报告。

### 8.4 异常矩阵

| 异常 | 产品行为 | 用户可执行动作 |
|---|---|---|
| 环境构建失败 | 展示失败步骤；有可用旧构建时说明差异并按策略回退 | 修复配置、重建、选择版本 |
| Worker 掉线 | 标记失联，保存已有记录，等待重连或进入恢复流程 | 更换执行目标、停止、查看恢复范围 |
| 工具调用结果不确定 | 标记不确定的外部操作，恢复时先确认结果 | 查看日志、确认是否继续 |
| 权限或凭证不足 | 进入等待输入，说明缺失能力和影响 | 提供授权、缩小范围、停止 |
| 子任务冲突或失败 | 父任务保留成功结果，展示受阻依赖 | 重试指定子任务、调整计划、人工处理 |
| 预算 / 时长上限 | 停止新增工作，保存进度并列出未完成事项 | 增加预算、缩减目标、结束任务 |
| 用户取消 | 停止调度与后续动作；已发生的外部操作仍可查 | 查看部分成果、恢复为新运行 |
| 自动化反复失败 | 达阈值暂停，保留触发链与失败原因 | 修改配置、试运行、重新启用 |

## 9. 四阶段建设路线

### 阶段一：远程执行

价值主张：交给云端后，用户离线也能完成一项可审查的工程任务。

上线必需：Web 与 CLI 入口、单仓库、托管隔离环境、长任务与日志、Computer Use、测试证据、PR、基础身份权限和预算限制。

优先覆盖修复缺陷、补充测试、小型功能三种任务。环境使用少量受支持模板；代码托管先完成一种集成。

退出门槛：三种场景均能完成“启动 → 离线执行 → 验证 → PR → 人工审查”；失败可诊断；客户端断开不丢结果；跨任务隔离和预算停止有效。

参考时期：Cursor 1–2 月的 CLI 接力、长期任务、电脑操作与工件交付。[R01–R04]

### 阶段二：Agent 平台

价值主张：将一次性远程执行变成可编程、可并行、可被事件调用的平台能力。

上线必需：异步子任务、统一运行对象、定时与 Webhook、代码事件、Skills / MCP、版本化环境配置、SDK / API、流式恢复。自托管先做受控试点。

退出门槛：相同目标可从 Web、CLI、API 和自动化进入；父子任务可追踪；事件去重与并发限制有效；API 断线后可恢复事件读取；自托管试点能证明执行与数据边界。

依赖：阶段一任务生命周期、权限和环境模型稳定。

参考时期：Cursor 3–4 月的 Automations、自托管、统一窗口与 SDK / API。[R05–R09]

### 阶段三：工程系统

价值主张：让团队通过既有仓库、工单、协作平台和 CI 协同交付。

上线必需：多仓库环境、独立 VM 子任务、本地云端交接、PR 持续修复、团队环境与密钥治理、用量和审计、Slack 工作流。移动端、更多工单集成、团队市场和 Hooks 按优先级递进交付。

退出门槛：能完成跨仓库功能交付及集成验证；工单与 PR 可追踪；团队环境可回滚；权限撤销有效；代码、测试、PR 状态和费用能对应到具体运行。

依赖：可靠事件处理、父子任务隔离、稳定 API 和环境配置版本。

参考时期：Cursor 5–7 月的开发环境、协作入口、移动端、团队 MCP 与 Hooks。[R10–R17]

### 阶段四：自治基础设施

价值主张：让一组受约束的 Agent 围绕目标和事件持续运行，并可调度托管或自有算力。

上线必需：长期目标、已有任务订阅与恢复、预构建与预热、Worker 池、休眠唤醒、任务树总预算和自治停止策略。

扩展项：自定义模式与记忆、第三方沙箱、桌面接管、无仓库构建、发布集成。原生代码托管需另立评审，确认外部托管平台确实成为主要限制后实施。

退出门槛：目标可以跨事件恢复且不会无限循环；坏构建可回退；池内任务不会重复领取；休眠恢复可验证；停止、权限撤销和预算限制覆盖全部子任务与订阅。

依赖：阶段三交付状态、环境治理和审计充分可靠，真实使用数据证明持续运行具有价值。

参考时期：Cursor 8–9 月的 Builds、Origin、订阅、长期目标、无仓库构建和机器池。[R18–R22]

## 10. MVP 与发布顺序

MVP 对应阶段一，目标用户为已有代码仓库且愿意审查 PR 的开发者。

| 顺序 | 交付单元 | 可评审结果 |
|---|---|---|
| 1 | 任务创建、隔离环境、运行日志、取消与预算 | 可从 Web 启动并观察一个云端任务 |
| 2 | 代码变更、测试记录、交付包和 PR | 可审查并接收一项实际代码修改 |
| 3 | CLI 接力、断线后持续执行与结果恢复 | 可将规划交给云端并关闭客户端 |
| 4 | Computer Use、截图和演示证据 | 可验证 Web 应用的实际交互变化 |
| 5 | 权限隔离、资源回收、失败诊断和用量核对 | 可向首批试点用户发布 |

这些交付单元属于一个阶段的实施顺序，不构成独立日期承诺。每个单元的技术设计需在开发前单独评审。

## 11. 指标与埋点

北极星指标：每周经用户接受的有效交付数。代码任务以关联 PR 合并、变更接受或显式验收为准；无代码任务单列验收结果，不用运行次数替代交付效果。

以下指标为建议采集口径，目标数值需通过试点基线确定：

| 指标 | 口径 | 对应决策 |
|---|---|---|
| 激活率 | 新用户中完成首次有效交付的比例 | 判断环境设置和首任务流程是否顺畅 |
| 任务交付率 | 已进入执行的任务中，观察窗口内获接受的比例 | 判断产品是否完成真实工作 |
| 无人工补充交付率 | 发起后无需新增用户输入且获接受的任务比例 | 判断自主执行能力 |
| 首次有效行动耗时 | 创建任务至首次有效读取、检查或修改；另记录首 token 时间 | 区分界面响应与实际启动效率 |
| 环境成功率 | 成功准备环境的运行数 / 环境准备尝试数 | 判断环境配置与构建质量 |
| 干预次数 | 每个有效交付所需用户补充、修正和接管次数 | 判断协作成本 |
| 单次有效交付成本 | 模型、计算、存储成本 / 获接受交付数 | 决定预热与并行策略 |
| 自动化有效率 | 产生有效交付或有效告警的执行数 / 自动化执行数 | 判断触发规则是否产生噪声 |
| 恢复成功率 | 可恢复中断中成功继续且无重复外部动作的比例 | 判断持续运行可靠性 |

按任务类型、仓库规模、模型和执行位置分组统计；失败与人工取消单列。长期任务指标基于观察窗口及创建批次计算，避免把尚未结束的任务当成成功或失败。

关键事件：task_created、run_queued、environment_ready、run_started、input_requested、subtask_created、verification_completed、artifact_created、pr_created、delivery_accepted、run_failed、budget_reached、subscription_triggered、worker_disconnected。

## 12. 非功能要求

- 可靠性：任务元数据、执行事件和工件持久保存；控制面重启后能恢复状态。涉及提交、评论、发布等外部动作时，应优先确认已有结果再重试。
- 隔离性：租户、环境、任务工作区和密钥按授权范围隔离；读取任务或工件不能绕过组织权限。
- 可观测性：每次运行关联环境版本、代码版本、模型、工具活动、用量、触发源和结果。
- 资源回收：结束或取消后的计算资源按策略释放；工件和代码成果按保留策略处理，不因释放 VM 丢失已交付结果。
- 性能：记录环境准备、队列等待、首 token、首次有效行动及工件加载的 P50/P95。具体 SLO 在首轮试点后评审，不采用参考产品的宣传倍数作为本产品承诺。
- 兼容性：入口和计算提供商共享任务协议；新增入口不得产生独立、无法互通的任务状态体系。
- 安全交互：仓库文本、网页、日志和外部消息都是任务数据，不授予额外权限。敏感外部操作遵循用户授权和团队策略。

## 13. 风险与设计取舍

| 风险 | 对产品的影响 | 当前取舍 |
|---|---|---|
| 七类能力同时建设 | 发布周期过长，无法验证核心价值 | 先完成单仓库交付闭环，再进入事件和并行 |
| 自动化与订阅混用 | 重复任务、上下文丢失和事件循环 | 两个独立对象，共用触发基础设施 |
| 自主运行缺少边界 | 长时间消耗资源却没有有效成果 | 目标、预算、时限、停止条件作为必备配置 |
| 多 Agent 产生冲突 | 局部结果成功但整体不可运行 | 隔离分支、父任务整合与集成验证 |
| 快照环境过时 | 执行环境与目标代码不一致 | 记录构建与代码版本，显示回退，保留新鲜度策略 |
| 自托管数据描述不清 | 用户误判信息是否离开内网 | 公开控制面、模型调用和执行面数据边界 |
| 原生代码托管范围膨胀 | 引入长期可靠性和生态兼容成本 | 保留为 P2，优先完成外部 SCM 集成 |
| 多端入口过多 | 相同任务在不同客户端行为分裂 | 共用 API 与状态模型，逐步开放客户端 |

## 14. 后续评审项

本稿可用于功能取舍和阶段讨论。进入实施前需确定以下事项：

1. 产品归属：独立 Cloud Agent 产品，还是纳入 RepoMesh 的能力模块。
2. 首批用户与任务：个人开发者或团队；优先缺陷修复、测试还是功能开发。
3. MVP 技术范围：首个代码托管平台、环境模板、模型接入方式及资源提供商。
4. 部署优先级：托管优先，或因试点客户条件将自托管提前为必需。
5. 定价与配额：模型、计算和存储的收费方式及预算超限规则。
6. 数据与恢复策略：保留周期、快照范围、跨端迁移边界、审计要求。
7. 里程碑：基于人力和技术验证结果制定时间计划。
