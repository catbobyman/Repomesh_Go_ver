# 共同设计规则与阅读方法

本目录把 B00 至 B11 的 API、数据库关系和设计理由放在一起。B00 至 B04 标明已有实现及其验收边界，后续批次区分已采用设计与候选。每个批次先说明用户能完成什么，再说明哪些记录必须一起保存，以及失败后如何继续。

Markdown 是本目录的内容源，HTML 由它生成。两种格式表达同一份设计。

## 采用状态与事实来源

| 标记 | 含义 | 开发时如何使用 |
| --- | --- | --- |
| 已实现 | 当前产品源码已经具备该行为 | 核对本章引用的源码和采用记录，保留兼容语义 |
| 已采用设计 | 相关契约章节已采用，但不代表产品已实现 | 按采用范围实施，并补业务验证 |
| 既有候选 | 当前专题已有具体提案，采用记录尚未接纳 | 保留候选身份，不能因为本目录重述而视作已采用 |
| 本次提案 | 本目录新增或具体化的字段、关系或内部能力 | 评审通过后更新唯一专题及采用记录，再实施 |
| 验证设计 | 将来要执行的检查与预期 | 没有执行结果前，不宣称通过 |

本目录是按批次组织的阅读入口。既有 API 契约及采用记录保留权威，本目录不会隐式替代它们。出现差异时先回到本章来源核查采用范围，再同步修正文档，不能按文件日期决定谁覆盖谁。新提案在采用前只由本目录维护，采用后同步到相应专题并标明替代关系。

基线取自当前工作树，包括 2026-09-14 的 B05/B06 设计收口和 2026-09-15 的 B05 范围缩减。B00、B01 已有验证证据。B02 已有本地实现与验证，但外部验收保持 PAUSED_BY_USER。B03、B04 已完成本地集成验证，不能写成整批外部业务验收通过。B05 当前只保留运行政策、只读摘要和模型应用；独立模型测试整体延期，产品仍未实施。D05、D06、C05、C06 和 P9 的候选身份不因本目录生成而改变。B07 至 B11 的开发与验收状态仍以交接和施工计划为准。

来源为 [当前交接](../current/HANDOFF.md)、[施工计划](../plan/IMPLEMENTATION-PLAN.md)、[B04 采用范围](../current/b04-model-sources-adoption.md) 和 [B05/B06 收口](../development/2026-09-14-b05-b06-design-closeout-01/README.md)。

### 物理合表与表清单

原物理合表基线记录了 B05-B11 的 63 张历史候选。2026-09-15 范围缩减后，其中 9 条模型测试专用提案延期，剩余 54 条活动映射承载于 27 张合并目标表，另有 `policy_bindings`、`policy_imports` 与 `business_plan_versions` 三张必需新表，当前设计共 30 张。`repomesh_modelbudget.windows` 从 B05 移交 B10；B05 只声明 4 张，B10 声明 11 张。B01-B04 的 36 张手册基线表（35 张业务表加 1 张系统表 `public.repomesh_schema_migrations`）、0007 扫描表和 0008 决策链三表都不动。业务计划版本 `business_plan_versions` 与执行层技术 `plan_revisions` 分开；B10 实施时在 B06 新 `issues` 上增补 `current_business_plan_version_id`、`business_plan_pointer_revision`、`next_business_plan_version_index` 三列，不改变 B06 表数。

机器可校验清单是 [table-manifest.json](./table-manifest.json)，合表规则与批次划分见 [B05-B11 物理合表专题](../current/b05-b11-storage-consolidation.md)。每张目标物理表只在所属批次的正文声明一次，写成独立一行：

```text

```

跨批次复用不重复声明，B00-B04 与 B08 不写声明。计数分列：手册基线 36 张加当前设计 30 张是手册范围 66 张；再计入 0007 扫描表 1 张与 0008 决策链表 3 张，全仓含扩展 70 张。HTML 首页的“设计专题”“文档卡片”“说明表格”只是文档统计，不是 API 数或已实现表数。

```bash
python3 docs/api-database/verify_design.py
```

该校验读取迁移源码、表清单和合表前正文快照，检查旧表覆盖、目标存在、去重、批次归属与正文声明。它只做静态文档检查，不执行迁移，也不证明数据库行为已经验证。

## 业务身份先于物理表

| 身份或关系 | 必须保留的事实 | 设计理由 |
| --- | --- | --- |
| 用户与会话 | 一个用户可有多条会话，会话有独立绑定、代次、撤销和过期状态 | 撤销一次登录不应靠覆盖用户唯一令牌来实现 |
| Project 与 Repository | 项目可关联多个仓库，仓库可被多个项目引用 | 用户增加仓库时仍在同一项目中工作 |
| Repository | 以 host 与稳定外部仓库 ID 识别，URL 可更新 | 改名后仍能识别原仓库及其历史结果 |
| Conversation 与 Issue | 独立身份、同项目关联，各自生命周期明确 | 一段讨论可以先于 Issue，也可以先后服务多个 Issue |
| Room | 运行时观察与关联，不充当 Conversation 或 Issue 主键 | 房间尚未建立时，已创建的业务记录仍然有效 |
| RepositoryIssue | 同一 Issue 与仓库内全历史唯一，首次真实委派登记，跨任务和轮次复用 | 选仓范围与真正开始的仓库工作有不同生命周期；重试不能制造新事项 |
| 配置修订与 SecretVersion | 引用确定且可追溯的版本，内容与可用性分开 | 重启后继续使用用户当时确认的配置，不偷偷切到最新版本 |
| Task、Attempt 与外部操作 | 业务任务、一次尝试、一次外部副作用分别有身份 | 网络重试不应凭空增加业务尝试，也不能重复启动同一外部动作 |

物理表可以合并，合并后仍要表达这些身份、作用域和约束。表数不设固定目标。只有当两类记录的写入者、唯一性、更新频率和删除规则相容时，合表才减少维护成本。

既有依据为 [领域术语](../../CONTEXT.md)、[当前认证迁移](../../internal/database/migrations/0003_authentication.sql)、[当前项目迁移](../../internal/database/migrations/0004_projects.sql) 和 [首批持久化设计](../current/backend-first-batch-persistence.md)。

## API 围绕业务操作设计

### 创建与重放共用一个操作身份

已有创建、更新和保存操作继续由所属业务域保存回执。作用域使用对应契约规定的 actor、项目、操作种类及客户端操作键组合，不能跨业务统一拼出一个新主键。schemaVersion 用于保存和解释原输入，不加入操作身份。

| 场景 | 需要保持的结果 | 设计理由 |
| --- | --- | --- |
| 同一操作键与相同输入再次提交 | 按原契约返回第一次操作结果 | 用户刷新或网络重试不会生成第二份业务对象 |
| 同一操作键改了业务输入 | 按原契约拒绝冲突，通常为 409 | 旧回执不能被新意图覆盖 |
| 业务提交成功但响应丢失 | 可查询或重放原操作 | 客户端不需要猜是否成功并换一个新键 |
| 正文按规则清理 | 在对应保留期保留必要占位，按契约返回已移除语义 | 清理正文不会让旧键变成新操作 |
| 缓存过期或丢失 | 回到数据库核对原操作 | Redis 的存活时间不改变业务事实 |

业务写入与回执在同一数据库事务中完成。需要后续工作的操作同时保存持久待办，再由后台处理。网络调用不放进长时间持锁事务。每条具体路径的锁序以所属专题为准，不能用一条笼统锁序覆盖创建、更新及维护路径。

来源为 [首批浏览器操作契约](../current/first-batch-browser-api-contract.md)、[Issue 创建契约](../current/issue-page-create-api-contract.md) 和 [锁序收口](../development/2026-09-14-b05-b06-design-closeout-01/README.md)。

### 授权与恢复信息属于同一业务边界

浏览器 API 继续按当前身份、项目和内容范围核权。知道一个 ID 或持有一个分页游标不等于拥有读取权限。恢复 API 也要核对主体与归属，不借原操作查询泄露他人的输入或密钥。

API 回执地址与浏览器恢复页面地址用途不同。前者返回原操作事实，后者供用户查看和继续操作。模型测试成功不作为应用模型或创建 Issue 的前置条件。

来源为 [页面恢复设计](../current/first-batch-recovery-design.md) 和 [B05/B06 收口](../development/2026-09-14-b05-b06-design-closeout-01/README.md)。

## 数据约束与生命周期

### 关系字段承担身份，JSON 承担载荷

被其他记录引用的身份要有明确目标和作用域。项目内编号使用项目内唯一约束。跨项目引用需要被拒绝。需要参与唯一性、资源排他或版本引用的字段不能只藏在无规则的 JSON 中。

JSON 可以保存不可变配置正文、版本化图快照和外部观察载荷。每类载荷需说明 schemaVersion、谁能写、更新条件和保留规则。一个历史版本若被独立引用，需要稳定且不可改写的身份。数组历史只有在引用与原子更新规则完整时才采用。

理由是后续维护者可以从关系和约束找到权威事实，重放时不必从几份可变 JSON 猜测当时使用了哪一个版本。现有配置修订已经允许 JSON 内容，见 [项目迁移](../../internal/database/migrations/0004_projects.sql)。

### 数据清理按内容与证据分别决定

| 数据种类 | 生命周期规则 | 设计理由 |
| --- | --- | --- |
| 业务正文及可重建正文的派生副本 | 服从所属内容的删除和权限规则 | 删除正文后不能通过旧摘要或向量绕过清理 |
| 操作身份及最小回执占位 | 服从该操作的账号或项目保留期 | 重试时仍能识别原操作，具体保留时长不在本目录另定 |
| SSE 事件 | 服从事件流补读窗口，过期时返回重建提示 | 客户端能够区分无更新与历史已清理 |
| 发送、停止与回收证据 | 服从对应执行或核查生命周期 | 租约结束后仍需判断进程是否停止、资源是否释放 |
| 密钥材料 | 服从版本引用、可用性、轮换和销毁协议 | 包装根轮换不应制造新的业务配置版本 |

来源为 [首批持久化设计](../current/backend-first-batch-persistence.md)、[认证与密钥开发说明](../current/authentication-development.md) 和 [团队执行策略](../current/team-execution-policy.md)。

## 后台与执行边界

Web、coordinator 和 host-executor 继续采用三个进程。Graph 是 coordinator 内模块。AgentTeams 负责有限仓内 DAG，RepoMesh 负责跨仓依赖、结果采纳和 Loop。受限主机边界不提供任意命令或任意挂载。

后续批次可以给出内部能力的输入、输出和错误语义。尚未采用的 HTTP 路径、RPC 传输、MCP schema 及主机消息格式必须标为候选，不因示例而冻结。

来源为 [三进程 ADR](../adr/0013-web-coordinator-host-executor-processes.md)、[Graph 与 Loop](../current/graph-loop-design.md) 和 [执行接入门槛](../current/execution-integration-gates.md)。

### 超时和重试不能改变执行事实

| 事实 | 设计要求 | 用户或维护者得到的结果 |
| --- | --- | --- |
| 外部请求结果未知 | 保存原操作身份，先核查，只有规定证据能结束 unknown | 超时不会直接导致重复收费或重复启动 |
| 执行领取过期 | 拒绝旧领取者迟到写入，另行确认实际停止或失去写能力 | 不会把租约到期误报为旧进程已结束 |
| 消息重复投递 | 用稳定投递身份识别重复 | 一条命令不会因为重连执行两次 |
| 业务 Attempt 失败 | 保存该次尝试及结果，按业务规则决定下一次 | 用户能追溯每一次执行 |
| 修复进入下一轮 | 单独记录业务轮次及采纳依据 | 技术重试不会绕过修复轮次规则 |

具体消费者还要把可能外发与已证实结果分开。每次外部副作用先保存稳定操作身份、规范输入与 `may_have_sent` 边界；提交确认后才允许调用外部系统。响应丢失、超时或重启后只核查原操作，不能换键自动重发。撤销本地租约、关闭页面或管理员确认都不能替代外部停止、未发送或写能力失效的证据。B09 的模型调用和 B10 的上游／宿主操作分别在自己的业务域持有这些事实，不共享 B05 已延期的测试表。

## 采用前检查

- 每个新增端点都能说明调用方、权限、原操作身份、输入输出和错误语义。

- 每个外部动作都能说明响应丢失后如何核查，哪个证据允许重试或终止。
- 每个状态标签都能追溯到采用记录、源码或本次提案，不把计划测试写成实测通过。
