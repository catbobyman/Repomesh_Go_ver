## 命令行接口：repomesh-web db

### repomesh-web db --help

#### 调用方与用途

操作者查看可用子命令与总超时说明。帮助路径不连接数据库，也不显示连接串。

#### 输入与返回

无参数或 `-h`／`--help` 时打印：

```text
Usage: repomesh-web db <check|migrate> [--database-url CONNECTION] [--timeout 30s]
The connection defaults to REPOMESH_DATABASE_URL. Only migrate changes the schema.
```

源码见 [main.go](../../cmd/repomesh-web/main.go) 第 90 行。

#### 错误与状态码

帮助路径固定退出 0；子命令自身的 `--help` 也退出 0，见 [main.go](../../cmd/repomesh-web/main.go) 第 104 行。

#### 设计理由

把“会改结构”和“只核查”写在帮助里，操作者不需要读源码就知道 `check` 不会改库。

### repomesh-web db check

#### 调用方与用途

部署人员、发布脚本和已经配置认证的进程启动路径。它回答“这个库的迁移历史是否与本二进制完全匹配”，不做任何写入。

#### 输入

| 参数 | 类型 | 必填 | 默认 | 含义 |
| --- | --- | --- | --- | --- |
| `--database-url` | string | 否 | 无 | PostgreSQL 连接串；未显式提供时读取 `REPOMESH_DATABASE_URL`。显式空值覆盖环境变量并按配置错误处理。 |
| `--timeout` | duration | 否 | `30s` | 连接与本次操作共用的总预算，必须为正。 |

解析见 [main.go](../../cmd/repomesh-web/main.go) 第 100 行至第 126 行。核查在 `RepeatableRead` 只读事务中进行，见 [database.go](../../internal/database/database.go) 第 80 行。

#### 输出

单行文本，例如当前 6 条迁移时：

```text
schema status=current current=6 target=6 pending=0
```

状态取值：`missing`（schema 不存在，`current=0`）、`pending`（历史是清单前缀但缺版本）、`current`（完全匹配）。输出见 [main.go](../../cmd/repomesh-web/main.go) 第 148 行。空库示例为 `schema status=missing current=0 target=6 pending=6`，见 [数据库开发说明](../current/database-development.md)。

#### 错误与状态码

| 状态 | 触发条件 | 退出码 |
| --- | --- | --- |
| 成功且完全匹配 | 历史等于编译清单 | 0 |
| 历史缺号、未知较新版本、名称或校验和不同 | `ErrHistoryMismatch` | 1 |
| 库为空或缺少待应用版本 | 输出 `pending` 或 `missing` | 1 |
| 连接失败、超时、取消或协议错误 | `safeError` 封装后的消息 | 1 |
| 连接串为空或无效、参数非法、`--timeout <= 0` | `ErrInvalidConfig` 或参数错误 | 2 |

错误文案不包含连接串、驱动原始正文或历史中的任意名称，见 [database.go](../../internal/database/database.go) 第 108 行。

#### 并发与重放

`check` 是只读且可重复的：同一历史并发核查互不影响，也不会创建 `public.repomesh_schema_migrations`。它在快照内读取全部历史行，因此不会把一次迁移的中间状态当成完整结果。

#### 设计理由

发布前需要一次不改库的确认。只读事务加精确前缀比较，让“数据库比二进制新”“历史被手工改过”和“只缺一个版本”得到不同但都明确的结论。

### repomesh-web db migrate

#### 调用方与用途

部署人员升级目标库的唯一路径。

#### 输入

与 `db check` 相同的两个参数，默认值相同，见 [main.go](../../cmd/repomesh-web/main.go) 第 100 行。

#### 输出

成功时为 `schema status=current current=N target=N pending=0`；重复执行保持同一行。B01 记录时刻为 `1/1/0`，见 [B01 完整验证](../development/2026-09-12-batch-01/b01-verification/checks.json)；B03 记录时刻为 `4/4/0`，见 [发布验收](../development/2026-09-12-b03-integration-01/release-validation-20260913-062934/summary.json)。

#### 事务与锁

| 步骤 | 事实 | 来源 |
| --- | --- | --- |
| 开启 `READ COMMITTED` 事务 | 迁移在一个短事务内完成 | [migrations.go](../../internal/database/migrations.go) 第 107 行 |
| 取事务级 advisory lock | 固定键 `0x5245504f4d455348`，同一时刻只有一个迁移者 | [migrations.go](../../internal/database/migrations.go) 第 21 行与第 112 行 |
| 锁后读取历史 | READ COMMITTED 在持锁者提交后取快照 | [migrations.go](../../internal/database/migrations.go) 第 116 行 |
| 逐条执行并写账本 | SQL 与 `INSERT INTO public.repomesh_schema_migrations` 同一事务 | [migrations.go](../../internal/database/migrations.go) 第 120 行 |
| 提交 | 提交失败返回 `ErrCommitUnconfirmed`，提示先核查再重试 | [migrations.go](../../internal/database/migrations.go) 第 130 行 |
| 失败回滚 | 独立 context，最多 5 秒 | [database.go](../../internal/database/database.go) 第 102 行 |

#### 错误与状态码

与 `db check` 相同的退出码约定；另外，提交结果未确认时错误文本为 `migration commit result is unconfirmed; run db check before retrying`（错误变量见 [database.go](../../internal/database/database.go) 第 19 行），并且不把未知提交结果当成已回滚。

#### 并发与重放

已应用的版本不会重复执行：清单是连续前缀校验的结果，`Migrate` 只遍历 `db.migrations[state.Current:]`。20 个并发迁移用例验证等待锁的进程在持锁者提交后重新读取历史，只应用剩余版本，见 [B01 完整验证](../development/2026-09-12-batch-01/b01-verification/checks.json) 与 [postgres_test.go](../../internal/database/postgres_test.go) 第 88 行。重复执行同一二进制是幂等的，成功输出保持 `current`。

#### 设计理由

迁移只前进、只在一个事务里提交，是“失败之后库要么是旧版本、要么是新版本，不存在半个版本”的实现方式。advisory lock 放在读历史之前，避免两个进程同时看到同一份待应用清单。

## 数据表

### public.repomesh_schema_migrations

#### 用途与写入者

迁移账本。唯一写入者是 `DB.Migrate`；`DB.Check` 只读。DDL 见 [0001_schema_migrations.sql](../../internal/database/migrations/0001_schema_migrations.sql)。

#### 对象状态

| 项目 | 状态 |
| --- | --- |
| 表 | 已实现 |
| 契约 | 已采用（[数据库开发说明](../current/database-development.md)） |
| 字段新增或修改 | 无；本文件只整理既有事实 |

#### 字段

| 字段 | 类型 | 必填 | 约束 | 人话含义 |
| --- | --- | --- | --- | --- |
| `version` | bigint | 是 | 主键，且 `CHECK (version > 0)` | 迁移序号，从 1 连续递增。 |
| `name` | text | 是 | `UNIQUE` | 迁移文件名，例如 `0001_schema_migrations.sql`。 |
| `checksum` | bytea | 是 | `CHECK (octet_length(checksum) = 32)` | 该 SQL 文件字节的 SHA-256。 |
| `applied_at` | timestamptz | 是 | 默认 `now()` | 账本行写入时间，不参与匹配判定。 |

#### 主外键、唯一性与索引

主键 `version`；`name` 唯一。没有外键与其他索引：表只服务于顺序读取与外键无关的历史比较，见 [0001_schema_migrations.sql](../../internal/database/migrations/0001_schema_migrations.sql)。

#### 事务关系

每个版本的 SQL 与对应账本行在同一事务中执行并提交；任一失败整次回滚，包括 `CREATE TABLE` 本身，见 [migrations.go](../../internal/database/migrations.go) 第 120 行。B01 用独立用例覆盖 SQL 失败回滚、账本行插入失败回滚、多文件原子升级与 COMMIT 时约束失败，见 [B01 完整验证](../development/2026-09-12-batch-01/b01-verification/checks.json)。

#### 状态转移

| 历史状态 | `db check` | `db migrate` |
| --- | --- | --- |
| 表不存在 | `missing`，退出 1 | 创建表并应用全部版本 |
| 连续前缀但不完整 | `pending`，退出 1 | 应用剩余版本 |
| 完全匹配 | `current`，退出 0 | 不执行任何迁移，输出 `current` |
| 缺号、较新版本、名称或校验和不同 | `ErrHistoryMismatch`，退出 1 | 同样拒绝，不写任何行 |

#### 删除与保留

账本行不删除、不降级。已应用文件必须保持原字节；迁移 SQL 通过 `.gitattributes` 固定 LF，见 [.gitattributes](../../.gitattributes) 首屏的 `internal/database/migrations/*.sql text eol=lf`。修改已应用 SQL 会让 `db check` 报名称或校验和差异。

#### 设计理由

账本用文件名和内容哈希锁定“当时执行了什么”，而不是只记版本号。两个开发者用不同内容改同一编号时，部署会在启动前失败，而不是让两边继续写入不同结构的库。

### 迁移清单

清单通过 `go:embed migrations/*.sql` 内嵌进二进制，见 [migrations.go](../../internal/database/migrations.go) 第 18 行。文件名必须是四位编号加小写下划线名称，编号从 1 连续且不能跳号，SQL 不能为空，见同文件第 23 行与第 32 行。校验和按文件字节计算 SHA-256，不依赖数据库写入的格式。

进程与数据库重启属于恢复范围，重启后不允许隐式迁移：配置认证的 Web 与 coordinator 在历史不匹配时拒绝启动，见 [deployment.go](../../internal/access/deployment.go) 第 94 行。

## 设计理由

显式迁移把“部署动作”和“进程启动”分开。进程启动只核查，因此一次意外的服务重启不会改变数据库结构；升级必须由操作者执行，并能在结果未知时先核查再决定。

历史比较使用文件名与内容哈希，而不是只比较版本号：编号相同但内容不同的迁移会被拒绝，防止两个分支各自发布后把库写成第三种状态。

超时与脱敏错误面向运维：连接串不会进入输出或日志，命令失败也不会泄漏目标库信息；`--timeout` 同时覆盖连接和操作，避免锁等待吃掉整次发布窗口。

## 验证清单

以下为可观察的预期结果。B01 历史记录已经执行过一批；复跑时必须由脚本断言真实数据库行为，跳过集成测试不算通过。

- 空库 `db check` 输出 `schema status=missing current=0 target=N pending=N` 并退出 1。
- `db migrate` 输出 `current/target/pending = n/n/0` 并退出 0；再次执行结果不变。
- PostgreSQL 重启后 `db check` 仍为 `current`；账本行数等于 `target`，每行校验和长度为 32 字节。
- 把任一行名称改成其他值后，`db check` 与 `db migrate` 都退出 1 并给出“migration history does not match this binary”类错误。
- `repomesh-web db reset` 这类未知子命令退出 2；未设置 `REPOMESH_DATABASE_URL` 且未给 `--database-url` 时退出 2。
- 非法连接串退出 2；连接不可达或超时退出 1，且输出不含连接串。
- 并发执行多个 `db migrate` 全部成功，最终历史不超过 `target` 且无重复行。
- 未配置认证启动 Web 时行为与 B00 相同：`/healthz` 200 且 `businessReady=false`，`/readyz` 503，Web 不连接数据库。
