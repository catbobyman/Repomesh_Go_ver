# B11 两轮换图与跨仓部分应用恢复（G5）

本批对应施工计划中的 B11，范围是 G5。用户能完成的事情有四件。第一，在第一轮验证发现明确业务缺陷后，在既有授权、预算、时限和循环上限内进入第二轮，只修复受影响仓库并重新判断证据适用性。第二，在两仓交付中一仓应用成功、一仓失败或未知时，看到逐目标真实状态，受影响范围保持停派工，已成功部分不被撤销。第三，看到旧 Attempt 的迟到结果被归档，不会解锁当前图或覆盖正式状态。第四，看到预算、时限、轮次上限或连续相同失败触发停止时，停止原因和累计消耗可追溯。

本批不另造通用 Go DAG 引擎，不做任意嵌套流程语言、图编辑器或动态插件平台，不恢复 Skill 工程与审批模式，不改变人工 Git 合并职责，不重设计 B10 已定的资源生命周期。

### 1.2 用户能完成什么

用户看到第一轮检查记录业务缺陷后，可以要求 Manager 在既定修复范围内组织第二轮。系统只对受影响仓库形成新的有限任务安排，未修改的参与仓库仍固定原基线，旧证据按新组合重新判断适用性。用户不需要理解上游 replan 限制，但页面必须显示计划是否真正应用、哪些目标已读回、哪些目标仍关闭。

两仓交付只成功一仓时，用户看到的是部分应用，不是整体完成。系统保留已成功部分，继续关闭受影响范围的派工，逐目标核查后恢复。旧 Attempt 的结果即使晚到，也只进入历史与适用性判断，不会因为内容看起来成功就自动放行当前依赖。

### 1.3 依赖

依赖 B10 的正式写方选择、Attempt 身份、资源生命周期、停止与写能力撤销协议。依赖 B09 的可信消息与调用授权。依赖 B05 的预算、时间政策与额度账本。依赖 B06 的 Issue、主 ChangeSet 与范围。依赖 B07 的只读投影。依赖锁定上游的 Controller REST 与 TeamHarness 图操作。

上游 replan 的前置条件已核对。[project_handler.go](../../third_party/AgentTeams/agentteams-controller/internal/server/project_handler.go)第 2413-2450 行要求项目 active、plan_type 为 dag 或未设置，并且没有 in_progress 或 submitted 任务。paused 项目不能直接 replan，B11 必须显式选择接法，不能把业务流程图上的“暂停、收敛、换图”直接翻译成两次原生调用。

### 1.4 明确边界

本批不选择上游补丁的最终形态，不冻结 replan 接法，不新增通用 DAG 引擎，不改变仓内依赖与环校验算法。它不把上游 `submitted`、`completed` 或工具 `ok` 当业务通过，不把部分应用写成整体完成，不把旧 Attempt 的迟到结果当新证据，不把预算重试或传输重试算作业务修复轮次。

## 2. API 与内部边界

### 2.1 内部边界：graph.Service.EvaluateRound

状态为本次提案，未实现。它接收有效计划、已采纳结果、固定组合、循环进展和带来源与修订的图观察，返回需要等待、可请求执行或应停止的判断。调用方是 coordinator 协调工作。

```go
type RoundEvaluationInput struct {
    IssueID            string
    RoundID            string
    AcceptedResults    []AcceptedResultRef
    CrossRepoEdges     []CrossRepoEdge
    UpstreamObservedAt time.Time
    StopSnapshot       StopSnapshot
}

type RoundEvaluation struct {
    Decision      string
    WaitReasons   []string
    ReadyLocalTaskIDs []string
    StopReason    string
    EvaluatedAt   time.Time
}

func (s *GraphService) EvaluateRound(ctx context.Context, in RoundEvaluationInput) (RoundEvaluation, error)
```

该方法在一个只读事务中按 `RoundID` 读取 B10 `round_plan_pointers` 的全部行与对应修订，判断以完整指针集合为准。读取期间集合变化时按 `pointer_revision` 重读，不任取单个。`Decision` 只允许 `wait`、`allow_dispatch`、`stop`。该方法不做数据库写入，不持有 Controller、GitHub 或 Docker 凭据，不直接创建 Worker 或占用资源。跨仓前驱未满足时，即使上游仓内节点 ready 也不能进入 `allow_dispatch`。

### 2.2 内部边界：rounds.Service.CloseRound

状态为本次提案，未实现。它收尾当前轮次并冻结结果事实。调用方是 coordinator 轮次工作。

```go
type CloseRoundCommand struct {
    IssueID       string
    RoundID       string
    Outcome       string
    EvidenceRefs  []string
    DecidedBy     string
    CauseOperationID string
}

func (s *Service) CloseRound(ctx context.Context, cmd CloseRoundCommand) (RoundTransition, error)
```

收尾前必须确认本轮无在途或 submitted 未核查任务，或者已按真实状态完成 submitted 收尾。收尾在同一短事务内读取本轮全部 `round_plan_pointers` 与对应修订、任务，逐个仓库确认，不按单条修订收尾。`Outcome` 只允许 `pass`、`business_defect`、`insufficient_evidence`、`budget_stop`、`time_stop`、`blocked`、`cancelled`。方法更新 B10 `rounds.state` 并追加一条 `round_transitions`，不另建收尾表，也不改变 `repository_issues.state`。失败与待补证不能记录为通过。旧 Attempt 迟到结果不阻止本轮收尾，但也不得被采纳为当前轮新证据。

### 2.3 内部边界：rounds.Service.OpenNextRound

状态为本次提案，未实现。它在已有授权和上限内开启下一轮。调用方是 coordinator 轮次工作。

```go
type OpenRoundCommand struct {
    IssueID          string
    PreviousRoundID  string
    Purpose          string
    ScopeRepositories []string
    CauseDecisionID  string
}

func (s *Service) OpenNextRound(ctx context.Context, cmd OpenRoundCommand) (Round, error)
```

`Purpose` 只允许 `repair`、`diagnostic`、`environment_recovery`。方法在 B10 的 `rounds` 插入一条 Issue 内轮次并追加 `round_transitions`；`ScopeRepositories` 是本次要换图的受影响仓库集合，每个仓库必须先在本 Issue 的固定范围内。本次提案规定，同一轮覆盖多个仓库时，每个受影响仓库各建立一条不可变 `plan_revisions`（B10 持有）并写入该仓的 `round_plan_pointers` 行，随后各自应用。每条修订绑定本 Issue 固定范围内的一个仓库；首次真实派工时 Attempt 才绑定该仓库的 `repository_issues`。已存在的事项跨轮次复用同一 id，轮次开启与收尾都不关闭事项。轮次行仍然只有一条，不按仓库复制业务轮次，也不复制事项身份。新轮次沿用同一 Issue、Manager 与业务 Plan Version，不因轮次推进重建业务身份。范围或上限改变时按计划变更规则处理，不能借“下一轮”绕开。

状态为本次提案，未实现。它把新的有限任务安排应用到一个受影响上游目标。调用方是 coordinator 换图工作。

### 2.5 内部边界：delivery.Service.RecordPartialApplication

### 2.6 内部边界：delivery.Service.RecoverTarget

```go
type AdmissionDecision struct {

func (s *GraphService) DecideResultAdmission(ctx context.Context, result ResultRef) (AdmissionDecision, error)
```

### 2.8 上游入口使用清单

以下端点和工具是固定上游版本的事实，不是 RepoMesh 产品 API。状态为上游存在、RepoMesh 未接入。

| 上游入口 | 本批用途 | 约束 |
| --- | --- | --- |

## 3. 数据表设计

以下表名为本次提案，未实现。物理 schema 建议并入 B10 的执行 schema，或使用 `repomesh_delivery`。本章不新增通用 operation、job 或 event 表，也不把表写成“登记到 foundations 的共享框架”。各业务域保留自己的操作回执；只有[首批持久化设计](../current/backend-first-batch-persistence.md)第 3 节已经采用的 DurableWork 机制可以复用于后台工作。`rounds` 与不可变 `plan_revisions` 由 B10 持有，本章只引用并扩展轮次转换、跨仓边和结果采纳。同一轮覆盖多个仓库时，轮次行只有一条，各仓的计划修订分别落在 `plan_revisions.repository_id`，仓库范围仍须落在本 Issue 的固定范围内。B11 复用 B10 的 Attempt、任务与仓库事项身份，不建第二套可修改执行状态，也不另造仓内事项。房间身份如被引用，统一引用 B07 的 `repomesh_issues.issue_room_links`，不另建 room 表。

### 3.1 round_transitions

用途是保存轮次状态转换与收尾采纳事实。写入者是 `CloseRound`、`OpenNextRound` 和恢复工作。本表扩展 B10 的 `rounds`，不另建轮次身份。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| id | text | 是 | 主键 |
| round_id | text | 是 | 引用 B10 的 `rounds` |
| from_state | text | 是 | 转换前状态 |
| to_state | text | 是 | 转换后状态 |
| outcome | text | 否 | 仅在收尾转换填写，取值同 §2.2 |
| evidence_refs | jsonb | 是 | 版本化证据引用数组，可为空数组 |
| decided_by | text | 是 | 可信协调或复核身份 |
| decided_at | timestamptz | 是 | 决定时间 |
| reason | text | 是 | 非敏感原因 |

本表只增不改，按 `decided_at` 与主键排序重放轮次历史。`from_state` 与 `to_state` 必须属于 B10 `rounds.state` 的枚举，写入事务核当前 `rounds.state` 等于 `from_state`。合法转换如下。

| 转换前 | 允许的转换后 |
| --- | --- |
| planned | active、cancelled |
| active | draining、applying、recovering、closed、cancelled |
| draining | applying、recovering、closed、cancelled |
| applying | recovering、closed、cancelled |
| recovering | applying、closed、cancelled |
| closed | 无 |
| cancelled | 无 |

`closed` 与 `cancelled` 是终态，不能回到 `active`。完成收尾的转换必须引用当前固定组合下的有效证据，`pass` 不能只引用上游 completed。B10 的 `rounds.state` 是当前值，本表是转换依据。

### 3.2 target_applications

用途是保存单个上游目标的应用、读回与恢复状态。写入者是 `ApplyPlanRevision`、`RecordPartialApplication` 与 `RecoverTarget`。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| id | text | 是 | 主键 |
| plan_revision_id | text | 是 | 唯一引用 B10 的不可变 `plan_revisions`；上游目标、仓库与绑定由该修订决定 |
| path | text | 是 | `resume_then_replan` 或 `paused_replan_patch` |
| state | text | 是 | `pending`、`publishing`、`applied`、`readback_ok`、`readback_mismatch`、`failed`、`unknown` |
| external_operation_id | text | 是 | 唯一外部逻辑操作身份 |
| base_revision | text | 否 | 应用前版本或 ETag |
| applied_revision | text | 否 | 应用后版本或 ETag |
| observed_at | timestamptz | 否 | 最近观察时间 |
| evidence | jsonb | 否 | 版本化证据摘要 |
| recovery_state | text | 是 | `none`、`open`、`recovering`、`recovered`、`unknown` |
| resume_condition | text | 否 | 恢复条件说明，未恢复目标必填 |
| recovery_observed_at | timestamptz | 否 | 最近恢复读回时间 |
| recovery_evidence | jsonb | 否 | 版本化恢复证据摘要 |

唯一约束为 `(plan_revision_id)`，一条修订只有一行，不复制 `plan_revisions` 的绑定或仓库。逐目标状态独立，部分成功不写成整批成功。`state` 只表示应用与读回，`recovery_state` 只表示恢复，两个枚举互不替代；`state` 的 `unknown` 表示应用或读回证据未知，`recovery_state` 的 `unknown` 表示恢复证据未知。

`state` 由 `ApplyPlanRevision` 与 `RecordPartialApplication` 写，合法转换为 `pending → publishing`、`publishing → applied、failed、unknown`、`applied → readback_ok、readback_mismatch、unknown`，以及 `readback_mismatch、unknown、failed → readback_ok、readback_mismatch、unknown`。`readback_ok` 是应用成功终态；`readback_mismatch` 与 `unknown` 保持目标关闭并保留恢复条件。

`recovery_state` 由 `RecoverTarget` 写，合法转换为 `none → open、recovering`、`open → recovering、unknown`、`recovering → recovered、unknown`、`unknown → recovering`。恢复读回确认一致时，`RecoverTarget` 在同一次写入把 `recovery_state` 置为 `recovered` 并把 `state` 更新为 `readback_ok`；不一致时保持 `readback_mismatch` 或写 `unknown`。完成条件是同一修订的 `state = readback_ok` 且 `recovery_state` 不是 `open` 或 `unknown`，未满足前受影响范围停止新派工。

设计理由。多目标更新没有跨系统原子性，一次调用不可能让所有仓库同时生效。逐目标事实让用户看到真实进度，也让恢复逻辑只重试未确认目标。

### 3.3 cross_repo_edges

用途是保存 RepoMesh 管理的跨仓依赖边。写入者是 Graph 规划与计划变更。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| id | text | 是 | 主键 |
| issue_id | text | 是 | Issue 归属 |
| round_id | text | 是 | 轮次归属 |
| from_task_id | text | 是 | 前驱本地任务，引用 B10 `execution_tasks` |
| to_task_id | text | 是 | 后继本地任务，引用 B10 `execution_tasks` |
| condition | text | 是 | `artifact_accepted`、`verification_evidence`、`business_acceptance` |
| state | text | 是 | `waiting`、`satisfied`、`invalidated` |
| evidence_ref | text | 否 | 满足条件时的证据引用 |
| updated_at | timestamptz | 是 | 最近更新时间 |

唯一约束为 `(round_id, from_task_id, to_task_id)`。跨仓边保存在 RepoMesh，不写入上游仓内 DAG。跨仓边未满足时，上游 ready 不能放行。

### 3.4 round_candidate_refs

用途是把一轮中的候选映射到已有 ChangeSet 候选身份。写入者是结果采纳与组合选择。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| id | text | 是 | 主键 |
| round_id | text | 是 | 轮次归属 |
| repository_id | text | 是 | 仓库归属 |
| candidate_ref | text | 是 | 指向 ChangeSet 候选的不透明稳定引用 |
| source_attempt_id | text | 是 | 来源 Attempt |
| accepted_for_combination | boolean | 是 | 是否进入本轮正式组合候选 |
| recorded_at | timestamptz | 是 | 记录时间 |

唯一约束为 `(round_id, repository_id, candidate_ref)`。本表不定义候选业务字段，也不替代 ChangeSet 的候选记录。未被接受的候选也保留来源与原因。

### 3.5 round_combinations

用途是保存本轮固定组合的执行映射。写入者是组合选择。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| id | text | 是 | 主键 |
| round_id | text | 是 | 轮次归属 |
| repository_id | text | 是 | 仓库归属 |
| fixed_sha | text | 是 | 该仓实际验证版本 |
| source_ref | text | 是 | 候选或未修改基线引用 |
| selected_by | text | 是 | 决定者 |
| selected_at | timestamptz | 是 | 选择时间 |

唯一约束为 `(round_id, repository_id)`。组合成员版本确定后不原地替换，新组合另建记录。该表是执行映射，业务组合身份仍由 ChangeSet 设计持有。

### 3.6 result_admissions

用途是保存 submitted 结果的采纳判断。写入者是 `DecideResultAdmission`。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| id | text | 是 | 主键 |
| result_ref | text | 是 | 上游结果稳定引用 |
| round_id | text | 是 | 当前轮次 |
| task_id | text | 是 | 本地任务 |
| attempt_id | text | 是 | 来源 Attempt |
| attempt_generation | bigint | 是 | 来源代次 |
| decision | text | 是 | 只允许 `admit_for_current_round`、`reject_stale` |
| reason_codes | jsonb | 是 | 版本化原因数组 |
| decided_at | timestamptz | 是 | 决定时间 |

唯一约束为 `(result_ref, attempt_generation)`。本表只增不改，只保存最终裁决；`needs_recheck` 是返回与等待状态，不写本表。证据不足时保持原 DurableWork 或 Attempt 等待核查，证据到达后写入第一条最终裁决，之后的重复或冲突写入被拒绝。旧 Attempt 迟到结果不能覆盖已有裁决。

设计理由。结果是否属于当前轮次是一个业务判断，不能只看上游状态是否为 submitted。保留判断依据后，迟到结果不会静默解锁当前依赖。

### 3.7 stop_decisions

用途是保存累计停止判断。写入者是协调或复核工作。它不是新的预算账本。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| id | text | 是 | 主键 |
| issue_id | text | 是 | Issue 归属 |
| round_id | text | 是 | 轮次归属 |
| reason | text | 是 | `round_limit`、`budget_limit`、`time_limit`、`same_failure_no_new_evidence`、`manual_stop` |
| consumption_refs | jsonb | 是 | 指向预算与时间账本的版本化引用 |
| decided_by | text | 是 | 决定者 |
| decided_at | timestamptz | 是 | 决定时间 |
| detail | text | 是 | 非敏感说明 |

累计消耗与上限读取 B05 的账本，本表只保存停止决定与依据。重启或换计划不清零累计值。

设计理由。停止原因是用户可见的业务事实，必须能追溯到当时预算、时限和轮次，而不是只留一句“已停止”。把累计账本留给 B05，避免出现两套消耗数字。

### 3.8 新增表必要性与删并说明

本节回应共同规则中“新增提案要有出处，能被合并的就合并”的要求。B11 不再复制 B10 已持有的轮次与计划修订。

| 表 | 必要性出处 | 结论 |
| --- | --- | --- |
| rounds | B10 的单轮执行已经需要稳定轮次身份 | 删除本章副本，引用 B10 的 rounds |
| plan_revisions | B10 的单轮发布已经需要不可变任务安排身份 | 删除本章副本，引用 B10 的 plan_revisions |
| round_outcomes | 收尾事实与轮次状态转换共享同一决定者和证据 | 合并入 round_transitions.outcome |
| partial_application_recoveries | 恢复状态与目标应用是 1 对 1、同一写入者 | 合并入 target_applications 的 recovery 字段 |
| round_transitions | 轮次转换需要独立追加历史 | 保留 |
| target_applications | 多目标部分应用与逐目标恢复需要独立状态 | 保留 |
| cross_repo_edges | 跨仓依赖需要独立边身份与证据 | 保留 |
| round_candidate_refs | 同一仓库可能产生多个候选，与组合不同生命周期 | 保留，引用 ChangeSet 候选身份 |
| round_combinations | 每轮每仓只有一个固定版本 | 保留，与候选表唯一性不同 |
| result_admissions | 结果采纳是 append-only 业务判断 | 保留，外部 accept 回执不能替代 |
| stop_decisions | 累计停止原因需要可追溯 | 保留，预算数字仍归 B05 |

## 4. 事务与恢复

### 4.1 轮次收尾

收尾先停止受影响范围的新派工，等待在途任务收敛，并按本轮完整 `round_plan_pointers` 与全部修订逐仓核对 submitted。每个 submitted 结果按真实状态收尾为成功、失败或证据不足，不能把失败或待补证改成通过。轮次收尾只结束本轮，不改变 `repository_issues.state`；全部收尾后更新 B10 `rounds.state` 并追加 `round_transitions`，再决定是否在既有授权与上限内开启下一轮。

### 4.2 换图接法

| 接法 | 步骤 | 风险 | 适用前提 |
| --- | --- | --- | --- |
| resume 后 replan | 停派工，收敛，pause，确认无在途，resume 到 active，replan，逐目标读回 | resume 到 replan 之间可能在受控范围外出现派工间隙，需要额外门禁 | 不改上游，但必须有可靠门禁与观察 |
| paused replan 补丁 | 停派工，收敛，保持 paused，用窄补丁应用新任务集，逐目标读回 | 需要维护上游补丁并验证新状态约束 | 允许窄上游补丁，且补丁验证通过 |

本章不选定接法，把它列为根代理与用户取舍点。无论选哪条，都必须满足停新派工、等在途收尾、核对 submitted、应用并读回。上游 pause 只是配合措施，不替代 RepoMesh 的停派工门禁。

### 4.3 多目标部分应用

本轮完整 `round_plan_pointers` 中每条修订的应用与读回独立记录在唯一的 `target_applications` 行上。一仓成功、一仓失败或未知时，保留成功部分，受影响修订保持关闭。恢复先按原 `external_operation_id` 读回，不重复应用。只有全部必要修订的 `state` 为 `readback_ok` 且 `recovery_state` 不是 `open` 或 `unknown` 时，才记录本次安排已落实并恢复允许的派工。B10 的 `plan_revisions` 保持不可变，不承载应用状态。

### 4.4 上游 Project 完成时点

不要在仍可能进入授权轮次时过早 complete 上游 Project。只有当前 Issue 的全部必要目标确认一致、没有后续获准轮次、且所有任务处于终态时，才允许调用 complete。上游 complete 只表示上游项目终态，不等于业务验收通过或交付完成。

### 4.5 迟到结果与旧代次

旧轮次、旧 Attempt 或旧 generation 的结果只写最终 `result_admissions` 裁决与观察记录；证据不足时返回 `needs_recheck` 并沿用等待核查，不产生裁决行。`reject_stale` 不解锁依赖，不覆盖当前图，不产生新的派工。结果看起来成功但归属或代次不符时仍按 stale 处理，不按内容相似度合并。

### 4.6 连续失败与停止

Graph 专题第 5 节现有候选数值为每个修复 Loop 默认 3 轮、诊断补证 2 轮、环境恢复 2 次，以及连续两轮同一失败且无新增有效证据时停止。这些是既有候选数值，本批不擅自采用。落实时必须与本 Issue 的计划、预算与时限一起固定，先到先停。换计划或重命名节点不清零累计消耗。

### 4.7 响应丢失与崩溃

换图响应丢失时先按原操作身份和目标读回，不重复应用。协调器重启后从 B10 的 `rounds`、完整 `round_plan_pointers`、`plan_revisions`、Attempt 记录，以及本章的 `target_applications`、`round_transitions` 重建责任。部分应用状态保留，不因重启自动恢复派工。未知外部动作保留核查责任和重新评估条件。

### 4.8 删除与保留

轮次、结果采纳、停止决定和交付映射在项目存续期保留归属、版本关联和决定依据。临时运行材料与产物按项目清理策略处理。旧 Attempt、旧组合和旧证据的历史保留，缺失正文标注归档或缺失，不冒充当前可复核证据。清理未知外部动作前先核查。

## 7. 待取舍点

| 取舍 | 选项 | 影响 | 本章默认写法 |
| --- | --- | --- | --- |
| 换图接法 | resume 后 replan，或 paused replan 窄补丁 | 决定门禁复杂度与上游维护成本 | 保留两条，要求逐目标读回 |
| submitted 收尾责任 | 由协调角色单点收尾，或按任务类型分散 | 影响状态一致性与审计 | 由协调角色持有收尾决策，证据来自执行侧 |
| 跨仓依赖表示 | 独立边表，或任务表内嵌数组 | 影响查询、唯一性与部分失败恢复 | 采用独立边表，便于逐边证据 |
| 候选与组合归属 | B11 自建业务身份，或引用 ChangeSet | 影响是否出现两套候选状态 | 引用 ChangeSet，本批只存执行映射 |
| 上游 complete 时点 | 全部目标一致后立即 complete，或等业务交付完成 | 影响跨轮复用与重新打开难度 | 等无后续获准轮次与全部目标一致 |
| 停止默认数值 | 沿用 Graph 专题候选值，或按项目另行确定 | 影响停止行为与用户预期 | 候选数值不擅自采用，随计划固定 |

本章只做设计、源码与文档核对，没有启动服务、数据库、浏览器、容器或真实上游实验，也没有把任何候选数值写成实测结论。
