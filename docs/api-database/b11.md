# B11 两轮换图与跨仓部分应用恢复（G5）

本批对应施工计划中的 B11，范围是 G5。用户能完成的事情有四件。第一，在第一轮验证发现明确业务缺陷后，在既有授权、预算、时限和循环上限内进入第二轮，只修复受影响仓库并重新判断证据适用性。第二，在两仓交付中一仓应用成功、一仓失败或未知时，看到逐目标真实状态，受影响范围保持停派工，已成功部分不被撤销。第三，看到旧 Attempt 的迟到结果被归档，不会解锁当前图或覆盖正式状态。第四，看到预算、时限、轮次上限或连续相同失败触发停止时，停止原因和累计消耗可追溯。

本批不另造通用 Go DAG 引擎，不做任意嵌套流程语言、图编辑器或动态插件平台，不恢复 Skill 工程与审批模式，不改变人工 Git 合并职责，不重设计 B10 已定的资源生命周期。

2026-09-15 的物理布局复核把 B10 与 B11 原来的 20 张候选表压到 11 张承载表，并按已采用的业务计划前置补一张 `business_plan_versions`，执行域共 12 张物理表。B10 持有 10 张，本章只新声明两张：`repomesh_execution.cross_repo_edges` 与 `repomesh_execution.result_admissions`。轮次转换、目标应用、候选映射、组合映射与停止决定不再各占一张表，分别并入 B10 的 `execution_records`、`plan_revisions` 与 `change_set_versions`。合并只改物理承载，本章的七个内部边界、上游入口清单、恢复语义与复用引用全部保留。B01 至 B04 的已有 36 张表不动，B05 至 B11 的设计表合计 34 张。

## 1. 范围与状态

### 1.4 用户能完成什么

用户看到第一轮检查记录业务缺陷后，可以要求 Manager 在既定修复范围内组织第二轮。系统只对受影响仓库形成新的有限任务安排，未修改的参与仓库仍固定原基线，旧证据按新组合重新判断适用性。用户不需要理解上游 replan 限制，但页面必须显示计划是否真正应用、哪些目标已读回、哪些目标仍关闭。

两仓交付只成功一仓时，用户看到的是部分应用，不是整体完成。系统保留已成功部分，继续关闭受影响范围的派工，逐目标核查后恢复。旧 Attempt 的结果即使晚到，也只进入历史与适用性判断，不会因为内容看起来成功就自动放行当前依赖。

### 1.5 依赖

依赖 B10 的正式写方选择、轮次与计划修订、Attempt 身份、资源生命周期、业务计划版本、停止与写能力撤销协议。依赖 B09 的可信消息与调用授权。依赖 B05 的预算、时间政策与额度账本。依赖 B06 的 Issue、主 ChangeSet 与仓库范围。依赖 B07 的只读投影。依赖锁定上游的 Controller REST 与 TeamHarness 图操作。

上游 replan 的前置条件已核对。[project_handler.go](../../third_party/AgentTeams/agentteams-controller/internal/server/project_handler.go)第 2413-2450 行要求项目 active、plan_type 为 dag 或未设置，并且没有 in_progress 或 submitted 任务。paused 项目不能直接 replan，B11 必须显式选择接法，不能把业务流程图上的“暂停、收敛、换图”直接翻译成两次原生调用。

### 1.6 明确边界

本批不选择上游补丁的最终形态，不冻结 replan 接法，不新增通用 DAG 引擎，不改变仓内依赖与环校验算法。它不把上游 `submitted`、`completed` 或工具 `ok` 当业务通过，不把部分应用写成整体完成，不把旧 Attempt 的迟到结果当新证据，不把预算重试或传输重试算作业务修复轮次。

本章只新声明 §3.1 与 §3.2 两张物理表。轮次、计划修订、应用恢复、转换、停止、候选与组合的字段定义由 [B10](./b10.md) 拥有，本章只引用真实列与真实键，不复制第二套定义，也不新增未计数的映射表、历史表或队列表。

## 2. API 与内部边界

### 2.1 内部边界：graph.Service.EvaluateRound

状态为本次提案，未实现。它接收有效计划、已采纳结果、固定组合、循环进展和带来源与修订的图观察，返回需要等待、可请求执行或应停止的判断。调用方是 coordinator 协调工作。

```go
type RoundEvaluationInput struct {
    IssueID            string
    RoundID            string
    AcceptedResults    []AcceptedResultRef
    CrossRepoEdges     []CrossRepoEdge
    UpstreamObservedAt time.Time
    StopSnapshot       StopSnapshot
}

type RoundEvaluation struct {
    Decision      string
    WaitReasons   []string
    ReadyLocalTaskIDs []string
    StopReason    string
    EvaluatedAt   time.Time
}

func (s *GraphService) EvaluateRound(ctx context.Context, in RoundEvaluationInput) (RoundEvaluation, error)
```

该方法在一个只读事务中先按 `RoundID` 读取 `rounds` 行，取得业务计划版本绑定、`business_plan_binding_revision`、`plan_set_revision`、`state_revision` 与当前组合，再读取 `plan_revisions` 中该轮全部 `is_current` 行。判断以「集合版本加每行 `pointer_revision`」为准，读取期间集合变化时重读，不任取单个指针。`Decision` 只允许 `wait`、`allow_dispatch`、`stop`。该方法不做数据库写入，不持有 Controller、GitHub 或 Docker 凭据，不直接创建 Worker 或占用资源。

放行条件不只判断仓内 ready。允许派工还要求本轮引用的业务计划版本仍是 Issue 当前有效版本且绑定修订一致。需要代码组合的检查必须有属于当前轮与当前计划集合的选择记录，组合成员与本次验证计划的 `validation_repository_ids` 精确一致；非代码检查按当前有效业务版本与固定候选或产物版本核验，不要求不存在的选择记录。参与验证的检查要有仍适用的验证记录与复核，其 `evaluated_plan_set_revision` 与当前 `plan_set_revision` 精确相等，且所有跨仓前驱边处于 `satisfied` 且修订一致。任一条件缺失或已失效时返回 `wait` 并给出原因。跨仓前驱未满足时，即使上游仓内节点 ready 也不能进入 `allow_dispatch`。

### 2.2 内部边界：rounds.Service.CloseRound

状态为本次提案，未实现。它收尾当前轮次并冻结结果事实。调用方是 coordinator 轮次工作。

```go
type CloseRoundCommand struct {
    IssueID       string
    RoundID       string
    Outcome       string
    EvidenceRefs  []string
    DecidedBy     string
    CauseOperationID string
}

func (s *Service) CloseRound(ctx context.Context, cmd CloseRoundCommand) (RoundTransition, error)
```

收尾前必须确认本轮无在途或 submitted 未核查任务，或者已按真实状态完成 submitted 收尾。收尾在同一短事务内读取本轮完整 `is_current` 计划集合与对应修订、任务，逐个仓库确认，不按单条修订收尾。`Outcome` 只允许 `pass`、`business_defect`、`insufficient_evidence`、`budget_stop`、`time_stop`、`blocked`、`cancelled`。方法更新 B10 `rounds.state` 与摘要，并追加一条 `execution_records` 的 `round_transition` 记录，不另建收尾表，也不改变 `repository_issues.state`。`pass` 必须引用当前组合下仍适用的验证记录与复核，不能只引用上游 `completed`。失败与待补证不能记录为通过。旧 Attempt 迟到结果不阻止本轮收尾，但也不得被采纳为当前轮新证据。

### 2.3 内部边界：rounds.Service.OpenNextRound

状态为本次提案，未实现。它在已有授权和上限内开启下一轮。调用方是 coordinator 轮次工作。

```go
type OpenRoundCommand struct {
    IssueID          string
    PreviousRoundID  string
    Purpose          string
    ScopeRepositories []string
    CauseDecisionID  string
}

func (s *Service) OpenNextRound(ctx context.Context, cmd OpenRoundCommand) (Round, error)
```

`Purpose` 只允许 `repair`、`diagnostic`、`environment_recovery`。方法在 B10 的 `rounds` 插入一条 Issue 内轮次并追加 `round_transition` 记录。默认沿用上一轮的业务计划版本，不因修复、诊断或环境恢复新建业务版本，也不重置累计限额。本轮覆盖多个仓库时，每个受影响仓库各建立一条不可变 `plan_revisions`，绑定该仓与本次业务计划版本，并写 `is_current` 与新的 `pointer_revision`，随后各自应用。`ScopeRepositories` 每个仓库必须同时落在业务计划的 `scope_repository_ids` 与本 Issue 的固定工作范围内。

按审查闭合的同版本复用规则如下。同一业务版本内的新技术安排可以继续派工，不要求该安排出现在首次激活的目标集合里。跨轮复用既有组合时，`change_set_versions` 的组合行不改写，方法在 `execution_records` 追加新的 `combination_selection`，保存本次 `selection_validation_plan_revision_id`、`evaluated_plan_set_revision` 与业务版本。它必须在 round 锁内读取本次完整计划集合，并要求组合成员仓库精确集合等于本次验证计划的 `validation_repository_ids`。仓库集合或固定版本不同必须新建组合；集合同版本而验收、环境或数据变化只新增选择与验证上下文。首次或变更业务版本的激活仍按 §4.6 的冻结目标集合核验。

### 2.4 内部边界：planning.Service.ApplyPlanRevision

状态为本次提案，未实现。它把新的有限任务安排应用到一个受影响上游目标。调用方是 coordinator 换图工作。

```go
type ApplyPlanCommand struct {
    PlanRevisionID string
    Path           string
    CauseOperationID string

func (s *Service) ApplyPlanRevision(ctx context.Context, cmd ApplyPlanCommand) (TargetApplication, error)
```

输入 `PlanRevisionID` 引用 B10 已创建的不可变计划修订，本章不新建计划修订表。上游目标、仓库与绑定由该修订的 `upstream_binding`、`issue_id` 与 `repository_id` 唯一决定，不再单独传 `TargetBinding`。`Path` 只允许 `resume_then_replan` 或 `paused_replan_patch`。两条接法都必须遵守停新派工、等在途收尾、核对 submitted、应用并读回的顺序。

方法写 `plan_revisions` 的应用列组：第一次调用建立 `application_id` 与 `external_operation_id`，写 `application_state='publishing'` 与 `application_may_have_sent_at`，外部调用在事务外。返回 `applied`、`readback_ok`、`readback_mismatch`、`failed`、`unknown` 对应 `application_state` 的推进。多目标部分成功保留逐目标事实，不把整批记为成功或失败。

### 2.5 内部边界：delivery.Service.RecordPartialApplication

状态为本次提案，未实现。它记录某个目标的应用结果与证据。调用方是 `ApplyPlanRevision` 与恢复工作。

```go
func (s *Service) RecordPartialApplication(ctx context.Context, application TargetApplication) error
```

应用与读回结果写入对应修订唯一的应用列组：更新 `application_state`、`application_observed_at`、`application_evidence` 与 `application_revision`，并追加一条 `execution_records` 的 `plan_observation`，引用具体 `plan_revision_id`。同一修订不出现第二行应用记录，也不复制绑定或仓库。`readback_mismatch` 与 `unknown` 都保持目标关闭，保留 `resume_condition`。该方法不释放 B10 的资源占用，也不启动新的派工。

### 2.6 内部边界：delivery.Service.RecoverTarget

状态为本次提案，未实现。它按目标执行恢复核查。调用方是 coordinator 恢复工作。

```go
type RecoveryCommand struct {
    IssueID       string
    RoundID       string
    PlanRevisionID string
    CauseApplicationID string
}

func (s *Service) RecoverTarget(ctx context.Context, cmd RecoveryCommand) (RecoveryObservation, error)
```

恢复按修订读取上游目标与绑定，先按原 `external_operation_id` 读回，不重复应用。方法推进 `recovery_state` 与 `recovery_observed_at`、`recovery_evidence`，并追加 `plan_observation`。恢复读回确认一致时，同次写入把 `recovery_state` 置 `recovered` 并把 `application_state` 更新为 `readback_ok`。只有本轮全部必要修订都满足 `application_state='readback_ok' AND recovery_state IN ('none','recovered')` 时，才记录本次安排已落实。仍缺目标时保持部分状态，受影响范围继续停止新派工。

### 2.7 内部边界：graph.Service.DecideResultAdmission

状态为本次提案，未实现。它判断一个 submitted 结果是否可以进入当前轮采纳。调用方是 coordinator 结果工作。

```go
type AdmissionDecision struct {
    ResultID        string
    Decision        string
    ReasonCodes     []string
    CurrentRoundID  string
}

func (s *GraphService) DecideResultAdmission(ctx context.Context, result ResultRef) (AdmissionDecision, error)
```

`Decision` 只允许 `admit_for_current_round`、`reject_stale`、`needs_recheck`。旧轮次、旧 Attempt 代次或归属不符的结果进入 `reject_stale`。证据不足进入 `needs_recheck`，它只是本次返回与等待状态，不写 `result_admissions`，维持原 DurableWork 或 Attempt 的核查责任。只有最终 `admit_for_current_round` 与 `reject_stale` 落库，写入规则见 §3.2。任何决定都不直接写上游 `completed`，也不让依赖自动放行。

## 3. 数据表设计

本章只新声明两张物理表，都在 `repomesh_execution`：`cross_repo_edges` 与 `result_admissions`。轮次、计划修订、应用与恢复列组、转换与停止记录、候选与组合、业务计划版本的定义分别在 [B10](./b10.md) 的 §4.1 至 §4.10，本章只引用真实列与真实键。复用位置如下。

- 轮次行与完整当前集合：`rounds` 的 `business_plan_version_id`、`business_plan_binding_revision`、`plan_set_revision`、`current_combination_id`、`combination_selection_revision` 与停止摘要。当前安排是 `plan_revisions` 中 `is_current=true` 的完整集合。
- 单目标应用与恢复：`plan_revisions` 的 `application_id`、`application_path`、`application_state`、`external_operation_id`、`application_canonical_input`、`application_may_have_sent_at`、`base_revision`、`applied_revision`、`recovery_state`、`resume_condition`、`application_revision` 列组。
- 轮次转换、停止、计划观察与验证：`execution_records` 的 `round_transition`、`stop_decision`、`plan_observation`、`verification`、`verification_review` 子型。`verification` 保存验证种类、组合或非代码候选、本次验证计划修订、本次计划集合版本、验收依据修订、环境与数据快照引用、结论与证据可用性；`verification_review` 只追加适用性复核，不覆盖原验证结果。
- 候选、组合与本次选择：`change_set_versions` 的 `candidate` 与 `combination` 子型，以及 `execution_records` 的 `candidate_review` 与 `combination_selection`。组合成员快照、组合上限、初审适用性与跨轮复用规则由 [B10 §4.9](./b10.md) 定义。
- 业务计划版本与激活：`business_plan_versions` 及 `execution_records` 的 `business_plan_decision`、`business_plan_target`。计划工作列组按 B10 §4.10 的 `plan_work_stage` 与 `plan_work_state` 两阶段定义；Issue 当前有效版本指针在 B06 的新 Issue 行，B11 只读。`rounds.business_plan_version_id` 是可显式变更的绑定并配 `business_plan_binding_revision`，`plan_revisions` 与 `attempts` 上的同名列是每行不可变的实际来源版本，不用轮次当前版本的可变复合外键绑定历史行。

共同类型。ID、上游绑定、ETag 与外部版本、验收依据修订、配置与 profile 版本都用 text，公开编码保持不透明字符串，客户端不按数值解析。内部 `plan_set_revision`、`pointer_revision`、`application_revision`、`edge_revision`、`transition_revision`、`selection_revision` 与 `attempt_generation` 计数用 bigint，时间用 timestamptz。所有复合外键都带 Issue 与轮次归属，需要时带仓库或任务。外键默认 RESTRICT，不级联删除历史。

共同约束。决定与版本写入追加，不覆盖旧决定；正文或证据正文只允许封闭的非正文引用与枚举，必须内联时给出可清理白名单与 `redacted_at`，清理只置空正文并保留身份、摘要、归属与决定。跨行数量、状态机、不可变列、追加链与证据当前性由具体触发器和受控事务维护，应用角色不获绕过触发器的直接写权限。JSON 只用于已定义形状的引用数组、成员快照与证据摘要，必须有 schemaVersion 与大小限制。这些规则与 [B10 §4](./b10.md) 相同，不在本章另立一套。

### 3.1 cross_repo_edges

物理表：`repomesh_execution.cross_repo_edges`

用途是保存 RepoMesh 管理的跨仓依赖边、逐边状态与按条件分支的证据引用。写入者是 Graph 规划、计划变更与结果采纳工作。边保存在 RepoMesh，不写入上游仓内 DAG；跨仓边未满足时，上游 ready 不能放行。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| `id` | text | 是 | 主键，永不复用。 |
| `project_id`、`issue_id` | text | 是 | 复合外键到 B06 `issues(project_id,id)`。 |
| `round_id` | text | 是 | 与 `issue_id` 组成复合外键到 B10 `rounds(id,issue_id)`。 |
| `from_task_id`、`from_repository_id` | text | 是 | 前驱任务与仓库；`(from_task_id,round_id,issue_id,from_repository_id)` 引用 `execution_tasks(id,round_id,issue_id,repository_id)`。 |
| `to_task_id`、`to_repository_id` | text | 是 | 后继任务与仓库；`(to_task_id,round_id,issue_id,to_repository_id)` 引用同一任务键。 |
| `condition` | text | 是 | `artifact_accepted`、`verification_evidence`、`business_acceptance`。 |
| `state` | text | 是 | `waiting`、`satisfied`、`invalidated`。 |
| `edge_revision` | bigint | 是 | 默认 0，只增；每次状态或证据变化递增，用于 CAS。 |
| `candidate_review_record_id`、`candidate_id` | text | 否 | `artifact_accepted` 分支使用；`(candidate_review_record_id,'candidate_review')` 引用 `execution_records(id,record_kind)`，`(candidate_id,issue_id,'candidate')` 引用 `change_set_versions(id,issue_id,version_kind)`。 |
| `verification_record_id`、`verification_review_record_id`、`combination_id` | text | 否 | `verification_evidence` 分支使用；两个记录分别按 `(id,'verification')` 与 `(id,'verification_review')` 引用 `execution_records(id,record_kind)`，组合按 `(combination_id,issue_id,'combination')` 引用 `change_set_versions(id,issue_id,version_kind)`。 |
| `business_acceptance_admission_id`、`business_acceptance_basis_revision` | text | 否 | `business_acceptance` 分支使用；准入行外键到 `result_admissions(id)`，依据版本只存不透明引用，不存正文。 |
| `external_evidence_ref`、`external_evidence_source`、`external_evidence_version`、`external_evidence_digest` | text | 否 | 证据正文在受控外部位置时的引用、来源、版本与摘要；四列同空或同非空。 |
| `evidence_plan_set_revision` | bigint | 否 | 满足时的整轮计划集合版本；当前集合变化后用于判定失效。 |
| `satisfied_at` | timestamptz | 否 | 最近一次满足时间。 |
| `satisfied_edge_revision` | bigint | 否 | 最近一次满足时的 `edge_revision`；与当前修订不等即表示该满足不再生效。 |
| `updated_at` | timestamptz | 是 | 最近更新时间。 |
| `redacted_at` | timestamptz | 否 | 受限清理时间；只置空可清正文列，保留关系与决定。 |

键与约束。

1. `UNIQUE(round_id,from_task_id,to_task_id)`。`CHECK (from_task_id <> to_task_id)` 与 `CHECK (from_repository_id <> to_repository_id)`，排除自环、跨轮、跨 Issue 与假跨仓关系。
2. `(issue_id,from_repository_id)` 与 `(issue_id,to_repository_id)` 分别引用 B06 工作范围 `repository_scopes(work_issue_id,repository_id)`，两端必须是本 Issue 的固定工作仓库。
3. 状态矩阵取代「当且仅当」的单句约束。
   - `waiting`：不写任何证据分支列、`satisfied_at`、`evidence_plan_set_revision` 与 `satisfied_edge_revision`，表示尚无可用的当前满足依据。
   - `satisfied`：按 `condition` 对应的证据分支完整、其余分支列全空，`satisfied_at` 与 `evidence_plan_set_revision` 非空，且 `satisfied_edge_revision = edge_revision`，表示证据在当前修订下仍适用。
   - `invalidated`：可以保留上一次满足的完整证据列、`satisfied_at`、`evidence_plan_set_revision` 与 `satisfied_edge_revision` 供审计，但 `edge_revision > satisfied_edge_revision`，不再作为放行依据；此前从未满足时这几组全空。
   - 重新满足时用新核查结果覆盖证据列与满足时间，`satisfied_edge_revision` 更新为当次修订；旧证据本身仍在 `execution_records`，不因覆盖丢历史。
4. `artifact_accepted` 分支要求 `candidate_review_record_id` 与 `candidate_id` 非空。基础核验是：初审记录指向同一候选且 `review_decision='accepted'`，并且是本次计划与范围内最新适用的接受决定；候选的 `source_task_id` 等于 `from_task_id`，需要时连同来源 Attempt 一并核对，候选属于同一 Issue、ChangeSet 与工作仓库，固定版本按 `artifact_version_kind` 取完整 Git SHA 或内容摘要，并与产物根一致。非代码候选以 `artifact_digest` 固定，不要求伪造 SHA。候选行按 `(candidate_id,issue_id,'candidate')` 复合引用 `change_set_versions(id,issue_id,version_kind)`。只有消费场景本身明确要求某个固定组合时，才额外核对该组合冻结成员中该仓库的候选 ID 与固定版本；普通上游候选被接受后即可放行下游依赖，不要求先构成最终验证组合。
5. `verification_evidence` 分支按验证记录的 subject 分支核验，不强制所有验证都有组合。
   - `code_combination`：要求 `combination_id` 非空并等于验证记录的组合，核本次选择记录，`validation_plan_revision_id` 等于该选择记录的验证计划修订，组合成员仓库集合等于该计划的 `validation_repository_ids`；前驱由组合中被验证的候选或任务归属核对到 `from_task_id`。
   - `non_code_artifact`：要求 `combination_id` 为空，不引用组合或选择记录。核验改为：验证记录绑定本次有效业务计划版本、固定的候选或产物版本与验收依据修订，`validation_plan_revision_id` 是本轮仍适用的验证计划修订，其 `validation_repository_ids` 覆盖本次要求的仓库集合。
   - 两种分支都要求 `verification_outcome='passed'`，并在锁定当前 `rounds` 行后把 `evaluated_plan_set_revision` 与当前 `plan_set_revision` 做精确相等比较。存在 `verification_review_record_id` 时必须指向该验证记录且 `review_outcome='applicable'`；没有复核记录时不能仅凭更旧的集合版本推断仍适用。
6. `business_acceptance` 分支要求 `business_acceptance_admission_id` 与 `business_acceptance_basis_revision` 非空，并且准入行 `decision='admit_for_current_round'`、任务与 Attempt 等于该边的来源任务。准入只表示结果进入当前轮，不等于完整交付验收；需要完整业务接受才能放行的依赖保持 `waiting`，直到存在真实业务接受决定，不把准入结果解释成完整验收。
7. 外部证据不是第四类满足分支。`external_evidence_ref` 四列只作为已登记本地证据的来源元数据，必须伴随 §3.1 三类分支之一的核心引用，并且该本地证据先经受控核查登记为 B10 `execution_records` 的对应子型；四列不能单独把边置为 `satisfied`，也不能替代前驱、组合或当前计划核验。
8. 边更改先锁所属 `rounds` 行，按 `edge_revision` 做 CAS。计划集合、当前组合或本次选择变化后重新核验适用性：仍适用的保持 `satisfied`，不再适用的置 `invalidated` 并递增修订。失效与重新满足保留旧证据记录，不删除边来绕过前驱，也不因某条证据记录后来被标记缺失而改写历史满足事实。

设计理由。跨仓前驱是业务条件，不是上游 ready 的投影。把三类条件拆成各自的类型化分支后，数据库能实际证明哪条候选初审、哪次验证、哪次准入支撑了这条边，而不是只留一个不透明引用。当前计划或组合变化时，旧满足状态会失效，新证据必须重新取得，依赖不会被旧观察静默解锁。

### 3.2 result_admissions

物理表：`repomesh_execution.result_admissions`

用途是保存 submitted 结果的最终采纳判断。写入者是 `DecideResultAdmission`。它只保存最终裁决，`needs_recheck` 是返回与等待状态，不写本表。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| `id` | text | 是 | 主键，永不复用。 |
| `project_id`、`issue_id` | text | 是 | 复合外键到 B06 `issues(project_id,id)`。 |
| `repository_id` | text | 是 | 与 `issue_id` 组成复合外键到 B06 工作范围。 |
| `result_namespace` | text | 是 | 上游实例、团队与 Project 的规范化编码；不同上游的相同短引用不碰撞。 |
| `result_ref` | text | 是 | 上游结果稳定引用。 |
| `round_id` | text | 是 | 本次裁决所针对的当前轮次；与 `issue_id` 引用 `rounds(id,issue_id)`。 |
| `source_round_id` | text | 是 | 结果实际来自的轮次；与 `issue_id` 引用 `rounds(id,issue_id)`，允许与 `round_id` 不同。 |
| `task_id`、`attempt_id` | text | 是 | 来源任务与 Attempt；`(attempt_id,task_id,source_round_id,issue_id,repository_id)` 引用 `attempts(id,task_id,round_id,issue_id,repository_id)`。 |
| `attempt_generation` | bigint | 是 | 从观察事实固定的代次，不要求等于 Attempt 当前领取代次。 |
| `observed_record_id` | text | 是 | 支撑判断的观察记录；`(observed_record_id,attempt_id,issue_id,repository_id,'observation')` 引用 `execution_records` 的观察唯一键。 |
| `evaluated_plan_set_revision` | bigint | 是 | 判断时读取的整轮计划集合版本。 |
| `decision` | text | 是 | 只允许 `admit_for_current_round`、`reject_stale`。 |
| `reason_codes` | jsonb | 是 | 版本化原因数组，只允许封闭枚举码，不存自由文本或正文。 |
| `decided_by` | text | 是 | 可信协调或复核身份。 |
| `decided_at` | timestamptz | 是 | 决定时间。 |

键与约束。

1. `UNIQUE(result_namespace,result_ref,attempt_generation)`。同一结果与代次的重复请求读取原裁决，不同裁决被拒绝。
2. `decision='admit_for_current_round'` 要求 `source_round_id = round_id`，并且在事务内锁 `rounds` 行核对业务计划绑定、完整当前计划集合与 `plan_set_revision`，核当前 Attempt 与观察代次有效。`decision='reject_stale'` 允许 `source_round_id` 与 `round_id` 不同，但仍必须是同一 Issue 的真实来源 Attempt 与观察。
3. 外部归属不明、无法映射到本地 Attempt 的结果先保持隔离观察，不伪造本地 Attempt 外键，也不写最终裁决。
4. 本表只增不改，不 UPDATE 旧裁决，也不 DELETE。它只保存枚举原因与归属，不内联正文；需要人工说明时使用受控外部证据引用，不在本表内联。
5. 观察记录缺失、被标记不可用或与 Attempt 代次不符时，不写准入行，保持待核查责任。旧轮次或旧代次的迟到结果可以 `reject_stale` 保留来源归属，但不得解锁依赖、覆盖当前图或产生新的派工。

设计理由。结果是否属于当前轮次是业务判断，不能只看上游状态是否为 submitted。把裁决轮次与来源轮次分开后，既能用真实外键保存旧轮 reject_stale 的来源，又不会让迟到结果静默解锁当前依赖。最终裁决的唯一性保证第一份决定不被后来的相似内容覆盖。

## 4. 事务与恢复

### 4.1 轮次收尾

收尾先停止受影响范围的新派工，等待在途任务收敛，并按本轮完整 `is_current` 计划集合与全部修订逐仓核对 submitted。每个 submitted 结果按真实状态收尾为成功、失败或证据不足，不能把失败或待补证改成通过。轮次收尾只结束本轮，不改变 `repository_issues.state`。全部收尾后更新 B10 `rounds.state` 与摘要、追加 `round_transition` 记录，再决定是否在既有授权与上限内开启下一轮。`pass` 必须引用当前组合下仍适用的验证记录与复核；验证记录缺失或复核为不再适用时，只能收尾为待补证或业务缺陷。

### 4.2 换图接法

| 接法 | 步骤 | 风险 | 适用前提 |
| --- | --- | --- | --- |
| resume 后 replan | 停派工，收敛，pause，确认无在途，resume 到 active，replan，逐目标读回 | resume 到 replan 之间可能在受控范围外出现派工间隙，需要额外门禁 | 不改上游，但必须有可靠门禁与观察 |
| paused replan 补丁 | 停派工，收敛，保持 paused，用窄补丁应用新任务集，逐目标读回 | 需要维护上游补丁并验证新状态约束 | 允许窄上游补丁，且补丁验证通过 |

本章不选定接法，把它列为根代理与用户取舍点。无论选哪条，都必须满足停新派工、等在途收尾、核对 submitted、应用并读回。上游 pause 只是配合措施，不替代 RepoMesh 的停派工门禁。同一逻辑操作重试沿用原 `external_operation_id` 与规范化输入，响应丢失先读回核查。

### 4.3 多目标部分应用

本轮完整当前计划集合中每条修订的应用与读回独立记录在该修订的应用列组上。一仓成功、一仓失败或未知时，保留成功部分，受影响修订保持关闭，`resume_condition` 说明恢复条件。恢复先按原 `external_operation_id` 读回，不重复应用，也不为同一修订建立第二个应用身份。只有全部必要修订满足 `application_state='readback_ok' AND recovery_state IN ('none','recovered')` 时，才记录本次安排已落实并恢复允许的派工；判断不写成「不是 open 或 unknown」，避免把 `recovering` 误包含。`plan_revisions` 的不可变图正文不承载应用状态。

### 4.4 上游 Project 完成时点

不要在仍可能进入授权轮次时过早 complete 上游 Project。只有当前 Issue 的全部必要目标确认一致、没有后续获准轮次、且所有任务处于终态时，才允许调用 complete。上游 complete 只表示上游项目终态，不等于业务验收通过或交付完成。

### 4.5 迟到结果与旧代次

旧轮次、旧 Attempt 或旧 generation 的结果按 §3.2 处理。映射到真实来源后可以写 `reject_stale` 最终裁决；证据不足时返回 `needs_recheck` 并沿用等待核查，不产生裁决行。`reject_stale` 保留 `source_round_id` 与来源 Attempt 的真实外键，但不解锁依赖、不覆盖当前图、不产生新的派工。结果看起来成功但归属或代次不符时仍按 stale 处理，不按内容相似度合并。

### 4.6 同版本下一轮、激活占有与未知恢复

同一业务计划版本内的下一轮不新建业务版本。`OpenNextRound` 默认沿用当前有效版本，按本次范围建立新技术修订；准入按 §2.3 与 §4.3 核有效指针、轮次绑定、完整当前集合与本次真实读回。同一版本内后续轮次的新安排不要求出现在首次激活的冻结目标集合中。只有复用旧技术修订作为本次目标时，才需要本次激活的 `verify_unchanged` 关系；首次或变更业务版本的 `confirm_effective` 仍严格核该次激活的冻结目标全集。

激活占有按 Issue 级排他，规则以 [B10 §4.10](./b10.md) 为准：部分唯一约束只作用于 `plan_work_stage='activation'` 且 `plan_work_state IN ('pending','applying','blocked','reconciling','unknown')` 的行，同一 Issue 至多一条。`permission` 阶段与 `ready_for_activation` 不占这个排他。`unknown`、权限暂不可确认与部分成功都保留占有，只有已经生效完成或按外部恢复协议证明旧流程不再可能继续写才离开占有集合。受影响上游 Project 持续停新派工，即使 Issue 当前有效版本指针仍指向旧版本。

许可与激活分列。`current_permission_record_id` 可以指向同一版本最近一次 `authorized` 或 `rejected` 的判断，只有 `begin_activation` 的 `cause_permission_record_id` 必须指向同版本 `authorized` 记录。首次自动许可读取失败时仍有持久责任：提案事务或首次自动评估事务写 `plan_work_id`、`plan_work_stage='permission'`、稳定的 `pending_permission_operation_id` 与租约字段，重启后按原操作继续核查，不写假 `rejected`，也不建立激活目标。授权为 `authorized` 后，permission 阶段可以进入 `ready_for_activation`；`begin_activation` 在同一事务固定完整目标集合与激活操作身份后才进入 activation 阶段，并建立对应工作责任。

旧技术修订的应用身份不可改写。旧操作结果未知时只能继续原操作核查；核清后确实需要再次外部写相同内容时，建立新的技术修订与自己的应用身份，业务版本无需改变，旧行与旧外部操作保留。

### 4.7 连续失败与停止

Graph 专题第 5 节现有候选数值为每个修复 Loop 默认 3 轮、诊断补证 2 轮、环境恢复 2 次，以及连续两轮同一失败且无新增有效证据时停止。这些是既有候选数值，本批不擅自采用。落实时必须与本 Issue 的业务计划版本、预算与时限一起固定，先到先停。停止决定写 `execution_records` 的 `stop_decision`，`rounds` 只更新最新摘要；累计消耗读取 B05 账本，换计划或重命名节点不清零累计消耗。

### 4.8 响应丢失与崩溃

换图响应丢失时先按原 `external_operation_id` 和目标读回，不重复应用。协调器重启后从 B10 的 `rounds`、完整当前计划集合、`plan_revisions` 应用列组、Attempt 与记录，以及本章的 `cross_repo_edges`、`result_admissions` 重建责任。业务计划许可或激活任务按原 `plan_work_id`、阶段、代次与租约恢复；租约到期只转移本地核查责任，不改变原操作身份与目标集合。部分应用状态保留，不因重启自动恢复派工。未知外部动作保留核查责任和重新评估条件。

### 4.9 删除与保留

轮次、结果采纳、停止决定、跨仓边与交付映射在项目存续期保留归属、版本关联与决定依据。记录只增不改；正文清理追加 `retention` 记录并置 `redacted_at`，不改身份、固定摘要与决定值。临时运行材料与产物按项目清理策略处理，缺失正文标注归档或缺失，不冒充当前可复核证据。跨仓边的证据引用在清理后保留关系；证据不再可用时边回到失效或等待，不放行新的派工。清理未知外部动作前先核查，清理不得让旧操作获得新的派工资格。

| B11-M-10 | 组合跨轮复用时新增选择记录，保存本次验证计划修订与整轮计划集合版本。成员仓库集合与验证计划不一致时选择被拒绝，组合版本行不被改写 |
| B11-M-11 | 轮次通过要求当前组合下仍适用的验证记录与复核。验证记录缺失、结论非通过或复核标记不再适用时，`pass` 被拒绝，只能收尾为待补证或业务缺陷 |
| B11-M-12 | 正文清理与保留：清理计划正文或证据正文后，追加 retention 记录并置 redacted 时间，身份、固定摘要、决定与外键保留；跨仓边因证据不可用而失效，不放行新派工 |
| B11-M-13 | 原 20 张提案表在新布局中各有且仅有一条去向，执行域 12 张表没有未声明的隐藏表，候选与组合不另建第二套映射权威 |

以上场景是待实现、待执行的验收设计。本章没有运行数据库、服务或真实上游实验，静态核对不能替代运行验收。

## 7. 待取舍点

| 取舍 | 选项 | 影响 | 本章默认写法 |
| --- | --- | --- | --- |
| 换图接法 | resume 后 replan，或 paused replan 窄补丁 | 决定门禁复杂度与上游维护成本 | 保留两条，要求逐目标读回 |
| submitted 收尾责任 | 由协调角色单点收尾，或按任务类型分散 | 影响状态一致性与审计 | 由协调角色持有收尾决策，证据来自执行侧 |
| 跨仓依赖表示 | 独立边表，或任务表内嵌数组 | 影响查询、唯一性与部分失败恢复 | 采用独立边表，按条件分支保存类型化证据 |
| 上游 complete 时点 | 全部目标一致后立即 complete，或等业务交付完成 | 影响跨轮复用与重新打开难度 | 等无后续获准轮次与全部目标一致 |
| 停止默认数值 | 沿用 Graph 专题候选值，或按项目另行确定 | 影响停止行为与用户预期 | 候选数值不擅自采用，随业务计划版本固定 |
| 业务接受的完整载体 | 先用准入记录支撑业务接受分支，或等待更完整的交付接受模型 | 影响需要完整业务接受的依赖何时能放行 | 准入只表示进入当前轮，缺完整业务接受时边保持 waiting |
| 验证记录的作者归属 | 由执行观察用例统一写，或由独立验证用例写 | 影响验证记录与组合选择的落库时机 | 归 B10 的 `execution_records` 验证子型，本章只消费与核验 |

本章只做设计、源码与文档核对，没有启动服务、数据库、浏览器、容器或真实上游实验，也没有把任何候选数值写成实测结论。
