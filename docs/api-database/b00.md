## 三进程与命令

三个入口共享一个 Go module 与版本变量，见 [version.go](../../internal/buildinfo/version.go) 第 1 行。共享源码不代表共享进程权限：Web 提供 HTTP，coordinator 承担后台工作，host-executor 承担受限主机执行，边界见 [三进程 ADR](../adr/0013-web-coordinator-host-executor-processes.md)。

### repomesh-web 启动

#### 调用方与用途

浏览器用户与部署人员的 HTTP 进程。未配置认证时提供探针、登录占位页和已构建前端；B00 只验证“能启动、能服务、不谎报业务就绪”。

#### 参数

| 参数 | 默认值 | 类型 | 必填 | 含义 |
| --- | --- | --- | --- | --- |
| `--addr` | `REPOMESH_WEB_ADDR`，其次 `127.0.0.1:8080` | string | 否 | HTTP 监听地址。 |
| `--assets` | `REPOMESH_WEB_ASSETS`，其次 `web/dist` | string | 否 | 已构建前端目录，相对启动工作目录解析。 |
| `--version` | 无 | bool | 否 | 打印 `repomesh-web <版本>` 后退出 0。 |
| `--auth-config` | `REPOMESH_AUTH_CONFIG` | string | 否 | 认证部署 JSON；提供后连接数据库并要求迁移已匹配，见 [main.go](../../cmd/repomesh-web/main.go) 第 63 行。 |

旗标定义与解析见 [main.go](../../cmd/repomesh-web/main.go) 第 39 行至第 45 行。多余位置参数直接拒绝并退出 2，见同文件第 55 行。当前源码在启动参数之前分派 `db` 与 `sources` 子命令，见第 33 行与第 36 行；它们分别属于 B01 与 B04，本文件不把子命令行为记到 B00 名下。

#### 行为与退出码

| 场景 | 结果 | 退出码 |
| --- | --- | --- |
| 正常启动 | 校验 `index.html` 存在，监听地址并服务探针、页面与静态资源 | 收到中断信号后 0 |
| 资源目录缺少 `index.html` | 返回“run npm --prefix web ci and npm --prefix web run build”类错误，不监听 | 1 |
| `--version` | 打印版本 | 0 |
| 位置参数或未知旗标 | 打印错误 | 2 |
| 提供 `--auth-config` 但启动失败 | 打印 `authentication startup:` 错误 | 1 |

服务端超时与日志见 [server.go](../../internal/web/server.go) 第 51 行与第 57 行；启动日志固定输出 `business_ready=false`。

#### 设计理由

把“能启动”和“业务可用”分开，开发和部署不会因为进程活着就误判功能可用。缺少前端资源时立即失败，而不是启动后返回 404，是为了让构建漏步骤在启动时暴露。

### repomesh-coordinator

#### 调用方与用途

后台协调进程。B00 只交付“真实声明未实现”的行为；B02 之后它在配置认证时承担认证维护与发现续扫。

#### 参数与行为

| 参数 | 默认值 | 含义 |
| --- | --- | --- |
| `-version` | 无 | 打印 `repomesh-coordinator <版本>` 后退出 0。 |
| `-auth-config` | `REPOMESH_AUTH_CONFIG` | 认证部署 JSON。 |

当前源码在未配置认证时打印“authentication is not configured; no background work is running”并退出 1，见 [main.go](../../cmd/repomesh-coordinator/main.go) 第 31 行；配置后进入 `RunOne` 循环，见同文件第 46 行。B00 记录时刻的文案是“not implemented (scaffold only); no queue, scheduling, Graph or AgentTeams integration is running”，保留在 [入口探针](../development/2026-09-12-batch-01/b00-runtime.json)。两条记录都表达同一事实：没有认证配置就没有后台工作。

#### 设计理由

后台进程不因为“文件存在”就假装工作。明确退出码让脚本能断言真实状态，也让未来的 Graph 与调度接入必须显式实现。

### repomesh-host-executor

#### 调用方与用途

受限主机执行进程的占位入口。当前只支持 `--version`，其余调用按未实现退出。

#### 参数与行为

`--version` 打印 `repomesh-host-executor <版本>` 并退出 0；不带该旗标时向 stderr 打印“not implemented (scaffold only); no listener, host commands, containers or Python analysis are enabled”并退出 1，见 [main.go](../../cmd/repomesh-host-executor/main.go) 第 18 行与第 19 行。

#### 设计理由

三进程架构要求主机能力走独立受限边界。先把“没有监听、没有任意命令、没有挂载”写成可观察事实，避免后续批次把 Web 进程当成能执行宿主机操作。

## 进程探针与静态页面

### GET /healthz

#### 调用方与用途

运维与验证脚本的存活探针。它只回答“Web 进程是否在服务”，不回答任何业务问题。

#### 输入与返回

无输入参数。`200 OK` 返回：

```json
{"process":"repomesh-web","version":"dev","status":"scaffold","businessReady":false}
```

字段含义：`process` 固定为 `repomesh-web`；`version` 来自 [version.go](../../internal/buildinfo/version.go) 第 5 行，本地构建为 `dev`；`status` 固定 `scaffold`；`businessReady` 固定 `false`，源码见 [server.go](../../internal/web/server.go) 第 99 行。

#### 错误与状态码

该路由不返回错误状态。验证脚本额外断言 `businessReady` 必须为 `false`，见 [verify-batch.ps1](../../scripts/verify-batch.ps1) 第 277 行。

#### 设计理由

探针被监控系统轮询，如果它承诺业务就绪，一次数据库或上游故障会表现为“服务突然不健康”，而实际业务能力从未存在。固定 `false` 让看板与服务状态都保持真实。

### GET /readyz

#### 调用方与用途

业务就绪探针。当前实现固定表示“业务能力未实现”。

#### 输入与返回

无输入参数。`503 Service Unavailable` 返回：

```json
{"status":"not_implemented","message":"Business capabilities are not implemented."}
```

源码见 [server.go](../../internal/web/server.go) 第 105 行。B00 记录时刻的响应与当前一致，见 [运行探针](../development/2026-09-12-batch-01/b00-runtime.json)。

#### 设计理由

只有真正接入业务能力的批次才有资格改变这个响应。沿用 503 可以让后续批次把“业务就绪”当成显式验收项，而不是顺手改一个字符串。

### 未配置认证时的 /api 行为

#### 调用方与用途

保护浏览器 API。认证未装配时，任何已注册接口都必须拒绝服务，而不是返回空数据。

#### 行为

| 路径形态 | 状态 | 响应 |
| --- | --- | --- |
| 已注册的认证接口，例如 `GET /api/session` | 503 | `{"error":{"code":"AUTH_NOT_CONFIGURED","message":"The request could not be confirmed.","details":{}}}`，见 [auth.go](../../internal/web/auth.go) 第 32 行与第 179 行。 |
| 已注册的项目接口，例如 `POST /api/projects` | 503 | `{"error":{"code":"AUTH_NOT_CONFIGURED","message":"The request could not be completed.","fieldErrors":[],"requestId":"..."}}`，见 [projects.go](../../internal/web/projects.go) 第 160 行与第 224 行。 |
| 未注册的 `/api/*`，例如 `GET /api/nonexistent` | 404 | `{"error":"not_implemented"}`，见 [server.go](../../internal/web/server.go) 第 112 行。 |

这里有一处需要按时间解释的差异：B00 记录时刻项目路由尚未注册，脚本记录的 `GET /api/projects` 是 `404 {"error":"not_implemented"}`，见 [B00 运行探针](../development/2026-09-12-batch-01/b00-runtime.json)；B02 的两次验收记录同样仍是 404，见 [verification-01](../development/2026-09-12-batch-02/verification-01/checks.json) 与 [verification-02](../development/2026-09-12-batch-02/verification-02/checks.json)。当前源码对同名路径返回 503 `AUTH_NOT_CONFIGURED`，见 [verify-batch.ps1](../../scripts/verify-batch.ps1) 第 271 行与 [B03 后端验收](../development/2026-09-12-b03-integration-01/backend-verification-20260913-062605/checks.json) 的 `http-/api/projects` 记录。这些 404 记录都不表示接口可用，差异来自后续批次注册了路由。

#### 设计理由

区分“路由存在但没有认证”和“路由不存在”能让页面在未配置部署里给出可解释错误；同时保持 `/api/*` 不为任何人返回伪造数据。

### 页面路由与静态资源

| 路径 | 行为 |
| --- | --- |
| `/`、静态资源 | 从 `--assets` 目录读取；不存在的文件返回 404。 |
| `/login`、`/auth/result/{id}`、项目与模型页面路由 | 返回 `index.html`，带 `Cache-Control: no-store` 与 `Referrer-Policy: no-referrer`，见 [server.go](../../internal/web/server.go) 第 122 行。 |
| 非 `GET`／`HEAD` 的页面请求 | 405，`Allow: GET, HEAD`，见 [server.go](../../internal/web/server.go) 第 116 行。 |

JSON 响应统一 `Cache-Control: no-store`，见 [server.go](../../internal/web/server.go) 第 142 行。

### scripts/verify-batch.ps1

#### 调用方与用途

开发者在本地重跑某一批的工程检查。脚本自行准备隔离资源并在结束时清理，证据写入唯一新目录。

#### 输入

| 参数 | 类型 | 必填 | 含义 |
| --- | --- | --- | --- |
| `-Batch` | `B00&#124;B01&#124;B02&#124;B03` | 否，默认 `B01` | 选择检查组合，见 [verify-batch.ps1](../../scripts/verify-batch.ps1) 第 2 行。 |
| `-PostgresBin` | string | B01 至 B03 必填 | PostgreSQL 二进制目录；B00 不需要。 |
| `-EvidenceDirectory` | string | 否 | 证据目录；已存在时拒绝覆盖，见第 22 行。 |

#### B00 组合的实际步骤

| 步骤 | 命令或断言 |
| --- | --- |
| 工具版本 | `go version`、`node --version`、`npm --version`，见 [verify-batch.ps1](../../scripts/verify-batch.ps1) 第 152 行。 |
| 工程检查 | `go build ./...`、`go test -json -count=1 ./...`、`go vet ./...`、`npm --prefix web ci`、`npm run typecheck`、`npm run build`，见第 187 行至第 204 行。 |
| 三入口 | 构建 `repomesh-web`、`repomesh-coordinator`、`repomesh-host-executor`，断言版本输出，并断言 coordinator 与 host-executor 按真实状态退出 1，见第 213 行起。 |
| HTTP 探针 | 真实启动 Web 二进制后断言 `/healthz` 200、`/readyz` 503、`/api/projects` 503、`/api/session` 503、`/login` 200、`/` 200，且 `/` 内容与构建产物一致，见第 271 行。 |

#### 结果语义

脚本在 `checks.json` 写入 `result`、`failure`、`cleanupPassed` 与逐项记录，见第 332 行。B00 与 B01 通过为 `VERIFIED`；B02、B03 分别写 `LOCAL_VERIFIED` 与 `BACKEND_LOCAL_VERIFIED`，其外部验收单独记录，避免把本地检查升级为整批通过。

#### 设计理由

同一批检查如果每次手工执行，结论依赖当时的命令历史。固定脚本把命令、版本、退出码与清理结果一起保存，评审者可以复跑同一组断言。

| 项目 | 内容 |

## 事务与恢复

B00 不定义业务事务、操作身份或恢复协议，因此没有可写的回执、幂等键或状态转移。相关工作区事实是“基线先记录再动手”：开始前的文件哈希与 Git 状态先归档，后续批次只能在允许清单内写入，见 [工作区基线](../development/2026-09-12-batch-01/baseline.json) 的 `note` 字段与 [实现方案](../development/2026-09-12-batch-01/design.md) 的工作区隔离说明。

## 设计理由

批次拆分把“工程可用”与“业务可用”分开。这样后续发生回归时，维护者可以先确认工程检查是否仍然通过，再判断问题属于业务实现还是构建链路；`businessReady=false` 与固定 503 让业务完成度只能由真实验收改变。

三个入口各自保留退出语义，是为了让脚本能断言真实状态而不是读日志猜。共享一个版本变量避免三个二进制声称不同版本；发布包不自动部署，避免“构建通过”被解释成“上线成功”。

## 验证清单

以下为可观察的预期结果，B00 历史记录已经执行过一次；复跑时应得到同样结论。

- `go build ./...`、`go test ./...`、`go vet ./...` 退出 0；前端 `npm ci`、`typecheck`、`build` 退出 0。
- `repomesh-web --version`、`repomesh-coordinator --version`、`repomesh-host-executor --version` 输出的版本与构建标签一致。
- 未配置认证时 `repomesh-coordinator` 与 `repomesh-host-executor` 退出 1，且不监听端口。
- `GET /healthz` 返回 200 且 `businessReady` 为 `false`；`GET /readyz` 返回 503。
- 未配置认证时已注册的 `/api/*` 返回 503 `AUTH_NOT_CONFIGURED`，未注册的 `/api/*` 返回 404 `not_implemented`，两者都不返回业务数据。
- `GET /` 返回的 HTML 与 `web/dist/index.html` 逐字节一致；不存在的静态路径返回 404。
- `scripts/build.ps1 -Version <新标签>` 在标签未使用时生成目录与 `release.json`，重复使用同一标签时拒绝覆盖。
