# B05 模型测试与应用

B05 在 B04 已保存的供应商快照上做两件事。用户先对某个固定模型发起一次连通性测试，明确可能收费后登记一次请求；再把自己有权项目里的模型换成另一个固定快照，同时完整保留原有 execution 配置。项目读接口另外返回固定预算与时限摘要，以及当前额度观察。

本批产品未实现，运行未验收。设计状态分三层：B04 已实现的事实是本批输入；测试预览与 handler 观察、unknown 运维关闭、逐路径锁序与共同 owner account 边界、schema2 唯一 `executionProfiles` 集合、窗口 scope 约束五项已在 [B05/B06 设计收口](../development/2026-09-14-b05-b06-design-closeout-01/README.md) 固定为后续实现基线；D05、D06、C05、C06 以及全部候选数值仍未采用。字段唯一来源是 [模型浏览器候选](../current/model-settings-browser-api-draft.md) 与 [首批浏览器契约 C05](../current/first-batch-browser-api-contract.md)，内部事务唯一来源是 [模型内部操作候选](../current/backend-model-operations-draft.md) 第 8 节与 [来源候选](../current/backend-first-batch-sources-draft.md) 第 9 节。跨批公共规则见 [公共规则](./foundations.md)。

本轮的存储合表只改物理承载。B05 原 16 张候选物理表合并为 9 张，测试、预留、发送许可、未核责任、关闭事实、观察证据、政策版本与来源绑定这些逻辑责任一条不少，API、字段、状态与验收状态都不因合表改变。映射与统计见[物理合表映射与统计](#b05-物理合表映射与统计)，合表授权与本轮制作范围见 [B05-B11 合表制作记录](../development/2026-09-15-table-consolidation-01/README.md)。B01 至 B04 的现有 36 张表、字段、约束与验收边界保持不动。

## 公共约定

本批字段骨架沿 B04 与 B03 的既有边界，不另建传输协议。

| 约定 | 行为 |
| --- | --- |
| 认证 | Cookie 会话；写请求要求单值 `Origin` 与 `X-CSRF-Token`；错误体与 B04 相同。 |
| 预览角色 | 预览只建立短期比较上下文，不是授权令牌，不预留额度或槽位，不发送模型请求。 |
| 固定快照 | 测试与新应用只针对当前已保存快照发起；已提交操作继续使用自己的快照，不受后续 head 变化影响。 |
| 模型秘密 | 只使用 `model-provider-key` 业务密文；比较 vault 与清理入口不向 transport 开放。 |
| 出站边界 | 固定目标与协议，禁止重定向、环境代理与自动重试；详细地址策略见 [来源候选](../current/backend-first-batch-sources-draft.md) 第 6 节。 |
| 费用语义 | 本地只记请求次数；`currency` 与金额字段始终为 null，不声称金额上限或账单结算。 |
| 运行无关 | 测试成功不是应用模型、创建 Issue 或启动运行的前置条件。 |

## 状态与枚举

对外状态由持久事实投影，内部 dispatch 子阶段不直接成为 HTTP 枚举，来源见 [模型浏览器候选](../current/model-settings-browser-api-draft.md) 第 4 节。

| 字段 | 取值 | 含义 |
| --- | --- | --- |
| `state` | `queued` | 已登记，尚无实际调用开始观察。 |
| `state` | `running` | 已观察到实际传输开始且尚未得到结果。 |
| `state` | `passed` | 该次请求取得完整、可解析、符合协议的成功响应。 |
| `state` | `failed` | 明确拒绝响应或已确认响应无效；可能已收费。 |
| `state` | `unknown` | 外部可能已发送，未能确认结果。超时、崩溃与结果落库失败都可能产生该状态。 |
| `state` | `rejected` | 已证明未进入可能发送阶段；当前协议下该分支没有发送许可，额度为 `released`。将来若采纳「许可后确定未发」的分支，额度保持 `consumed`。 |
| `budget.status` | `reserved`、`consumed`、`released` | 本地 1 次请求额度；只有尚未生成发送许可的确定未发记录才能从 `reserved` 释放为 `released`。已有许可的记录保持 `consumed`，不退款。 |
| `charge.status` | `not_sent`、`possible`、`unknown` | 费用观察，不表示金额结算。 |
| `recovery.state` | `open`、`closed_without_result`、`not_needed` | `passed`、`failed`、`rejected` 为 `not_needed`；已运维关闭的 unknown 为 `closed_without_result`，历史 `state` 仍为 `unknown`。 |
| `resultRevision` | 不透明字符串 | 只做等值比较或由服务端单调推进，客户端不比较字典序。 |

## HTTP API

以下路径与字段是待采用的机器协议，均未实现。路径以 [模型浏览器候选](../current/model-settings-browser-api-draft.md) 的 M02 接口目录为准。

### POST /api/model-test-previews

#### 调用方与授权

模型设置页。调用者必须拥有该供应商，且目标模型行属于该供应商当前已保存修订。

#### 输入

| 字段 | 类型 | 必填 | 约束 | 含义 |
| --- | --- | --- | --- | --- |
| `providerId` | string | 是 | UUID 形状 | 目标供应商。 |
| `providerRevision` | string | 是 | UUID 形状 | 目标修订，必须等于当前 head。 |
| `modelRowId` | string | 是 | UUID 形状 | 目标模型行。 |

#### 返回

`200 OK`，返回预览对象。关键字段为 `previewId`、`expiresAt`、`providerId`、`providerRevision`、`modelRowId`、`modelId`、`secretVersionId`、`policyRevision`、`cost`、`requestLimit`、`canSubmit`、`reasonCodes`。`cost` 取 `{basis:"request_count",units:1,mayCharge:true,currency:null,maxEstimatedCharge:null}`。`requestLimit.maxOutputTokens` 取 `min(16, 该模型 maxOutputTokens)`，其中 16 是候选值，未采用；`requestLimit.timeoutSeconds` 取固定时限政策版本值，不得预览一个值而实际执行另一个值。

`canSubmit` 为 false 时 `reasonCodes` 可能包含 `TEST_ALREADY_OUTSTANDING`、`QUOTA_UNAVAILABLE`、`EGRESS_NOT_ALLOWED`、`SECRET_UNAVAILABLE`、`PROFILE_UNAVAILABLE`、`TEST_HANDLER_UNAVAILABLE`、`LIMIT_UNSUPPORTED`。只有 `TEST_ALREADY_OUTSTANDING` 分支额外返回顶层 `existingTestId` 与 `links.operation`，且两者同时出现。

#### 错误与状态码

| 状态 | code | 触发条件 |
| --- | --- | --- |
| 404 | `RESOURCE_NOT_FOUND` | 供应商、修订或模型行不可见。 |
| 409 | 不适用 | 预览不返回业务冲突；冲突在提交阶段表达。 |
| 503 | `AUTHORIZATION_UNCONFIRMED` | 当前资格或出站资格无法确认。 |
| 503 | `TEST_HANDLER_UNCONFIRMED` | 处理器登记读取失败。该失败不创建预览记录，也不使用 `RESULT_UNCONFIRMED`。 |
| 503 | `AUTH_NOT_CONFIGURED`、`RESULT_UNCONFIRMED` | 未配置认证；数据库不可用。 |

#### 并发与重放

预览在同一次当前主体观察中分别读取三项事实：当前 actor 未核清测试、额度窗口、匹配协议的处理器登记。三者互不替代。预览不预留额度或槽位，因此预览通过不构成提交许可；提交阶段必须在事务内重查并以 409 拒绝竞争。

#### 设计理由

预览要回答“现在能不能再发一次可能收费的请求”，因此必须同时看到占用、额度与处理器。把预览当锁会让两个标签页互相阻塞；把它当纯展示又会漏掉提交竞争。实现选择展示加提交重查。

### POST /api/model-tests

#### 调用方与授权

测试表单。写请求要求 `Origin` 与 CSRF；`Idempotency-Key` 就是本次 `testId`。

#### 输入

| 字段 | 类型 | 必填 | 约束 | 含义 |
| --- | --- | --- | --- | --- |
| `previewId` | string | 是 | 未过期且属于当前 actor | 预览定位。 |
| `confirmPotentialCharge` | boolean | 是 | 必须为 true，false 返回 422 | 明确可能收费。 |

#### 返回

首次登记 `202 Accepted`，请求体为 `TestResult`。原键与原输入重放返回原回执。`TestResult` 字段为 `testId`、`providerId`、`providerRevision`、`modelRowId`、`state`、`resultRevision`、`acceptedAt`、`observedAt`、`result`、`budget`、`charge`、`recovery`、`links.operation`。`202` 只表示本地登记与持久责任，不表示测试通过。

#### 错误与状态码

| 状态 | code | 触发条件 |
| --- | --- | --- |
| 409 | `TEST_PREVIEW_CHANGED` | 版本或政策已经变化。 |
| 409 | `TEST_PREVIEW_EXPIRED` | 预览过期。 |
| 409 | `TEST_ALREADY_OUTSTANDING` | 当前 actor 已有 `queued`、`running` 或 `recovery.open` 的 unknown。当前 actor 仍可读阻断记录时，`error.details` 为 `{existingTestId,links:{operation}}`。 |
| 409 | `TEST_BUDGET_UNAVAILABLE` | 额度不足。 |
| 409 | `TEST_HANDLER_UNAVAILABLE` | 没有匹配协议与输出限制映射的处理器登记。 |
| 503 | `TEST_HANDLER_UNCONFIRMED` | 处理器登记读取失败，不登记测试、不预留额度、不消费预览。 |
| 422 | `VALIDATION_FAILED` | 字段非法或 `confirmPotentialCharge` 不为 true。 |
| 409 | `IDEMPOTENCY_CONFLICT` | 同键不同规范化输入。 |

#### 并发与重放

提交先按 `(actor,testId)` 读原操作，命中且输入一致时直接返回原回执，优先于预览期限、处理器、未核清测试、额度与其他新建检查。没有原操作时，短事务重查全部条件后登记 `queued`、预留 1 单位额度、写唯一测试工作与接受事实，并把预览消费绑定到该 `testId`。同一预览只能有一个 `testId` 消费。锁序以[锁序与事务归属](#b05-锁序与事务归属)第 2 条为唯一权威：binding → session → account → tests 操作槽 → catalog/profile → Provider → preview → test policy_binding/policies → 原 UTC 窗口 → account 锁下读 tests 未核责任 → secret availability。本节不另外维护第二套可照做的物理顺序。

#### 设计理由

先登记再发送，崩溃时留下可核查责任，不会静默丢失一次可能收费的请求。原键重放优先于新条件，避免用户刷新页面后既拿不到原结果又多发一次请求。

### GET /api/model-tests/{testId}

#### 调用方与授权

结果页与恢复页。只查询当前 actor 自己的测试；不触发新的模型请求。

#### 输入

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| 路径 `testId` | UUID 形状字符串 | 是 | 原操作键。 |

#### 返回

与登记响应同形的 `TestResult`，`state`、`observedAt` 与 `result` 随持久事实推进。`result` 非 null 时包含 `code`、`summary`、`latencyMs` 与 `usage`。`usage` 只来自可核实响应，缺失为 null。不保存供应商原始响应正文。

#### 错误与状态码

| 状态 | code | 触发条件 |
| --- | --- | --- |
| 404 | `MODEL_TEST_NOT_FOUND` | 当前 actor 无该键记录。这不证明操作未发生。 |
| 410 | `MODEL_TEST_RESULT_REMOVED` | 展示正文已清理；不触发新探测。 |
| 401、503 | `AUTHENTICATION_REQUIRED`、`RESULT_UNCONFIRMED` | 会话失效；数据库不可用。 |

#### 并发与重放

轮询建议间隔 2、5、10、30 秒（候选值，未采用），隐藏页面时暂停，单请求合并。一次客户端查询在途时，其后回读覆盖旧结果；按 actor、目标与请求代次丢弃晚到响应。`resultRevision` 只作等值比较。

#### 设计理由

查询是只读动作，用户核查未知状态时不会因为轮询本身增加外发次数。旧响应丢弃规则避免切换标签页后把旧测试结果画到新目标上。

| `modelRowId` | string | 是 | UUID 形状 | 候选模型行。 |

#### 返回

`200 OK`，返回应用预览。字段为 `previewId`、`expiresAt`、`projectId`、`expectedProjectRevision`、`before`、`candidate`、`canApply`、`reasonCodes`。`before.model` 用三分支联合，不用裸 null。

| 分支 | 字段 |
| --- | --- |
| 未配置 | `{status:"unconfigured"}`。 |
| 可读 | `{status:"readable",reference:ProfileChoice,modelProfileId,modelProfileVersion,providerId,providerRevision,modelRowId,links:{snapshot}}`。 |
| 受限 | `{status:"restricted",reasonCodes:["ORIGINAL_MODEL_UNAVAILABLE"]}`，不返回名称、地址、profile、provider 或行 ID。 |

`before.execution` 保留原引用与有效版本；原有效版本无法确认时 `canApply=false` 且 `reasonCodes` 含 `EXECUTION_SNAPSHOT_UNCONFIRMED`。已知固定历史版本当前不可用时允许受限保存并给出对应 reason。原模型受限不阻止有权的配置修复。

#### 错误与状态码

| 状态 | code | 触发条件 |
| --- | --- | --- |
| 404 | `RESOURCE_NOT_FOUND` | 项目不可见或候选不可读。 |
| 503 | `AUTHORIZATION_UNCONFIRMED` | 当前资格未知。 |
| 503 | `RESULT_UNCONFIRMED` | 数据库或秘密可用性读取失败。 |

#### 并发与重放

预览是短期记录，绑定 actor、项目、项目修订、配置修订、原模型、原 execution 完整引用与候选固定版本。它不是授权令牌，也不消费任何东西。预览期间的 Provider head 变化会让提交返回冲突并要求重新预览。

#### 设计理由

应用只换模型，却必须证明 execution 被完整保留。把原 execution 的完整引用与有效版本放进预览，提交时逐项比较，才能避免“看起来没变、实际换成新默认”的漂移。

### POST /api/projects/{projectId}/model-applications

#### 调用方与授权

与应用预览同源。写请求要求 `Origin` 与 CSRF；`Idempotency-Key` 是本次 `applicationId`。

#### 输入

| 字段 | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| `previewId` | string | 是 | 未过期且属于当前 actor 与该项目的预览。 |

#### 返回

成功 `200 OK`，返回 `{applicationId,outcome:"committed",projectId,projectRevision,configurationRevision,providerRevision,modelProfileId,retainedExecutionVersionId,committedAt,links:{project,operation}}`。`retainedExecutionVersionId` 必须与预览一致。确定拒绝返回持久拒绝回执，主键字段改为 `applicationId`。没有实际变化时保留原配置与项目修订，仍然写入本操作回执并消费预览。

#### 错误与状态码

| 状态 | code | 触发条件 |
| --- | --- | --- |
| 409 | `MODEL_APPLICATION_PREVIEW_CHANGED` | 候选或项目比较基线变化。 |
| 409 | `PROJECT_REVISION_CONFLICT` | 项目在预览后变化。 |
| 409 | `EXECUTION_SNAPSHOT_UNCONFIRMED` | 原 execution 有效版本无法确认。 |
| 409 | `PREVIEW_ALREADY_CONSUMED` | 同一预览已被其他操作消费。 |
| 409 | `IDEMPOTENCY_CONFLICT` | 同键不同输入。 |
| 410 | `MODEL_APPLICATION_RESULT_REMOVED` | 原记录已清理。 |
| 503 | `RESULT_UNCONFIRMED` | 提交结果未知。 |

#### 并发与重放

提交先重放原 `applicationId`，再检查预览、项目与配置修订、候选固定版本、原 execution 引用与有效版本。锁序以[锁序与事务归属](#b05-锁序与事务归属)第 8 条为唯一权威：binding → session → account → project → application 操作槽（仅提交）→ catalog/profile → Provider → preview（提交）→ secret availability，与 B03 项目写共用 `project` 前缀。冲突整笔不写配置。

#### 设计理由

项目模型与 execution 必须一起固定。若应用走完整配置 PATCH，就会重新解析 execution 默认并可能换掉用户的运行配置。专用应用把改动面收窄到模型引用，其他固定参数逐项复制。

### GET /api/projects/{projectId}/model-applications/{applicationId}

#### 调用方与授权

应用结果未知时的原操作查询。按当前项目外壳资格核权，不要求先恢复所有旧仓库读权。

#### 输入

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| 路径 `projectId` | string | 是 | 项目身份。 |
| 路径 `applicationId` | UUID 形状字符串 | 是 | 原应用键。 |

#### 返回

与提交同形的已提交或已拒绝回执。重放不代表项目当前仍是该版本，当前配置要另读项目接口。

#### 错误与状态码

| 状态 | code | 触发条件 |
| --- | --- | --- |
| 404 | `MODEL_APPLICATION_NOT_FOUND` | 当前 actor 在该项目无此键记录。 |
| 410 | `MODEL_APPLICATION_RESULT_REMOVED` | 原记录已清理。 |
| 401、503 | `AUTHENTICATION_REQUIRED`、`RESULT_UNCONFIRMED` | 会话失效；数据库不可用。 |

#### 并发与重放

只读原操作，不核新条件、不消费预览。原回执固定，当前项目快照另行读取。

#### 设计理由

丢响应时用户需要一条不依赖重发路径的核查手段。把回执与当前状态分开，避免把历史成功读成“现在还是这个模型”。

### GET /api/projects/{projectId} 的 C05 只读字段

#### 调用方与授权

项目页复用现有项目读取。新增两个字段，不新增策略查询端点，字段唯一来源是 [首批浏览器契约 C05](../current/first-batch-browser-api-contract.md) 第 10 节。

#### 返回

`configuration` 内新增 `fixedSummary` 与 `quotaObservation`。

| 字段 | 形状 |
| --- | --- |
| `fixedSummary.configurationRevision` | string。 |
| `fixedSummary.executionVersionId` | string 或 null。 |
| `fixedSummary.budget` | `{status:"available",policyId,policyVersion,scope:"project_model_runtime",unit:"request",period:"utc_day",limit,maxUnresolved}` 或 `{status:"unresolved",reasonCodes}`。 |
| `fixedSummary.timeLimits` | `{status:"available",policyId,policyVersion,modelRequestTimeoutSeconds,workerAttemptLimitSeconds}` 或 `{status:"unresolved",reasonCodes}`。 |
| `quotaObservation` | `known`、`unknown`、`not_configured` 三分支，`known` 含窗口起止、`effectiveLimit`、`reserved`、`consumed`、`remaining`、`observedAt`。 |

`available` 表示原固定参数可读，不表示当前启用、额度充足或进程停止。`unresolved` 不填 0 或推荐默认值。`not_configured` 只用于原固定配置没有可解析运行预算。`unknown` 表示没有可靠账本或读取失败，不伪造 0。

#### 错误与状态码

可选额度观察失败时返回 `quotaObservation.unknown`；项目主体或配置快照整体不可读时整次返回 503 `AUTHORIZATION_UNCONFIRMED`，不拼旧快照。

#### 并发与重放

固定摘要与 `effective` 来自同一配置版本；额度允许稍后变化。只读 GET 不创建窗口、不消费额度、不重解析默认、不跟随新默认。

#### 设计理由

用户需要在项目页看到“当时的预算与时限是多少”以及“今天还剩多少”，但两者来源不同。把固定历史与当前额度分开，就不会因为后来政策变化而篡改历史配置的展示。

## 协调进程内部边界

测试外发只由 coordinator 的 `TestRunner` 负责，Web 不持有出站调用对象。相关声明见 [b05.go.txt](../development/2026-09-13-b04-b06-design-01/b05.go.txt)。

### 一次发送许可

每个 `testId` 只能从未发阶段原子生成一次随机 `sendPermit` 与 `externalOperationId`，在同一事务里持久 `may_have_sent` 并把额度从 `reserved` 转为 `consumed`。只有收到本次事务明确 COMMIT 回执、且持有内存一次性许可的进程可以进入 transport。许可事务 COMMIT 回执丢失时，即使随后从数据库读到许可记录，也进入 `unknown`，不重新取得或恢复发送能力。重启只重新领取尚未有许可的 `queued` 记录，存在许可的一律核查。

### 处理器登记

有限登记表 `repomesh_models.test_handler_instances` 记录 coordinator 实例的随机不可复用 `instanceId`、确切 `protocolVersion`、注册与续期时间以及租约。候选参数为 60 秒租约、20 秒续期。Web 预览与新提交只读取未过期且支持该目标输出限制的登记。没有记录为 `TEST_HANDLER_UNAVAILABLE`；读取失败为 503 `TEST_HANDLER_UNCONFIRMED`。租约过期不是撤销证明，不能自动关闭 unknown 或重新授予许可。

### repomesh-coordinator model-tests unknown inspect

只读检查命令，路径为 `model-tests unknown inspect --actor-id <ID> --test-id <UUID>`。它返回 actor、测试、外部操作、发送许可、发送实例、凭据能力引用、状态、recovery、budget 与既有关闭回执，不读取原始 Secret、响应正文或许可 nonce。

### repomesh-coordinator model-tests unknown close

关闭命令，路径为 `model-tests unknown close --actor-id <ID> --test-id <UUID> --close-key <UUID> --evidence <PATH>`。

| 项目 | 语义 |
| --- | --- |
| 操作员身份 | 来自受控执行环境与专用数据库管理凭据。coordinator 用实际 DB `session_user`、固定部署身份与 `repomesh_model_test_maintainer` 角色生成不透明主体，每个事务重新核对；命令正文不能自报操作员。 |
| 证据 | schema 1 严格包含 actor、测试、外部操作、发送许可、发送实例、凭据能力 id 与 version，以及两类材料：准确发送实例退出材料的受控引用与 SHA-256，旧发送能力撤销材料的受控引用、SHA-256 与核查时间。 |
| 两类证据缺一不可 | 租约到期、请求超时、单次 PID 查询无结果、进程重启与 coordinator 重启都不能单独满足关闭条件。 |
| 校验 | 逐项比较证据与持久 tests 行的发送许可、sender 实例及凭据能力身份和版本；拒绝缺项、摘要非法、错绑、重用 `senderInstanceId`、权限不足或状态不是 `recovery.open` 的 unknown。 |
| 事务结果 | 保持 `state=unknown` 与额度已消费，设置 `recovery=closed_without_result`，原子清除该 actor 与该 test 的 outstanding，并追加含全部绑定、证据摘要、操作员主体与 `closedAt` 的白名单审计。 |
| 重放 | 以 `(deploymentIdentity, closeKey)` 保存原操作；同键同输入返回原回执，同键异输入冲突。COMMIT 未知时用原键恢复。 |
| 迟到结果 | 只能作为同一 `externalOperationId` 的追加观察保存，不改变 unknown、关闭事实、额度或审计，也不创建另一次发送。 |
| 不做什么 | 不退款、不释放旧许可、不重发、不伪造成 `failed` 或 `passed`；本地撤销不表示供应商远端凭据已撤销。 |

关闭命令只解除本地新测试阻塞。系统同时记录该能力引用的本地 `revokedAt` 与证据摘要，并禁止该 sender 与 permit 再取得凭据。它不冻结任何提供商的凭据查询、撤销或结果查询协议。

## 数据表

以下九张表是 B05 本轮的候选物理设计，全部未实现、未采用。物理名在本轮冻结，不再写「实施时任选 schema」；旧稿的逻辑名 `models` 与 `modelbudget` 按[物理合表映射与统计](#b05-物理合表映射与统计)落地，`repomesh_modelbudget` 是新建 schema，`repomesh_models` 与 `repomesh_sources` 是既有 schema。

本节只描述本轮新增的候选表。B04 已实现的 `repomesh_models` 快照族与 `repomesh_secrets`、B03 的 `repomesh_projects`、B02 的 `repomesh_access.accounts`，以及 schema 1 的 `repomesh_sources.imports`、`deployment`、`import_serialization` 都保持字段、约束与行为不变，本节只引用它们的既有唯一键。需要物理外键时直接指向已存在的唯一键，不假设旧表有未声明的复合唯一键。账号共同锁沿收口设计锁既有 account 行，不给 account 增加计数、指针或操作列。

全部新表都由触发器保护不可变事实，只开放各专用用例函数；普通 Web 与 Runner 角色没有直接任意 `UPDATE`、`DELETE` 权限。跨表最终一致性用新表上的延迟 constraint trigger 按主键回读终态。需要保存 HTTP 回执时允许带 schema 标签的有限白名单 JSON，校验器拒绝未知字段、非法分支与超限正文；事实仍来自结构列。规范化输入 `bytea` 只做精确重放比较，不能替代结构列与外键。实际迁移在实施时另编号，并沿用现存表的精确约束名。

### repomesh_modelbudget.windows

物理表：`repomesh_modelbudget.windows`

用途与写入者：本地请求次数账本，测试窗口与项目运行窗口共用。测试登记、发送许可、未发释放与项目配置初始化在各自事务里写入；只读查询不创建窗口。

| 字段 | 类型 | 必填 | 约束 | 含义 |
| --- | --- | --- | --- | --- |
| `scope_kind` | text | 是 | `actor_model_test` 或 `project_model_runtime` | 账本范围类型，复合主键第一部分。 |
| `actor_scope_id` | text | 否 | 外键到 `repomesh_access.accounts(id)` | actor 范围。 |
| `project_scope_id` | text | 否 | 外键到 `repomesh_projects.projects(id)` | 项目范围。 |
| `scope_id` | text | 是 | 生成列，取两个外键中非空者 | 由选中外键派生，复合主键第二部分。 |
| `start_utc` | timestamptz | 是 | 必须等于该时刻的 UTC 日零点 | 窗口起点，复合主键第三部分。 |
| `end_utc` | timestamptz | 是 | 恰好等于 `start_utc + interval '24 hours'` | 窗口终点，固定 24 小时，不随数据库会话时区或夏令时变化。 |
| `request_limit` | integer | 是 | 1 到 2147483647；同窗只降不升 | 当日上限，也是 C05 `effectiveLimit` 的来源之一。 |
| `reserved` | bigint | 是 | 默认 0，非负 | 预留计数。 |
| `consumed` | bigint | 是 | 默认 0，非负 | 已消费计数。 |
| `revision` | text | 是 | 不可为空 | 窗口修订，计数或上限变化时推进。 |

关键约束与理由。主键 `(scope_kind,scope_id,start_utc)` 拒绝同一 scope 同一天的第二行。互斥 CHECK 对两个外键显式写 `IS NOT NULL` 与 `IS NULL`：`actor_model_test` 恰好有 actor 外键，`project_model_runtime` 恰好有 project 外键，`scope_id` 只能等于所选外键，调用方不能自报另一个身份。`start_utc` 的 CHECK 用 UTC 规范构造判断它等于自身 UTC 日零点，例如与 `date_trunc('day', start_utc AT TIME ZONE 'UTC') AT TIME ZONE 'UTC'` 相等，不依赖会话 `TimeZone`。`end_utc` 的 CHECK 用 `start_utc + interval '24 hours'` 判断，不能写 `+ 1 day`：`timestamptz + interval '1 day'` 按会话时区解释，跨夏令时边界时可能不是 24 小时。

本表不加 `reserved + consumed <= request_limit` 的 CHECK。同一天下调上限可以低于已消费金额，此时剩余投影是 `max(0, request_limit - reserved - consumed)`，新登记被拒绝，历史计数不被篡改。窗口更新触发器禁止改身份、`start_utc`、`end_utc`，也禁止提高同一窗口的 `request_limit`；计数只由专用预算函数更新。

`policyId` 与 `policyVersion` 不进入主键，政策切换或换版本继续命中同一窗口。生命周期上，项目配置初始化只为本项目建档，测试登记只为 actor 建档；窗口按 UTC 日自然新建，跨日照旧在原窗口结算，历史消费与预留责任存在时不删行。物理列名用 `request_limit`，旧稿的逻辑名 `limit` 是 PostgreSQL 保留关键字，直接当列名会被解析成语法错误，语义不变。

分支 CHECK 逐列写清楚。`kind='test'` 时必须为 NULL 的列是 `project_id`、`expected_project_revision`、`before_configuration_revision`、`before_model_selection`、`before_model_profile_id`、`before_model_profile_version`、`before_model_default_revision`、`before_model_material_state`、`before_execution_selection`、`before_execution_profile_id`、`before_execution_profile_version`、`before_execution_default_revision`、`before_execution_state`、四个 `before_execution_*_policy_*` 列、`before_fixed_canonical`、`before_fixed_digest` 与 `consumed_application_id`；四个条件生成列在此分支分别为 `budget`、`time`、`egress`、`actor_model_test`。`kind='apply'` 时必须为 NULL 的列是 `budget_kind`、`budget_scope`、`budget_policy_id`、`budget_policy_version`、`time_kind`、`time_policy_id`、`time_policy_version`、`egress_kind`、`egress_policy_id`、`egress_policy_version`、`test_binding_revision`、`max_output_tokens`、`timeout_seconds` 与 `consumed_test_id`；四个 `before_execution_*_policy_*` 列按 `policy_bindings` 的 execution 补充写明或全空。消费列按 kind 最多命中一个正确分支，`consumed_at` 与消费键同空或同非空；消费键只有 NULL 转固定绑定，禁止释放后再用。反向一致性由延迟 constraint trigger 在提交时按主键回读核对：apply 分支要求被消费的应用操作反向引用本预览；test 分支要求 `tests.preview_id` 等于本预览 `id`（`tests` 上有 `UNIQUE(preview_id)`），且该测试的固定模型快照、secret 版本与三类政策版本逐项等于本预览记录的对应列，任一项不一致整笔回滚。

固定输入、类型、actor、期限、`before_fixed_digest` 与 before 证据的非正文列不可更新。触发器只允许三件事：写消费列、把 `removed_at` 从 NULL 置为固定时间、在设置 `removed_at` 的同一次更新里把 `before_fixed_canonical` 置空。这是唯一的受限清理白名单；`removed_at IS NULL` 的 apply 行必须保留正文，`removed_at` 置位后正文必须为空，所以清理既不会因 NOT NULL 失败，也不会把原配置正文留在行内。原模型受限不阻止预览：`before_model_material_state='unavailable'` 时对外返回受限分支，内部比较材料仍保留，公开受限不反向删掉内部逐项比较。清理后保留身份、`before_fixed_digest`、必要固定字段与消费墓碑，不硬删后让同一预览 ID 复活。预览是短期比较上下文，不预留额度、不占槽位，通过预览不构成提交许可。

状态矩阵用显式 CHECK 按完整允许组合写，不靠零散单列限制拼出来。发送许可列组要么全空要么全有，合法行必须命中且只命中下列之一。

| --- | --- | --- | --- |
| `queued` | 全空 | `reserved` | `open` |
| `queued` | 全有 | `consumed` | `open` |
| `running` | 全有 | `consumed` | `open` |
| `passed` | 全有 | `consumed` | `not_needed` |
| `failed` | 全有 | `consumed` | `not_needed` |
| `unknown` | 全有 | `consumed` | `open` 或 `closed_without_result` |
| `rejected` | 全空 | `released` | `not_needed` |

未列出的组合必须被 CHECK 拒绝。特别地，`queued` 没有许可却是 `released` 或 `consumed`、`rejected` 带许可或 `consumed` 都不能写入：前者会形成未核占用但没有预留的任务，后者是当前没有采纳的「许可后确定未发」分支。将来采纳该分支时先扩本矩阵，再同步 B05 状态表、HTTP 契约与关闭协议。许可列组一经写齐禁止更新。

`work_state` 与未核责任必须一致：`is_outstanding=true` 时 `work_state` 不能是 `done`；完整关闭组与未发拒绝都要求 `work_state='done'`，`recovery='open'` 的未知责任不能提前标成 `done`。这样未核扫描的根不会变成查不到的死责任。

发送许可列组（`external_operation_id`、`send_permit_id`、`may_have_sent_at`、`sender_instance_id`、`credential_capability_id`、`credential_capability_version`）同空或全有。许可事务在同一事务里写齐它们，把 `budget_status` 从 `reserved` 改为 `consumed`，窗口 `reserved` 减 1、`consumed` 加 1。nonce 不持久化；数据库只保存不可恢复的许可身份，内存里的一次许可必须依明确 COMMIT 回执生成。

领取契约：`claimed` 要求 `claim_owner_instance_id`、`claim_generation`、`claim_lease_until` 齐全，代次只增。没有许可的 `queued` 可被新代次领取；已有许可的记录只进核查工作，不再产生发送权。领取的 owner 可以变化，真实 sender 永远是发许可时的实例。

索引：部分索引 `(actor,test_id) WHERE is_outstanding` 支撑未核扫描；条件索引支撑 `work_state` 的 `ready` 与 `reconciling` 扫描（例如按 `next_check_at` 排序）。不另建待办表。未核计数在 account 锁内按 `is_outstanding` 谓词查询，不维护第二个计数权威；`maxUnresolved` 取自明确政策参数，当前候选是每 actor 1 笔，将来改数值只修订 Preview 与 Submit 的公开形状，不需要改本表。

关闭事实：`UNIQUE (close_deployment_identity,close_key) WHERE close_key IS NOT NULL`。本地撤销四列与关闭列组同空或全有，摘要按 `sha256:` 校验；`closed_at` 与状态、恢复、预算和撤销完整性联动，全部关闭列从 NULL 一次写齐后不可改，因此一个测试最多一条关闭事实。关闭行不复制可漂移的发送绑定副本，关闭输入由 `close_canonical_input` 逐项与同一行的固定发送列比较；accepted、permit、closure 三组事实自带白名单审计主体、时间与绑定，不另建审计表。

预算账本规则：存在发送许可的请求不退款。确定未发拒绝发生在许可之前，走 `reserved` 到 `released`；若将来采纳「许可后确定未发」的新分支，预算保持 `consumed`，不能把已消费倒流为释放。展示正文清理只置 `removed_at`，测试身份、固定版本、许可、预算、未核责任与关闭材料保留。测试的 `canonical_input` 只含 `previewId` 与收费确认，不含敏感正文，必须保留以支持同键精确重放，清理不修改它。`is_outstanding` 不因 `removed_at` 或 UTC 跨日改变，30 天正文清理不能删除未核责任。

启动、续期与退役各自独立成短事务，不锁 account。租约过期不是撤销证明，不能自动关闭 unknown 或重新授予许可。外键使用 `ON DELETE RESTRICT`：被 `tests` 或 `test_observations` 引用的实例永久保留最小墓碑，未被引用的失效登记也保留 ID 与注册事实，防止同 ID 复用。有限租约登记表示有限的活跃集合，不是按 TTL 删除全部历史身份。

## 事务与恢复

以下路径冻结本轮锁序。所有同类对象按稳定 ID 排序；所有 owner 业务写必须先锁 owner account，拿到后段锁后不得回取 account。绑定与浏览器 session 只在当前浏览器授权入口取，后台内部收证与关闭不伪造用户 session。网络、DNS、外部核查、证据文件读取与验真都在事务外完成，事务内重核身份与本地约束，不持业务锁跨网络。

### 锁序与事务归属

1. 新测试预览：binding → session → account → catalog/profile → Provider → test policy_binding；读取对应不可变 policies、窗口、该 actor 未核责任与 handler 有效登记（不额外锁 handler）→ secret availability → INSERT preview。handler 观察失败整笔不创建 preview；只读观察不是授权。
2. 测试登记：binding → session → account → tests 操作槽 → catalog/profile → Provider → preview → test policy_binding/policies → 原 UTC 窗口 → 在 account 锁下读 tests 的未核责任 → secret availability。操作槽由 account 串行做「无行」检查，最终由主键兜底，不持假行到响应之外。命中原 test 先精确重放，不再取新资格的后段锁。成功时同事务创建 tests 行与预留、窗口 `reserved` 加 1、preview 消费与接受审计；tests 就是唯一工作。
3. Runner 领取：先非锁扫描候选 actor 与 test 定位，再逐个短事务走 account → tests，用 CAS 推进 claim generation 与 lease；只有没有许可的 `queued` 能获得发送型 claim。不存在先持 tests 再取 account 的 `FOR UPDATE SKIP LOCKED` 反序。claim 只是领取，不是发权；handler 登记不与该事务互等。
4. 发送许可：account → tests → catalog/profile → Provider → test policy_binding/policies → 原 BudgetWindow → secret availability。核当前 actor 启用、旧 claim 代次、固定 secret 与出站策略及本地能力；不要求当前 Provider head 仍等于旧 head。一次写齐 permit、外部操作、sender 与能力，窗口 `reserved` 减 1、`consumed` 加 1，tests 置 `consumed`。确定 COMMIT 后才把内存里的一次许可交给 transport。政策变化需要拒绝时只能在许可前释放，固定历史不重绑新政策。
5. 未发拒绝与释放：account → tests → 原 BudgetWindow，核没有 permit 且代次仍然当前；窗口 `reserved` 减 1，tests 同事务写 `released`、`rejected`、`not_needed` 与 `done`。已有 permit 禁止退款。
6. 只追加观察：account → tests → INSERT observation，不读 handler 的 `FOR UPDATE`。失权 actor 仍可由内部收证函数维护责任。采纳在相同 account → tests 前缀内检查 claim generation 与 result_revision 的 CAS，不需要改窗口，预算已经 `consumed`。有冲突保持 unknown；closed 与 removed 限制分别生效。
7. unknown 关闭：先验实际 DB `session_user`、部署身份与维护角色，按 `(close_deployment,close_key)` 无锁查原回执优先。新操作走 account → tests → 必要的本地能力撤销核验，不锁也不更新 handler 租约；核两类证据全部绑定后，原子写撤销、关闭、recovery 与审计（`is_outstanding` 自动变 false）。预算不变，无需锁窗口。全局 close 唯一索引冲突且目标 actor 不同时整笔回滚，再在新事务里查原键比较，禁止持本 actor 锁追锁另一个 actor。不同 key 命中已关闭 test 返回既有关闭回执，不写第二事实。COMMIT 未知时用原 key 恢复。
8. 应用预览与提交：binding → session → account → project → application 操作槽（仅提交）→ catalog/profile → Provider → preview（提交）→ secret availability；读取 execution 补充与不可变 policies 不修改。先重放，再完整比较 before，projects 原用例只替换模型，no-op 仍回执。新配置与项目窗口初始化按其既有 project 前缀，窗口在 secret 前按统一顺序；本次应用保留 execution，不重设它的预算窗口。
9. 项目额度初始化：原项目配置路径 binding → session → account → project → operation → catalog/profile → 政策引用 → 本项目 UTC 窗口 → secret availability。只读 C05 从同一项目配置快照读新补充与 `policy_versions`，额度查询在 savepoint 失败回滚后投影 unknown；连接与主体失败仍返回 503。GET 不创建窗口。
10. 来源导入 schema1 与 schema2 共同前缀：旧 import_serialization 单例 → 双表原键查询 → 新输入涉及的 owner accounts 按 ID → catalog → profile 与版本按 ID → policy_versions 按 `(kind,id,version)` → policy_bindings 按主键 → 按 schema 返回原回执（延迟外键允许回执同事务后插入）。schema1 原数据路径照旧；两个 schema 绝不分别用两个互斥锁。导入不取 binding、session、project 或 Provider；交互路径也不取 import 单例。没有政策查询晚回取 account。
11. 清理：测试与预览走 account → 目标行；应用走 account → project → application 行；清理与采纳使用相同前缀，`removed` 只清正文。handler 续期与退役用独立实例锁，永不在持该锁时启动业务事务。

### 恢复与失败验收

以下预期结果只登记后续要执行的检查，本轮没有运行数据库或并发实验。

| 场景 | 预期结果 |
| --- | --- |
| 同 test 键同输入 | 即使预览过期、handler 退役或政策变化，也先返回原操作；异 preview 等异输入返回 409；不会第二次预留。 |
| 同 actor 多键并发 | account 串行 COUNT 与 INSERT，不依赖页面禁按钮；候选上限 1 只接受一笔；跨日与 removed 仍阻断 open unknown。 |
| 同 preview 不同键 | 唯一消费与反向外键最终检查，最多一笔接受；应用确定拒绝可以持久，但不得制造第二消费。 |
| 预览过期或政策变化 | 新提交 409 且不预留；原接受操作先重放。 |
| 许可事务失败 | 回滚预算与 permit，尚无发送；之后可以再领取。 |
| 许可 COMMIT 回执丢失 | 无论查到 permit 与否都不能据此发送；查到保守进入 unknown，查不到按事务恢复，不自动换键。 |
| 已确认 permit 后发送前崩溃 | 最多零次实际请求，预算 consumed，unknown；数据库记录不产生可恢复的发送权。 |
| 发出请求后丢响应 | 最多一次本地 transport 调用；原 `externalOperationId` 稳定，unknown 不退款，不自动新请求。 |
| handler 过期 | 阻止新预览与提交（没有其他合格 handler 时），不撤销旧 sender、不清 unknown、不再授 permit。 |
| 运维关闭缺证据或错绑 | 无关闭事实，预算保持 consumed，outstanding 保留；全部核对成功才在同一 tests 行写完整关闭组。 |
| 同 closeKey 并发不同 actor 与 test | 唯一索引冲突后回滚，再按原键比较；异输入冲突，不跨 actor 倒序加锁。 |
| 不同 closeKey 关闭同 test | 最多一个关闭事实。 |
| 关闭 COMMIT 未知 | 用原 closeKey 与原 canonical 恢复。 |
| 关闭后迟到结果 | 只追加同一外部操作的观察，不改变 unknown、关闭事实与额度，不重建已 removed 的正文。 |
| 同窗口换政策或下调上限 | 命中原主键，历史消费不清零，不违反伪造的「余额必须非负」CHECK；新登记可用额度为 0。 |
| UTC 换日 | 原窗口消费保留，不重置计数；跨日不清 actor 未核责任。 |
| schema1 同键原输入 | 原表按原字节返回回执；schema2 同键原输入在新表恢复原字节回执；跨 schema 同键无论顺序都冲突。 |
| schema2 同 import 并发 | 共同入口先取旧 import_serialization 单例，防止同时提交双表；结果查询不改旧 wire。 |
| v1 execution 补政策 | 拒绝；v2 新 version 同事务生成原执行字段与完整政策补充，失败不留半个版本。 |
| projects 读不到补充 | 返回 unresolved，不填默认或零。 |
| 同 policy 版本复用 | 同一 `(policy_kind,id,version)` 同内容可复用，异内容整笔拒绝；项目与测试引用同一版本权威，没有同步两份政策的故障窗口。 |
| 应用保留 execution | 应用后固定 JSON 中 execution 选择、版本与参数完全等于原项目；默认变化不影响结果。 |
| 预览过期时重放既有成功 | 原回执优先，不再执行预览校验。 |
| 原记录清理 | 有权者 410，旧键不复用。 |

## 设计理由

测试与应用的共同风险是“用户以为没发生，系统已经发生”。测试登记落在本地数据库，发送许可只存在于确认过提交的进程内存中，因此重启与查询都不会凭空多出一次模型请求。运维关闭要求两类带外证据，是因为租约、超时和进程重启都不能证明远端已经停止。

只换模型的应用保护的是 execution 的既有固定版本。用户调整模型时，不应该顺带改变并发、预算、时限或模板引用。固定摘要与额度观察分开展示，避免把“当初配置了什么”和“现在还能用多少”混成一个数字。

把旧 16 张压到 9 张的依据是写入者、唯一性、更新频率和删除规则相容，不是表越少越好。测试身份、预留、发送许可、未核责任与关闭事实都围绕同一条 `(actor,testId)` 行，写入者与生命周期一致，合并后每条语句仍只改一行，同时让「领取唯一待办、一次许可、一次关闭」由同一行的 CHECK 表达。政策三种版本与 project 侧两条重复权威同为不可变版本，判据一致，因此合成 `policy_versions` 一张版本表；重复权威合并后，项目与测试引用同一行，没有两份政策需要同步。测试观察与处理器实例的写入者、追加性与保留期和测试根本不同，保持独立。应用操作和测试不同：一个预览可能被不同 application 键尝试并产生确定拒绝，合并会制造错误的 1:1。

九张不是八张，是因为既有 `repomesh_sources.imports` 的 `CHECK (schema_version = 1)` 与两条既有版本表的不可变行不能为凑数而破坏。schema 2 原导入需要新物理表，execution 政策补充需要不可变的新承载。给旧表塞新职责会同时破坏已实现约束和历史行。合表也没有减少逻辑责任：测试、预留、许可、未核责任、关闭、观察、预览消费和应用回执都能在本文件按名字找到承载列与约束。

## 验证清单

以下是可观察行为的预期结果，不是已运行测试。完整映射见 [设计验收映射](../development/2026-09-13-b04-b06-design-01/ACCEPTANCE.md) 的 B05 部分与 [收口记录](../development/2026-09-14-b05-b06-design-closeout-01/README.md)，T10 到 T14 只登记待执行。

| 检查 | 预期观察 |
| --- | --- |
| 预览占用 | 额度有余量但存在未核清测试时，预览返回 `canSubmit=false`、`TEST_ALREADY_OUTSTANDING` 与本人可读定位；额度状态独立返回。 |
| 预览竞争 | 预览之后提交时条件变化，提交仍返回 409，不登记也不发送。 |
| handler 观察 | 没有登记时预览阻止提交；读取失败时 503 `TEST_HANDLER_UNCONFIRMED` 且无新记录；原键重放优先于这些检查。 |
| 许可原子性 | 许可事务回执丢失后不会出现第二次发送；重启只处理无许可记录。 |
| 未知关闭 | 缺任一材料保持 open；两类齐全时 state 仍 unknown、预算 consumed、outstanding 清除、审计写入。 |
| 额度账本 | 同 scope 同 UTC 日只能有一行窗口；降低上限只阻止新增；新日不清未核责任。 |
| schema 2 导入 | schema 1 回执不被升级；schema 2 只接受一个 `executionProfiles`；重复集合、同键跨 schema 与伪造 scope 均拒绝。 |
| 应用保留 execution | 应用后固定 JSON 中 execution 选择、版本与参数完全等于原项目；默认变化不影响结果。 |
| no-op 应用 | 引用与版本完全相同时保留原修订，仍写回执并消费预览。 |
| inherit 转 reference | 即使有效模型相同，选择依据变化产生一个新配置修订。 |
| C05 分支 | 固定摘要与 `effective` 同版本；无可信窗口给 unknown 而不是 0；GET 不写表。 |
| C06 分支 | 未配置、可读、受限三分支精确；受限不泄露 ID；只读可读分支取指定快照。 |
| 合表映射 | 9 个物理声明与 16 条旧提案一一对应，每张表只声明一次；每个表章节标题与正文的物理表名一致。 |
| 单行多责任 | tests 一行同时给出预留状态、领取状态与关闭组，互相矛盾的组合被 CHECK 拒绝。 |
| 未核计数 | account 锁内按 `is_outstanding` 谓词计数；并发登记只接受一笔；没有第二张计数表。 |
| 政策复用 | 项目与测试引用同一 `(policy_kind,id,version)` 行；同版本异内容整笔拒绝。 |
| v1 补全 | 已存在执行版本没有政策补充时，v1 补全请求被拒绝，必须新 version。 |
