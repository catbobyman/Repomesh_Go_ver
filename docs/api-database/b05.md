# B05 运行政策与模型应用

B05 在 B04 已保存的不可变供应商、模型和秘密版本之上补两项管理能力：导入并固定运行预算、时限和出站政策；只替换项目模型而完整保留原 execution 配置。项目读取同时返回固定政策摘要。B05 不发送模型请求，不实现独立模型连通性测试，也不负责 AgentTeams 运行接入。

2026-09-15 用户决定收缩 B05：原单模型测试、测试预览、测试 handler、SendPermit、测试额度预留、unknown 关闭和测试观察整体延期，不再作为 B06 的前置。需要临时核对供应商连通性时，可以在受控运维环境使用 AgentTeams 的 `agt llm-preflight`；它不是 RepoMesh 产品能力、业务验收或运行放行证据。正式 Manager 模型调用的可能外发、核查和用量事实仍由 B09 自己持有，不能复用运维 preflight 结果。

本批产品未实现，接口和四张物理表仍是待采用设计。已实现事实来自 B03 的项目和固定配置、B04 的不可变模型快照与业务密文。跨批公共规则见 [公共规则](./foundations.md)。

## 物理表与历史提案去向

当前 B05 声明四张目标表：一张模型应用操作表和三张政策来源表。原 16 条候选表映射中，九条测试专用记录延期；预算窗口移交 B10；其余映射收敛到本章四张表。

| 历史提案 | 当前去向 | 理由 |
| --- | --- | --- |
| `models.previews` | 延期，不建表 | 应用预览改为无状态比较；测试预览随测试子系统延期。 |
| `models.tests`、`modelbudget.test_reservations`、`models.test_dispatch`、`models.actor_outstanding_tests`、`models.unknown_test_closures` | 延期，不建表 | 都只服务独立模型测试。 |
| `models.test_observations`、`models.test_handler_leases` | 延期，不建表 | 没有测试外发就没有对应观察和 handler 生命周期。 |
| `modelbudget.windows` | B10 `repomesh_modelbudget.windows` | 第一个真实消费者是 B09/B10 运行路径，账本由 B10 落地并供 B09/B11 引用。 |
| `models.application_operations` | `repomesh_models.application_operations` | 保留项目模型应用的幂等操作和稳定回执。 |
| `budget_policies`、`time_limit_policies`、`egress_policies`、`request_policy_versions`、`time_policy_versions` | `repomesh_sources.policy_versions` | 使用一个不可变政策版本权威，避免项目侧复制。 |
| `test_bindings` | 不保留 test 分支 | 测试子系统延期；`policy_bindings` 只保留 execution 分支。 |
| schema 2 导入原操作 | `repomesh_sources.policy_imports` | 旧 `imports` 仍只接收 schema 1，不能原地改写。 |

## 公共约定

| 约定 | 行为 |
| --- | --- |
| 认证 | Cookie 会话；写请求要求单值 `Origin` 与 `X-CSRF-Token`；请求不接受客户端自报 owner。 |
| 固定快照 | 预览和提交都只针对 B04 已保存的不可变模型快照；不把 Provider 当前 head 当历史引用。 |
| 无状态预览 | 预览只返回当前比较基线，不落库、不消费、不授权；提交携带完整预期修订并在项目锁下重查。 |
| 幂等操作 | `Idempotency-Key` 是 `applicationId`；同键同规范输入返回原结果，同键异输入返回 409。 |
| 专用变更 | 模型应用只替换模型引用，execution 选择、参数、预算与时限引用逐项保留。 |
| 运行无关 | 应用模型不启动 Manager、Worker 或 AgentTeams，不证明模型可调用。 |
| 政策与额度分离 | B05 固定不可变政策；B10 持有实际运行额度窗口。政策存在不等于仍有额度。 |

## HTTP API

以下路径和字段仍是待采用协议，均未实现。

### POST /api/projects/{projectId}/model-application-previews

调用者必须是项目 owner 且具备配置资格。请求包含 `providerId`、`providerRevision` 和 `modelRowId`，三者必须组成 B04 中可读的固定模型快照。

成功返回：

```json
{
  "projectId": "project-id",
  "expectedProjectRevision": "project-revision",
  "expectedConfigurationRevision": "configuration-revision",
  "before": {
    "model": {"status": "readable"},
    "executionVersionId": "execution-version"
  },
  "candidate": {
    "providerId": "provider-id",
    "providerRevision": "provider-revision",
    "modelRowId": "model-row-id"
  },
  "canApply": true,
  "reasonCodes": []
}
```

`before.model` 使用三个封闭分支：

| 分支 | 字段 |
| --- | --- |
| 未配置 | `{status:"unconfigured"}`。 |
| 可读 | `{status:"readable",reference,modelProfileId,modelProfileVersion,providerId,providerRevision,modelRowId,links:{snapshot}}`。 |
| 受限 | `{status:"restricted",reasonCodes:["ORIGINAL_MODEL_UNAVAILABLE"]}`，不披露名称、地址、profile、provider 或模型行 ID。 |

原模型受限不阻止有权修复配置；原 execution 固定版本无法确认时返回 `canApply=false` 和 `EXECUTION_SNAPSHOT_UNCONFIRMED`。预览不返回 `previewId` 或 `expiresAt`，也不保存数据库行。它只是提交表单所需的当前比较结果。

错误包括：项目或候选不可见时 404 `RESOURCE_NOT_FOUND`；当前资格未知时 503 `AUTHORIZATION_UNCONFIRMED`；数据库或秘密可用性无法确认时 503 `RESULT_UNCONFIRMED`。

### POST /api/projects/{projectId}/model-applications

写请求要求 `Origin`、CSRF 和 UUID 形状的 `Idempotency-Key`。请求包含：

| 字段 | 类型 | 必填 | 含义 |
| --- | --- | --- | --- |
| `expectedProjectRevision` | string | 是 | 无状态预览返回的项目修订。 |
| `expectedConfigurationRevision` | string | 是 | 无状态预览返回的配置修订。 |
| `providerId` | string | 是 | 候选供应商。 |
| `providerRevision` | string | 是 | 候选不可变修订。 |
| `modelRowId` | string | 是 | 候选模型行。 |

首次成功返回 `200 OK`：

```json
{
  "applicationId": "application-id",
  "outcome": "committed",
  "projectId": "project-id",
  "projectRevision": "project-revision",
  "configurationRevision": "configuration-revision",
  "providerRevision": "provider-revision",
  "modelProfileId": "model-profile-id",
  "retainedExecutionVersionId": "execution-version",
  "committedAt": "2026-09-15T00:00:00Z",
  "links": {
    "project": "/api/projects/project-id",
    "operation": "/api/projects/project-id/model-applications/application-id"
  }
}
```

同键同输入返回原回执。没有实际变化时保留原配置和项目修订，仍保存 `committed` 的 no-op 回执。确定拒绝不保存独立失败行；客户端按当前状态重新预览后以新键提交。可能的错误：

| 状态 | code | 触发条件 |
| --- | --- | --- |
| 404 | `RESOURCE_NOT_FOUND` | 项目或候选不可见。 |
| 409 | `PROJECT_REVISION_CONFLICT` | 项目修订变化。 |
| 409 | `CONFIGURATION_REVISION_CONFLICT` | 配置修订变化。 |
| 409 | `EXECUTION_SNAPSHOT_UNCONFIRMED` | 原 execution 固定版本无法确认。 |
| 409 | `IDEMPOTENCY_CONFLICT` | 同键不同规范输入。 |
| 410 | `MODEL_APPLICATION_RESULT_REMOVED` | 原回执正文已清理。 |
| 503 | `RESULT_UNCONFIRMED` | 提交结果未知，按原键查询。 |

提交先查原操作，再按 `binding → session → account → project → application operation → catalog/profile → provider → secret availability` 取锁和重查。项目修订、配置修订、候选固定版本或原 execution 任一变化都整笔失败。网络调用不在事务中；本路径本身没有网络调用。

### GET /api/projects/{projectId}/model-applications/{applicationId}

用于提交响应丢失后的原操作查询。按当前项目外壳资格核权，不重新验证候选或当前配置。成功返回原 `committed` 回执；当前项目快照另读项目接口。未找到返回 404 `MODEL_APPLICATION_NOT_FOUND`，正文已清理返回 410 `MODEL_APPLICATION_RESULT_REMOVED`，数据库无法确认返回 503 `RESULT_UNCONFIRMED`。

### GET /api/projects/{projectId} 的 C05 只读字段

项目读取的 `configuration` 增加 `fixedSummary` 与 `quotaObservation`：

| 字段 | 形状 |
| --- | --- |
| `fixedSummary.configurationRevision` | string。 |
| `fixedSummary.executionVersionId` | string 或 null。 |
| `fixedSummary.budget` | `{status:"available",policyId,policyVersion,scope:"project_model_runtime",unit:"request",period:"utc_day",limit}` 或 `{status:"unresolved",reasonCodes}`。 |
| `fixedSummary.timeLimits` | `{status:"available",policyId,policyVersion,modelRequestTimeoutSeconds,workerAttemptLimitSeconds}` 或 `{status:"unresolved",reasonCodes}`。 |
| `quotaObservation` | B10 未实现前固定 `{status:"unavailable",reasonCodes:["RUNTIME_LEDGER_NOT_AVAILABLE"]}`；B10 落地后由它定义 `known`／`unknown` 投影。 |

固定摘要与项目配置来自同一版本，不跟随政策 head。GET 不创建窗口、不消费额度、不把缺失填成 0。B06 只读取固定政策是否完整，不以 `quotaObservation` 作为创建 Issue 的门槛；首次真实运行在 B09/B10 校验实际额度。

## 数据表

本章四张表均为候选、未实现。

### repomesh_models.application_operations

物理表：`repomesh_models.application_operations`

用途与写入者：保存一次项目模型应用的幂等身份和稳定成功回执。只由 Web 专用应用事务写入。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| `project_id`、`actor`、`application_id` | text | 是 | 复合主键；项目和账号外键。 |
| `canonical_schema` | integer | 是 | 固定 1。 |
| `canonical_input` | bytea | 清理前是 | 包含两个预期修订及候选三元组的规范输入。 |
| `canonical_input_digest` | text | 是 | 清理后仍保留。 |
| `project_revision`、`configuration_revision` | text | 是 | 提交后结果修订，归属于本项目。 |
| `provider_revision`、`model_profile_id` | text | 是 | 实际采用的固定模型引用。 |
| `retained_execution_version_id` | text | 是 | 必须等于应用前 execution 固定版本。 |
| `committed_at`、`accepted_principal` | 时间、text | 是 | 提交时间与可信主体。 |
| `receipt_schema`、`receipt` | integer、jsonb | 清理前是 | 原 wire 回执。 |
| `removed_at` | timestamptz | 否 | 只清正文的时间。 |

同键同输入返回本行，同键异输入冲突。no-op 也写本行，但不制造新配置修订。受限清理只清 `canonical_input` 和 `receipt`，保留主键、摘要、结果引用与墓碑，旧键不能复用。本表不引用预览表。

### repomesh_sources.policy_versions

物理表：`repomesh_sources.policy_versions`

用途与写入者：预算、时限、出站三种不可变政策的唯一版本权威，只由受控 schema 2 导入写入。

| 字段组 | 约束与含义 |
| --- | --- |
| 身份 | 主键 `(policy_kind,id,version)`；`policy_kind` 为 `budget`、`time`、`egress`。 |
| 来源 | `deployment_id`、`created_by_import_id` 复合外键到 `policy_imports`；带创建时间和规范摘要。 |
| budget | `scope_kind='project_model_runtime'`、`unit='request'`、`period='utc_day'`、正整数 `request_limit`、`enabled`。不再有测试专用 `actor_model_test` 或 `max_unresolved`。 |
| time | `model_request_timeout_seconds` 与 `worker_attempt_limit_seconds` 在受控范围内。 |
| egress | 非空 `approved_base_urls`、请求体上限、端口／私网／重定向限制。 |

三个子型用完整互斥 CHECK。政策行不可更新和删除；变更创建新版本。运行路径引用确切版本，不查询“最新”替换在途依据。

### repomesh_sources.policy_bindings

物理表：`repomesh_sources.policy_bindings`

用途与写入者：为每个不可变 execution 版本补充确切政策引用。模型测试延期后，本表只保留 `execution` 分支。

主键为 `(execution_profile_id,execution_version)`，复合外键到 `repomesh_sources.execution_versions(profile_id,version)`；`owner` 必须与来源执行版本一致。预算引用固定到 `policy_versions` 的 `project_model_runtime` 行，时限和出站政策引用固定到对应 kind。补充分支与新 execution 版本在同一 schema 2 导入事务创建；旧 v1 版本不能原地补全，必须创建新版本。

### repomesh_sources.policy_imports

物理表：`repomesh_sources.policy_imports`

用途与写入者：保存 schema 2 部署导入的原操作，只由受控导入入口写入，全行不可变。

主键 `(deployment_id,import_id)`；`schema_version=2`、`canonical_schema=2`。保存规范输入、固定回执、提交时间和实际 `session_user`。回执保持 schema 1 原字段并增加 `budgetPolicies`、`timeLimitPolicies`、`egressPolicies`；schema 2 顶层只有一个 `executionProfiles` 集合，每个版本必须引用完整预算、时限和出站政策。没有 `testBindings`。

既有 `repomesh_sources.imports` 继续只接收 schema 1。两个表共享 `(deployment_id,import_id)` 逻辑键和 `import_serialization` 单例：任一表命中先比较或重放，跨 schema 同键冲突；结果查询同时查两表且不要求调用者猜 schema。

## 事务与恢复

| 场景 | 预期结果 |
| --- | --- |
| schema 2 同键并发 | 共同导入锁保证只有一份结果；同输入重放，异输入冲突。 |
| 旧 execution 补政策 | 拒绝修改既有不可变版本；以新 execution version 完整导入。 |
| 应用与项目更新并发 | 共用 account、project 锁和预期修订；只有一方基于同一修订提交。 |
| 应用只换模型 | execution 选择、版本和参数逐项等于应用前事实。 |
| no-op 应用 | 原配置修订不变，但原操作回执可恢复。 |
| 提交回执丢失 | 不换键；查询原 `applicationId`，最终只存在一条操作。 |
| 原回执清理 | 返回 410，旧键不复用；当前项目配置不受影响。 |
| B10 尚未实现 | 固定政策可读，`quotaObservation` 明确 unavailable；不伪造余额。 |
