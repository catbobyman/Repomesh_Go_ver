# B06 Issue 原子创建

B06 让用户在某个项目里填写标题、目标、约束、验收条件与本次仓库，选择新建会话或关联已有会话，然后一次提交创建完整的 Issue。提交只等待本地事务，不等待模型、实例或房间。事务成功时，必要会话、Issue、主 ChangeSet、页面来源、内容范围、幂等回执、持久待办与创建事件一起生效；任一写入失败全部回滚。

本批产品未实现。Issue 创建契约 v1 与 P1 原子范围是已采用设计，不是已实现功能；P9 的 Issue 固定配置引用与 S06 的 App 能力门槛仍是既有候选，尚未采用。创建条件、已有会话候选、提交与原结果查询四条路由属于 B06，Issue 详情、rooms 与 SSE 属于 B07，不在本章。字段唯一来源是 [Issue 创建契约](../current/issue-page-create-api-contract.md)，内部事务唯一来源是 [首批持久化设计](../current/backend-first-batch-persistence.md) 第 7 节与 [配置绑定候选](../current/issue-configuration-binding-design.md) 第 8 节。跨批公共规则见 [公共规则](./foundations.md)。

本轮按用户授权对 B05 至 B11 的物理存储做合表。B06 与 B07 的 14 张原提案表压到 7 张物理表，其中 6 张属于 B06，`repomesh_issues.issue_room_links` 属于 B07，B08 不新增物理表。合表只改字段的物理位置；已采用的 API、业务身份、原回执、状态机和清理语义不变。完整映射见“本轮物理合表”。

## 本轮物理合表

B06 与 B07 合并前共 14 张提案表，合并后保留 7 张：`repomesh_issues.conversations`、`issues`、`changesets`、`repository_scopes`、`issue_events`、`project_issue_counters` 和 `issue_room_links`。前六张归 B06，最后一张归 B07。B08 声明 0 张新表。

合表的依据来自已采用设计本身。[首批持久化设计](../current/backend-first-batch-persistence.md) 第 1 节允许把逻辑记录合并到物理表，前提是保留外键、唯一性、比较和保留保障；同节规定 CreationSource、创建操作与 Issue 一一对应；第 7.1 节规定本批每个 Issue 只有一个初始 `issue_continue`。这些一对一事实可以直接落在 Issue 行。操作与 Issue 的身份仍分别生成，查询入口仍按原操作作用域访问，初始待办保留稳定 `work_id` 和自己的状态，不把 Issue 状态当待办状态。

说人话的理由有三条。

1. 同一个 Issue 的创建操作、页面来源、卡片、初始待办和事件流计数都是一对一记录，写入事务、清理路径和保留规则相同。合成字段组后，谁创建了它、卡片指向哪个会话、待办归谁、事件流计数到哪一号，都能从 Issue 行读出，不需要额外连接。
2. 三张范围表说的是同一件事：某个 Issue 或某个会话在哪些仓库里有内容。它们的差别只有 owner 类型和“是不是工作范围”。用 owner 判别列加 `is_work` 标志表达后，一个 Issue 的工作范围与内容范围都能用普通唯一约束约束住，外键目标也更直接。
3. ChangeSet 必须保持独立表。[ChangeSet 设计](../current/changeset-design.md) 已采用 CS1 至 CS14，主 ChangeSet 要承载候选、组合、PR 与历史，Issue 与主 ChangeSet 各有独立身份。当前一对一创建不足以证明两者的完整生命周期可以合并，所以没有为了表数把它塞进 Issue。

`project_issue_counters` 和 `issue_events` 也无法并入 Issue 行。前者每个项目一行，分配项目内编号；后者每个事件一行，必须逐条保留与重放。把事件塞进 JSON 会失去逐事件主键和清理边界。

合并前的 14 张表各有一次去向，映射如下。

| 原物理表 | 新承载 | 不能丢失的事实 |
| --- | --- | --- |
| `conversations` | `conversations` | 独立会话身份、标题派生来源、内容范围修订。 |
| `issues` | `issues` | Issue 稳定身份、number、主会话、主 ChangeSet、正文与清理。 |
| `creation_operations` | `issues` 的创建字段组 | 独立操作 ID、原复合作用域唯一键、原比较器与输入、稳定回执、removed 占位。 |
| `changesets` | `changesets` | 主 ChangeSet 独立 ID 与同 Issue 归属。 |
| `issue_repository_scope` | `repository_scopes` 的 Issue 行且 `is_work = true` | 非空、明确的工作仓库集合、同项目仓库外键。 |
| `issue_content_scope` | `repository_scopes` 的全部 Issue 行 | 内容集合只增不减，包含工作集合。 |
| `conversation_content_scope` | `repository_scopes` 的 Conversation 行 | 整段内容核权与范围版本。 |
| `page_sources` | `issues` 的 page source 字段组 | `page_source_id`、`issue_page` 来源、操作、会话与 Issue 一致，没有假 message。 |
| `conversation_cards` | `issues` 的 card 字段组 | `conversation_card_id`、同一来源与主会话；卡片从 Issue 行投影，不另存正文副本。 |
| `continuation_work` | `issues` 的 continuation 字段组 | `work_id`、cause 操作、`issue_continue`、blocked 到 cancelled 的清理责任。 |
| `issue_event_streams` | `issues` 的 event 字段组 | generation、`last_sequence`、清理边界、同流串行。 |
| `issue_events` | `issue_events` | 逐事件主键、与业务事实同事务提交、可重放。 |
| `project_issue_counters` | `project_issue_counters` | 项目锁下单调分配，禁止 `MAX+1`。 |
| `issue_room_links` | `issue_room_links` | main 与 leader 互斥、最新观察，以及 B09 与 B10 需要的完整复合外键。 |

合并没有把任何字段移进 B01 至 B04 的 36 张已有表（含 1 张系统表），没有用视图冒充剩余物理表，也没有引入通用的 entity、operation、job 或 event 表。B06 声明的六张物理表都在候选 schema `repomesh_issues`，全部未实现。

## 公共约定

| 约定 | 行为 |
| --- | --- |
| 认证 | Cookie 会话来自服务端可信上下文；写请求要求单值 `Origin` 与单值 `X-CSRF-Token`；请求不接受客户端 `userId`、角色或 owner。 |
| 请求体 | UTF-8 JSON 上限 256 KiB；重复属性、格式错误与非法 Unicode 返回 400 `INVALID_JSON`；合法 JSON 的未知字段返回 422 `VALIDATION_FAILED`。 |
| 幂等键 | `Idempotency-Key` 必填 UUID，就是本次 `creationId`；作用域为项目、可信操作者、页面创建入口与 `creationId`。 |
| 错误体 | `{"error":{"code","message","fieldErrors","requestId"}}`，由 [projects.go](../../internal/web/projects.go) 第 206 行的统一封装生成；`requestId` 不等于业务操作身份。 |
| 操作记录 | 创建操作只保存 `committed` 或清理占位 `removed`，不保存 `failed` 或 `running` 状态；可确认的验证失败不留下持久失败记录。 |
| 恢复 | 结果未知时保留原键与原输入，先查询原操作；404 不证明旧请求将来不会提交。 |
| 运行无关 | 创建成功只说明本地业务提交完成，不表示 runtime Ready、计划生效、模型接收或 Worker 派发。 |

## HTTP API

以下路径与字段已采用，均未实现。B06 只实施四条路由。

### GET /api/projects/{projectId}/issue-creation-options

#### 调用方与授权

创建表单打开时调用。调用者必须是当前登录用户，且当前能读取该项目。查询先核项目可见性，再返回允许披露的仓库与限制。

#### 输入

| 参数 | 类型 | 必填 | 约束 | 含义 |
| --- | --- | --- | --- | --- |
| 路径 `projectId` | string | 是 | 当前项目稳定身份 | 请求体不重复声明项目。 |
| `cursor` | string | 否 | 分页位置 | 仓库候选继续位置。 |
| `limit` | integer | 否 | 默认 50，最大 100 | 单页条数。 |

#### 返回

`200 OK`，形状为 `{projectId,creationContextRevision,defaultConversationMode,allowedConversationModes,canSubmit,blockingReasons,repositories,nextCursor,repositoryAnalysis}`。

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `creationContextRevision` | string | 服务端不透明令牌，覆盖本地仓库范围、配置引用与适用创建策略。它不是 SSE 游标，也不是可解析的历史配置引用。 |
| `defaultConversationMode` | string | 固定 `new`。 |
| `allowedConversationModes` | array | `new` 与 `existing`。 |
| `canSubmit` | boolean | 当前有创建资格、通用必要配置满足且存在可选范围；不承诺任意仓库组合都能提交。 |
| `blockingReasons` | array | 可披露的阻止原因。 |
| `repositories[]` | array | `repositoryId`、`displayName`、`selectable`、`reasons`、`observedAt`。名称只对用户可读仓可见。 |
| `nextCursor` | string 或 null | 末页为 null。 |
| `repositoryAnalysis` | object | B06 固定返回 `{availability:"unavailable",reasonCodes:["INTEGRATION_NOT_AVAILABLE"]}`。 |

`selectable` 同时要求用户可读与已观察到的 App 工作能力。确认不可读的仓库按可见性规则处理，未知返回 503，不返回空成功。

#### 错误与状态码

| 状态 | code | 触发条件 |
| --- | --- | --- |
| 404 | `RESOURCE_NOT_FOUND` | 项目不可见。 |
| 409 | `CREATION_CONTEXT_CHANGED` | 本地修订变化导致游标失效，页面从首屏重读。 |
| 503 | `AUTHORIZATION_UNCONFIRMED` | 外部能力或权限未知。 |
| 503 | `AUTH_NOT_CONFIGURED`、`RESULT_UNCONFIRMED` | 未配置认证；数据库不可用。 |

#### 并发与重放

每页重新核权；外部观察不承诺跨页快照一致。查询成功不授予执行能力，也不创建任何对象。

#### 设计理由

表单需要在用户点提交前知道哪些仓库可选用。把不可读仓库与未知混成一个空列表，会让用户以为项目里没有仓库，而不是当前无法确认。

### GET /api/projects/{projectId}/issue-creation-conversations

#### 调用方与授权

用户明确选择“关联已有会话”时调用。只返回当前可读且可关联的同项目会话。

#### 输入

| 参数 | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| 路径 `projectId` | string | 是 | 当前项目。 |
| `cursor`、`limit` | string、integer | 否 | 默认 50，最大 100，按稳定 id 排序。 |

#### 返回

`200 OK`，形状为 `{items:[{id,title}],nextCursor}`。游标是遍历位置，不是授权；新增的较早位置条目需要刷新。

#### 错误与状态码

与创建条件查询一致。会话内容范围已扩大时必须重新观察全部集合，不能凭旧的小范围返回新正文。

#### 并发与重放

提交时再次验证所选会话。选择失效、跨项目或不可关联时返回 404 `RESOURCE_NOT_FOUND` 或可披露的 409 `CONVERSATION_UNAVAILABLE`，不静默改选新会话。

#### 设计理由

会话可以独立于 Issue 存在，也可以先后服务多个 Issue。候选列表只帮助定位，不构成关联许可。

### POST /api/projects/{projectId}/issues

#### 调用方与授权

创建表单的明确提交。写请求要求 `Origin` 与 CSRF；`Idempotency-Key` 是本次 `creationId`。

#### 输入

| 字段 | 类型 | 必填 | 约束 | 含义 |
| --- | --- | --- | --- | --- |
| `expectedCreationContextRevision` | string | 是 | 来自创建条件查询 | 检测表单打开后本地条件变化。 |
| `conversation` | object | 否 | 省略等价 `{"mode":"new"}` | 关联方式。 |
| `conversation.mode` | string | 是 | `new` 或 `existing` | `new` 不允许带 `id`；`existing` 必须带 `id`。 |
| `conversation.id` | string | 仅 `existing` | 同项目可关联会话 | 已有会话。 |
| `title` | string | 是 | 非空白，最多 200 个 Unicode 标量 | 标题，不承担去重身份。 |
| `description` | string | 是 | 非空白，最多 20,000 个 Unicode 标量 | 目标、约束与预期结果。 |
| `repositoryIds` | array | 是 | 非空、不重复、最多 100，全部属于当前项目且满足本次创建条件 | 本次工作仓库。 |
| `acceptanceCriteria` | array | 否 | 省略等价空数组；最多 100 项，每项最多 2,000 标量 | 用户明确内容。 |
| `repositoryAnalysisId` | string | 否 | 同项目、同操作者的分析 UUID | B06 无可信分析来源，识别并规范化字段，但新操作用它返回 404。 |

规范化按解析后的允许字段比较。对象键顺序不影响相等；仓库集合排序后比较；省略验收数组规范化为空数组；省略 `conversation` 规范化为 `mode=new`。文本保留提交内容，数组顺序保留，服务端生成规范输入与摘要，不信任客户端摘要。

请求不接受顶层 `conversationId`、`conversationMode`、`userId`、角色、房间 ID、计划状态、`startRuntime`、`approved`、分支或密钥。

#### 返回

首次成功 `201 Created`，`Location` 为 `/api/issues/{issueId}`。同键同输入的已提交重试返回 `200 OK` 及同一回执。回执形状为 `{creationId,status,projectId,createdAt,source,issue,mainChangeSet,conversation,links}`。

#### 错误与状态码

| 状态 | code | 触发条件 |
| --- | --- | --- |
| 400 | `INVALID_JSON`、`INVALID_IDEMPOTENCY_KEY` | 正文格式或幂等键非法。 |
| 401 | `AUTHENTICATION_REQUIRED` | 会话失效。 |
| 403 | `CREATE_NOT_ALLOWED`、`ORIGIN_REJECTED` | 项目可见但当前无创建资格；写请求 Origin 不符。 |
| 404 | `RESOURCE_NOT_FOUND` | 项目、仓库或分析来源不可见。 |
| 409 | `CREATION_CONTEXT_CHANGED` | 本地条件与令牌不一致。 |
| 409 | `IDEMPOTENCY_CONFLICT` | 同键不同规范化输入。 |
| 409 | `CREATION_REQUIREMENTS_UNMET` | 已知必要配置或能力不满足，返回可披露原因。 |
| 409 | `CONVERSATION_UNAVAILABLE` | 所选会话不可关联。 |
| 409 | `ANALYSIS_NOT_APPLICABLE` | 分析未完成或与输入不符。 |
| 410 | `CREATION_RESULT_REMOVED`、`ANALYSIS_RESULT_REMOVED` | 原结果或分析正文已清理。 |
| 413 | `REQUEST_TOO_LARGE` | 请求体超过 256 KiB。 |
| 422 | `VALIDATION_FAILED` | 字段缺失、非法长度、重复仓库、未知字段。 |
| 429 | `RATE_LIMITED` | 遵循实际返回的 `Retry-After`。 |
| 503 | `AUTHORIZATION_UNCONFIRMED`、`RESULT_UNCONFIRMED` | 外部权限未知；提交结果未知。 |

#### 并发与重放

服务端先按 `(projectId, actor, issue_page, creationId)` 读原操作。命中已提交记录时按存量 Issue 与关联会话的完整内容范围核当前读权，然后按所存 `schemaVersion` 比较输入并返回 200 或 409。命中被清理的占位时先返回 410，不进入正文比较。只有无命中才校验新条件。

新操作的创建与应用共用项目行锁，锁序本身是收口基线。Issue 固定哪个配置修订依赖未采用的 P9 候选：P9 采用后，创建先锁项目并读取当前固定配置修订 C1，则 Issue 固定 C1；应用先提交 C2 时旧创建令牌返回 409，刷新后以新输入与新操作创建于 C2。P9 采用前，本节只固定项目锁序，不承诺 Issue 固定配置引用。

#### 设计理由

一次提交创建三种业务身份，避免出现只有会话或只有 Issue 的半套记录。重放优先于新条件，用户刷新页面时不会因为项目期间换了配置而拿不到原结果，也不会被拒绝成一次新创建。

### GET /api/projects/{projectId}/issue-creations/{creationId}

#### 调用方与授权

丢响应或切页后核查原操作。只查询当前操作者在该项目的页面创建操作。

#### 输入

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| 路径 `projectId` | string | 是 | 项目身份。 |
| 路径 `creationId` | UUID 形状字符串 | 是 | 原操作键。 |

#### 返回

`200 OK`，与提交成功同一回执形状。读取使用存量 Issue 与关联会话的完整内容范围，不要求重新通过 App 写权限、预算或创建条件。

#### 错误与状态码

| 状态 | code | 触发条件 |
| --- | --- | --- |
| 404 | `CREATION_NOT_FOUND` | 当前可见范围内没有已提交记录。这不证明旧请求将来不会提交。 |
| 410 | `CREATION_RESULT_REMOVED` | 记录已清理，键不复用。 |
| 403、404 | 不披露原内容 | 失去当前访问权时按契约返回受限结果。 |
| 503 | `RESULT_UNCONFIRMED` | 数据库不可用。 |

#### 并发与重放

查询不产生新对象，也不因为一次 404 释放键。原输入仍可恢复时，页面可以用原键与原输入重试；只有键时只做核查。

#### 设计理由

用户需要一种不依赖重发的手段判断原操作。把 404 明确定义为“本次查询未见结果”，避免页面把未知改写成失败并另建一个 Issue。

### 浏览器恢复路由

`GET /projects/{projectId}/issue-creations/{creationId}` 只调用上述原操作查询，页面不要求提前知道 `issueId`。首次提交前，确切允许输入与原键保存在 `sessionStorage` 并按可信主体、项目与 `creationId` 隔离；`localStorage` 只保存同主体隔离的项目、`creationId` 与时间等最小索引，不保存标题、正文或仓库名。

## repomesh_issues.conversations

物理表：`repomesh_issues.conversations`

用途与写入者：业务会话。B06 的创建事务只在“新建会话”分支写本表，已有会话分支只关联，不改它的创建来源与标题。B09 的独立会话创建也写本表，两个页面来源列可以都为空。

基础列如下。

| 字段 | 类型 | 必填 | 约束 | 含义 |
| --- | --- | --- | --- | --- |
| `id` | text | 是 | 主键 | 会话身份。 |
| `project_id` | text | 是 | 外键到项目；与 `id` 组成唯一键 | 会话属于一个项目。 |
| `title` | text | 否 | 可清理为 null | 标题。 |
| `title_redacted_at` | timestamptz | 否 | 与 `title` 不可同时非空 | 清理时间。 |
| `revision` | text | 是 | 无 | 会话业务快照修订，列表与页头返回的 `revision`。 |
| `created_at` | timestamptz | 是 | 无 | 创建时间，列表与页头返回的 `createdAt`。 |
| `content_scope_revision` | text | 是 | 无 | 内容范围修订。 |
| `removed_at` | timestamptz | 否 | 无 | 清理时间。 |

保留 `UNIQUE(project_id, id)` 与到现有项目表的复合外键，删除会话行受 RESTRICT 保护，不做级联删除。

`revision` 是会话自己的业务快照修订，改名或业务字段变化时提升。它与 `content_scope_revision`（范围修订）和 `last_message_sequence`（消息序号）互不替代：消息写入提升的是序号与范围修订，不把消息序号当业务 revision，也不拿业务 revision 当分页水位。`created_at` 在会话创建时写入，独立创建分支与页面创建分支都用它，列表与页头按这两列投影。

页面派生来源列是两个可空列：`created_by_page_operation_id text NULL`、`title_origin_operation_id text NULL`。两列各自的 `(project_id, operation_id)` 都用可延迟复合外键引用 `issues(project_id, creation_operation_id)`。原 `created_by_operation_id` 改名为 `created_by_page_operation_id`，名称只表示页面来源，不再兼任其他来源。必要新会话在创建事务里设创建来源；复制 Issue 标题时同时设标题来源。已有会话不改创建来源与标题。

标题约束与触发器：

1. `title` 与 `title_redacted_at` 不能同时非空。两者都空表示未命名会话，是合法状态；普通会话可以不提交标题，不能被“二选一”误拒。
2. 仅当 `title_origin_operation_id` 非空时才检查标题来源分支：未清理记录（`title_redacted_at IS NULL`）要求 `title` 非空；已清理记录（`title` 为空、`title_redacted_at` 非空）允许保留来源，因为清理派生标题后来源关系仍需可追溯。没有来源（`title_origin_operation_id IS NULL`）的未命名会话不受本条约束。两个有来源分支都要求来源 Issue 的 `main_conversation_id` 是本会话，用延迟约束触发器检查，避免把同项目另一 Issue 标成本会话的标题来源。
3. B09 的普通会话可以独立创建，两列都可以为空。B06 只要求自己新建的分支 `created_by_page_operation_id` 非空并与本操作一致，不对整表施加非空 Issue 依赖。

独立创建字段组与 B09 已对齐。九列物理可空，由完整分支 CHECK 约束。

| 字段 | 类型 | 必填 | 约束 | 含义 |
| --- | --- | --- | --- | --- |
| `standalone_creation_id` | text | 否 | 分支完整性 | 独立创建的客户端操作键。 |
| `standalone_creation_actor` | text | 否 | 引用稳定 account | 独立创建的调用者。 |
| `standalone_creation_schema_version` | integer | 否 | 分支完整性 | 原输入比较 schema。 |
| `standalone_creation_exact_input` | bytea | 否 | 活记录非空 | 确切输入。 |
| `standalone_creation_canonical_input` | bytea | 否 | 活记录非空 | 规范化输入。 |
| `standalone_creation_receipt` | jsonb | 否 | 活记录非空 | 冻结的封闭版本回执。 |
| `standalone_creation_committed_at` | timestamptz | 否 | 分支完整性 | 提交时间。 |
| `standalone_creation_removed_at` | timestamptz | 否 | 清理占位 | 清理时间。 |
| `standalone_first_message_id` | text | 否 | 延迟复合外键 | 同事务首消息。 |

键与分支规则：部分唯一约束 `(project_id, standalone_creation_actor, standalone_creation_id) WHERE standalone_creation_id IS NOT NULL`，entry 固定为 `conversation_create`。该索引覆盖 removed 行，绝不按活状态过滤。创建来源 XOR 二选一：页面 `created_by_page_operation_id` 非空且整组 standalone 列为空；或者页面列为空，standalone 的 id、actor、schema 与 committed_at 非空。第二分支的活记录还要求 exact、canonical 与 receipt 齐全，清理占位这三项全空，但键、actor、时间与 `standalone_first_message_id` 保留。`standalone_creation_actor` 引用稳定 account。

独立创建回执只保存 B09 第 2.7 节定义的封闭版本化形状，冻结当次的 title、revision、messageId 与 sequence，不能用当前 title 重建原结果。回执里的 revision 是当次业务快照副本，与列表投影读的 `revision` 列分开：后来改名提升本表 `revision`，不回写旧回执。title 只能显式提交或不提交，不从首消息正文派生，所以本表不需要额外的标题来源标记列；既有页面来源列 `title_origin_operation_id` 只表达“会话标题复制自某个 Issue”，与独立创建无关。`firstMessage` 省略时 `standalone_first_message_id` 与回执里的 sequence 都为 null，不造消息、工作或投递。有首消息时，本地列 `(project_id, id, standalone_first_message_id)` 用可延迟复合外键引用 B09 `repomesh_messaging.conversation_messages(project_id, conversation_id, id)`，其中本表的 `id` 就是目标表的 `conversation_id`，并在提交时核回执身份与序号。`submission_id` 按完整创建作用域稳定派生，不能只用裸 `creationId`。首消息的字段来源与完整性由 B09 负责，本列只保存身份引用。

清理独立创建的会话时，同一个事务在锁住本会话行后清空 `standalone_creation_exact_input`、`standalone_creation_canonical_input` 与 `standalone_creation_receipt`，并写 `standalone_creation_removed_at`。回执里冻结的标题副本随回执一起清除。键、actor、`standalone_creation_schema_version`、`standalone_creation_committed_at`、`standalone_first_message_id` 与那个部分唯一索引全部保留，索引继续覆盖 removed 行。首消息的正文清理由 B09 在同一事务内完成，本表只保留身份引用。会话的当前标题按它自己的来源规则处理：独立改名后的标题不属于这条创建回执，不被误删。

消息计数字段落在本表，B09 不再有独立的 counter 表。

| 字段 | 类型 | 必填 | 约束 | 含义 |
| --- | --- | --- | --- | --- |
| `last_message_sequence` | bigint | 是 | 默认 0，`CHECK (last_message_sequence >= 0)` | 已分配的最大消息序号。 |
| `message_sequence_updated_at` | timestamptz | 否 | 无 | 最近一次分配时间。 |

B06 创建时两列保持 0 与 null。B09 的每条真实消息写路径先锁本会话行，分配序号并持锁到提交，分页水位读这一列，允许序号间隙。页面来源卡片不分配消息序号。

## repomesh_issues.issues

物理表：`repomesh_issues.issues`

用途与写入者：Issue 身份、创建操作、页面来源、初始待办与事件流计数。这些记录的写入者都是创建事务，后续只有清理路径更新正文与状态。清理后身份、范围、配置引用与 cause 关系仍可查。

| `main_changeset_id` | text | 是 | 可延迟复合外键到本 Issue 的主 ChangeSet | 主 ChangeSet。 |

| `content_scope_revision` | text | 是 | 无 | 内容范围修订。 |
| `work_scope_revision` | text | 是 | 无 | 工作范围修订。 |
| `created_at` | timestamptz | 是 | 无 | 创建时间。 |

键与唯一性：`UNIQUE(project_id, id)`、`UNIQUE(project_id, number)`、`UNIQUE(project_id, id, main_conversation_id)`。主会话用 `(project_id, main_conversation_id)` 外键引用 `conversations`；主 ChangeSet 用 `(project_id, id, main_changeset_id)` 可延迟外键引用 `changesets(project_id, issue_id, id)`。身份、所属项目、首次主会话、主 ChangeSet 与创建时间不可更新。业务正文编辑若将来采用，必须提升 `revision`；本批只有创建与清理。

`UNIQUE(project_id, id, main_conversation_id)` 是主房间的引用目标，B07 的 main 房间靠它约束到本 Issue 自己的主会话。这是 B06 表定义的正式复合键，不再是引用他章的增量提案。

业务计划版本三列属于 B10 的增量，落在本行的原因是它按 Issue 一对一保存当前指针与编号，不值得为此另建一张 B06 表。三列在首批 B06 建表时就位，但不引用尚不存在的执行表：`repomesh_execution.business_plan_versions` 与 `(project_id, id, current_business_plan_version_id)` 到它的可延迟复合外键都随 B10 落地时才建立，B10 表侧提供 `(project_id, issue_id, id)` 普通唯一键作为引用目标。B10 采用前，`current_business_plan_version_id` 保持 null，`business_plan_pointer_revision` 与 `next_business_plan_version_index` 取默认值，P1 创建不依赖任何已有计划。B10 采用后，只在业务计划生效事务里写指针、指针修订与决定记录，同一 Issue 锁下分配 `next_business_plan_version_index`，允许回滚留下编号间隙，不用无锁 `MAX+1`。第一版尚未生效时指针为空，任何真实 Delegate 都被阻止，不能因为 Issue 已建或计划已建就启动执行。

下游行绑定的是不可变来源，不引用本行的可变指针：B10 的 `rounds.business_plan_version_id` 与 `business_plan_binding_revision`、`plan_revisions.business_plan_version_id`、`attempts.business_plan_version_id` 都固定当次实际使用的业务计划版本。同一 Issue 上同时最多一个未终结激活由 `business_plan_versions` 的部分唯一索引约束，Delegate 与技术应用在生效事务里核对该占用。本增量不改 B01 至 B04 的既有表。

P9 仍为候选。若另行采用，其 `initial_configuration_revision` 放在本行，同项目外键引用 `repomesh_projects.configuration_revisions(project_id, revision)`，历史配置删除受 RESTRICT 保护，owner、profile 与密文一致性按原候选落实。操作结果与待办不再复制第二个 pin，两者通过本行取得同一事实，回执仍不暴露 pin。当前物理合表不把 P9 的 NOT NULL 要求写成已采用义务；P9 收口前仍然不得落库真实可接续 Issue，原开工条件不撤销。

### 创建操作字段组

| 字段 | 类型 | 必填 | 约束 | 含义 |
| --- | --- | --- | --- | --- |
| `creation_operation_id` | text | 是 | 唯一 | 操作稳定身份。 |
| `creation_actor` | text | 是 | 外键到稳定 account | 可信操作者。 |
| `creation_entry` | text | 是 | `CHECK (creation_entry = 'issue_page')` | 页面创建入口。 |
| `creation_id` | text | 是 | 无 | 客户端幂等键。 |
| `creation_schema_version` | integer | 是 | `CHECK (creation_schema_version = 1)` | 输入比较 schema。 |
| `creation_exact_input` | bytea | 否 | 活记录非空 | 确切输入。 |
| `creation_canonical_input` | bytea | 否 | 活记录非空 | 规范化输入。 |
| `creation_digest` | bytea | 否 | 活记录非空 | 比较加速器。 |
| `creation_receipt` | jsonb | 否 | 活记录非空 | 稳定回执。 |

核心唯一键是 `UNIQUE(project_id, creation_actor, creation_entry, creation_id)`，它覆盖活行与 removed 行，不能建成只约束活跃行的部分唯一索引。另设 `UNIQUE(project_id, creation_operation_id)` 与 `UNIQUE(project_id, creation_operation_id, id)`，供会话来源、卡片与后续引用使用。`schema_version` 保留，即使操作转 removed 也不改。Issue ID 仍不是 `creationId`，也不是 `creation_operation_id`。

表上没有独立的 running 或 failed 操作行。服务端先生成全部业务 ID，再在同一事务插入本行，循环外键延迟到提交检查，未完成的中间状态对外不可见。

结构化结果直接来自本行的 `id`、`number`、`main_changeset_id`、`main_conversation_id`、`project_id` 与 `created_at`，稳定回执在创建时就由这些值构造。回执 schema 沿用既有 HTTP 形状，回执的 JSON 身份与时间用检查函数或延迟触发器核对。清理正文时不允许保留 exact、canonical、digest 或 receipt。分支 CHECK 必须完整：非 removed 要求正文、原输入与回执非空；removed 要求这些敏感字段都为空，身份与操作作用域仍非空。摘要只用于比较加速，最终比较用 canonical bytes。

本字段组只实现当前页面创建来源。将来接入可信 Manager 创建时，需要先确定它自己的 entry 与来源约束再显式扩展，不能把任意 entry 放进本次 CHECK，也不虚构它的消息来源。

### 页面来源和卡片字段组

| 字段 | 类型 | 必填 | 约束 | 含义 |
| --- | --- | --- | --- | --- |
| `page_source_id` | text | 是 | 唯一 | 页面来源稳定身份。 |
| `conversation_card_id` | text | 是 | 唯一 | 会话卡片稳定身份。 |
| `page_source_kind` | text | 是 | `CHECK (page_source_kind = 'issue_page')` | 来源类型由服务端固定。 |

来源 actor、操作、Issue、项目与会话都直接取自本行已有事实，不再复制一套可能串线的 ID。卡片与来源的关系由同一行提供，延迟完整性检查要求两者同时存在。本方案不设来源或卡片的独立正文副本：卡片展示的标题、正文与仓库集合都从本行及 `repository_scopes` 投影。本表不新增无来源的消息正文、`message_id` 或投递记录。

### 初始待办字段组

| 字段 | 类型 | 必填 | 约束 | 含义 |
| --- | --- | --- | --- | --- |
| `continuation_work_id` | text | 是 | 唯一 | 待办稳定身份。 |
| `continuation_kind` | text | 是 | `CHECK (continuation_kind = 'issue_continue')` | 本批唯一类型。 |
| `continuation_state` | text | 是 | 创建为 `blocked` | 待办状态。 |
| `continuation_reason` | text | 是 | 创建为 `INTEGRATION_NOT_AVAILABLE` | 阻止原因。 |
| `continuation_cancelled_at` | timestamptz | 否 | 仅清理转换时非空 | 取消时间。 |

cause 恒为本行的 `creation_operation_id`，target 恒为本行的 `id`，项目与 actor 也取自本行。需要 SQL 外键的跨批消费者引用 `UNIQUE(project_id, id, continuation_work_id)`，不能只记一个裸 `work_id`。等价唯一性 `UNIQUE(creation_operation_id, continuation_kind, id)` 明确声明，本行一对一本来已排除重复。

创建时只能是 `blocked`、`INTEGRATION_NOT_AVAILABLE` 加空时间。本批唯一允许的更新是转成 `cancelled`、`CONTENT_REMOVED` 加非空时间，禁止反向。removed 必须已 cancelled；blocked 不得存在外发事实。本批没有 externalOperationId、phase 或 leaseOwner 字段与记录，所以不会把已外发的待办误当成可取消。

[首批持久化设计](../current/backend-first-batch-persistence.md) 第 3 节列的逻辑 DurableWork 字段如果保留物理位置，就作为本 Issue 的同一初始责任字段组；将来消费者按单独采用协议增加租约与核查字段。本次合表不授权运行任何消费者，也不把这些列泛化成所有任务共用的列。B09 消息处理与 B10 执行各自持有自己的责任记录，不往本字段组追加第二条任务。创建或清理后都能按同一 `work_id` 恢复原责任，内存唤醒不是事实。

### 事件流字段组

| 字段 | 类型 | 必填 | 约束 | 含义 |

| `event_generation` | text | 是 | 无 | 当前事件流代次。 |
| `event_last_sequence` | bigint | 是 | `CHECK (event_last_sequence >= 0)` | 当前代次已分配的最大序号。 |
| `event_pruned_through` | bigint | 是 | 默认 0，`CHECK (event_pruned_through >= 0 AND event_pruned_through <= event_last_sequence)` | 已清理连续前缀的末序号。 |

创建事务写入 generation 与序号 1，`event_pruned_through` 为 0。同一个 Issue 的事件写入先锁本 Issue 行，更新 `last_sequence` 并插入事件，持锁到提交；所有写路径都遵守这一顺序。事件字段不与 Issue 业务 `revision` 混用，更新计数不伪造业务编辑。`event_pruned_through` 表示当前代次已清理连续前缀的末序号，即使事件表为空或整个窗口都被删除，也能精确判断重放缺口。

## repomesh_issues.changesets

物理表：`repomesh_issues.changesets`

用途与写入者：ChangeSet 身份。本批只创建主 ChangeSet。

| 字段 | 类型 | 必填 | 约束 | 含义 |
| --- | --- | --- | --- | --- |
| `id` | text | 是 | 主键 | ChangeSet 身份。 |
| `project_id` | text | 是 | 与 `issue_id`、`id` 组成唯一键 | 所属项目。 |
| `issue_id` | text | 是 | 同上 | 所属 Issue。 |
| `kind` | text | 是 | `CHECK (kind = 'main')` | 本批只有主 ChangeSet。 |
| `created_at` | timestamptz | 是 | 无 | 创建时间。 |

键与关系：`UNIQUE(project_id, issue_id, id)` 供 Issue 主 ChangeSet 外键引用，`UNIQUE(project_id, issue_id)` 保证本批每个 Issue 恰好一个主 ChangeSet，`(project_id, issue_id)` 可延迟外键引用 `issues(project_id, id)`。Issue 与 ChangeSet 互相引用的循环在提交时检查，删除受 RESTRICT 保护。

主 ChangeSet 的独立 ID 与后续历史承载保留。将来支持非 main 的 ChangeSet 时，需要显式迁移把 `UNIQUE(project_id, issue_id)` 放宽为 `kind = 'main'` 的部分唯一约束，当前不提前扩展枚举。

## repomesh_issues.repository_scopes

物理表：`repomesh_issues.repository_scopes`

用途与写入者：一行表示某个 Issue 或某个 Conversation 对一个仓库的内容范围归属。Issue 行上的 `is_work` 表示该仓库同时属于工作集合。创建事务写第一批行，后续内容引入只追加。

| 字段 | 类型 | 必填 | 约束 | 含义 |
| --- | --- | --- | --- | --- |
| `scope_id` | text | 是 | 主键 | 范围行身份。 |
| `project_id` | text | 是 | 同项目复合外键 | 所属项目。 |
| `repository_id` | text | 是 | 同项目复合外键 | 仓库。 |
| `issue_id` | text | 否 | Issue 分支 | Issue owner。 |
| `conversation_id` | text | 否 | Conversation 分支 | 会话 owner。 |
| `is_work` | boolean | 是 | 默认 false | 是否为该 Issue 的工作仓库。 |
| `introduced_by_page_operation_id` | text | 否 | 同项目复合外键到 Issue 创建操作 | 页面引入依据。 |
| `work_issue_id` | text | 生成列 | `GENERATED ALWAYS AS (CASE WHEN is_work THEN issue_id ELSE NULL END) STORED` | 工作范围专用引用值。 |
| 首次引入时间与依据 | 时间、text | 是 | 按原逻辑字段 | 引入记录。 |

完整分支 CHECK：`(issue_id IS NOT NULL AND conversation_id IS NULL) OR (issue_id IS NULL AND conversation_id IS NOT NULL AND is_work = false)`，再加 `CHECK (NOT is_work OR issue_id IS NOT NULL)`。两类 owner 都有实体外键：`(project_id, issue_id)` 引用 `issues`，`(project_id, conversation_id)` 引用 `conversations`，`(project_id, repository_id)` 引用现有 `repomesh_projects.project_repositories`，删除都受 RESTRICT 保护。页面引入时 `(project_id, introduced_by_page_operation_id)` 引用 Issue 的操作唯一键；将来由真实消息引入范围时，依据由 B09 定义，不能要求所有 conversation 范围都来源于 Issue。

唯一性：`UNIQUE(issue_id, repository_id)` 与 `UNIQUE(conversation_id, repository_id)` 分别防重复，NULL 分支由 CHECK 排他。`UNIQUE(work_issue_id, repository_id)` 与 `UNIQUE(project_id, work_issue_id, repository_id)` 是工作范围的专用外键目标。这两个是普通唯一约束，不能用部分唯一索引充当外键目标。B07 与 B10 通过它们选中的一定是 `is_work = true` 的 Issue 行，只属于历史内容集合的仓库不能当工作仓库使用。

原 `issue_repository_scope(issue_id, repository_id)` 的下游外键改指 `repository_scopes(work_issue_id, repository_id)`，本地引用列名 `issue_id` 与 `repository_id` 不变。原 `issue_content_scope` 按 `issue_id IS NOT NULL` 读全部 Issue 行；原 `conversation_content_scope` 按 `conversation_id` 读全部会话行。每个 Issue 提交时至少有一个 `is_work = true` 行，工作集合天然是内容集合的子集。延迟约束检查每个 Issue 的内容仓库都出现在它主会话的内容集合中。范围新增与 owner 范围修订提升在同一事务完成，任何内容行删除、owner 身份改写或仓库身份改写都被拒绝。本批的工作标志创建后不可改；将来的范围缩减如另行采用，只能改 `is_work`，不能删内容行，已有执行外键或责任存在时仍然 RESTRICT。旧文档里的“范围只增不减”说的是内容保护范围，不能读成当前工作集合可以随意扩大。

只锁范围子行不足以避免并发写入范围偏差。所有范围扩展先锁项目，再按会话或 Issue 的固定对象顺序锁 owner，检查包含关系与修订；创建、清理与消息引入都走同一规则。后续扩大 Issue 内容范围时必须同步扩大主会话范围，不能先发布新内容再补权限集合。

## repomesh_issues.issue_events

物理表：`repomesh_issues.issue_events`

用途与写入者：Issue 级事件。创建事务写第一个事件，之后的写入由 B07 的事件路径与通知路径负责。

| 字段 | 类型 | 必填 | 约束 | 含义 |
| --- | --- | --- | --- | --- |
| `issue_id` | text | 是 | 外键到 Issue，删除 RESTRICT | 所属 Issue。 |
| `generation` | text | 是 | 主键的一部分 | 事件流代次。 |
| `sequence` | bigint | 是 | `CHECK (sequence > 0)`，主键的一部分 | 流内序号。 |
| `kind` | text | 是 | `CHECK (kind = 'snapshot_invalidated')` | 本批唯一事件类型。 |
| `created_at` | timestamptz | 是 | 无 | 事件时间。 |

主键是 `(issue_id, generation, sequence)`。删除 Issue 受 RESTRICT 保护，事件保留清理显式执行。不对 `generation` 建到 Issue 当前代次的外键，否则换代会强迫删除历史事件。

写入触发器或仓储协议检查三件事：写入者持有 Issue 锁、写入的 generation 等于当前流代次、序号来自本事务分配。创建完整性只要求在首次创建提交时存在第 1 个事件，不能要求每次更新 Issue 时都存在创建事件，否则 24 小时保留清理会被误拒绝。

默认保留 24 小时来自已采用的创建契约。清理先锁 Issue，只删除当前代次的连续前缀并原子推进 `event_pruned_through`；旧代次记录也可以按保留规则清理。`Last-Event-ID` 仍是不透明保护的 `(issue_id, generation, sequence)`。错 Issue、篡改、旧 generation、`sequence < event_pruned_through` 或 `sequence > event_last_sequence` 都返回 `resync_required`；`sequence = event_pruned_through` 可以从下一序号重放。将来要换代时，必须锁 Issue、明确生成新 generation 并初始化计数与边界，不能靠进程重启自动换代。

重放在有界一致快照中读取 generation、边界、高水位与事件。清理前取得完整快照的重放可以完成，清理后建立快照的按新边界判定。发布器只扫描已提交事件，发送不删行、不记浏览器已读，重启后扫描主库恢复。线上仍发送 `issue.changed`，`changed` 保守投影为 `["issue","rooms"]`；事件不复制正文、房间凭据或授权状态。连接期间重新核权限，失权立即停止发送。B07 的详情与 rooms 仍是分开读取，文档不宣称跨请求属于同一快照。

用途与写入者：项目内编号分配。创建事务加锁更新。

| 字段 | 类型 | 必填 | 约束 | 含义 |
| --- | --- | --- | --- | --- |
| `project_id` | text | 是 | 主键，外键到现有项目 | 项目。 |

## 约束触发器清单

以下触发器是候选设计。实施时必须用破坏性 SQL 证明拒绝行为，不能只跑成功路径。

| 触发器 | 责任 |
| --- | --- |
| `creation_aggregate_complete` | 按操作主键读取最终行；非 removed 要求规范输入、回执、结果与 schema 齐全，且唯一 Issue、主 ChangeSet、主会话、来源、卡片、非空范围、一个初始 blocked 待办与序号 1 事件存在。 |
| `issue_origin_consistent` | Issue 与操作双方插入或身份变更都排队检查相等与同项目归属，防止只插孤立 Issue。 |
| `scope_complete` | Issue 插入与范围插入或删除都排队，最终至少一仓，内容范围是工作范围超集，会话范围是 Issue 内容范围超集。 |
| `title_origin_consistent` | 仅当 `title_origin_operation_id` 非空时按最终行核标题分支：未清理记录要求 `title` 存在；已清理记录（`title` 为空、`title_redacted_at` 非空）允许保留来源。未命名且无来源的会话（两列都空）合法，不受本条约束。有来源时来源 Issue 的 `main_conversation_id` 必须等于本会话。 |
| `continuation_transition_checked` | 只允许 `blocked/INTEGRATION_NOT_AVAILABLE` 到 `cancelled/CONTENT_REMOVED` 的单向转换；removed 必须已 cancelled，禁止反向与删除。 |
| `event_stream_write_protocol` | 事件写入必须持有 Issue 锁，generation 等于当前流代次，序号由本事务分配；清理只推进连续前缀。 |
| `immutable_configuration_fact`、`immutable_provider_fact`、`immutable_creation_identity` | 禁止事实更新或删除；白名单只允许正文清理与操作转 removed，不允许 removed 回到活。秘密重包与可用性更新不改变身份。 |
| `creation_receipt_consistent` | 结构化结果列是权威，回执由同一结果构造且关键身份与时间一致；清理时删除回执。 |
| `configuration_owner_and_binding_consistent` | 按最终行核两个固定 profile 的 owner 都等于项目 owner，固定 JSON 中秘密四元组与物化参数等于所引用的不可变版本。 |

循环关系使用 `DEFERRABLE INITIALLY DEFERRED`。约束检查针对当前最终行，不依赖触发时尚不完整的旧快照。延迟检查覆盖 Issue 与 ChangeSet 双向归属、必要新会话创建来源、范围包含关系、来源与卡片存在、创建回执一致、初始 blocked 待办与序号 1 事件。创建完整性只在创建聚合首次提交时要求初始状态，后续清理走 removed 分支，后续事件保留不再要求最早事件存在。身份更新、范围删除与 removed 复活用立即保护拒绝。

## 表关系与保留

关系以 Issue 行为中心：`conversations` 提供会话与消息计数，`changesets` 提供主 ChangeSet，`repository_scopes` 提供内容与工作范围，`issue_events` 提供逐条事件，`project_issue_counters` 分配项目内编号。创建操作、页面来源、卡片与初始待办都是 Issue 行的字段组。

新增对象是候选 schema `repomesh_issues` 的六张表。复用对象是 B03 的 `repomesh_projects.configuration_revisions`、`project_repositories` 与 B02 的 `repomesh_access.accounts`。

清理只删正文与可重建副本：清空 Issue 正文、exact、canonical、digest 与 receipt，取消确定未外发的初始待办，写 `removed_at`。固定配置引用、范围身份、来源与卡片关系、待办 cause、ChangeSet 与会话身份全部保留。被 Issue 引用的配置修订删除受 RESTRICT 保护。内容范围只增不减。创建查重与项目内编号由主键和唯一键覆盖，列表与详情查询需要的索引在 B07 定稿时按实际查询补充。

## 事务与恢复

### 创建事务步骤

1. 限制信封与请求体，认证，并按 `(projectId, actor, issue_page, creationId)` 预查原操作。
2. 命中已提交结果时按存量完整内容范围核权，removed 先返回 410，然后按所存 schema 返回 200 或 409。
3. 无结果才规范化新输入，读取范围与会话版本，事务外取得全范围观察。预核失败时用短事务重查，让期间提交的赢家优先。
4. 开短 `READ COMMITTED` 事务，候选初值 `lock_timeout=2s` 与事务总预算 5 秒。按下面的锁序取锁，再查原操作。
5. 新操作比较 `expectedCreationContextRevision`，锁已有会话并比较可关联性与范围修订，锁目录、固定版本与政策，检查完整参数、确切秘密版本可用性与运行预算门槛。创建本身不消费也不预留额度。
6. 同项目锁下选定唯一初始配置修订，插入必要会话、Issue 整行、范围、主 ChangeSet 与创建事件，提交前延迟核所有最终关系。Issue 行同时承载创建操作、页面来源、卡片、初始 blocked 待办与事件流计数。
7. COMMIT 获确认才返回 201；已知同键赢家返回 200；提交回执丢失返回 503 `RESULT_UNCONFIRMED`，由原键查询。

短事务内要重查原键，命中时优先返回旧结果；只有无命中才校验新的 `creationContextRevision`、会话范围与固定政策。表上没有“已受理”占位提交，未完成的事务对外不可见。

### 锁序

共同 owner 边界保留：交互写先锁 binding、session 与 account，再锁 project 与所需 connection；持有后段锁后不再回头拿 account 锁。原独立操作行的锁现在就是目标 Issue 行的锁。

已存在的业务对象统一按会话先、Issue 后取锁，同类对象按 ID 排序。原操作键预查得到会话 ID 后，先锁 conversation 再锁 Issue，然后重读作用域与归属，防止陈旧定位。不存在的操作靠 owner 与 project 锁加最终操作唯一约束串行，不能把一次“SELECT 不到行”当锁。目录、profile、policy 与 secret 锁仍按现行逐路径规则，B03 与 B04 不改。

完整顺序为：主体 binding、session 与 account，然后 project 与所需 connection，然后 conversations 按 id，然后 Issue 按 id，再进入后续批次对象。不需要的对象层可以跳过。

### 权限观察

Issue 专用观察仍由 access 产生，包含 actor、credentialVersion 与 connectionRevision、accessEpoch、准确仓库集合、每仓用户观察时间，以及所选工作仓库的 App 安装身份、权限版本与观察时间。当前用户须能读取提交范围与所关联会话的完整内容范围。

| 规则 | 内容 |
| --- | --- |
| 观察覆盖 | 新创建的必要观察候选为提交前 60 秒内，使用数据库 `clock_timestamp`，不得来自未来。 |
| 本地代次 | 本地 `accessEpoch` 改变立即使旧观察失效。回滚后重新获取，不能持锁访问 GitHub。 |
| App 能力 | 推荐 S06 最低 Metadata read、Contents write、Pull requests write，作为待采用门槛。B02 登录成功不推导该能力。 |
| 失败区分 | 外部明确不足按当前契约返回隐藏 404 或可披露 409；未知返回 503 `AUTHORIZATION_UNCONFIRMED`。 |
| 原结果读取 | 只要求当前内容读取权，不要求重新通过 App 写权限、预算与创建条件。 |

### 清理

清理是仅由组装注入的维护入口，B06 没有浏览器删除路由。清理沿创建相同的锁序锁主会话与 Issue，然后清空 Issue 正文、exact、canonical、digest 与 receipt，取消未外发的初始待办，写 `removed_at`。

派生标题只在 `title_origin_operation_id` 等于被清理的创建操作时才清理并置 `title_redacted_at`。关联的已有会话保留原名，独立改名后的标题不被本 Issue 的清理删除。

清理独立创建的会话时，同一事务在锁住会话行后清空该会话 standalone 的 exact、canonical 与 receipt，并写 `standalone_creation_removed_at`；键、actor、提交时间、首消息身份与部分唯一索引保留。回执里冻结的标题副本一并清除，独立改名后的当前标题保留。首消息正文清理由 B09 在同一事务内完成，B06 不保留第二份副本。

Issue、operation、source、card、work、ChangeSet 与会话身份，以及全部范围行都保留。所有清理在一个事务里提交，没有物理删除，没有键复用，也没有反向复活。如果将来有消费者扩展了外发事实，本维护入口必须先判定适用性，不能用 `cancelled` 推断外部已经停止。

### 恢复场景

| 场景 | 预期结果 |
| --- | --- |
| 同键同输入并发 | 一处操作、一个 Issue、一个主 ChangeSet、一个必要会话与一套范围；其余请求返回 200 或 503 后按原键查询得到 200。 |
| 同键不同输入 | 只保留赢家输入，其他请求 409 或核查未知；正文不能后到覆盖。 |
| 任一写入点失败 | 主库没有半套聚合与待办；故意提交孤立操作、孤立 Issue、空范围或错主 ChangeSet 都被数据库拒绝。 |
| 丢 HTTP 响应 | 页面冻结原键与原输入，一次查询 404 仍表示未知，最终得到唯一三种业务 ID 与回执。 |
| 创建与配置应用交错 | 创建先提交则 Issue 固定 C1（依赖未采用的 P9 候选）；应用先提交则旧令牌 409，刷新后新输入创建于 C2；重放不核新条件。 |
| 关联已有会话时扩大范围或撤权 | 卡片与范围原子写入；旧观察先回滚再核全范围；原结果读取不凭旧小范围披露。 |
| 普通会话零 Issue | 会话按 B09 的独立创建分支落库，两个页面来源列为空；不写 Issue，不写房间关联，也不分配消息序号。 |
| B10 未采用、计划尚未生效 | Issue 行的业务计划三列保持默认（指针 null、指针修订 0、下一编号 1）；创建聚合不引用不存在的执行表，任何真实 Delegate 都被阻止。 |
| 清理后旧键迟到创建 | 同事务清正文与派生、保留固定引用与范围占位；有权 410 先于正文比较，无权 404；旧键不产生新 Issue，待办只转 cancelled 且保留 cause。 |
| SSE 保留清理与重放交错 | 先提交的小号先可见；清理与重放之间没有半个窗口；全部事件清空后仍能按 `event_pruned_through` 判断旧游标缺口。 |
| B03 部分仓库失权后修复模型 | 原项目仓库全集保留；应用不需要旧仓全部读权；增仓失败不留局部配置或范围变更。这需要运行 B03 全量原回归，不能用 Issue 成功用例替代。 |
| 项目切到 C2 后重启 | 数据库待办仍能沿 Issue 与 C1（依赖未采用的 P9 候选）取得同一模型、参数、秘密与版本，状态保持 blocked；不调用真实消费者，也不证明 G1 或 G2。 |
| 缺材料或秘密撤销 | 项目仍可按 B03 规则受限保存；新 Issue 失败且无聚合；被引用配置删除被 RESTRICT 拒绝。 |

## 跨批引用与唯一事实

| 事实 | 唯一权威 |
| --- | --- |
| 项目、仓库集合、配置修订与目录写口 | B03 的 `repomesh_projects`。 |
| 供应商修订、模型行与业务密文 | B04 的 `repomesh_models` 与 `repomesh_secrets`。 |
| 完整 execution 政策与额度窗口 | B05 的候选对象；B06 只读取门槛，不写测试或应用表。 |
| Issue、会话、主 ChangeSet、范围、来源、待办与事件 | 本批的 `repomesh_issues` 六张表。 |
| 详情、rooms 与 SSE 投递 | B07；B06 只写创建事件与流计数。 |
| 消息、澄清与运行映射 | B09 的 `repomesh_messaging`；本批不预铺消息、提交、投递或 Manager 会话。 |
| 执行范围与仓库事项 | B10；本批只提供引用键，不建执行表。 |

本批为其他批次提供的真实引用键如下。

1. `conversations` 的 `UNIQUE(project_id, id)`：B09 消息与 `manager_sessions` 的复合外键目标。
2. `issues` 的 `UNIQUE(project_id, id)`、`UNIQUE(project_id, id, main_conversation_id)` 与 `UNIQUE(project_id, creation_operation_id)`：B07 主房间、B10 轮次与仓库事项、创建来源的引用目标。
3. `changesets` 的 `UNIQUE(project_id, issue_id, id)`：主 ChangeSet 的引用目标，供 B10 与 B11 的版本表使用。
4. `repository_scopes` 的 `UNIQUE(work_issue_id, repository_id)` 与 `UNIQUE(project_id, work_issue_id, repository_id)`：B07 Leader 房间与 B10 工作范围的外键目标，选中项一定是 `is_work = true` 的行。
5. `issues` 的 `UNIQUE(project_id, id, continuation_work_id)`：跨批消费者引用初始待办的引用目标。

B09 侧为 B06 提供首消息引用目标：`conversation_messages(project_id, conversation_id, id)` 与 `UNIQUE(project_id, conversation_id, committed_sequence)`。`conversations` 用本地列 `(project_id, id, standalone_first_message_id)` 对前一个键做可延迟复合外键，首消息省略时为 null。这条外键随 B09 六张表落地时建立；首批 B06 的页面创建分支只写自己的 Issue 聚合，不创建、也不等待尚不存在的消息表。B10 的 `repository_issues`、`plan_revisions` 与派工记录通过上面的工作范围键与房间键引用本批事实，不复制工作范围或房间观察。B10 的 `business_plan_versions` 反向引用 `issues(project_id, id)`，本批的 `current_business_plan_version_id` 再延迟外键指回它的 `(project_id, issue_id, id)`；两个方向的引用都在 B10 落地时建立。

## 设计理由

一次提交创建多种业务身份，是为了让用户看到的结果与数据库事实一致。若先建会话再建 Issue，任何中间失败都会留下需要人工判断的孤记录。把范围、来源与待办放进同一事务，还能保证丢失响应后的查询一定拿到完整结果。

固定配置引用保护的是“这个 Issue 当时使用什么配置”。若只按创建时间推断，后台重启后就无法证明使用了哪个版本。固定引用与当前项目配置分开，项目后来换模型不会改变在途 Issue。

把一对一记录合成字段组，减少的是表和连接，不是约束。创建操作、页面来源、卡片、初始待办与事件流计数仍然各自有稳定身份与唯一键，清理时仍然分开判定该保留什么、该清空什么。范围表合并后，工作范围由生成列加普通唯一约束表达，外键目标不再可能是内容行。

创建成功不等于运行开始。待办以真实 `blocked` 状态保存，运行接入仍按执行门槛另行验收，文档不会把管理面可创建写成运行就绪。

## 验证清单

以下是可观察行为的预期结果，不是已运行测试。完整映射见 [设计验收映射](../development/2026-09-13-b04-b06-design-01/ACCEPTANCE.md) 的 B06 部分，DB01 至 DB08 与 CB01 至 CB05 全部未执行；DB09 至 DB13 是本次合表新增的静态核验要求，同样未执行。

| 检查 | 预期观察 |
| --- | --- |
| DB01 同键并发 | 一条操作、一个 Issue、一个主 ChangeSet、一个必要会话、来源与卡片、一条 blocked 待办与一个创建事件。 |
| DB02 同键异输入 | 只有赢家输入持久，其他请求 409 或核查未知。 |
| DB03 每写点失败 | 无半套聚合；孤立操作、孤立 Issue、空范围、错主 ChangeSet 提交被拒绝。 |
| DB04 丢响应 | 先查询 404 仍未知，最终原三 ID 与回执稳定。 |
| DB05 配置 CAS 交错 | 锁后条件相同才提交，冲突 409，重放不核新条件。 |
| DB06 扩大内容范围 | 卡片与范围原子，旧小范围不能披露新正文，全范围核权后恢复。 |
| DB07 B03 回归 | 部分仓库失权后仍能修复模型；增仓失败无局部变更。 |
| DB08 清理 | 正文与派生同事务清理，固定引用与范围占位保留，旧键零新 Issue，待办只转 cancelled。 |
| DB09 跨项目与错分支拒绝 | 直接 SQL 尝试跨项目范围、一行同时挂两个 owner、conversation 行 `is_work = true`、Leader 引用仅内容仓、主房间挂错会话、B09 绑定 Leader 房间、B10 错 Issue 同仓与 Issue 挂错主 ChangeSet，全部提交失败。 |
| DB10 removed 旧键 | 清理后旧键任意正文仍返回 410，且不能用同一键建新 Issue。 |
| DB11 清理后追溯 | 清理后范围、身份、来源卡片关系与 work cause 仍可查，待办状态为 cancelled，没有物理删除。 |
| DB12 事件边界 | 先提交的小号先可见；清理与重放没有半个窗口；全部事件清空后仍能按 `event_pruned_through` 判断旧游标缺口。 |
| DB13 普通会话与卡片 | 普通会话零 Issue 可落库；页面来源卡片不分配消息序号，也不产生消息或投递记录。 |
| CB01 成功与失败 | 操作与 Issue 同一初始配置，待办可沿 Issue 追溯；失败全无。 |
| CB02 创建与应用并发 | 创建先提交固定 C1（依赖未采用的 P9 候选）；应用先提交使旧令牌 409；no-op 应用不换修订。 |
| CB03 重启追溯 | 清缓存重启后仍由数据库取得同配置，状态 blocked。 |
| CB04 约束拒绝 | 空引用、跨项目引用、操作与 Issue 引用不一致、篡改固定秘密或执行参数均被拒绝。 |
| CB05 受限保存 | 缺材料项目仍可受限保存；新 Issue 失败无聚合；被引用配置不删除。 |
| I06 观察时效 | 最终以数据库时钟核 60 秒与代次，超过即回滚重核，未知 503 不冒充 denied。 |
| I07 分析来源 | 未启用来源不静默丢弃 ID；同名不同键是两条独立 Issue；已有会话不改名、不造消息。 |
| I08 原结果范围 | 按存量完整范围核权，removed 有权 410 先于正文比较，范围不由新输入驱动。 |
