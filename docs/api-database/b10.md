# B10 受限宿主下单仓单轮执行（G3／G4）

本批对应施工计划中的 B10，范围是 G3 与 G4。用户能完成的事情有六件。第一，在一个 Issue 明确的一个仓库范围内，由 Manager 或 Leader 组织当前轮次的有限 DAG。第二，把候选就绪任务派给一个 Worker，并在统一短事务中占用该 Worker 与所需容量。第三，在一个独立 Attempt 环境中启动执行，读回真实任务状态和产物。第四，请求停止、撤销写能力并核查资源回收。第五，在响应丢失、协调器重启、租约到期或旧进程仍活时保持未知状态，不启动替补。第六，覆盖 Controller REST、TeamHarness MCP 与共享文件等可达入口，证明不获准动作不会产生业务副作用。

本批限定单仓、单轮，不做 B11 的跨轮换图与跨仓部分应用，不重写仓内 DAG，不建立通用宿主命令平台或 Kubernetes 调度层。单仓是本章计划与验收的校验范围；轮次身份按 Issue 保留，同一 Issue 的后续轮次可由 B11 覆盖多个受影响仓库。

### 1.2 用户能完成什么

用户为某个 Issue 选定一个仓库范围后，可以看到当前轮次的有限任务安排、任务依赖和真实候选就绪状态。用户可以要求停止某个任务或整轮执行，并看到停止请求、实际停止和资源回收分别记录。用户不会看到页面把上游 `completed` 直接显示成业务已验收，也不会在停止证据缺失时看到系统自动启动替补。

### 1.3 依赖

依赖 B09 的可信运行上下文与调用授权，依赖 B06 的 Issue 与主 ChangeSet，依赖 B05 的运行预算、时间和出站政策版本，依赖 access 的仓库观察，依赖 coordinator 的持久待办领取，依赖 host-executor 的受限宿主动作，依赖选定上游实例的 Controller REST、TeamHarness 与存储。项目运行额度窗口由本批首次落地，不再依赖 B05 的测试账本。

### 1.4 明确边界

本批不新增浏览器派工写接口，执行状态读取归 B07 的只读投影。它不开放原生 `delegate_task`、Controller 直写、共享文件覆盖或任意容器命令作为产品入口。它不承诺 Controller 已提供全局容量、公平排队、单 Worker 单任务租约或完整 Git 工作副本隔离。它不把租约到期当进程停止，不把取消元数据当资源释放，不把上游 `completed` 当业务通过。仓库事项身份只表达 RepoMesh 内的稳定委派归属，不是上游 Project、Task 或 Attempt 身份；上游引用仍落在 `plan_revisions.upstream_binding`，不引入通用工作项平台。

### 2.2 G3 的两种写方方案

| 方案 | 内容 | 优点 | 代价与风险 |
| --- | --- | --- | --- |
| A 单一正式写方 | RepoMesh 执行 Adapter 是 RepoMesh 管理项目的唯一正式 Project 与 Task 元数据写方；原生 delegate、Controller 直写、shared 覆盖和 Worker 自持写凭据在受管项目中封闭或围栏 | 责任唯一，校验点集中，便于把权限、计划、预算和容量检查放在同一入口 | 需要凭据与能力层封闭，可能需要窄上游补丁；不封闭时只是页面限制 |
| B 共同条件写 | 所有写方遵守带版本的条件写或共同清单，MCP 与 shared 路径也携带同一条件 | 保留多写方灵活性，理论上不改上游职责 | 需要统一 ETag 或版本协议，MCP 覆盖路径当前不具备同等保证，验证成本高 |

本章默认推荐 A，并把它列为待根代理与用户取舍的决策点。推荐理由是 G3 的验收要求覆盖可达旁路，而当前上游 MCP 与 shared 路径不具备同一条件写保证。若选 A，执行 Adapter 需要同时持有受限 Controller 凭据与受控共享存储写能力，Worker 不直接获得正式元数据写凭据。若选 B，必须先用真实交错写实验证明 MCP、REST 与 shared 三条路径都遵守同一版本条件，本章不预设该实验已通过。

### 2.3 单仓单轮的写入清单

| 写入对象 | 唯一写入者 | 凭据与校验点 | 不允许的路径 |
| --- | --- | --- | --- |
| 轮次与任务本地映射 | coordinator 执行模块 | 数据库短事务，核 Issue、计划、权限、预算与容量 | 浏览器直写、Worker 自报 |
| 仓库内事项登记与停用 | coordinator 执行模块 | 首次实际派工的数据库短事务，核 Issue、仓库已在本 Issue 固定范围、同仓未重复登记 | 选仓、创建 Issue 或只建立计划直接登记，B07 造行，按每轮复制新身份 |
| 上游 Project 元数据 | 执行 Adapter | 受控 Controller 凭据，带版本条件与读回 | 原生 delegate 绕过、shared 覆盖 |
| 上游 Task 元数据 | 执行 Adapter | 受控 taskflow 或 REST 窄接口，稳定任务编码 | Worker 或 Leader 自持写凭据直连 |

## 3. API 与内部边界

### 3.1 内部边界：execution.Adapter

状态为本次提案，未实现。它是 RepoMesh 到选定上游实例的窄适配层，只封装本批需要的能力。调用方是 coordinator 执行模块。

```go
type Adapter interface {
    EnsureReady(ctx context.Context, workerRef string) (ReadyObservation, error)
    ReadWorkflow(ctx context.Context, binding ProjectBinding) (WorkflowObservation, error)
    PlanDAG(ctx context.Context, binding ProjectBinding, plan TaskGraph) (PlanObservation, error)
    ReadyNodes(ctx context.Context, binding ProjectBinding) ([]ReadyNode, error)
    Delegate(ctx context.Context, op DispatchOperation) (UpstreamObservation, error)
    ObserveTask(ctx context.Context, binding ProjectBinding, taskRef string) (TaskObservation, error)
    AcceptResult(ctx context.Context, op AcceptOperation) (UpstreamObservation, error)
    Pause(ctx context.Context, binding ProjectBinding, reason string) (UpstreamObservation, error)
    CancelTask(ctx context.Context, op CancelOperation) (UpstreamObservation, error)
    ReadArtifact(ctx context.Context, binding ProjectBinding, taskRef, path string) (ArtifactObservation, error)
}
```

每个方法返回带来源、观察时间、版本或 ETag、原始状态与规范化状态的观察值。Adapter 不持有 Issue 配置，不决定业务采纳，不写本地数据库。具体传输是 Controller REST、TeamHarness stdio 还是两者组合，由实施时按锁定版本选定，本章不冻结传输。

### 3.2 内部边界：execution.Service.PlanRound

状态为本次提案，未实现。它建立单仓单轮计划映射。调用方是 coordinator 计划工作。

```go
type PlanRoundCommand struct {
    ProjectID        string
    IssueID          string
    RoundID          string
    RoundIndex       int
    Purpose          string
    RepositoryID     string
    BusinessPlanVersionID string
    ExpectedBusinessPlanBindingRevision int64
    Tasks            []TaskDraft
    CauseOperationID string
}

type RoundPlan struct {
    RoundID        string
    PlanRevisionID string
    TaskIDs        []string
}

func (s *Service) PlanRound(ctx context.Context, cmd PlanRoundCommand) (RoundPlan, error)
```

输入范围必须恰好一个仓库，并且该仓库已在本 Issue 的固定范围内；这是 B10 的计划与验收校验范围，不是 `rounds` 行上的单仓列。同一轮覆盖多个仓库时，调用方按仓库各调用一次并复用同一 `RoundID`；`RoundID` 留空时新建轮次行。任务依赖由仓内 DAG 能力校验，跨仓前驱由 B11 在已有任务身份上扩展。方法在同一短事务中创建或复用本 Issue 的轮次行、创建一条不可变 `plan_revisions`、按 `is_current` 与 `pointer_revision` 列组写本仓当前指针，再写任务映射与发布责任，不启动执行。规划只产生本地映射，不登记仓库事项。提交顺序与整集合 CAS 见 §4.3，没有延迟外键。`BusinessPlanVersionID` 与预期绑定修订由可信调用或可信服务读取提供；规划阶段允许引用尚未生效的业务版本用于准备，真正派工才要求 effective。冲突返回 `PLAN_REVISION_CONFLICT`，权限未知返回 `AUTHORIZATION_UNCONFIRMED`。

### 3.3 内部边界：execution.Service.Delegate

状态为本次提案，未实现。它完成原子预留后的受控派工。调用方是 coordinator 派工工作。

```go
type DelegateCommand struct {
    PlanRevisionID  string
    TaskID          string
    WorkerRef       string
    RoomLinkID      string
    CapacityRequest CapacityRequest
    DispatchOperationID string
    BusinessPlanVersionID string
    ExpectedBusinessPlanBindingRevision int64
    ExpectedPlanSetRevision int64
}

func (s *Service) Delegate(ctx context.Context, cmd DelegateCommand) (Attempt, error)
```

方法先在一个短事务中登记 Attempt、占用 Worker、预留容量并写入 `execution_operations`，事务提交后才准备环境。首次为该 `(issue_id, repository_id)` 真实委派时，同一事务创建或复用 `repository_issues` 行，并把本次 Attempt 归属到该事项；事项的仓库必须等于任务所属计划修订的仓库。锁序、业务版本门禁与容量 scope 锁见 §5.1、§5.2 与 §5.7：先按统一锁序读 Issue 当前 effective 业务版本、round 绑定修订与完整当前计划集合，再锁任务行核全部历史替补许可，最后在 capacity scope 锁内统计该 scope 的全部未释放占用。实际调用上游前再次核验计划、权限、预算、容量、租约与 Worker 状态。`DispatchOperationID` 由服务端分配，同一逻辑操作重试复用。`RoomLinkID` 可选，写到 Attempt 的 `room_link_id`，引用 B07 的 `repomesh_issues.issue_room_links`。

### 3.4 内部边界：execution.Service.Observe

状态为本次提案，未实现。它读取并规范化上游观察、host-executor 观察和产物事实。调用方是 coordinator 观察工作与 reconcile。

```go
func (s *Service) Observe(ctx context.Context, attemptID string) (AttemptObservation, error)
```

返回原始状态、规范化状态、观察来源、观察时间、版本或 ETag、产物摘要与缺失证据。观察只追加，不原地覆盖旧观察。`submitted` 与 `completed` 都不自动触发业务采纳。

### 3.5 内部边界：execution.Service.RequestStop

状态为本次提案，未实现。它登记停止请求并驱动实际停止核查。调用方是受控维护入口或协调器停派工工作。

```go
func (s *Service) RequestStop(ctx context.Context, attemptID, reason string) (StopOperation, error)
```

停止请求先写本地 `stop_requested_at` 与稳定操作身份，再调用上游取消和 host-executor 停止动作。返回 `requested`、`stop_observed`、`stop_unconfirmed` 三种结果之一。只有真实进程停止或写能力被撤销的证据齐全，才能从 `stopping` 前进到 `stopped`。停止请求本身不释放 Worker 或容量。

### 3.6 内部边界：execution.Service.Reclaim

状态为本次提案，未实现。它在停止与写能力撤销核查后回收资源。调用方是 coordinator 回收工作。

```go
func (s *Service) Reclaim(ctx context.Context, attemptID string) (ReclaimObservation, error)
```

回收按资源种类分别记录。容器、目录、网络、卷和 Worker 占用分别有已释放、释放未知和泄漏三种结果。释放未知时保留占用，不把容量立即分给其他任务。历史 Attempt 记录在证据和必要产物保存完成后回收。

### 3.7 内部边界：host-executor 有限动作

状态为本次提案，未实现。host-executor 只接受经过核验的有限动作，不开放任意宿主命令或挂载入口。建议动作清单如下。

| 动作 | 输入 | 结果与不变量 |
| --- | --- | --- |
| `PrepareAttempt` | attemptId、环境模板版本、仓库快照引用、资源类、限额 | 只创建已登记资源；返回实际资源标识与观察 |
| `StartAttempt` | attemptId、启动命令标识、只读输入引用 | 启动前再核身份与版本；返回已启动或启动未知 |
| `ObserveAttempt` | attemptId、资源标识 | 返回进程、容器、目录、网络的原始观察 |
| `RequestStop` | attemptId、原因、稳定操作编号 | 只请求停止；实际停止另观察 |
| `RevokeWriteCapability` | attemptId、能力种类 | 撤销 Git、存储或控制面写能力；返回撤销证据或未知 |
| `ReclaimAttempt` | attemptId、资源标识、回收清单 | 逐项回收并返回逐项结果；未知项保留占用 |
| `VerifyStopped` | attemptId、资源标识 | 核验进程、容器与写能力；不能只读取消元数据 |

传输编码不在本批冻结。可以按实施条件选择内部队列、受限 socket 或受控 HTTP，但都必须携带稳定操作编号、attempt 身份、能力版本与证据摘要。宿主执行器不持有模型 Key，不读取 Issue 正文，不决定业务采纳。

## 4. 数据表设计

以下表名为本次提案，未实现，全部位于候选 schema `repomesh_execution`。本章不新增通用 operation、job 或 event 表，也不把表写成「登记到 foundations 的共享框架」。各业务域保留自己的操作回执；只有[首批持久化设计](../current/backend-first-batch-persistence.md)第 3 节已经采用的 DurableWork 机制可以复用于后台工作。所有外部引用使用不透明文本，不把上游短名当本地主键。若任务或 Attempt 需要房间归属，只加 `room_link_id` 外键引用 B07 的 `repomesh_issues.issue_room_links`，不建第二套 room 表，也不在本地复制 room 可用性观察。

本章所有工作范围外键一律指向 `repomesh_issues.repository_scopes(work_issue_id,repository_id)` 这个普通唯一键；本地列名仍写 `issue_id` 与 `repository_id`，物理顺序对应 `work_issue_id` 与 `repository_id`。Issue 归属指向 `repomesh_issues.issues(project_id,id)`，主 ChangeSet 归属指向 `repomesh_issues.changesets(project_id,issue_id,id)`。不引入多态 kind 常量去引用「可能是内容范围」的裸键。

### 4.0 repomesh_modelbudget.windows

物理表：`repomesh_modelbudget.windows`

用途是保存项目真实运行请求的 UTC 日额度窗口。B05 只提供不可变政策，不再为延期的模型测试预铺账本；本表由 B09 模型调用、B10 派工与停止决定在统一预算协议下写入，B11 只读取累计消费依据。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| `project_id` | text | 是 | 外键到 `repomesh_projects.projects(id)`，与窗口起点组成主键。 |
| `start_utc` | timestamptz | 是 | UTC 日零点；主键第二部分。 |
| `end_utc` | timestamptz | 是 | 恰好 `start_utc + interval '24 hours'`。 |
| `request_limit` | integer | 是 | 正整数；同一窗口只降不升。 |
| `reserved` | bigint | 是 | 默认 0、非负；已经取得本地执行资格但尚未终结的数量。 |
| `consumed` | bigint | 是 | 默认 0、非负；已经进入可能外发边界的数量。 |
| `revision` | text | 是 | 计数或限制变化时推进。 |

主键 `(project_id,start_utc)` 保证同一项目同一 UTC 日只有一行。政策 ID 和版本不进入主键，切换政策仍累计到同一项目窗口；每个消费记录另外保存实际政策版本。`start_utc` 用 UTC 规范表达式校验，不能依赖数据库会话时区。窗口不加 `reserved + consumed <= request_limit` 的 CHECK：当政策下调到低于历史消费时，历史不能被篡改，剩余量投影为 `max(0, request_limit - reserved - consumed)`，新预留被拒绝。

所有额度变化先锁项目，再锁本窗口。预留与对应业务责任同事务提交；进入 `may_have_sent` 时把 reserved 转为 consumed；只有有证据确定未进入可能发送阶段才能释放 reserved。超时、租约到期、unknown、停止请求或本地回收都不能退款。GET 不创建窗口；尚无窗口返回 unavailable，而不是伪造全额余额。

### 4.1 repomesh_execution.rounds

物理表：`repomesh_execution.rounds`

用途是保存 Issue 内业务轮次的身份与最新摘要，完整转换历史放在 §4.8 的 `execution_records`。写入者是 `PlanRound`、B11 的 `OpenNextRound`、`CloseRound` 与恢复工作。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| `id` | text | 是 | 主键，永不复用。 |
| `project_id`、`issue_id` | text | 是 | 复合外键到 `repomesh_issues.issues(project_id,id)`；Issue 归属不依赖任何房间。 |
| `round_index` | integer | 是 | Issue 内递增，`CHECK (round_index >= 1)`；`UNIQUE(issue_id,round_index)` 防重复轮号。 |
| `purpose` | text | 是 | `initial`、`repair`、`diagnostic`、`environment_recovery`。 |
| `state` | text | 是 | `planned`、`active`、`draining`、`applying`、`recovering`、`closed`、`cancelled`。 |
| `business_plan_version_id` | text | 是 | 本次执行依据的业务计划版本；复合外键 `(project_id,issue_id,business_plan_version_id)` 到 `business_plan_versions(project_id,issue_id,id)`。 |
| `business_plan_binding_revision` | bigint | 是 | 默认 0，只增；显式业务版本变更时递增，普通 `OpenNextRound` 不递增。 |
| `plan_set_revision` | bigint | 是 | 默认 0，随完整多仓当前计划集合变化递增，供整集合 CAS。 |
| `state_revision` | bigint | 是 | 默认 0，每次合法转换递增；`execution_records` 的 `round_transition` 记录转换前后值。 |
| `outcome` | text | 否 | 收尾结论，取值同 B11 §2.2；仅收尾转换填写。 |
| `last_transition_record_id`、`last_stop_record_id` | text | 否 | 最近转换记录与最近停止决定，分别以常量 `record_kind` 列组成复合外键引用 §4.8。 |
| `stop_reason`、`stop_decided_at` | text、timestamptz | 否 | 最新有效停止摘要；多次停止逐条留在记录表，摘要不清除旧决定。 |
| `current_combination_id` | text | 否 | 当前固定组合；与同 Issue 的常量 `combination` 子型组成复合外键引用 `change_set_versions`，空表示尚未选定。 |
| `combination_selection_revision` | bigint | 是 | 默认 0，只增；选择或复用组合时推进，选择历史在 §4.8。 |
| `created_at`、`closed_at`、`closed_reason` | timestamptz、timestamptz、text | 是、否、否 | 创建时间与非敏感收尾摘要。 |

唯一约束为 `UNIQUE(issue_id,round_index)`、`UNIQUE(id,issue_id)`、`UNIQUE(id,project_id,issue_id)`；后两个供本节与 B11 的复合外键引用。轮次是 Issue 内业务轮次，不按仓库复制，本表不加 `repository_id` 或单条 `current_plan_revision_id`。一轮的当前安排是 `plan_revisions` 中 `is_current` 行的完整集合。

轮次状态图沿用原 B11：`planned → active 或 cancelled`；`active → draining、applying、recovering、closed、cancelled`；`draining → applying、recovering、closed、cancelled`；`applying → recovering、closed、cancelled`；`recovering → applying、closed、cancelled`；`closed` 与 `cancelled` 无后继。每次转换与摘要同事务提交，转换记录保存转换前后的 `state_revision`，`UNIQUE(round_id,transition_revision)` 防重复。

业务计划绑定规则：`planned` 轮次可以引用一个尚未生效的业务计划版本，用于准备和登记激活目标；真正 `Delegate` 必须核该版本已生效且当前指针一致。已有有效版本时，跨轮默认复用原版本。业务版本变更只能在显式激活事务里完成，同时提升 `business_plan_binding_revision` 并记录决定，不能借普通开新轮换掉执行依据。历史 plan、task 与 Attempt 各自保存实际依据版本，改当前指针不改写过去。

索引：`(issue_id,round_index DESC)`；部分索引 `(state,created_at) WHERE state NOT IN ('closed','cancelled')`。Graph 的 Evaluate、Close 与 Delegate 先锁本行，再按 `plan_set_revision` 与完整当前计划集合判断，不任取单条。

### 4.2 repomesh_execution.repository_issues

物理表：`repomesh_execution.repository_issues`

用途是保存 Issue 内每个仓库的稳定工作身份（Repository Issue）。它与 B06 的 `repository_scopes` 工作行不是同一个东西：范围行说明本 Issue 允许涉及哪些仓库，创建后不可变；本表记录真实开始过的仓库工作，有自己的生命周期。写入者是 `Delegate`（首次登记与复用）与 Issue 终结或明确停用入口；B11 复用同一身份，B07 的 Leader 投影按 `(issue_id, repository_id)` 读取本表的 id，不新增第二套仓内事项表，也不把选仓范围直接当工作身份。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| id | text | 是 | 主键，永不复用 |
| project_id | text | 是 | 项目归属 |
| issue_id | text | 是 | Issue 归属，与 project_id 一起引用 B06 的 `issues(project_id, id)` |
| repository_id | text | 是 | 仓库归属，与 issue_id 一起引用 B06 工作范围 `repository_scopes(work_issue_id, repository_id)` |
| state | text | 是 | `active`、`closed` |
| created_at | timestamptz | 是 | 首次真实委派登记时间 |
| closed_at | timestamptz | 否 | 停用时间 |
| closed_reason | text | 否 | 非敏感停用原因 |

唯一约束为 `(issue_id, repository_id)`，覆盖全历史，不允许停用后再建一条；另给 `(id, issue_id, repository_id)` 唯一键供 §4.5 Attempt 的复合外键引用。登记时点沿用[首批持久化设计](../current/backend-first-batch-persistence.md)第 1 节的采用语义：创建 Issue、仅选择仓库、只建立计划修订都不登记；首次为该仓真实委派时由 §3.3 的派工事务创建该行。

生命周期规则如下。同一 Issue 的后续轮次、重试与再次委派复用同一行，普通轮次收尾只结束本轮，不自动把本行置为 `closed`。默认只有在 Issue 终结或明确停用该仓事项时才停用；如果允许显式重新启用，必须复用原 id 并把 `state` 从 `closed` 改回 `active`，不插入第二行。停用只表示不再为该事项登记新工作，不证明上游进程已停止、资源已释放或房间已关闭；这些事实各自记录。Issue 完成后新增工作另建关联 Issue，不在本表扩写出第二段生命周期。

应用与恢复状态机沿用原 B11 §3.2：`pending → publishing`；`publishing → applied、failed、unknown`；`applied → readback_ok、readback_mismatch、unknown`；`readback_mismatch、unknown、failed → readback_ok、readback_mismatch、unknown`。放行条件是显式完成集合 `application_state='readback_ok' AND recovery_state IN ('none','recovered')`，不写成「不是 open 或 unknown」，避免把 `recovering` 误包含。应用历史如需完整序列，写 §4.8 的 `plan_observation`，引用具体修订。

保留 `UNIQUE(plan_revision_id,local_key)`、`UNIQUE(plan_revision_id,upstream_task_id)`、`UNIQUE(id,issue_id,repository_id)`；新增 `UNIQUE(id,round_id,issue_id,repository_id)` 供 §4.5 使用。首次创建顺序是 task → Attempt → 回填 `current_attempt_id`，全部立即外键，不需要延迟约束。状态推进按任务行锁与当前代次 CAS，上游 `completed` 不能直接写成 `accepted`。索引 `(round_id,plan_revision_id,state)`。任务本身不携带仓库事项 id；首次实际委派时由 Attempt 指向该仓事项，同一事项可跨轮次拥有多个任务。B11 的跨仓边与结果采纳只引用本表已经存在的任务身份。

| `may_have_started_at` | timestamptz | 否 | 只能从空变为非空。 |

### 4.6 repomesh_execution.resource_reservations

物理表：`repomesh_execution.resource_reservations`

用途是原子预留 Attempt 所需的 Worker 与各类资源，并逐项记录释放、未知与泄漏。写入者是 `Delegate` 与 `Reclaim`。原 `worker_leases` 与 `resource_reservations` 合并为一张表，`resource_kind='worker'` 承载原 Worker 排他。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| `id` | text | 是 | 主键，永不复用；新占用一定新建行与更高 `generation`。 |
| `attempt_id` | text | 是 | 复合外键到 `attempts(id,task_id,issue_id,repository_id)` 的 `id` 列组；占用属于同一次 Attempt。 |
| `resource_kind` | text | 是 | `worker`、`capacity_slot`、`clone_dir`、`container`、`network`、`volume`。 |
| `resource_key` | text | 是 | 稳定资源键；worker 键是经过实例与团队作用域消歧的 Worker 引用，不能只用显示名。 |
| `capacity_scope_kind`、`capacity_scope_id`、`slot_index` | text、text、integer | `capacity_slot` 必填 | 容量的有型作用域与槽号；`capacity_scope_kind` 取 `global`、`project`、`team`，非容量子型三列全 NULL。 |
| `state` | text | 是 | `reserved`、`active`、`released`、`release_unconfirmed`、`leaked`。 |
| `generation` | bigint | 是 | 预留代次。 |
| `reserved_at`、`released_at` | timestamptz | 是、否 | 预留与释放时间。 |
| `owner_manager` | text | 是 | 生命周期管理者，只允许 controller、host_executor 等已明确角色；同一资源不能两头管理。 |

约束：`resource_key` 必须等于由 `capacity_scope_kind`、`capacity_scope_id`、`slot_index` 按不可变函数构造的规范编码，容量子型才能被唯一索引与计数查询命中；`UNIQUE(attempt_id,resource_kind,resource_key,generation)`；部分唯一索引 `UNIQUE(resource_kind,resource_key) WHERE state IN ('reserved','active','release_unconfirmed','leaked')`（leaked 也占位，防止把泄漏槽当空位复用）；部分唯一索引 `UNIQUE(attempt_id) WHERE resource_kind='worker' AND state <> 'released'`；索引 `(attempt_id,state,resource_kind)` 与 `(state,reserved_at) WHERE state IN ('release_unconfirmed','leaked')`。

容量分配与降额规则（修复原「只锁选中槽位」缺口）：分配前先按规范化 scope 排序取得各 capacity scope 的事务 advisory lock，再读取适用上限与该 scope 全部未释放 reservation 数量，包含编号高于新上限的槽、`reserved`、`active`、`release_unconfirmed` 与 `leaked`。只有「全量占用加本次需求不超过上限」时才挑选可用槽，并由部分唯一索引兜底。降额或容量政策切换走同一把 scope 锁或明确版本 CAS；不清理旧占用，不新增容量表。跨 global、project、team 的锁一次全部取得或整笔回滚。拿到 scope 或 resource 锁之后不得回拿上层业务锁。单个 resource key 的 advisory lock 继续保护 Worker、目录、容器、网络与卷。示例：容量从 4 降到 2 且槽 3、4 仍在用时，新的第 3 笔分配必须失败，而不是只看槽 1、2 是否空闲。

每个 Attempt 的首次登记必须同事务包含一条 Worker 与全部适用容量 reservation，由受控写入口与提交约束验证，不允许只提交半套预留。租约超时或 `unknown` 不自动释放；`leaked` 回到 `released` 必须补实际回收观察。环境准备在事务外，准备失败只能释放有证据未使用或已经实际释放的资源。

| `baseline_observation` | `fixed_sha`、`target_branch`、`repository_source_ref`、`binding_revision`；`round_id` 与 `repository_id` 非空，`attempt_id` 与 `plan_revision_id` 为空，可以在尚无 Attempt 时登记受控固定基线证据。 |

普通唯一键与部分索引：`UNIQUE(id,record_kind)`、`UNIQUE(id,round_id,record_kind)`、`UNIQUE(id,issue_id,round_id,record_kind)`、`UNIQUE(id,issue_id,repository_id,record_kind,artifact_kind)`、`UNIQUE(id,attempt_id,issue_id,repository_id,record_kind)`、`UNIQUE(id,project_id,issue_id,business_plan_version_id,record_kind,plan_action)`、`UNIQUE(plan_operation_id,project_id,issue_id,business_plan_version_id,plan_action)`；部分唯一索引 `UNIQUE(candidate_id,review_revision) WHERE record_kind='candidate_review'`、`UNIQUE(round_id,transition_revision) WHERE record_kind='round_transition'`、`UNIQUE(round_id,selection_revision) WHERE record_kind='combination_selection'`、`UNIQUE(plan_operation_id) WHERE record_kind='business_plan_decision'`、`UNIQUE(activation_operation_id,round_id,repository_id) WHERE record_kind='business_plan_target'`。部分唯一索引不能充当外键目标，因此所有跨行引用都使用上面的普通复合唯一键，引用方带常量判别列。

查询索引：`(attempt_id,recorded_at,id)`、`(round_id,record_kind,recorded_at,id)`、`(candidate_id,review_revision DESC) WHERE record_kind='candidate_review'`、`(artifact_id,recorded_at DESC,id) WHERE record_kind='retention'`、`(attempt_id,capability_kind,capability_version,observed_at DESC) WHERE record_kind='write_revocation'`。最近状态用视图或 window query 读取，不新增物理当前表。

写入与清理规则：每种记录只由对应受控用例写入；`candidate_review` 写入口先锁 Issue → round → candidate，不能无锁追加接受或撤回判断；正式准入仍单独在 B11 的 `result_admissions`。root 行 append-only，回收与删除只追加 `retention`；正文清理走受限白名单，把 `evidence`、`reason`、`detail` 或业务计划操作输入置空并写 `redacted_at`，同时保留身份、归属、固定 SHA、决定值与最小未核证据。清理不能给旧计划重新执行或换键重发。

### 4.9 repomesh_execution.change_set_versions

物理表：`repomesh_execution.change_set_versions`

用途是保存 ChangeSet 的两个不可变业务版本子型：某次正式提交的固定产物 Candidate，以及 Manager 一次选定的固定仓库版本集合 Combination。它们同属 ChangeSet 的版本事实，共用稳定 ID、归属、创建人、时间与规范化摘要；本表不是任意版本对象注册表，不加入 plan、PR、消息或预算 kind。B10 首次单仓正式提交就需要 Candidate，B11 复用并消费组合；schema 位置不把业务采纳权交给执行 Adapter。

公共列：`id`（主键）、`version_kind`（`candidate`、`combination`）、`project_id`、`issue_id`、`changeset_id`、`origin_round_id`、`created_by`、`created_at`、`schema_version`、`canonical_digest`、`source_operation_id`、`canonical_input bytea`、`redacted_at`。`UNIQUE(source_operation_id)` 保证同一逻辑提交只有一条版本；重复键比较 schema 与规范化输入，同键异输入冲突，比较器版本不进入唯一键。`archive` 时保留身份、摘要、归属与来源决定，受限清理只清可清正文并写 `redacted_at`。

Candidate 专用列：`repository_id`、`source_task_id`、`source_attempt_id`、`source_artifact_id`、常量 `artifact_record_kind='artifact'`、`artifact_version_kind`、`fixed_sha`、`artifact_digest`、`submitted_by`、`submitted_at`。`(source_attempt_id,source_task_id,origin_round_id,issue_id,repository_id)` 复合外键到 `attempts` 五列唯一键；`(source_artifact_id,source_attempt_id,issue_id,repository_id,artifact_record_kind)` 复合外键到 `execution_records` 产物根唯一键；`(issue_id,repository_id)` 引用 B06 工作范围。`artifact_version_kind='git_commit'` 时 `fixed_sha` 非空且 `artifact_digest` 为空；`content_digest` 时反向。正式提交未接受仍创建 Candidate，最新初审从 §4.8 的 `candidate_review` 读，本表不改状态。

Combination 专用列：`selection_purpose`（`formal`、`diagnostic`）、`selection_basis_ref`、`validation_plan_revision_id`、`members jsonb`、`member_count`、`member_digest`、`applied_max_combination_members integer`、`applied_max_combination_snapshot_bytes bigint`、`combination_limit_config_revision text`。`validation_plan_revision_id` 用 `(validation_plan_revision_id,origin_round_id,issue_id)` 复合外键到 `plan_revisions` 的三列唯一键，表示初次组合选定的工作与验收上下文；跨轮复用组合不改写它。三个 applied 限制列创建时冻结、均为正非空，值是部署载入时对两个有效数值与限制 schema 规范化得到的内容指纹加实际数值，不引用新配置表；candidate 分支三列为空。

成员快照是唯一允许的无约束 JSON，形状封闭为 `{schemaVersion:1,members:[...]}`，每项只允许候选成员 `{repositoryId,sourceKind:"candidate",candidateId,fixedSha,acceptedReviewId}` 或基线成员 `{repositoryId,sourceKind:"baseline",baselineObservationId,fixedSha}`。formal 组合的 `acceptedReviewId` 必填，diagnostic 可为空。非代码 Candidate 保留完整业务身份与固定摘要，不为套用 Git 组合伪造 SHA；扩大成员到非代码版本须显式升 schemaVersion 并补校验。

`validate_change_set_combination` 是 BEFORE INSERT 专用触发器，任何一步失败都整笔回滚，不存在可对外引用的半套组合：先锁所属 Issue 与 origin round，核有效业务计划版本、完整 current 计划集合与 `validation_repository_ids`，用 `jsonb_to_recordset` 展开成员比较精确集合，并逐项核对同 Issue 工作范围；再按 `candidateId` 排序 `FOR UPDATE` 锁候选版本，按 `baselineObservationId` 排序 `FOR KEY SHARE` 锁基线观察，核对同项目、同 Issue、同 ChangeSet、同仓库与固定 SHA 完全相等；formal 组合读取每个候选在当前适用计划与范围内的最大 `review_revision`，必须是 accepted，且 `acceptedReviewId` 恰好指向该记录；最后计算规范化 `member_count` 与 `member_digest`，一次插入完整不可变行。候选初审写入口同样先锁 Issue → round → candidate。

跨轮复用规则（R10-02）：组合版本保留 `origin_round_id`，不得改成新轮。新一轮复用组合时在 §4.8 追加新的 `combination_selection` 记录，保存本次 `selection_validation_plan_revision_id` 与 `evaluated_plan_set_revision`，在 round 锁内读取本次完整 current 计划集合并比较组合成员的精确仓库集合等于该验证计划的 `validation_repository_ids`；不同仓库集合或 SHA 必须新建组合，同集合同版本而验收、环境或数据变化只新增 selection 与 verification 上下文，不改旧组合。`candidate_review` 的适用性按本次计划与范围重新核验，旧 `acceptedReviewId` 不是永久许可。同一 Candidate 可进入多个组合，同一组合可跨轮复验，一轮可先后选择 C1、C2。

唯一与索引：`UNIQUE(id,issue_id,changeset_id,version_kind)`、`UNIQUE(id,issue_id,version_kind)`、`UNIQUE(id,issue_id,changeset_id,repository_id,version_kind)`；索引 `(changeset_id,version_kind,created_at DESC,id)`、`(source_attempt_id) WHERE version_kind='candidate'`、`(issue_id,repository_id,created_at DESC) WHERE version_kind='candidate'`。组合成员查询用只读视图投影 `jsonb_to_recordset(members->'members')`，按 Candidate 找组合用 `jsonb_path_ops` 包含查询后精确展开，不增加隐藏成员表。候选与组合行禁止 UPDATE payload 与 DELETE；判断变化追加 §4.8 记录。

### 4.10 repomesh_execution.business_plan_versions

物理表：`repomesh_execution.business_plan_versions`

用途是保存已采用的业务计划版本、自动许可、逐目标激活与生效事实。它是 ADR-0003 与 ADR-0015 要求、原 20 张提案没有建模的业务前置，不是上游 `plan_revisions` 的改名。写入者是 Issue 计划用例与可信协调器；B11 跨轮与业务变更只读取和引用本表，不另建权威。

| 字段组 | 列与约束 |
| --- | --- |
| 身份 | `id` 主键；`project_id`、`issue_id` 非空，复合外键到 `repomesh_issues.issues(project_id,id)`；`version_index bigint CHECK (>0)` 在同 Issue 锁下分配，允许间隙，不用无锁 `MAX+1`；`base_plan_version_id` 可空，用 `(project_id,issue_id,base_plan_version_id)` 复合自 FK，禁止自环与祖先环；`created_by`、`created_at` 非空。`UNIQUE(project_id,issue_id,id)` 是 B06 Issue 指针外键的目标，`UNIQUE(issue_id,version_index)` 防重复编号。 |
| 提案原操作 | `proposal_operation_id` 全期唯一；`proposal_schema_version`、`proposal_canonical_input`、`proposal_exact_input`、`proposal_committed_at`、`proposal_removed_at`。原操作结果就是本版本的身份、归属、编号与时间；同键同输入返回原结果，异输入冲突，不按当前许可状态重建回执。 |
| 业务内容 | `plan_schema_version`、`canonical_plan`（业务目标、范围、依赖、验收与上限的封闭正文，受限清理后可为空）、`plan_digest`（清理前必填，清理后可空）、`scope_repository_ids text[]`（非空、无重复、逐项核 B06 工作范围）、`acceptance_basis` 与其稳定版本、`repair_round_limit`、`diagnostic_round_limit`、`environment_recovery_limit`（非负整数），以及确切政策列：`budget_kind='budget'`、`budget_policy_id`、`budget_policy_version`、`budget_scope='project_model_runtime'` 用 `(budget_kind,budget_policy_id,budget_policy_version,budget_scope)` 复合外键到 `repomesh_sources.policy_versions(policy_kind,id,version,scope_kind)`；`time_kind='time'`、`time_policy_id`、`time_policy_version` 用 `(time_kind,time_policy_id,time_policy_version)` 复合外键到 `policy_versions(policy_kind,id,version)`。正文、范围、验收、上限、政策引用与 base 提交后不可更新，改内容必须新建版本。 |
| 当前摘要 | `current_permission_record_id` 指最近一次确定的 `evaluate_permission` 决定，`authorized` 与 `rejected` 都是有效事实；`current_activation_record_id` 指 `begin_activation`；`effective_activation_record_id` 指 `confirm_effective`。三列都可空，且必须同 project、Issue、版本；`permission_revision`、`activation_revision bigint` 默认 0、只增。摘要只是已提交记录的索引，不能在没有来源记录时直接写 `authorized` 或 `effective`。 |
| 两阶段计划责任 | `plan_work_id` 全期唯一；`plan_work_stage` 取 `permission` 或 `activation`；`plan_work_state` 取 `pending`、`ready_for_activation`、`applying`、`blocked`、`reconciling`、`unknown`、`effective`、`rejected`、`cancelled`；`pending_permission_operation_id`（permission 阶段非空，指向本次自动许可操作，可扫描恢复）；`activation_operation_id`（activation 阶段非空，等于 begin 决定的操作身份）；`claim_generation`（默认 0）、`lease_owner`、`lease_until`、`next_run_at`、`blocked_reason`。未领取时 `lease_owner` 与 `lease_until` 可空，不能要求一个尚未领取的责任行必须带租约；permission 阶段 `activation_operation_id` 必须为空，activation 阶段必须非空。authorized 提交后先停在 `plan_work_stage='permission'` 与 `plan_work_state='ready_for_activation'`，只有 `begin_activation` 与完整目标集合、activation operation 同事务提交后才切到 activation 阶段。 |
| 清理 | `removed_at`、`redacted_at` 可空；敏感正文与操作原输入可清空，身份、提案键、base、范围、政策与上限关联、许可与生效决定、外部核查责任保留；移除后不能再次激活。 |

约束与裁决修复：

1. Issue 级激活排他（BP-02）：部分唯一索引 `UNIQUE(issue_id) WHERE plan_work_stage='activation' AND plan_work_state IN ('applying','blocked','reconciling','unknown','pending')`。只有已经取得外部写权的 activation 阶段独占 Issue；permission 阶段与 `ready_for_activation` 不占独占，多个候选版本可以同时等待分析，符合 BP-03。`begin_activation` 在 Issue 锁下检查该 Issue 全部版本的未终结 activation，同原 activation 恢复走原键，其他版本 begin 冲突或保持明确待核；`unknown`、权限暂不可确认与部分成功都保留占有，只有已生效完成或按外部恢复协议证明旧流程不再可能继续写才离开占有集合。Delegate 与技术应用在 Issue 锁下检查该占有与其冻结受影响目标集合，受影响上游 Project 持续停新派工。
2. 首次许可 unknown 与准备状态（BP-03）：提案事务或首次自动评估事务即写 `plan_work_id`、`plan_work_stage='permission'`、稳定 `pending_permission_operation_id` 与 generation、next_run 字段（未领取时租约两列留空）；权限读取失败、超时或重启后按原 pending operation 继续核查，不写假 `rejected`。authorized 提交后保持 permission 阶段的 `ready_for_activation`，允许尚未构造 activation 目标的准备窗口；明确拒绝写 `plan_work_state='rejected'` 终态并终结本次责任，后来重新评估使用新逻辑 operation，旧决定保留。
3. 同版本后续技术安排（BP-01）：本表只表示业务版本生效证据，不把首次激活的目标集合当成后续所有轮次的派工白名单。同版本内 `OpenNextRound` 可创建新技术修订，其准入按 §5 的「同版本技术应用门禁」核 effective 版本、round 绑定、完整 current 集合、本次真实 readback 与现有上限；只有复用旧来源版本时才需要本次激活的 `verify_unchanged` 关系。
4. 再次外部写需要新技术修订（BP-04）：旧技术修订的应用身份不可改写。旧操作 unknown 时只能继续原操作核查；旧流程核清后确实需要再次写相同图内容时，新建技术 `plan_revisions` 身份并生成自己的应用身份，业务版本无需改变，旧行与旧外部操作保留。
5. 决定引用（BP-05）：`current_permission_record_id` 指向最近一次确定的 `evaluate_permission` 记录，`authorized` 或 `rejected` 都可，最新是拒绝时不能保留旧 authorized 摘要；`current_activation_record_id` 指向 `begin_activation`；`effective_activation_record_id` 指向 `confirm_effective`。`begin_activation` 的 `cause_permission_record_id` 必须指向同版本且决定为 authorized 的许可记录；后续重新许可不改旧 begin 的历史依据。这些引用使用 §4.8 的普通复合唯一键，不用部分唯一索引充当外键目标。

仓库内 DAG 不复制到本表；`scope_repository_ids` 由触发器逐项核对工作范围，不当作任意 entity 列表。循环上限与技术换图、改名、新轮无关，累计计数由真实 round 历史按 purpose 计算，不新增第二份消费账本。预算或时限权威尚未可采用时，新版本保持未获准并写 blocked 责任，不伪造 `authorized`。Go 内部提案为 `PlanRound`、`Delegate`、`OpenNextRound` 明确业务版本 ID 与预期修订，或由可信服务读取；不改已采用的浏览器 API。

## 5. 事务与恢复

统一锁序（所有分配、应用、释放与配置生效路径必须同序）：principal 的 binding、session、account → project 与必要 connection → conversation（需要时）→ Issue → 业务计划版本按 id（生效事务涉及新旧版本时先收齐 ID 再排序）→ rounds 按 id → 当前 plans 按 repository_id 与 plan id → tasks 按 id → Attempt → `change_set_versions` 候选按 id → capacity scope 事务 advisory lock 按规范化 scope 排序 → 具体 resource_key 锁按 kind 与 key 排序 → reservation、operation、record 具体行。容量 scope 锁位于 Candidate 之后、resource key 之前；同层按规范化值排序。拿到 capacity scope 或 resource key 锁之后不得回拿上层业务锁；修改容量若不需要上层对象可以从 scope 层开始。操作原结果预查只做只读最小定位，不能先锁 record 或 decision 再反拿 Issue。外部权限观察在事务外，锁后核主体代次、仓库集合与范围修订。

### 5.1 原子派工与启动前核验

派工先在一个短数据库事务内完成候选检查、业务版本门禁、Attempt 登记、Worker 占用与容量预留。首次为该仓真实委派时，同一事务创建或复用 `repository_issues` 行并写进 Attempt。业务门禁按 §5.2 执行；计划或修订变更先锁 `rounds` 行，核 `business_plan_binding_revision` 与完整 current 集合及 `plan_set_revision`，再写新修订与新指针。容量按 §5.7 在 scope 锁内统计全部未释放占用后选槽。竞争同一 Worker 或最后一个容量槽位的请求不能同时成功。事务提交后才准备独立环境；实际启动前再次核验计划集合、权限、预算、容量、租约、Worker 状态与写能力版本，准备期间发生撤权、暂停或取消时不得继续启动。

### 5.2 同版本技术应用门禁（BP-01）

业务版本的生效证据与同版本后续技术安排准入分开判断。首次或变更业务版本的 `confirm_effective` 仍严格核该 activation 的冻结全集，不放宽。同一 effective 业务版本内，`PlanRound` 与 `OpenNextRound` 照常创建新技术修订并走 `plan_revisions` 的应用与真实读回；这类 `plan_observation` 保存 `business_plan_version_id`、round 绑定修订、完整 `plan_set_revision` 与本次技术应用身份，不强迫填写 activation operation 或 target record。

`Delegate` 核 Issue 当前 effective 版本、round 当前业务版本与绑定修订、完整 current 技术计划集合、该技术计划本次真实的 `application_state='readback_ok'` 与 `recovery_state IN ('none','recovered')`、当前权限与原有上限。复用旧来源版本时另核本次 activation 的 `verify_unchanged` 关系；不能把所有后续新安排都要求存在于首次 activation 的目标快照里。业务版本 V1 首次生效后，只修复受影响仓库而新增的 R2 技术安排只要在 V1 范围与上限内、应用并读回成功，就可以派工，V1 与首次 activation 的目标集合不变。

### 5.3 响应丢失与同键异参

上游派工响应丢失时先按 `external_operation_id` 查原操作，不生成第二个 Attempt。同键不同仓库、任务或 Worker 返回冲突。host 动作响应丢失时先查 `execution_operations` 与原资源状态，不重复创建目录、容器或网络。取消响应丢失时保留 `stopping`，先核实际停止，再决定是否重试同一操作。`may_have_sent` 之后不换号、不重建启动操作。

### 5.4 崩溃与重启

协调器重启后从持久 Attempt、预留、操作与记录重建责任。计划责任按本轮 `is_current` 的完整集合恢复，不把某一条指针当成整轮计划。未启动的预留可以按条件重试；已 `may_have_started` 的 Attempt 必须先观察真实状态。租约到期只表示可以重新领取核查任务，不表示旧进程已停止。业务计划的两阶段责任按 §4.10 恢复：permission 阶段扫描原 pending operation，activation 阶段按原 activation operation 与逐目标事实核查；数据库无法确认旧写能力失效时保持 `unknown` 并保留占用。

### 5.5 停止、写能力撤销与回收

停止分四步。第一，登记停止请求与稳定操作身份。第二，请求上游取消与宿主停止。第三，分别核验进程停止与 Git、对象存储、控制面写能力撤销。第四，按资源种类回收并逐项记录。任何一步未知都保持占用与未知状态，不自动启动替补，也不把资源分给其他任务。`replacement_allowed` 只有终态且证据齐全才能为 true；容器停止不能代替 Git 撤销，撤销一种能力不能代替其他能力。

### 5.6 迟到结果与证据适用性

旧 Attempt 的观察、产物或上游状态晚到时只追加记录。当前 reconcile 按 `attempt_id`、`claim_generation`、任务与轮次归属判断是否记录为当前尝试的新观察；业务采纳由 B11 的 `result_admissions` 单独决定。迟到结果不能覆盖正式状态、不能解锁当前依赖，也不能作为新 Attempt 已启动的证据。旧组合成员不变，但新的拒绝或失效初审会阻止新的正式启动；既有在途验证保留启动时的实际输入与依据，结果采纳重新判断适用性。

### 5.7 容量降额与全量占用（R10-03）

容量的上限与占用按 scope 聚合，不能只看本次选中的槽号。分配前按规范化 scope 排序取得事务 advisory lock，读取适用上限与该 scope 全部未释放 reservation，包含高于新上限的槽号与 `leaked`、`release_unconfirmed` 状态。只有全量占用加需求不超过上限时才挑选空槽，唯一索引只作兜底。降额或容量政策切换在相同 scope 锁下进行，不清理旧占用，也不新增容量表；跨 global、project、team 的锁一次全部取得或整笔回滚。释放路径同样按 scope 锁统计，不能把 `leaked` 当空位。

### 5.8 删除与保留

Attempt 历史在证据与必要产物保存完成后回收执行资源，业务记录不随容器删除。临时运行材料按项目清理策略处理，归属、版本关联、决定与操作结果在项目存续期保留。正文清理走受限白名单：把 `canonical_plan`、`plan_digest`、`task_set_digest`、`canonical_input`、`payload_digest`、`evidence`、`reason`、`detail` 以及业务计划操作原输入置空并写 `redacted_at`，保留身份、归属、固定 Git SHA、产物内容摘要、政策与范围关联、许可与生效决定、外部操作身份与最小未核证据。清理未知外部动作前必须先核查；清理不得让旧计划重新执行、换键重发或给旧操作新的派工资格；追加 `retention` 保留可用性变化，不用一条「已删」掩盖旧正文仍在。
