# B10 受限宿主下单仓单轮执行（G3／G4）

本批对应施工计划中的 B10，范围是 G3 与 G4。用户能完成的事情有六件。第一，在一个 Issue 明确的一个仓库范围内，由 Manager 或 Leader 组织当前轮次的有限 DAG。第二，把候选就绪任务派给一个 Worker，并在统一短事务中占用该 Worker 与所需容量。第三，在一个独立 Attempt 环境中启动执行，读回真实任务状态和产物。第四，请求停止、撤销写能力并核查资源回收。第五，在响应丢失、协调器重启、租约到期或旧进程仍活时保持未知状态，不启动替补。第六，覆盖 Controller REST、TeamHarness MCP 与共享文件等可达入口，证明不获准动作不会产生业务副作用。

本批限定单仓、单轮，不做 B11 的跨轮换图与跨仓部分应用，不重写仓内 DAG，不建立通用宿主命令平台或 Kubernetes 调度层。单仓是本章计划与验收的校验范围；轮次身份按 Issue 保留，同一 Issue 的后续轮次可由 B11 覆盖多个受影响仓库。

### 1.2 用户能完成什么

用户为某个 Issue 选定一个仓库范围后，可以看到当前轮次的有限任务安排、任务依赖和真实候选就绪状态。用户可以要求停止某个任务或整轮执行，并看到停止请求、实际停止和资源回收分别记录。用户不会看到页面把上游 `completed` 直接显示成业务已验收，也不会在停止证据缺失时看到系统自动启动替补。

### 1.3 依赖

依赖 B09 的可信运行上下文与调用授权，依赖 B06 的 Issue 与主 ChangeSet，依赖 B05 的 request 政策、时间政策与预算观察，依赖 access 的仓库观察，依赖 coordinator 的持久待办领取，依赖 host-executor 的受限宿主动作，依赖选定上游实例的 Controller REST、TeamHarness 与存储。

### 1.4 明确边界

本批不新增浏览器派工写接口，执行状态读取归 B07 的只读投影。它不开放原生 `delegate_task`、Controller 直写、共享文件覆盖或任意容器命令作为产品入口。它不承诺 Controller 已提供全局容量、公平排队、单 Worker 单任务租约或完整 Git 工作副本隔离。它不把租约到期当进程停止，不把取消元数据当资源释放，不把上游 `completed` 当业务通过。仓库事项身份只表达 RepoMesh 内的稳定委派归属，不是上游 Project、Task 或 Attempt 身份；上游引用仍落在 `plan_revisions.upstream_binding`，不引入通用工作项平台。

### 2.2 G3 的两种写方方案

| 方案 | 内容 | 优点 | 代价与风险 |
| --- | --- | --- | --- |
| A 单一正式写方 | RepoMesh 执行 Adapter 是 RepoMesh 管理项目的唯一正式 Project 与 Task 元数据写方；原生 delegate、Controller 直写、shared 覆盖和 Worker 自持写凭据在受管项目中封闭或围栏 | 责任唯一，校验点集中，便于把权限、计划、预算和容量检查放在同一入口 | 需要凭据与能力层封闭，可能需要窄上游补丁；不封闭时只是页面限制 |
| B 共同条件写 | 所有写方遵守带版本的条件写或共同清单，MCP 与 shared 路径也携带同一条件 | 保留多写方灵活性，理论上不改上游职责 | 需要统一 ETag 或版本协议，MCP 覆盖路径当前不具备同等保证，验证成本高 |

本章默认推荐 A，并把它列为待根代理与用户取舍的决策点。推荐理由是 G3 的验收要求覆盖可达旁路，而当前上游 MCP 与 shared 路径不具备同一条件写保证。若选 A，执行 Adapter 需要同时持有受限 Controller 凭据与受控共享存储写能力，Worker 不直接获得正式元数据写凭据。若选 B，必须先用真实交错写实验证明 MCP、REST 与 shared 三条路径都遵守同一版本条件，本章不预设该实验已通过。

### 2.3 单仓单轮的写入清单

| 写入对象 | 唯一写入者 | 凭据与校验点 | 不允许的路径 |
| --- | --- | --- | --- |
| 轮次与任务本地映射 | coordinator 执行模块 | 数据库短事务，核 Issue、计划、权限、预算与容量 | 浏览器直写、Worker 自报 |
| 仓库内事项登记与停用 | coordinator 执行模块 | 首次实际派工的数据库短事务，核 Issue、仓库已在本 Issue 固定范围、同仓未重复登记 | 选仓、创建 Issue 或只建立计划直接登记，B07 造行，按每轮复制新身份 |
| 上游 Project 元数据 | 执行 Adapter | 受控 Controller 凭据，带版本条件与读回 | 原生 delegate 绕过、shared 覆盖 |
| 上游 Task 元数据 | 执行 Adapter | 受控 taskflow 或 REST 窄接口，稳定任务编码 | Worker 或 Leader 自持写凭据直连 |
| Attempt 环境 | host-executor | 有限动作与登记的资源归属 | 任意宿主命令、任意挂载 |

| Git 写操作 | Worker 使用受限仓库凭据 | 分支与路径策略，撤销写能力可核查 | 长期全仓凭据、页面隐藏按钮代替鉴权 |

## 3. API 与内部边界

### 3.1 内部边界：execution.Adapter

状态为本次提案，未实现。它是 RepoMesh 到选定上游实例的窄适配层，只封装本批需要的能力。调用方是 coordinator 执行模块。

```go
type Adapter interface {
    EnsureReady(ctx context.Context, workerRef string) (ReadyObservation, error)
    ReadWorkflow(ctx context.Context, binding ProjectBinding) (WorkflowObservation, error)
    PlanDAG(ctx context.Context, binding ProjectBinding, plan TaskGraph) (PlanObservation, error)
    ReadyNodes(ctx context.Context, binding ProjectBinding) ([]ReadyNode, error)
    Delegate(ctx context.Context, op DispatchOperation) (UpstreamObservation, error)
    ObserveTask(ctx context.Context, binding ProjectBinding, taskRef string) (TaskObservation, error)
    AcceptResult(ctx context.Context, op AcceptOperation) (UpstreamObservation, error)
    Pause(ctx context.Context, binding ProjectBinding, reason string) (UpstreamObservation, error)
    CancelTask(ctx context.Context, op CancelOperation) (UpstreamObservation, error)
    ReadArtifact(ctx context.Context, binding ProjectBinding, taskRef, path string) (ArtifactObservation, error)
}
```

每个方法返回带来源、观察时间、版本或 ETag、原始状态与规范化状态的观察值。Adapter 不持有 Issue 配置，不决定业务采纳，不写本地数据库。具体传输是 Controller REST、TeamHarness stdio 还是两者组合，由实施时按锁定版本选定，本章不冻结传输。

### 3.2 内部边界：execution.Service.PlanRound

状态为本次提案，未实现。它建立单仓单轮计划映射。调用方是 coordinator 计划工作。

```go
type PlanRoundCommand struct {
    ProjectID        string
    IssueID          string
    RoundID          string
    RoundIndex       int
    Purpose          string
    RepositoryID     string
    Tasks            []TaskDraft
    CauseOperationID string
}

type RoundPlan struct {
    RoundID        string
    PlanRevisionID string
    TaskIDs        []string
}

func (s *Service) PlanRound(ctx context.Context, cmd PlanRoundCommand) (RoundPlan, error)
```

输入范围必须恰好一个仓库，并且该仓库已在本 Issue 的固定范围内；这是 B10 的计划与验收校验范围，不是 `rounds` 行上的单仓列。同一轮覆盖多个仓库时，调用方按仓库各调用一次并复用同一 `RoundID`；`RoundID` 留空时新建轮次行。任务依赖由仓内 DAG 能力校验，跨仓前驱由 B11 在已有任务身份上扩展。方法在同一短事务中创建或复用本 Issue 的轮次行，创建一条不可变 `plan_revisions`，写本仓的 `round_plan_pointers` 行，再写任务映射和发布责任，不启动执行。规划只产生本地映射，不登记仓库事项。提交顺序见 §4.1，没有延迟外键。冲突返回 `PLAN_REVISION_CONFLICT`，权限未知返回 `AUTHORIZATION_UNCONFIRMED`。

### 3.3 内部边界：execution.Service.Delegate

状态为本次提案，未实现。它完成原子预留后的受控派工。调用方是 coordinator 派工工作。

```go
type DelegateCommand struct {
    PlanRevisionID  string
    TaskID          string
    WorkerRef       string
    RoomLinkID      string
    CapacityRequest CapacityRequest
    DispatchOperationID string
}

func (s *Service) Delegate(ctx context.Context, cmd DelegateCommand) (Attempt, error)
```

方法先在一个短事务中登记 Attempt、占用 Worker、预留容量并写入 `dispatch_operations`，事务提交后才准备环境。首次为该 `(issue_id, repository_id)` 真实委派时，同一事务创建或复用 `repository_issues` 行，并把本次 Attempt 归属到该事项；事项的仓库必须等于任务所属计划修订的仓库。实际调用上游前再次核验计划、权限、预算、容量、租约与 Worker 状态。`DispatchOperationID` 由服务端分配，同一逻辑操作重试复用。`RoomLinkID` 可选，写到 Attempt 的 `room_link_id`，引用 B07 的 `repomesh_issues.issue_room_links`。

### 3.4 内部边界：execution.Service.Observe

状态为本次提案，未实现。它读取并规范化上游观察、host-executor 观察和产物事实。调用方是 coordinator 观察工作与 reconcile。

```go
func (s *Service) Observe(ctx context.Context, attemptID string) (AttemptObservation, error)
```

返回原始状态、规范化状态、观察来源、观察时间、版本或 ETag、产物摘要与缺失证据。观察只追加，不原地覆盖旧观察。`submitted` 与 `completed` 都不自动触发业务采纳。

### 3.5 内部边界：execution.Service.RequestStop

状态为本次提案，未实现。它登记停止请求并驱动实际停止核查。调用方是受控维护入口或协调器停派工工作。

```go
func (s *Service) RequestStop(ctx context.Context, attemptID, reason string) (StopOperation, error)
```

停止请求先写本地 `stop_requested_at` 与稳定操作身份，再调用上游取消和 host-executor 停止动作。返回 `requested`、`stop_observed`、`stop_unconfirmed` 三种结果之一。只有真实进程停止或写能力被撤销的证据齐全，才能从 `stopping` 前进到 `stopped`。停止请求本身不释放 Worker 或容量。

### 3.6 内部边界：execution.Service.Reclaim

状态为本次提案，未实现。它在停止与写能力撤销核查后回收资源。调用方是 coordinator 回收工作。

```go
func (s *Service) Reclaim(ctx context.Context, attemptID string) (ReclaimObservation, error)
```

回收按资源种类分别记录。容器、目录、网络、卷和 Worker 占用分别有已释放、释放未知和泄漏三种结果。释放未知时保留占用，不把容量立即分给其他任务。历史 Attempt 记录在证据和必要产物保存完成后回收。

### 3.7 内部边界：host-executor 有限动作

状态为本次提案，未实现。host-executor 只接受经过核验的有限动作，不开放任意宿主命令或挂载入口。建议动作清单如下。

| 动作 | 输入 | 结果与不变量 |
| --- | --- | --- |
| `PrepareAttempt` | attemptId、环境模板版本、仓库快照引用、资源类、限额 | 只创建已登记资源；返回实际资源标识与观察 |
| `StartAttempt` | attemptId、启动命令标识、只读输入引用 | 启动前再核身份与版本；返回已启动或启动未知 |
| `ObserveAttempt` | attemptId、资源标识 | 返回进程、容器、目录、网络的原始观察 |
| `RequestStop` | attemptId、原因、稳定操作编号 | 只请求停止；实际停止另观察 |
| `RevokeWriteCapability` | attemptId、能力种类 | 撤销 Git、存储或控制面写能力；返回撤销证据或未知 |
| `ReclaimAttempt` | attemptId、资源标识、回收清单 | 逐项回收并返回逐项结果；未知项保留占用 |
| `VerifyStopped` | attemptId、资源标识 | 核验进程、容器与写能力；不能只读取消元数据 |

传输编码不在本批冻结。可以按实施条件选择内部队列、受限 socket 或受控 HTTP，但都必须携带稳定操作编号、attempt 身份、能力版本与证据摘要。宿主执行器不持有模型 Key，不读取 Issue 正文，不决定业务采纳。

| `POST /api/v1/projects/{id}/pause` | 停新调度 | 不打断正在执行的任务 |
| `POST /api/v1/projects/{id}/replan` | B11 换图 | active 且无 in_progress 或 submitted |
| `POST /api/v1/projects/{id}/tasks/{taskId}/cancel` | 请求取消任务 | reason 必填，不等于进程已停 |
| `POST /api/v1/projects/{id}/complete` | B11 收尾 | 所有任务必须终态 |
| `projectflow.plan_dag` | 仓内 DAG 建立 | 复用上游依赖与环校验 |
| `projectflow.ready_nodes` | 候选就绪读取 | 非 active 返回空，assigned 可能重复出现 |
| `projectflow.accept_task_result` | 结果接受 | 必须先核归属与业务采纳 |
| `taskflow.delegate_task` | 委派任务 | 核可信身份，不能依赖传入 role |
| `taskflow.submit_task` | Worker 提交结果 | 提交不等于业务接受 |
| `taskflow.cancel_task` | 请求取消 | 不等于资源释放 |

## 4. 数据表设计

以下表名为本次提案，未实现。物理 schema 建议使用 `repomesh_execution`。本章不新增通用 operation、job 或 event 表，也不把表写成“登记到 foundations 的共享框架”。各业务域保留自己的操作回执；只有[首批持久化设计](../current/backend-first-batch-persistence.md)第 3 节已经采用的 DurableWork 机制可以复用于后台工作。仓库内事项身份复用同文第 1 节已经采用的 RepositoryIssue 逻辑记录，本章只给出物理提案，不新增另一套仓内事项概念。所有外部引用使用不透明文本，不把上游短名当本地主键。若任务或 Attempt 需要房间归属，只加 `room_link_id` 外键引用 B07 的 `repomesh_issues.issue_room_links`，不建第二套 room 表，也不在本地复制 room 可用性观察。

### 4.1 rounds

用途是保存 Issue 内业务轮次的最小身份。写入者是 `PlanRound` 与轮次状态推进。B11 复用本表并追加轮次转换记录，不另建 rounds。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| id | text | 是 | 主键 |
| project_id | text | 是 | 项目归属 |
| issue_id | text | 是 | Issue 归属 |
| round_index | integer | 是 | Issue 内递增，从 1 开始 |
| purpose | text | 是 | `initial`、`repair`、`diagnostic`、`environment_recovery` |
| state | text | 是 | `planned`、`active`、`draining`、`applying`、`recovering`、`closed`、`cancelled` |
| created_at | timestamptz | 是 | 创建时间 |
| closed_at | timestamptz | 否 | 收尾时间 |
| closed_reason | text | 否 | 最小收尾原因，详细采纳由 B11 扩展 |

唯一约束为 `(issue_id, round_index)` 与 `(id, issue_id)`；后者供 §4.3 的复合外键引用。轮次是 Issue 内业务轮次，不按仓库复制。一轮中每个参与仓库的当前计划修订由 §4.4 `round_plan_pointers` 逐行保存；本表没有单个“当前修订”列，读取与修改都以该轮的完整指针集合为准。

本次提案的插入顺序是 `rounds` → `plan_revisions` → `round_plan_pointers`，同一短事务完成，全部是普通立即外键，没有环，也没有延迟约束。该表不替代业务 Plan Version，本章也不加指向 B11 表的外键。

### 4.2 repository_issues

用途是保存 Issue 内每个仓库的稳定工作身份（Repository Issue）。它与 B06 的 `issue_repository_scope` 不是同一个东西：范围记录说明本 Issue 允许涉及哪些仓库，创建后不可变；本表记录真实开始过的仓库工作，有自己的生命周期。写入者是 `Delegate`（首次登记与复用）与 Issue 终结或明确停用入口；B11 复用同一身份，B07 的 Leader 投影按 `(issue_id, repository_id)` 读取本表的 id，不新增第二套仓内事项表，也不把选仓范围直接当工作身份。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| id | text | 是 | 主键，永不复用 |
| project_id | text | 是 | 项目归属 |
| issue_id | text | 是 | Issue 归属，与 project_id 一起引用 B06 的 `issues(project_id, id)` |
| repository_id | text | 是 | 仓库归属，与 issue_id 一起引用 B06 的 `issue_repository_scope(issue_id, repository_id)` |
| state | text | 是 | `active`、`closed` |
| created_at | timestamptz | 是 | 首次真实委派登记时间 |
| closed_at | timestamptz | 否 | 停用时间 |
| closed_reason | text | 否 | 非敏感停用原因 |

唯一约束为 `(issue_id, repository_id)`，覆盖全历史，不允许停用后再建一条；另给 `(id, issue_id, repository_id)` 唯一键供 §4.6 的复合外键引用。登记时点沿用[首批持久化设计](../current/backend-first-batch-persistence.md)第 1 节的采用语义：创建 Issue、仅选择仓库、只建立计划修订都不登记；首次为该仓真实委派时由 §3.3 的派工事务创建该行。

生命周期规则如下。同一 Issue 的后续轮次、重试与再次委派复用同一行，普通轮次收尾只结束本轮，不自动把本行置为 `closed`。默认只有在 Issue 终结或明确停用该仓事项时才停用；如果允许显式重新启用，必须复用原 id 并把 `state` 从 `closed` 改回 `active`，不插入第二行。停用只表示不再为该事项登记新工作，不证明上游进程已停止、资源已释放或房间已关闭；这些事实各自记录。Issue 完成后新增工作另建关联 Issue，不在本表扩写出第二段生命周期。

### 4.3 plan_revisions

用途是保存不可变的上游任务安排身份，一轮中每个参与仓库各有一条。写入者是 `PlanRound`。B11 只引用，不原地修改。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| id | text | 是 | 主键 |
| round_id | text | 是 | 轮次归属，与 issue_id 一起引用 `rounds(id, issue_id)` |
| issue_id | text | 是 | Issue 归属，必须与轮次同 Issue |
| revision_index | integer | 是 | 轮次内递增 |
| repository_id | text | 是 | 本修订的仓库归属，与 issue_id 一起引用 B06 的 `issue_repository_scope(issue_id, repository_id)` |
| upstream_binding | jsonb | 是 | 实例、团队、上游 Project 的不透明引用，带 schemaVersion |
| task_set_digest | text | 是 | 有限任务集合摘要 |
| created_by | text | 是 | 可信写入者 |
| created_at | timestamptz | 是 | 创建时间 |

唯一约束为 `(round_id, revision_index)`、`(round_id, repository_id, id)` 与 `(id, issue_id, repository_id)`；后两者分别是 §4.4 指针外键和 §4.5 任务外键的被引用键。本表用两条普通立即复合外键把 `(round_id, issue_id)` 固定到本 Issue 的轮次、把 `(issue_id, repository_id)` 固定到本 Issue 的仓库范围；只写 `repository_id` 不能排除跨 Issue 同仓串线。所有业务列创建后不可更新；应用与读回状态由 B11 的 `target_applications` 持有，本表不保存可变的 applied 或 verified 状态。B11 的同一轮出现多个受影响仓库时，各仓分别建立一条修订并各自应用，轮次行仍然只有一条。

### 4.4 round_plan_pointers

用途是保存一轮中每个参与仓库的当前计划修订指针。写入者是 `PlanRound` 与计划变更；读取者是 B11 的 Evaluate、Close 与目标应用。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| round_id | text | 是 | 与 repository_id 组成主键；与 issue_id 一起引用 `rounds(id, issue_id)` |
| issue_id | text | 是 | Issue 归属，与本轮一致 |
| repository_id | text | 是 | 本轮参与仓库，与 issue_id 一起引用 B06 的 `issue_repository_scope(issue_id, repository_id)` |
| current_plan_revision_id | text | 是 | 本仓当前修订；`(round_id, repository_id, current_plan_revision_id)` 复合外键引用 `plan_revisions(round_id, repository_id, id)` |
| pointer_revision | bigint | 是 | 指针修订，默认 1；每次换修订递增，供完整集合 CAS |
| updated_at | timestamptz | 是 | 最近更新时间 |

主键为 `(round_id, repository_id)`。一轮的当前安排是这些行的完整集合，不是某一行或某一列。写入顺序为 `rounds` → `plan_revisions` → `round_plan_pointers`，全部普通立即外键，无环、无需延迟约束。修改指针时先锁 `rounds` 行，再按本轮的完整指针集合与各行的 `pointer_revision` 做 CAS，只允许换成本轮同仓的另一条不可变修订。B11 的 Evaluate、Close 与目标应用读取同一轮的全部指针后再判断，不任取单个。移出某仓时删除该指针行，必须先确认该仓没有在途工作。

### 4.5 execution_tasks

用途是保存本地任务身份与上游任务映射。写入者是 `PlanRound` 与 `Observe`。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| id | text | 是 | 本地任务主键 |
| plan_revision_id | text | 是 | 与 issue_id、repository_id 一起引用 `plan_revisions(id, issue_id, repository_id)` |
| issue_id | text | 是 | Issue 归属，由复合外键固定 |
| repository_id | text | 是 | 仓库归属，由复合外键固定 |
| local_key | text | 是 | 计划内稳定任务键 |
| upstream_task_id | text | 是 | 编码后的上游任务身份，含项目与轮次前缀 |
| depends_on | text[] | 是 | 依赖的本地任务键 |
| state | text | 是 | `planned`、`ready`、`dispatched`、`assigned`、`in_progress`、`submitted`、`accepted`、`failed`、`cancelled` |
| attempt_id | text | 否 | 当前 Attempt |
| created_at | timestamptz | 是 | 创建时间 |
| updated_at | timestamptz | 是 | 最近更新时间 |

唯一约束为 `(plan_revision_id, local_key)`、`(plan_revision_id, upstream_task_id)` 与 `(id, issue_id, repository_id)`；最后一个是 §4.6 Attempt 外键的被引用键。任务显式携带 Issue 与仓库，并用复合外键绑定到计划修订；只靠 `plan_revision_id` 加一个仓库列不能排除跨 Issue 同仓串线。上游任务编码必须避免不同 Issue、轮次或 Attempt 使用同一短编号造成路径与通知碰撞。任务本身不携带仓库事项 id；首次实际委派时由 §4.6 的 Attempt 指向该仓事项，同一事项可跨轮次拥有多个任务。B11 的跨仓边与结果采纳只引用本表已经存在的任务身份。

### 4.6 attempts

用途是保存一次执行尝试。写入者是 `Delegate`、`Observe`、`RequestStop` 与 `Reclaim`。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| id | text | 是 | 主键 |
| task_id | text | 是 | 引用任务 |
| issue_id | text | 是 | Issue 归属，由两条复合外键固定 |
| repository_id | text | 是 | 仓库归属，由两条复合外键固定 |
| repository_issue_id | text | 是 | 首次真实委派时创建或复用；与 issue_id、repository_id 一起引用 `repository_issues(id, issue_id, repository_id)` |
| project_id | text | 是 | 与 issue_id 组成复合外键，引用 B06 `issues(project_id, id)`；另参与可空房间引用，项目归属不依赖房间是否存在 |
| room_link_id | text | 否 | 可空的派工或 Leader 房间归属；非空时引用同项目、同 Issue、同仓库的 B07 关联 |
| attempt_no | integer | 是 | 任务内递增 |
| worker_ref | text | 是 | 占用的 Worker |
| state | text | 是 | `prepared`、`starting`、`running`、`submitted`、`stopping`、`stopped`、`unknown`、`reclaimed`、`failed` |
| replacement_allowed | boolean | 是 | 是否允许为同一任务开替补，默认 false；见下方替换规则 |
| claim_generation | bigint | 是 | 领取代次 |
| lease_until | timestamptz | 否 | 本地租约，不等于进程停止 |
| may_have_started_at | timestamptz | 否 | 只能由空变非空 |
| stop_requested_at | timestamptz | 否 | 停止请求时间 |
| stopped_observed_at | timestamptz | 否 | 实际停止证据时间 |
| write_capability_revoked_at | timestamptz | 否 | 写能力撤销证据时间 |
| reclaimed_at | timestamptz | 否 | 回收完成时间 |
| created_at | timestamptz | 是 | 创建时间 |

唯一约束为 `(task_id, attempt_no)`。部分唯一索引 `UNIQUE (task_id) WHERE state IN ('prepared','starting','running','submitted','stopping','unknown')` 保证每个任务至多一个未收敛 Attempt；`stopped`、`reclaimed`、`failed` 是终态。本表用两条复合外键把 Attempt 同时锁定到同一 Issue 同一仓库：`(task_id, issue_id, repository_id)` 引用 `execution_tasks(id, issue_id, repository_id)`，`(repository_issue_id, issue_id, repository_id)` 引用 `repository_issues(id, issue_id, repository_id)`；跨 Issue 同仓或跨仓的 Attempt 在语句时被拒绝，不靠事务里的口头检查。

替换规则。`replacement_allowed` 默认 false，并设置数据库 CHECK：`NOT replacement_allowed OR (state IN ('stopped','reclaimed','failed') AND (may_have_started_at IS NULL OR (stopped_observed_at IS NOT NULL AND write_capability_revoked_at IS NOT NULL)))`。未证实失去写能力的 Attempt 即使已经终态也保持 false。状态更新使用限定旧状态与 `claim_generation` 的条件 UPDATE：终态不允许回到 `prepared`、`starting`、`running`、`submitted`、`stopping` 或 `unknown`；`stopped`、`failed` 只可在回收完成后进入 `reclaimed`，`reclaimed` 不再转移。重复观察可以补充终态证据，不能重新启动同一 Attempt。

新 Attempt 的登记和替补许可更新使用同一个任务行锁。`Delegate` 在同一短事务中先锁所属 `rounds` 行核对完整计划指针，再以 `SELECT ... FOR UPDATE` 锁定 `execution_tasks` 的任务行；持锁读取该任务全部历史 Attempt，只有全部 `replacement_allowed = true`（首次执行时历史为空）才能插入新行并占用 Worker、预留容量。所有更改替补许可的路径也先锁该任务行，禁止先锁 Attempt 再反向请求任务锁。任务行一直存在，首次执行也有可锁对象，不以“尚无 Attempt 行”为并发保护。部分唯一索引继续负责拒绝第二条未收敛记录；历史许可检查不能仅放在事务外。

项目归属由非空的 `(project_id, issue_id)` 外键独立保证，`room_link_id` 为空也不能绕过。`room_link_id` 非空时，`(project_id, issue_id, repository_id, room_link_id)` 复合外键引用 B07 的 `issue_room_links(project_id, issue_id, repository_id, room_link_id)`，B07 的 main／leader 互斥检查保证该行只能是同 Issue 同仓库的 `leader` 房间，main 房间不能作为派工归属。

设计理由。一次业务任务可以有多次执行尝试，但任何时刻只有一个尝试占住任务的活跃状态。租约字段只服务于领取核查，进程是否停止由独立观察决定。

### 4.8 resource_reservations

用途是原子预留 Attempt 所需容量与资源。写入者是 `Delegate` 与 `Reclaim`。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| id | text | 是 | 主键 |
| attempt_id | text | 是 | 引用 Attempt |
| resource_kind | text | 是 | `capacity_slot`、`clone_dir`、`container`、`network`、`volume` |
| resource_key | text | 是 | 稳定资源键 |
| state | text | 是 | `reserved`、`active`、`released`、`release_unconfirmed`、`leaked` |

部分唯一索引 `(resource_kind, resource_key)` 在 state 为 reserved、active 或 release_unconfirmed 时成立，保证同一资源不被两个 Attempt 同时占用。容量扣减与 Attempt 登记同事务提交，环境准备在事务外。

### 4.9 dispatch_operations

用途是保存上游派工、取消与结果接收的稳定逻辑操作身份。写入者按 `kind` 分别是 `Delegate`（`delegate`）、`RequestStop`（`cancel`）与结果接收用例（`accept_result`）。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| id | text | 是 | 主键 |
| attempt_id | text | 是 | 引用 Attempt |
| kind | text | 是 | `delegate`、`cancel`、`accept_result`；写入者分别是 `Delegate`、`RequestStop`、结果接收用例 |
| schema_version | integer | 是 | 比较器版本 |
| canonical_input | bytea | 是 | 规范化输入 |
| external_operation_id | text | 否 | 唯一外部逻辑操作身份 |
| state | text | 是 | `prepared`、`may_have_sent`、`observed`、`reconcile_required`、`failed_before_send` |
| may_have_sent_at | timestamptz | 否 | 只能由空变非空 |
| observed_at | timestamptz | 否 | 最近观察 |

三种 `kind` 共用同一操作身份规则，同键同输入重试返回原结果，同键异输入冲突。外部调用前写 `may_have_sent`，失败后先按 `external_operation_id` 核查。`schema_version` 不进入唯一键。`accept_result` 只保存上游接收回执与观察，业务采纳由 B11 的 `result_admissions` 单独决定；外部 accept 回执不能替代业务采纳，也不能直接解锁依赖。

### 4.11 attempt_observations

用途是追加保存执行观察。写入者是 `Observe` 与 reconcile。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| id | text | 是 | 主键 |
| attempt_id | text | 是 | 引用 Attempt |
| source | text | 是 | `controller_rest`、`teamharness_mcp`、`artifact_store`、`host_executor` |
| raw_status | text | 否 | 上游原始状态 |
| normalized_status | text | 是 | 本地规范化状态，附带映射版本 |
| binding_revision | text | 否 | ETag 或版本 |
| payload_digest | text | 是 | 观察载荷摘要 |
| observed_at | timestamptz | 是 | 观察时间 |
| claim_generation | bigint | 否 | 观察时领取代次 |

本表只增不改。迟到观察可以追加，只有当前 reconcile 逻辑能采纳为正式状态。观察缺失时保留未知，不推导成功。

### 4.12 attempt_artifacts

用途是登记执行产物与保留状态。写入者是 `Observe` 与 `Reclaim`。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| id | text | 是 | 主键 |
| attempt_id | text | 是 | 引用 Attempt |
| kind | text | 是 | `candidate`、`log`、`report`、`test_data`、`other` |
| ref | jsonb | 是 | 受控位置引用，带版本 |
| digest | text | 是 | 内容摘要 |
| state | text | 是 | `observed`、`verified`、`archived`、`missing`、`deleted` |
| observed_at | timestamptz | 是 | 观察时间 |

产物引用不扩大查看权限。归档与删除分别记录，缺失正文不能冒充仍可复核的证据。

### 4.13 write_capability_revocations

用途是分别记录 Git、存储和控制面写能力的撤销请求与证据。写入者是 `RequestStop` 与 host-executor 观察。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| id | text | 是 | 主键 |
| attempt_id | text | 是 | 引用 Attempt |
| capability_kind | text | 是 | `git`、`object_store`、`controller` |
| state | text | 是 | `requested`、`observed`、`unknown` |
| requested_at | timestamptz | 是 | 请求时间 |
| observed_at | timestamptz | 否 | 撤销证据时间 |
| evidence | jsonb | 否 | 版本化证据摘要 |

撤销一种能力不等于停止进程，也不等于其他能力已撤销。三者都必须单独核查。

设计理由。停止请求、进程停止和写能力撤销是三件不同的事。只写取消元数据不能阻止旧进程继续提交或上传，因此需要独立证据把这三件事分别推进。

### 4.14 新增表必要性与删并说明

本节回应共同规则中“新增提案要有出处，能被合并的就合并”的要求。B10 只保留单轮执行真正需要的表。

| 表 | 必要性出处 | 结论 |
| --- | --- | --- |
| rounds | ADR-0015 的按获准轮次映射；单轮也需要稳定轮次身份 | 新增，B10 持有最小轮次；按 Issue 登记，不按仓库复制 |
| repository_issues | 首批持久化设计第 1 节已经采用的 RepositoryIssue 逻辑记录；每 Issue 同仓 0..1 条稳定工作身份，首次真实委派登记 | 新增，B10 持有物理提案；B11 复用同一 id，B07 只读投影，不另建仓内事项表 |
| plan_revisions | ADR-0015 的上游任务安排修订；必须不可变 | 新增，B10 持有；一轮内每条修订绑定本 Issue 范围中的一个仓库；B11 只引用并另存应用状态 |
| round_plans | 原本是 round 到计划修订的单指针 | 删除；单指针表达不了多仓轮次，改为按仓的 round_plan_pointers |
| round_plan_pointers | 一轮中每个参与仓库的当前修订；读取与 CAS 都要完整集合 | 新增，B10 持有；主键 `(round_id, repository_id)`，指针修订随换修订递增 |
| execution_tasks | 本地任务身份与上游映射；跨批碰撞要求 | 保留；显式携带 issue_id 与 repository_id，用复合外键绑定计划修订 |
| attempts | 一次执行尝试身份与停止/回收生命周期 | 保留；复合外键同时固定任务、仓库事项的 Issue 与仓库；补 replacement_allowed |
| worker_leases | 单 Worker 单活跃任务的排他约束 | 保留，唯一性与 attempts 不同 |
| resource_reservations | 按资源种类的原子排他与逐项释放 | 保留 |
| dispatch_operations | 派工与取消的外部操作身份 | 保留，改为 delegate、cancel、accept_result；accept_result 不是业务采纳 |
| host_operations | 受限宿主动作的幂等请求与观察 | 保留，与上游操作目标不同 |
| attempt_observations | 追加观察证据与迟到结果 | 保留 |
| attempt_artifacts | 产物引用、摘要与保留状态 | 保留，生命周期与观察不同 |
| write_capability_revocations | 写能力撤销证据 | 保留，与进程停止分开 |

## 5. 事务与恢复

### 5.1 原子预留与启动前核验

派工先在一个短数据库事务内完成候选检查、Attempt 登记、Worker 占用和容量预留。首次为该仓真实委派时，同一事务创建或复用 `repository_issues` 行并写进 Attempt。计划或修订的变更先锁 `rounds` 行，再按本轮完整指针集合与各行的 `pointer_revision` 做 CAS，随后才写新修订与新指针；Evaluate、Close 与目标应用读取完整指针集合，不任取单个。竞争同一 Worker 或同一容量的请求不能同时成功。事务提交后才准备独立环境。实际启动前再次核验计划、权限、预算、容量、租约、Worker 状态和写能力版本。准备期间发生撤权、暂停或取消时不得继续启动。

### 5.2 响应丢失与同键异参

上游派工响应丢失时先按 `external_operation_id` 查原操作，不生成第二个 Attempt。同键不同仓库、任务或 Worker 返回冲突。host-executor 响应丢失时先查 `host_operations` 和实际资源状态，不重复创建目录、容器或网络。取消响应丢失时保留 `stopping`，先核实际停止，再决定是否重试同一操作。

### 5.3 崩溃与重启

协调器重启后从持久 Attempt、预留、派工操作和观察重建责任。计划责任按本轮完整 `round_plan_pointers` 集合恢复，不把某一条指针当成整轮计划。未启动的预留可以按条件重试；已 `may_have_started` 的 Attempt 必须先观察真实状态。租约到期只表示可以重新领取核查任务，不表示旧进程已停止。数据库无法确认旧写入能力失效时保持 `unknown` 并保留占用。

### 5.4 停止、写能力撤销与回收

停止分四步。第一，登记停止请求与稳定操作身份。第二，请求上游取消与宿主停止。第三，分别核验进程停止和 Git、存储、控制面写能力撤销。第四，按资源种类回收并逐项记录。任何一步未知都保持占用与未知状态，不自动启动替补，也不把资源分给其他任务。

### 5.5 迟到结果

旧 Attempt 的观察、产物或上游状态晚到时只追加观察。当前 reconcile 按 `attempt_id`、`claim_generation`、任务与轮次归属判断是否记录为当前尝试的新观察；业务采纳由 B11 的 `result_admissions` 单独决定。迟到结果不能覆盖正式状态，不能解锁当前依赖，也不能作为新 Attempt 已启动的证据。旧 Attempt 结果保留历史与适用性判断。

### 5.6 删除与保留

Attempt 历史在证据与必要产物保存完成后回收执行资源，但业务记录不随容器删除。临时运行材料按项目清理策略处理，归属、版本关联、决定和操作结果在项目存续期保留。清理未知外部动作前必须先核查；清理不得让旧操作获得新的派工资格。正文清理沿用 B06 与 B09 的墓碑规则。

## 8. 待取舍点

| 取舍 | 选项 | 影响 | 本章默认写法 |
| --- | --- | --- | --- |
| G3 写方 | 单一正式写方，或共同条件写 | 决定凭据面、上游补丁范围与旁路封闭方式 | 推荐单一正式写方，等待根代理与用户取舍 |
| 派工传输 | Controller REST、TeamHarness MCP 或组合 | 决定 Adapter 实现与条件写能力 | 保持 Adapter 接口，不冻结传输 |
| host-executor 传输 | 内部队列、受限 socket 或受控 HTTP | 影响部署与鉴权，不影响动作清单 | 动作与不变量先行，传输待定 |
| 上游补丁 | 是否允许为写方封闭或 paused replan 加窄补丁 | 影响维护成本与升级兼容 | 只在必要范围设计，不在本批实现 |
| 资源计量 | 按槽位、按资源类或实测容量 | 影响容量预留与公平调度 | 先按资源类与容量槽位建模，数值待测量 |
| 仓库事项登记时点 | 首次实际派工时登记（本章默认），或提前到首个计划修订 | 决定页面何时出现仓内事项，以及计划修订能否直接绑定事项 | 默认首次实际派工登记，沿用持久化协议“真实委派才登记”；提前到计划修订会产生未生效计划的仓内事项 |

本章只做设计与源码核对，没有启动服务、数据库、浏览器、容器或真实上游实验，也没有声称发现或复现死锁。
