## 本轮物理合表

B07 在这轮合表里只有一张自己的表 `repomesh_issues.issue_room_links`，原表名与新表名相同。它与 B06 的六张一起组成合并后的 7 张。合并前的 14 行完整映射写在 [B06](./b06.md) 的“本轮物理合表”一节，本章不重复整张映射表。

除房间表外，B07 的设计有三处随合表调整。

1. 列表游标不再扩现有 `repomesh_projects.cursors`。B03 与 B04 的字段、约束、kind 枚举和读写行为保持原样；B07 改用签名不透明游标，服务端把位置与校验信息放在游标载荷里，不写新表、不加新列。
2. 事件流计数不再有独立的 `issue_event_streams` 表。generation、`last_sequence` 与清理边界 `pruned_through` 落在 [B06](./b06.md) 的 `issues` 行上，事件本身仍在 `issue_events`。
3. 范围读取目标从 `issue_content_scope`、`issue_repository_scope` 改为 `repository_scopes`。工作仓库用生成列 `work_issue_id` 加普通唯一约束表达，B07 的 Leader 房间与 B10 的工作范围都引用这个真实键。

说人话：游标本来就不需要长期存储。它只要能在下一页请求里证明“谁、在哪份过滤条件下、扫到哪个位置”，并且过期后能被拒绝。把它签名后放进客户端，省掉一张游标行的写入与清理，也避免动 B03 已有的表。事件计数和范围是同一批数据的不同读法，读的目标改成合并后的真实表即可。

## 接口卡片

以下接口与页面恢复规则中，列表、详情、rooms、SSE、会话读取都是“已采用设计，未实现”。路径与字段保持既有契约原文，本批只补实现需要的输入输出、错误、并发和恢复细节。新增字段或新错误码逐项标注为本次提案。

### Issue 列表

调用方是 Issue 列表页 `/projects/{projectId}/issues`，也服务创建成功后的列表刷新。

| 项 | 内容 |
| --- | --- |
| 方法与路径 | `GET /api/projects/{projectId}/issues`，已采用设计。 |
| 输入 | `q` 可选，最多 200 个 Unicode 标量，对标题做字面大小写不敏感子串匹配；`repositoryId` 可选，过滤涉及该仓的事项；`cursor` 不透明；`limit` 默认 50，范围 1 至 100。 |
| 返回 | `items` 数组，元素为 `id`、`number`、`title`、`repositoryIds`、`mainChangeSetId`、`source`、`createdAt`、`revision`；`nextCursor` 为字符串或 null。正文、执行状态与隐藏对象计数都不返回。 |
| 授权 | 当前登录主体 + 项目访问资格 + 每个条目完整内容范围当前可读。先确定本地可访问对象与范围观察，再做标题过滤，防止用 `q` 探测隐藏标题。 |
| 错误 | `400 INVALID_CURSOR`、`401 AUTHENTICATION_REQUIRED`、`404 RESOURCE_NOT_FOUND`（项目或过滤仓库不可披露）、`409 CURSOR_EXPIRED`、`422 VALIDATION_FAILED`、`429 RATE_LIMITED`、`503 AUTHORIZATION_UNCONFIRMED`。 |
| 并发与重放 | 只读，无副作用，无可重放写入。分页不持有跨页数据库快照；允许 `items` 为空但 `nextCursor` 非空。 |
| 理由 | 重试和双击只产生读取；隐藏事项不进入计数、标题匹配或错误正文，避免通过搜索差异推断无权对象存在。 |

分页实现规则。服务端按 `(projectId, id)` 上已有的唯一索引做稳定 keyset 扫描，游标载荷里的位置是最后扫描的稳定 ID，不是最后可见 ID。位置、limit、过滤指纹与排序版本都由服务端签名绑定；服务端重新核权后，逐条对候选判定。明确拒绝的条目跳过且不计数，内核权结果未知时整次返回 503，不得返回看似完整的成功列表。`nextCursor` 为 null 才表示遍历结束。

`repositoryId` 过滤的语义是“内容范围包含该仓”，读的是 `repository_scopes` 的 Issue 行，不是当前工作范围。跨项目或当前不可读的仓库统一返回隐藏式 404；核查未知返回 503。该过滤不能与 `q` 组合成可用于探测隐藏范围的查询。

### Issue 最小详情

调用方是详情页 `/issues/{issueId}`，以及从 rooms 或会话返回后的重读。

| 项 | 内容 |
| --- | --- |
| 方法与路径 | `GET /api/issues/{issueId}`，已采用设计。 |
| 输入 | 路径参数 `issueId`，不透明稳定 ID。 |
| 返回 | `id`、`number`、`projectId`、`revision`、`title`、`description`、`repositoryIds`、`acceptanceCriteria`、`mainChangeSetId`、`source`、`createdAt`。`revision` 只表示 Issue 业务快照修订。 |
| 授权 | 需要该 Issue 完整内容范围的当前读权。未知返回 503，明确无权返回隐藏式 404。 |
| 错误 | `401 AUTHENTICATION_REQUIRED`、`404 RESOURCE_NOT_FOUND`、`429 RATE_LIMITED`、`503 AUTHORIZATION_UNCONFIRMED`，正文已清理时为本次提案的新码 `410 ISSUE_CONTENT_REMOVED`。 |
| 并发与恢复 | 读一致快照；外部核权在事务外完成；响应发出前复核内容范围版本未变，变化则重读或拒绝。 |
| 理由 | 业务记录与运行观察分开显示，刚创建的 Issue 不因缺少房间依据被标成执行中。 |

读取时序。按[首批持久化](../current/backend-first-batch-persistence.md) §4.1 的有界只读一致快照取业务记录、内容范围与本地访问依据，事务外核当前外部资格，返回前重比范围版本。页面分别读取详情与 rooms，两次请求不宣称是跨系统同一快照。

`repositoryIds` 从 `repository_scopes` 的 Issue 行投影；详情页只展示内容范围，不把工作范围标志当成用户可见字段。

`410 ISSUE_CONTENT_REMOVED` 是本次提案的新增错误码，用于正文已被清理、身份与关系仍保留的事项。正文清理只删标题、正文、验收项与派生副本，保留范围、主会话、主 ChangeSet、配置引用与操作身份。采用本错误码时同步到拥有错误表的专题，当前错误码表见 [Issue 创建契约](../current/issue-page-create-api-contract.md) 第 6 节，本文不另立一套错误框架。

### Issue rooms 读取

调用方是详情页的房间区域与房间路由 `/issues/{issueId}/rooms/{roomId}`。

| 项 | 内容 |
| --- | --- |
| 方法与路径 | `GET /api/issues/{issueId}/rooms`，已采用设计。 |
| 输入 | 路径参数 `issueId`。不接受客户端指定 `roomId` 作为授权依据。 |
| 返回 | `issueId`；`main` 含 `conversationId`、`availability`、`reason`、`roomId`、`canEnter`、`observedAt`；`leaders` 数组元素含 `repositoryIssueId`、`repositoryId`、同形观察字段与固定 `readOnly:true`。 |
| 枚举 | `availability` 为 `ready / preparing / unavailable / unknown`；`reason` 为 `NOT_ASSOCIATED / NOT_READY / ACCESS_RESTRICTED / OBSERVATION_STALE`，正常就绪为 null。 |
| 授权 | `canEnter=true` 必须同时满足当前读权、实际关联与就绪依据。点击进入房间时重新核权，旧快照不能继续授权。 |
| 错误 | `401 AUTHENTICATION_REQUIRED`、`404 RESOURCE_NOT_FOUND`、`429 RATE_LIMITED`、`503 AUTHORIZATION_UNCONFIRMED`。 |
| 并发与恢复 | 房间观察是行内最新状态，读取取每条关联的当前观察。观察过期按 `unknown` 加 `OBSERVATION_STALE`，不把旧 `ready` 继续展示。 |
| 理由 | 会话存在、选仓列表或创建回执都不能证明房间存在或可进入；空 `leaders` 只说明当前无可披露入口，不推断没有委派。 |

观察来源是本次提案的表 `repomesh_issues.issue_room_links`，同时保存确定关联与最后观察状态，写入方是后台协调进程在真实取得运行观察之后。房间身份按 RepoMesh instance 加外部 room 作用域保存，裸 `room_id` 不是跨实例的全局业务身份。新观察按单调 revision 与 runtime generation 条件更新，探测失败写 `unknown` 并保留原关联，旧 generation 的迟到更新被拒绝。本批只定义读取投影与过期语义，不冻结上游房间标识的传输方式、MCP schema 或任何带凭据地址。`roomId` 是 RepoMesh 的内部稳定关联标识，不是上游地址。

### Issue SSE 失效通知

调用方是详情页的单一 Issue 级订阅，路径 `/api/issues/{issueId}/events`，媒体类型 `text/event-stream`，已采用设计。

| 项 | 内容 |
| --- | --- |
| 输入 | 路径参数 `issueId`；重连可带不透明 `Last-Event-ID`。长期令牌不放入 URL。 |
| 返回 | 连接建立后先发 `resync_required`，数据只含 `issueId`；随后发送 `event: issue.changed`，数据为 `{"issueId":"iss_103","changed":["rooms"]}`，`changed` 允许 `issue`、`rooms` 或两者。 |
| 授权 | 建立、重放和每次发送前都核当前权限；未授权连接返回普通 401 或隐藏 404，不建立成功流；失权关闭连接并停止内容。 |
| 错误与恢复 | 游标可重放时继续；游标过期、代次不符或不可验证时发送 `resync_required`，要求重查快照。默认事件保留 24 小时、每 15 秒发送注释心跳，两者是可调运行参数。 |
| 并发与重放 | 通知与其对应的本地事实变更同事务持久化，提交后发布；重复通知允许合并，不承诺 exactly-once。单快照最多一个在途查询，期间再收通知置为需再查询。 |
| 理由 | 事件只声明“某个快照失效”，权限与状态以查询为准，避免通知字段泄露隐藏房间或模型内容。 |

事件不携带模型内容、计划状态或房间名。断连不把 Issue 标为失败，也不自动重发创建请求。SSE 延后时，创建回执与原操作查询仍然独立可用。

### 项目会话列表

调用方是会话侧栏，路径 `GET /api/projects/{projectId}/conversations`，已采用设计。

输入与分页规则同 Issue 列表；返回 `items` 数组，元素为 `id`、`title`、`createdAt`、`revision`，以及 `nextCursor`。只返回会话完整内容范围当前可读的对象，不返回隐藏对象数量，未知权限整次 503。该列表不定义消息正文、发送或订阅。创建表单使用的 `GET /api/projects/{projectId}/issue-creation-conversations` 属于 B06，本批列表是项目会话侧栏的通用只读列表，两者不互相替代。

| 项 | 内容 |

### 会话历史与澄清只读

只读消费三个已采用端点，定义在[消息澄清契约](../current/conversation-message-clarification-api-contract.md) §3 与 §4，本批不复制字段。

- `GET /api/projects/{projectId}/conversations/{conversationId}/messages?limit=50&cursor=...` 返回按提交序号升序的 `items` 与 `nextCursor`。游标绑定主体、会话、内容范围版本、水位与位置；非法 400 `INVALID_CURSOR`，过期 409 `CURSOR_EXPIRED`，范围变化 409 `CONVERSATION_CONTEXT_CHANGED`。
- `GET /api/projects/{projectId}/conversations/{conversationId}/messages/{messageId}` 返回单条消息投影，用于定位原消息、问题或答复。
- `GET /api/projects/{projectId}/conversations/{conversationId}/clarifications/{clarificationId}` 返回问题当前状态、可回复性、候选与原因码。本批只读，`canReply` 在本批页面不提供提交动作。

消息保存 `POST .../messages`、原提交查询与答复提交属于 [./b09.md](./b09.md) 的范围，本批不实现、不展示可用输入框。

消息分页水位读 B06 `conversations` 行的 `last_message_sequence`；分配序号与写消息都在 B09，本文只读这一列。游标的签名与载荷归消息专项，B07 列表游标的做法可以复用同一实现，但两者不共用同一个游标种类。

只读页面必须区分“没有历史”与“历史读取未接入”。当消息存储或端点尚未实现时，页面显示“历史读取未接入，当前不能确认会话内容”，不得把 404 或空数组当空历史成功。

### 浏览器恢复路由与读取代次

## repomesh_issues.issue_room_links

物理表：`repomesh_issues.issue_room_links`

用途与写入者：Issue 的主房间与 Leader 房间关联及最新观察。写入方是后台协调进程，读取方是 B07。它同时保存确定关联与最后观察状态，不为只读页新增观察历史表。上游房间标识按不透明引用保存，不含凭据或地址。

| 字段 | 类型与约束 | 人话含义 |
| --- | --- | --- |
| `room_link_id` | `text PRIMARY KEY` | 本关联的内部 ID，对应响应里的 `roomId`。 |
| `project_id`、`issue_id` | 非空复合外键引用 `issues(project_id, id)` | 关联属于同一项目的同一 Issue。 |
| `kind` | 非空，取值 `main` 或 `leader` | 主房间与 Leader 房间的读法不同。 |
| `instance_id` | 非空不透明字符串 | RepoMesh 稳定运行实例身份，房间身份跨实例不共用。 |
| `upstream_room_ref` | 非空不透明字符串 | 该实例内的外部房间引用，与 `instance_id` 一起构成房间身份。 |
| `conversation_id` | `main` 分支非空，复合外键 `(project_id, issue_id, conversation_id)` 到 `issues(project_id, id, main_conversation_id)` | 主房间必须挂在该 Issue 的主会话上，只属于同项目还不够。 |
| `repository_id` | `leader` 分支非空，复合外键 `(issue_id, repository_id)` 到 `repository_scopes(work_issue_id, repository_id)` | Leader 入口对应的仓库，必须同时在同一 Issue 的工作范围内。 |
| `created_at`、`retired_at` | 时间列，后者可空 | 关联退役后不再对外提供入口；退役不删除行。 |
| `availability` | 非空，取 `ready / preparing / unavailable / unknown` | 最近一次真实观察的可用状态，待办排队不映射成 `preparing`。 |
| `reason_code` | 可空，取契约枚举 | 允许披露的原因。 |
| `observed_at`、`expires_at` | 非空时间列 | 观察时刻与失效时刻；过期投影为 `unknown` 加 `OBSERVATION_STALE`。 |
| `observation_revision` | 非空 `bigint` | 单调递增的观察版本，只有更大的值才能覆盖。 |
| `runtime_generation` | 非空不透明字符串 | 产生观察的运行代次，旧代次的迟到写入被拒绝。 |
| `observer` | 非空 | 写入观察的后台执行身份，便于追溯。 |

`repositoryIssueId` 是已经采用的仓库事项业务身份，逻辑记录由[首批持久化设计](../current/backend-first-batch-persistence.md) 第 1 节定义；它在同一 Issue 与仓库内全历史唯一，首次真实委派才登记。具体物理表由 [B10 的 repository_issues 提案](./b10.md) 定义。本表不重复保存这个身份，也不增加指向后续批次表的前置外键。B10 持久化提案采用并实现后，Leader 投影按 `(issue_id, repository_id)` 读取该行的 id，并结合当前授权与房间关联决定可披露条目；此前没有真实仓库事项时，`leaders` 返回空数组。只选中仓库、建立计划或读取页面都不能补造事项和 Leader 入口。

分支约束写成完整 CHECK：`(kind = 'main' AND conversation_id IS NOT NULL AND repository_id IS NULL) OR (kind = 'leader' AND conversation_id IS NULL AND repository_id IS NOT NULL)`。这样一行只表达一种房间关联，不会同时挂会话和仓库。

唯一性：`main` 关联用部分唯一索引 `(issue_id) WHERE kind = 'main' AND retired_at IS NULL` 限定每个 Issue 至多一条有效主房间；房间身份用 `UNIQUE(issue_id, kind, instance_id, upstream_room_ref)` 限定，裸 `upstream_room_ref` 不能跨实例当作同一房间。另设 `UNIQUE(project_id, issue_id, conversation_id, room_link_id)` 供 B09 的 Manager 会话以完整作用域引用自己的 main 房间，以及 `UNIQUE(project_id, issue_id, repository_id, room_link_id)` 供 B10 的仓库执行引用 Leader 房间；知道同项目的另一个房间 ID，也不能把它绑到错误的 Issue 或仓库。两个复合键都是普通唯一约束，可以充当外键目标。

跨批引用：本表主键 `room_link_id` 是稳定引用目标，B09 的 `manager_sessions` 与 B10 的派工记录通过 `room_link_id` 引用本表（见 [./b09.md](./b09.md) 与 [./b10.md](./b10.md)），不复制房间可用性、原因码、观察时刻、过期时刻、观察版本或运行代次。B09 的 `manager_sessions` 引用 main 房间的四列键；Leader 房间不出现在那条引用里。消息与投递记录经各自会话引用间接定位房间，不保存裸 `room_id`。

本表的业务边界：它是 Issue 的 main 与 leader 房间投影，`project_id` 与 `issue_id` 非空，只为已有 Issue 登记关联。普通对话可以先于 Issue 存在（见 [./b09.md](./b09.md)），这类会话的运行绑定由 B09 的 `manager_sessions` 自身通过 `manager_instance_ref`、`transport_session_ref` 与 `state` 持有，不经过本表；会话关联到 Issue 后才引用本表的 `room_link_id`，并校验同项目范围。本表只承担 Issue 房间一种业务生命周期，不作为全系统统一 room 表，也不为无 Issue 会话造行。

写入规则：探测成功与新关联登记都在条件更新中比较。普通观察只在当前代次内写入，`observation_revision` 必须严格大于当前值；`runtime_generation` 不等于当前值的写入一律拒绝。探测失败写 `unknown` 并保留原关联，不删除、不降级关联本身。读取投影只取该行的最后状态，`canEnter` 由当前读权、关联有效性与观察状态共同计算，不是存储列。观察过期时长属于运行策略，本批不冻结数值。

状态转移：关联从准入时创建为有效行，真实观察把 `availability` 在 `unknown`、`preparing`、`ready`、`unavailable` 之间按最新证据移动；探测失败只能写入更晚 revision 的 `unknown`，不能删除关联；上游关闭或重映射时置 `retired_at`，此后停止对外入口并拒绝新的观察覆盖。非当前代次的写入与更小 revision 的写入一律拒绝，不产生半新半旧状态。

代次分工：本表只保存运行实例代次 `runtime_generation`。代次是不透明身份，不按字符串或字典序比较新旧。普通观察只能在当前代次内写入并递增 `observation_revision`；要切换代次，只能走可信切换路径：由可信运行适配器在事务里锁 Issue 与关联行，CAS 旧 generation，原子登记新 generation 与对应的第一条观察，旧代次其后的所有写入全部拒绝。没有可信切换事务时，任何以新代次名义送达的观察都不被接受。

Manager 逻辑会话代次 `manager_session_epoch` 归 B09 的 `manager_sessions`，与本表的运行实例代次不能互相替代；旧 Manager 代次的回写即使伴随更新的房间观察 revision 也要在那侧拒绝，本文不为它增加字段。

房间观察与它的失效事件在同一本地事务写入，先锁 Issue 再锁关联行，避免与事件计数路径逆序取锁。

## 事件流与 SSE 游标

事件与流计数由 B06 的表定义承载：逐事件行在 `repomesh_issues.issue_events`，generation、`event_last_sequence` 与 `event_pruned_through` 在 `repomesh_issues.issues` 行上。B07 需要它们的通知投影与重放，增量如下，未采用。

1. `changed` 是按事件种类计算的读取投影，不新增列。事件唯一事实仍是 [./b06.md](./b06.md) 的 `issue_events`：当前只定义 `snapshot_invalidated` 一种事件与 `created_at`。该种类不区分失效对象，SSE 数据按保守值 `["issue","rooms"]` 投影，客户端按两类快照都要重查处理；B06 若在表定义中增加能区分对象的事件种类，本投影再按种类映射为 `["issue"]`、`["rooms"]` 或两者。本文不新增列，也不建立第二个事件权威。
2. 事件插入继续在持有 Issue 行锁的事务内完成，序号按流递增。所有同 Issue 的事件写路径使用同一锁，禁止用全局自增序列推断提交顺序。
3. `Last-Event-ID` 表达 `(issue_id, generation, sequence)`，由服务端签名保护，与列表游标同一实现方式。签名无效、错 Issue、篡改、旧 generation、序号小于等于 `event_pruned_through` 但不在可重放边界内、或大于 `event_last_sequence` 时发送 `resync_required`；`sequence` 等于 `event_pruned_through` 时可以从下一序号重放。
4. 发布器只扫描已提交事件；发送成功不删除事件，也不记为浏览器已读。保留窗口清理先锁 Issue，只删除当前代次的连续前缀并原子推进 `event_pruned_through`，因此事件表为空时仍能判断旧游标的缺口。

事件类型仍沿用 B06 的 `snapshot_invalidated`，本批不新增事件类型；`changed` 只是通知投影，SSE 线上的事件名保持已采用的 `issue.changed`。

游标过期始终走完整补查，不假装连续补齐。清理事件不级联删除 Issue 或房间关联。

## 会话与消息只读对象

会话业务身份复用 B06 的 `conversations`。消息、提交与澄清的逻辑记录属于消息专项，见[消息内部设计](../current/backend-message-clarification-design.md) §3，其字段与唯一约束不在本文复制。B07 只依赖三件事。

1. 会话内容范围核权：读取标题、消息与澄清前必须通过 `repository_scopes` 的会话行与当前外部观察。
2. 消息分页水位：按提交序号稳定排序，游标绑定主体、会话、内容范围版本与水位，水位读 `conversations.last_message_sequence`。
3. 问题快照可定位：`clarificationId` 就是问题身份，不另造 questionId。

消息写入、答复唯一性、澄清状态机与投递责任归 [./b09.md](./b09.md)，本批不实现。普通会话可以没有 Issue，本批的房间表不为它登记行。

## 事务、并发与恢复

正常读取流程。认证与项目资格核验后，按有界只读事务读取业务记录与范围，事务外获取当前外部观察，返回前重比范围版本，然后投影响应。列表逐条核权；详情与 rooms 分开读取，各自返回自己的快照。需要写事件计数的路径先锁会话再锁 Issue，与 B06 顺序一致。

响应丢失。读取无写入，客户端直接重试即可。页面不得因为一次读取失败重新发送创建或消息写入请求；原创建操作只按 B06 的 `creationId` 查询。

身份边界。本批没有新的业务操作身份：创建与重放的幂等身份仍由 B06 的 `creationId` 与其作用域决定；`runtime_generation` 只是外部执行观察代次，既不能替代 `creationId`，也不能替代 B09 的 Manager 会话代次。事件载荷可以带 `schemaVersion`，但 `schemaVersion` 不参与幂等键，也不把事件变成新的业务操作。

同键异参与重放。本批接口没有幂等键。`Last-Event-ID` 篡改或跨 Issue 复用时按不可验证处理，发送 `resync_required`，不接受为授权。分页游标篡改、跨种类或跨项目使用返回 `INVALID_CURSOR`，过期返回 `CURSOR_EXPIRED`。

并发。内容范围在读取期间扩大的，按响应前版本复核结果重建或拒绝，不用旧小范围返回新正文。房间观察与读取并发时以最新已提交观察为准。事件写入与发布器并发时，发布器只看到已提交行；清理与重放并发时，先于清理开始的有效重放可以完成，之后请求收到 `resync_required`。

崩溃。后台发布器重启后按主库扫描恢复，不依赖内存广播。浏览器断线后按原游标重连；不能重放时完整补查。进程重启不改变已提交的业务记录。

迟到结果。切 Issue、切会话或切项目后到达的响应按代次丢弃，不能填进新上下文。旧权限下的成功响应在失权后不构成继续读取的依据。

删除。Issue 正文清理后详情返回 410 提案码，列表不再返回该条目，SSE 关闭或要求重查。会话与消息的清理语义沿消息专项，不在本批新增删除路由。

## 生命周期

| 对象 | 创建 | 变更 | 结束 |
| --- | --- | --- | --- |
| Issue 业务快照 | B06 创建事务 | 后续业务编辑提升 `revision` | 正文清理后 `removed_at` 非空，身份与关系保留。 |
| 内容范围 | 创建时写入，只增不减 | 新内容引入时同事务追加并提升范围版本 | 不随工作范围缩减而删除。 |
| 房间关联与观察 | 后台取得真实关联后写入单行 | 每次真实观察按 revision 与 generation 条件覆盖最后状态 | 上游关闭或重映射时置 `retired_at` 并停止入口，行保留。 |
| 事件 | 与对应事实同事务插入 | 同流递增序号 | 超出保留窗口后不可重放，触发完整补查。 |
| 列表游标 | 首次请求签发 | 每页重新签发下一位置 | 过期或版本变化后失效，要求从首页刷新。 |

## 设计理由

详情与 rooms 分成两个请求，是因为业务记录已经提交，而房间是否就绪属于外部运行事实。把两者绑成一次请求，会让房间核查失败连带显示成事项读取失败，或者反过来用旧房间状态给业务记录背书。

事件只发失效通知，是因为通知无法承载权限变化后的正文。用户收到通知后重新查询，服务端在查询时重新核权，这样失权后既不会继续泄露旧内容，也不需要撤销已经发出的正确历史响应。

游标由服务端签名而不是落库，是因为它的生命周期短、只服务下一页请求。签名绑定主体、项目、过滤与位置后，换账号、换筛选或范围变化都会显式失效，页面从第一页刷新，避免把两段不同条件的页拼成一份看似完整的列表；同时不必给 B03 已有的表加列。

房间关联独立于选仓列表，是因为创建时选择的仓库只是工作范围。真实 Leader 房间只在首次实际委派后出现，由运行观察写入。按选仓伪造房间会让用户以为工作已经启动。

会话只读页头单独设计，是因为页头失败与消息失败的处理不同。页头拿不到时必须隐藏旧标题，而页面仍可分别报告消息读取是否可用，两者都不授予内容权限。

| 编号 | 前提与动作 | 预期结果 |

| B07-V02 | 列表筛选包含一个已失权 Issue | 该条目不出现在 `items`，不进入总数，错误正文与 `q` 匹配结果都不泄露其标题。 |

| B07-V05 | 篡改游标、换主体使用、等待过期 | 分别为 `INVALID_CURSOR`、不匹配、`CURSOR_EXPIRED`；页面从第一页刷新。 |

| B07-V07 | 房间无真实关联 | `availability=unavailable`、`reason=NOT_ASSOCIATED`、`canEnter=false`、`roomId=null`；不显示伪造准备中。 |
| B07-V08 | 房间观察过期后再读取 | 投影为 `unknown` 加 `OBSERVATION_STALE`，不继续显示旧 `ready`。 |
| B07-V09 | 主房间就绪后上游关闭 | 关联退役后入口消失；关联行保留可追溯，不按选仓重建入口。 |
| B07-V10 | SSE 断线、重复通知、过期游标 | 断线显示可能过期；重复通知合并；过期游标触发 `resync_required` 并要求重查。 |
| B07-V11 | SSE 连接期间失权 | 连接关闭并停止发送；不通过事件字段暗示隐藏房间存在。 |
| B07-V12 | 只读会话页头成功但消息读取未接入 | 页头正常显示；消息区域显示“历史读取未接入”，不显示空历史成功。 |
| B07-V13 | 会话内容范围扩大后继续翻旧游标 | 返回 `CONVERSATION_CONTEXT_CHANGED`，不混合旧水位与新范围。 |
| B07-V14 | 401 与换账号 | 清除对应身份的敏感草稿、派生缓存与订阅；新账号不能继承旧游标或旧响应。 |
| B07-V15 | 正文清理后读取详情、重放事件 | 详情返回 410 提案码；事件不可重放时要求重查；旧操作查询仍按 B06 返回移除占位。 |
| B07-V16 | 发布进程重启后重连订阅 | 按主库事件恢复或补齐；不因内存丢失漏发通知，也不把断连记成业务失败。 |
| B07-V17 | 旧 generation 或更小 `observation_revision` 的迟到观察到达 | 条件更新拒绝覆盖，页面继续显示较新的已提交状态。 |
| B07-V18 | 房间探测失败 | 写入 `unknown` 并保留原关联；恢复探测成功后按新 revision 覆盖，不新建第二条主房间关联。 |
| B07-V19 | Leader 房间引用仅内容仓、main 房间挂错会话 | 两条插入都被复合外键拒绝，投影不返回伪造 Leader 入口。 |
| B07-V20 | 列表游标落在 `repository_scopes` 工作标志之外 | `repositoryId` 过滤只按内容范围命中；工作范围键只用于 Leader 房间引用，不扩大列表结果。 |
| B07-V21 | 可信代次切换与普通观察交错 | 切换事务锁 Issue 与关联行、CAS 旧 `runtime_generation` 后登记新代次与首条观察；普通观察带旧代次或同代次不递增 revision 时被拒绝，代次按不透明身份比较，不按字符串排序。 |
