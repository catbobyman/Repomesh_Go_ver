# B09 真实 Manager 会话与投递（G1／G2）

本批对应施工计划中的 B09，范围是 G1 与 G2 的最小真实 Manager 往返。用户能完成的事情有三件。第一，在已建 Issue 的固定配置下或普通讨论的新请求下保存一条消息，并把这条消息可靠地交给该项目的 Manager 会话。第二，看到 Manager 的受控提问、目标判断、回复和通过工具创建的 Issue 结果，而不把聊天文本当成控制命令。第三，在响应丢失、进程重启、租约过期或旧会话回写时，按原操作身份恢复并区分本地已保存、外部已投递、Manager 已收到和实际已处理四种事实。

本批不包含 Worker 派工、Attempt 容器、跨仓执行、换图、预算编辑、更正系统和完整聊天面板。它还依赖 B06 的 Issue 固定配置绑定和 B07 的只读查询边界，但不等待它们全部实现即可评审。

### 1.2 用户能完成什么

用户在一个 Issue 相关的会话里发出真实消息后，可以确认消息已经本地保存，并在后续读取中看到它是否进入投递、是否被 Manager 会话接受、是否产生问题或回复。用户不需要理解协议细节，但页面必须把四种事实分开显示。本地保存成功不等于投递成功，投递成功不等于 Manager 收到，Manager 回复也不等于计划生效或 Worker 已开始工作。

普通讨论可以先于 Issue 存在。用户发出的每一条普通消息都走同一个消息保存用例，只有新的可恢复模型处理请求才固定配置。用户随后指定某个 Issue 时，后续受控动作核对该 Issue 的固定配置，讨论记录不倒填为 Issue 的创建配置。

普通会话在关联 Issue 前没有房间关联，Manager 会话的运行绑定由 `manager_sessions` 自身通过 `manager_instance_ref`、`transport_session_ref` 与 `state` 持有。会话关联 Issue 后，当前运行上下文写入该行的 `issue_id`，绑定按同项目、同 Issue、同会话引用该 Issue 的主房间投影；同项目同 Issue 的 Leader 房间只服务仓库执行派工，不绑 Manager 会话。房间关联不是普通会话准备的前置条件。同一会话仍可先后关联多个 Issue，当前代次只表达当前运行上下文；更换上下文必须新建代次。

## 2. API 设计

### 2.1 已有会话消息五端点

以下五条路径来自[消息澄清浏览器契约](../current/conversation-message-clarification-api-contract.md)第 1 节，状态为已采用设计、未实现。本章不新增字段，只在 §2.2 至 §2.6 说明调用约束和 B09 补上的投递语义。

| 方法与路径 | 作用 | 成功 |
| --- | --- | --- |
| `POST /api/projects/{projectId}/conversations/{conversationId}/messages` | 保存普通消息或带引用答复 | 201 首次，200 同键重放 |
| `GET /api/projects/{projectId}/conversations/{conversationId}/message-submissions/{submissionId}` | 原操作者核查原提交 | 200 同一不可变回执 |
| `GET /api/projects/{projectId}/conversations/{conversationId}/messages` | 按提交序号分页历史 | 200 |
| `GET /api/projects/{projectId}/conversations/{conversationId}/messages/{messageId}` | 定位原消息、问题或答复 | 200 单一投影 |
| `GET /api/projects/{projectId}/conversations/{conversationId}/clarifications/{clarificationId}` | 读取当前问题状态、可回复性和目标 | 200 |

五条路径都以当前内容范围核权，权限未知返回 503，不以空结果掩盖未知。分页高水位、游标和失权清理沿用契约，不在 B09 重开设计。

### 2.2 POST /api/projects/{projectId}/conversations/{conversationId}/messages

这是本批唯一新增消息的业务写入口。状态为已采用设计、未实现。B09 只补两点。第一，保存事务在首次提交成功时登记 `conversation_continue` 工作。第二，投递责任与消息同事务落库，但外部调用在事务外。

| 项目 | 内容 |
| --- | --- |
| 调用方 | 具备该会话发言资格且通过同源 Cookie 与 CSRF 校验的登录用户 |
| 方法与路径 | `POST /api/projects/{projectId}/conversations/{conversationId}/messages` |
| 幂等键 | `Idempotency-Key` 必须是 UUID，作用域 `(projectId, conversationId, actorUserId, entry=conversation_message, submissionId)` |
| 输入 | `content` 必填，非全空白，最多 20000 Unicode 标量；`replyTo` 可选，提供时为 `clarificationId` 与 `expectedRevision` 两个必填字段 |
| 返回 | `submissionId`、`status=committed`、`conversationId`、`messageId`、`sequence` 十进制字符串、`committedAt`、`replyTo.answeredRevision` 或 null、`links.message`、`links.operation` |
| 错误 | 400、401、403、404、409、410、413、422、429、503，业务码沿用契约第 5 节 |
| 授权与作用域 | 保存时核整个项目仓库范围并原子扩展会话内容范围，答复另核原问题、原请求和原操作者 |
| 并发与重放 | 同键同输入返回原回执，同键异输入 409，不覆盖正文；问题按行锁串行，不同键并发只有赢家整笔保存 |

设计理由。同一事务保存消息、序号、答复关联、原操作回执和投递待办，用户双击不会得到两条消息，响应丢失后重试仍返回第一次提交的消息。投递失败只影响投递观察，不把已保存消息回滚成失败。

### 2.3 GET /api/projects/{projectId}/conversations/{conversationId}/message-submissions/{submissionId}

状态为已采用设计、未实现。调用方是原操作者。返回与首次提交相同的不可变回执。404 `MESSAGE_SUBMISSION_NOT_FOUND` 只表示此刻没有可见提交，不证明原请求不会提交。结果清理后返回 410，键在项目保留期内不复用。它不返回当前 Manager 处理状态，投递状态由 §2.9 单独读取。

设计理由。原操作查询冻结的是当次提交事实，不随问题后来被替代或目标后来改变而改写。用户可以在网络不确定时安全重试，而不会因为当前状态变化得到与第一次不同的回执。

### 2.4 GET /api/projects/{projectId}/conversations/{conversationId}/messages

状态为已采用设计、未实现。调用方是当前内容范围可读的登录用户。`limit` 默认 50，范围 1 到 100，`cursor` 为不透明字符串。返回按会话提交序号升序的 `items` 与 `nextCursor`。每个 `Message` 投影包含 `id`、`sequence`、`author`、`content`、`createdAt`、`replyTo`、`clarificationId`。分页不承诺总数，不冻结问题处理状态。

设计理由。以提交序号排序并以高水位分页，避免页码在并发提交时漏消息或重复消息。处理状态另读，历史列表不会因为某条问题后来解决而改变遍历结果。

### 2.5 GET /api/projects/{projectId}/conversations/{conversationId}/messages/{messageId}

状态为已采用设计、未实现。返回单条消息投影，形状与列表项一致。`author.kind` 只允许 `user`、`manager`、`system`，作者由服务端可信入口产生，客户端不能提交。正文按不可信展示内容处理，不执行其中 HTML 或脚本。

设计理由。问题、答复和普通消息共用一种定位方式，恢复页面可以直接打开原消息，不必遍历整个会话；作者由服务端绑定，模型或用户无法伪造系统消息。

### 2.6 GET /api/projects/{projectId}/conversations/{conversationId}/clarifications/{clarificationId}

状态为已采用设计、未实现。返回 `id`、`revision`、`state`、`sourceMessageId`、`questionMessageId`、`answerMessageId`、`candidates`、`resolution`、`supersededBy`、`actions.canReply`、`reasonCodes`。状态只允许 `open`、`answer_saved`、`resolved`、`superseded`、`invalidated`。`resolution` 只在 `resolved` 非 null，`outcome=issue_target` 必须有 `issueId`，`outcome=no_work` 必须为 null。读取不授予执行权限。

设计理由。问题有稳定身份和修订，并发答复与旧页面回写会被拒绝，用户不会覆盖别人的答复，也不会因为按钮隐藏值被解释成正式目标。

### 2.7 POST /api/projects/{projectId}/conversations

状态为本次提案，未实现。它补齐契约明确留下的首条消息创建缺口。页面可以先创建业务会话并同时提交第一条消息，不拆成三次写操作。

| 项目 | 内容 |
| --- | --- |
| 调用方 | 项目 owner 或当前具备项目访问资格的登录用户 |
| 方法与路径 | `POST /api/projects/{projectId}/conversations` |
| 幂等键 | `Idempotency-Key` 为 UUID，作用域 `(projectId, actor, entry=conversation_create, creationId)` |
| 输入 | `title` 可选，1 到 200 字符；`firstMessage` 可选，提供时为 `{content:string}`，规则同 §2.2；`issueId` 可选，必须属于同项目且当前可读 |
| 返回 | `creationId`、`conversationId`、`title`、`revision`、`createdAt`、`messageId` 或 null、`sequence` 或 null、`links.conversation`、`links.operation` |
| 错误 | 400、401、403、404、409、410、422、429、503；新增 `409 CONVERSATION_CREATION_CONFLICT` 表示同键异参 |
| 授权与作用域 | 创建不扩大内容范围；有首条消息时按项目全仓范围保存消息并登记内容范围与投递待办 |
| 并发与重放 | 同键同输入返回原回执；同键异输入 409；两个不同键创建同名会话是两个独立会话 |

首条消息不新建另一套幂等作用域。它在 `message_submissions` 中使用 `entry=conversation_create_first_message`，`submission_id` 固定为本次 `creationId`，与 `entry=conversation_message` 的键空间隔离。`schemaVersion` 只用于选择比较器，不进入幂等主键。空会话创建不登记 Manager 准备工作，只有第一条消息提交成功才登记。不带 `issueId` 的普通会话同样走本节创建流程：它先没有房间关联，Manager 会话的运行绑定由 §3.10 自身持有，会话成为某 Issue 的主会话后才引用该 Issue 的房间投影。

### 2.8 GET /api/projects/{projectId}/conversations/{conversationId}/manager-session

状态为本次提案，未实现。调用方是当前会话可读用户。返回 `bindingId`、`issueId`（当前运行上下文，可为 null）、`state`、`managerSessionEpoch`、`observedAt`、`reasonCodes`。`state` 只允许 `unbound`、`preparing`、`ready`、`degraded`、`unknown`。它不返回上游实例名、房间标识、会话密钥或工具凭据。房间与会话的具体传输引用留在服务端，避免页面把可变传输标识当业务身份。该读取不触发准备或投递。

设计理由。页面可以区分会话是否可用，却拿不到可被误用的传输凭据。替换房间或运行实例时，本地业务身份不随外部短名改变。

### 2.9 GET /api/projects/{projectId}/conversations/{conversationId}/message-deliveries/{messageId}

状态为本次提案，未实现。调用方是当前会话可读用户。返回 `messageId`、`state`、`observedAt`、`reasonCode`、`attemptCount`。`state` 只允许 `prepared`、`may_have_sent`、`accepted_by_transport`、`observed_at_manager`、`reconcile_required`、`failed_before_send`。探测失败不新增状态值，`state` 保持最近已证实的推进值或进入 `reconcile_required`，`reasonCode` 说明未证实原因。它不返回上游请求编号、凭据或原始响应正文。该读取不重发。页面把它与 §2.2 的本地回执分开显示。

状态为本次提案，未实现。只有可信运行适配器认证为本项目 Manager 且绑定实际实例、会话、代次的调用可以提交控制动作。服务端为每个处理步骤签发短期、不可转移的调用授权引用，并把 `authenticatedService`、`managerSessionEpoch`、`project`、`conversation`、`actor`、`logicalRequest`、`sourceMessage`、`inputKind`、`acceptedAnswer`、`sourceVersions`、`processingWorkId`、`claimGeneration`、`leaseUntil`、`expectedRequestRevision`、`expectedQuestionRevision`、`commandSlotId`、`allowedActions`、`expiresAt` 写入 `manager_call_authorizations`。模型不能自报 role、actor、conversationId 或授权值。

### 2.14 内部边界：MCP 工具与动作

`repomesh_create_issue` 与 `repomesh_get_issue_creation` 的工具名已采用，来源见[Manager 工具专题](../current/manager-create-issue-tool-design.md)。完整可执行 JSON Schema、传输身份与注入口仍是本次提案、未实现。首版建议只给项目 Manager 暴露这两个工具，输入与页面创建共用 `expectedCreationContextRevision`、`title`、`description`、`repositoryIds`、`acceptanceCriteria`，另由可信适配层承接逻辑创建操作引用与来源消息引用。项目、发起人、Manager 身份和来源会话由上下文绑定。

澄清控制动作沿用[消息后端设计](../current/backend-message-clarification-design.md)第 6 节的建议动作名 `propose_clarification`、`decide_message_target`、`replace_clarification`、`get_message_control_result`。它们是内部能力候选，不是已注册 MCP 工具。每次提交核 `commandSlotId`、`claimGeneration`、`managerSessionEpoch`、问题修订与答复身份，任何不符返回内部 `STALE_PROCESSING_CONTEXT`，不追加公开已解决记录。

### 2.15 内部边界：configuration.ResolveIssueConfiguration

状态为本次提案，未实现。它把 Issue 的 `initialConfigurationRevision` 解析为一次受控模型调用所需的不可变闭包。签名建议如下。

type ResolvedConfiguration struct {

    ProjectID                string

    ModelProfileVersion      string

    ProviderRevision         string

func (s *Service) ResolveIssueConfiguration(ctx context.Context, tx pgx.Tx, projectID, issueID string) (ResolvedConfiguration, error)

解析沿 Issue、ProjectConfigRevision、ModelProfileVersion、ProviderRevision、ModelSnapshot、SecretVersion，以及 ExecutionProfileVersion、模板、预算和时限政策。解析不做 latest 查找。材料缺失或被限制时返回 `CONFIGURATION_UNAVAILABLE` 并保持 blocked，不自动换 Key、不换 profile、不静默使用项目当前配置。普通讨论按新的模型处理请求固定当时配置，重试和重启沿原请求引用。

## 3. 数据表设计

以下表名、schema 与字段是本次提案，未实现。物理 schema 建议使用 `repomesh_messaging`，实施时在现有 0001 至 0006 迁移之后追加。本章不新增通用 operation、job 或 event 表，也不把任何表写成“登记到 foundations 的共享框架”。各业务域保留自己的操作回执。后台工作复用[首批持久化设计](../current/backend-first-batch-persistence.md)第 3 节已经采用的 DurableWork 机制，消息解释使用本章的 `message_processing_entries`，投递使用 `message_deliveries`，两者都由对应域持有。跨项目引用一律带 `project_id` 复合约束，外键默认 RESTRICT。所有 `JSONB` 载荷都必须带版本字段并说明权威来源。

### 3.1 message_submissions

用途是保存一次消息提交的幂等身份和确切输入。写入者是 `messaging.Service.SubmitMessage` 和会话创建用例。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| submission_id | text | 是 | 主键；服务端生成或由会话创建键派生，永不复用 |
| project_id | text | 是 | 引用项目 |
| conversation_id | text | 是 | 同项目复合外键到 conversations |
| actor | text | 是 | 引用账号 |
| entry | text | 是 | `conversation_message` 或 `conversation_create_first_message` |
| schema_version | integer | 是 | 比较器版本，不进入唯一键 |
| exact_content | bytea | 否 | 确切正文与引用，removed 后清空 |
| canonical_input | bytea | 否 | 规范化输入，removed 后清空 |
| message_id | text | 否 | 成功结果，removed 后保留必要归属 |
| committed_at | timestamptz | 否 | 提交时间 |
| removed_at | timestamptz | 否 | 正文清理时间 |

唯一约束为 `(project_id, conversation_id, actor, entry, submission_id)`。检查约束保证每行只有完整提交或无正文墓碑两种可见形态。删除正文时清空 exact_content 与 canonical_input，保留作用域、键、结果归属和内容权限范围。

### 3.2 conversation_messages

用途是保存不可变消息事实和会话内提交序号。写入者与 §3.1 相同，Manager 回复入口也写本表但作者为 manager。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| id | text | 是 | 主键，服务端生成 |
| project_id | text | 是 | 项目归属 |
| conversation_id | text | 是 | 会话归属 |
| committed_sequence | bigint | 是 | 会话内提交顺序，正数 |
| author_kind | text | 是 | `user`、`manager` 或 `system` |
| actor | text | 否 | 用户消息必填，服务消息为空 |
| service_binding_id | text | 否 | Manager 消息必填，引用 manager_sessions |
| content | text | 是 | 消息原文，最长 20000 Unicode 标量 |
| reply_to_clarification_id | text | 否 | 用户答复引用 |
| clarification_id | text | 否 | 服务端问题消息引用 |
| created_at | timestamptz | 是 | 提交时间 |
| removed_at | timestamptz | 否 | 正文清理时间 |

唯一约束为 `(project_id, conversation_id, committed_sequence)` 与 `(project_id, conversation_id, id)`。检查约束保证用户消息有 actor 且无 service_binding_id，Manager 消息相反。正文不可变，删除时用墓碑并清空 content，同时移除派生摘要。

### 3.3 conversation_message_counters

用途是在会话行锁下分配提交序号。写入者是所有消息写路径。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| conversation_id | text | 是 | 主键并引用会话 |
| project_id | text | 是 | 同项目复合约束 |
| last_sequence | bigint | 是 | 已提交最大序号，默认 0 |
| updated_at | timestamptz | 是 | 最近分配时间 |

所有写路径先锁本行再分配序号并持锁到提交，避免已见大序号后晚提交小序号。序号允许间隙，不承诺连续。

### 3.4 message_processing_entries

用途是为每条真实消息登记稳定的处理入口。写入者是消息提交事务。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| entry_id | text | 是 | 主键 |
| message_id | text | 是 | 引用消息 |
| handler | text | 是 | 首期只允许 `interpret_message` |
| state | text | 是 | `ready`、`claimed`、`done`、`blocked`、`retry_wait` |
| claim_generation | bigint | 是 | 领取代次，默认 0 |
| lease_until | timestamptz | 否 | 当前领取租约 |
| next_run_at | timestamptz | 是 | 下次可扫描时间 |
| created_at | timestamptz | 是 | 创建时间 |

唯一约束为 `(message_id, handler)`。队列重试复用同一行，不生成新请求。租约到期不等于旧进程停止，只表示可以重新领取；旧代次回写必须被拒绝。

### 3.5 logical_work_requests

用途是固定一条消息的一次单项解释身份。写入者是 coordinator 的首次处理事务。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| id | text | 是 | 主键 |
| project_id | text | 是 | 项目归属 |
| conversation_id | text | 是 | 会话归属 |
| processing_entry_id | text | 是 | 引用处理入口 |
| root_source_message_id | text | 是 | 根来源消息，创建后不可重绑 |
| source_revision | bigint | 是 | 来源修订 |
| source_unit | text | 是 | 首期只允许 `whole_message_single_request` |
| actor | text | 是 | 原操作者 |
| state | text | 是 | `pending`、`awaiting_clarification`、`answer_pending`、`resolved`、`needs_decomposition`、`invalidated` |
| current_question_id | text | 否 | 当前问题指针 |
| resolution_id | text | 否 | 最终解释指针 |
| revision | bigint | 是 | 请求修订 |
| created_at | timestamptz | 是 | 创建时间 |

唯一约束为 `(processing_entry_id, source_unit)`。`state` 不是 Issue 生命周期。`resolved` 的 outcome 只有 `issue_target` 或 `no_work`，不授权计划修改或派工。

### 3.6 clarifications

用途是保存 Manager 发布的公开问题及其修订。写入者是受控控制动作。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| id | text | 是 | 主键，服务端生成，永久不复用 |
| logical_request_id | text | 是 | 引用逻辑请求 |
| source_message_id | text | 是 | 原来源消息 |
| question_message_id | text | 是 | 同事务发布的问题消息 |
| revision | bigint | 是 | 问题修订 |
| state | text | 是 | `open`、`answer_saved`、`resolved`、`superseded`、`invalidated` |
| candidates | jsonb | 是 | 版本化候选数组，可为空，最多 20 条 |
| superseded_by | text | 否 | 后继问题 |
| invalidation_reason | text | 否 | 非敏感失效原因 |
| created_at | timestamptz | 是 | 创建时间 |
| updated_at | timestamptz | 是 | 最近状态时间 |

部分唯一索引 `(logical_request_id)` 在 `state in ('open','answer_saved')` 时成立，保证同一请求同一时刻至多一个可答复问题。候选按 `issueId` 去重，按集合比较，省略等价空集合。

### 3.7 clarification_answers

用途是保存唯一有效答复并锁住所消费的问题修订。写入者是答复提交事务。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| clarification_id | text | 是 | 主键并引用问题 |
| answer_message_id | text | 是 | 唯一引用答复消息 |
| submission_id | text | 是 | 引用消息提交 |
| actor | text | 是 | 答复者，必须等于原请求操作者 |
| answered_revision | bigint | 是 | 提交前问题修订 |
| answered_at | timestamptz | 是 | 提交时间 |

`clarification_id` 与 `answer_message_id` 都唯一。不同键并发答复同一问题时只有赢家整笔提交，输家 409 且不保存孤立消息。`answered_revision` 永远是提交前版本，不回写为当前版本。

### 3.8 target_resolutions

用途是保存一条逻辑请求的最终目标解释。写入者是 `decide_message_target` 成功事务。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| id | text | 是 | 主键 |
| logical_request_id | text | 是 | 唯一引用逻辑请求 |
| input_kind | text | 是 | `root_message` 或 `clarification_answer` |
| source_message_id | text | 是 | 依据消息 |
| accepted_answer_id | text | 否 | 答复分支必填 |
| outcome | text | 是 | `issue_target` 或 `no_work` |
| issue_id | text | 否 | 目标 Issue |
| request_revision | bigint | 是 | 判断时请求修订 |
| control_operation_id | text | 是 | 引用控制操作 |
| created_at | timestamptz | 是 | 创建时间 |

检查约束为 `issue_target` 必须有同项目可读 `issue_id`，`no_work` 必须为空。该表唯一约束保证同一请求最多一个最终解释，提交后不原地换目标。

### 3.9 control_operations

用途是保存一次受控控制动作的稳定身份和不可变结果。写入者是 `messaging` 控制事务。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| command_slot_id | text | 是 | 主键，协调器分配，跨领取代次不变 |
| action | text | 是 | `propose_clarification`、`decide_message_target`、`replace_clarification` 或 `get_message_control_result` |
| schema_version | integer | 是 | 比较器版本 |
| canonical_input | bytea | 否 | 规范化输入，removed 后清空 |
| result | jsonb | 否 | 不可变结果，removed 后清空 |
| committed_at | timestamptz | 否 | 提交时间 |
| removed_at | timestamptz | 否 | 清理时间 |

`command_slot_id` 唯一。同槽位不同动作或不同输入返回冲突，不覆盖首个成功结果。旧领取者写入因代次失效被拒绝，但已提交结果可在当前可信作用域查询。

### 3.10 manager_sessions

用途是把项目会话映射到当前 Manager 会话代次。写入者是 `BindingService.Ensure` 与 coordinator 观察器。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| id | text | 是 | 主键 |
| project_id | text | 是 | 项目归属 |
| conversation_id | text | 是 | 会话归属 |
| issue_id | text | 否 | 当前运行上下文的 Issue；无 Issue 的普通会话为空 |
| room_link_id | text | 否 | 非空时要求 `issue_id` 非空，并与 `project_id`、`issue_id`、`conversation_id` 一起引用 B07 的 `issue_room_links(project_id, issue_id, conversation_id, room_link_id)`；该目标是主房间，Leader 房间不能绑定 Manager 会话 |
| manager_instance_ref | text | 是 | 上游实例不透明引用 |
| manager_session_epoch | bigint | 是 | Manager 会话代次 |
| transport_session_ref | jsonb | 是 | 版本化不透明 Manager 会话引用，只表达会话，不进入浏览器 |
| state | text | 是 | `unbound`、`preparing`、`ready`、`degraded`、`unknown` |
| superseded_at | timestamptz | 否 | 代次被替换时间；为空表示当前代次 |
| observed_at | timestamptz | 否 | 最近观察时间 |
| created_at | timestamptz | 是 | 创建时间 |
| updated_at | timestamptz | 是 | 最近更新时间 |

唯一约束为 `(project_id, conversation_id, manager_session_epoch)`，另用部分唯一索引 `(project_id, conversation_id) WHERE superseded_at IS NULL` 保证每个会话至多一个当前代次。写路径要求本行 `superseded_at IS NULL`；旧代次保留但失去写权限。检查约束为 `room_link_id IS NULL OR issue_id IS NOT NULL`。普通会话先于 Issue 存在，它的运行绑定由本行的 `manager_instance_ref`、`transport_session_ref` 与 `state` 承担，不等待也不伪造 B07 房间关联。会话关联 Issue 后，`(project_id, issue_id, conversation_id, room_link_id)` 四列一起引用 B07 `repomesh_issues.issue_room_links` 的同名唯一键；B07 的主房间与 Leader 房间互斥检查保证非空 `conversation_id` 只能引用该会话的主房间，跨项目、跨 Issue、跨会话或 Leader 房间的引用都被拒绝。更换当前 Issue 上下文或房间引用必须新建代次并把旧行写 `superseded_at`，不允许原地改写。B07 表保持 `issue_id` 非空，只为已有 Issue 登记关联，不为无 Issue 会话造行。`manager_session_epoch` 表示 Manager 逻辑会话代次，与 room 观察的 `runtime_generation` 是两个事实，不能互相替代。`transport_session_ref` 必须带 `schemaVersion` 与来源；房间标识、裸 room_id 与房间观察不在这里复制。具体传输编码不在本批冻结。

### 3.11 manager_call_authorizations

用途是为一次处理步骤签发短期、不可转移的调用授权。写入者是控制步骤领取事务。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| id | text | 是 | 主键 |
| manager_session_id | text | 是 | 引用会话绑定 |
| logical_request_id | text | 是 | 业务作用域 |
| conversation_id | text | 是 | 会话作用域 |
| processing_work_id | text | 是 | 引用持久待办 |
| claim_generation | bigint | 是 | 领取代次 |
| lease_until | timestamptz | 是 | 数据库时钟判断的租约 |
| input_kind | text | 是 | `root_message` 或 `clarification_answer` |
| accepted_answer_id | text | 否 | 答复分支固定依据 |
| expected_request_revision | bigint | 是 | 防旧判断覆盖 |
| expected_question_revision | bigint | 否 | 有问题时必填 |
| command_slot_id | text | 是 | 固定控制槽位 |
| allowed_actions | text[] | 是 | 互斥动作白名单 |
| expires_at | timestamptz | 是 | 授权过期 |

授权引用只由适配器附加为传输凭据，不放进公开消息、浏览器 URL 或模型可填写字段。后端每次从数据库重建约束并核撤销与代次，不只验签。

### 3.12 message_deliveries

用途是保存一条消息的稳定外部投递身份。写入者是消息提交事务，状态由 Dispatcher 推进。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| id | text | 是 | 主键 |
| message_id | text | 是 | 唯一引用消息 |
| manager_session_id | text | 是 | 目标 Manager 会话 |
| external_operation_id | text | 是 | 唯一外部逻辑操作身份 |
| state | text | 是 | `prepared`、`may_have_sent`、`accepted_by_transport`、`observed_at_manager`、`reconcile_required`、`failed_before_send` |
| claim_generation | bigint | 是 | 领取代次 |
| lease_until | timestamptz | 否 | 领取租约 |
| may_have_sent_at | timestamptz | 否 | 只能由空变非空 |
| observation_revision | bigint | 是 | 观察修订，默认 0，只有更高修订能覆盖最新观察 |
| last_observation_source | text | 否 | `transport`、`manager` 或 `maintenance` |
| last_observed_state | text | 否 | 最近一次观察状态，允许 `prepared`、`may_have_sent`、`accepted_by_transport`、`observed_at_manager`、`reconcile_required`、`failed_before_send`、`unknown` |
| last_evidence | jsonb | 否 | 版本化证据摘要，不存凭据 |
| last_observed_at | timestamptz | 否 | 最近观察时间 |
| created_at | timestamptz | 是 | 创建时间 |

唯一约束为 `external_operation_id` 与 `message_id`。`claim_generation` 不是外部消息编号。投递重试复用同一 `external_operation_id`，新逻辑投递才生成新行。状态到 `may_have_sent` 后不得再改投递目标或换会话。观察按 `observation_revision` 条件更新，低修订或旧 `claim_generation` 的迟到观察被拒绝；探测失败只把 `last_observed_state` 写成 `unknown`，`state` 保持最近已证实的推进值或进入 `reconcile_required`，并保留原关联，不删除、不降级会话绑定。

本表只引用 `manager_session_id`，不保存裸 room_id。Issue 房间的身份、可用性、观察修订和运行代次由 B07 的 `repomesh_issues.issue_room_links` 持有；无 Issue 的普通会话没有房间投影，投递只依赖会话自身的运行绑定。本表不新增第二套 room 或 room 观察记录。

### 3.13 manager_calls

用途是 G1 的实际消费证据。它记录一次受控模型调用的固定配置闭包、外部操作身份和观察结果，防止重启后无法证明某个 Issue 使用了哪个版本。写入者是 `manager.CallService`。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| id | text | 是 | 主键 |
| project_id | text | 是 | 项目归属 |
| conversation_id | text | 是 | 会话归属 |
| logical_request_id | text | 是 | 引用逻辑请求 |
| issue_id | text | 否 | Issue 目标分支必填 |
| purpose | text | 是 | `message_interpretation` 或 `manager_turn` |
| attempt_generation | bigint | 是 | 逻辑调用重试代次 |
| configuration_revision | text | 否 | Issue 固定配置修订，普通讨论为空 |
| model_profile_id | text | 是 | 模型 profile |
| model_profile_version | text | 是 | 不可变版本 |
| provider_revision | text | 是 | Provider 修订 |
| row_id | text | 是 | 模型行 |
| secret_version_id | text | 是 | 确切秘密版本身份 |
| execution_profile_version | text | 否 | 执行政策版本 |
| resolved_config | jsonb | 是 | 不含秘密的版本化快照 |
| resolved_digest | text | 是 | 快照摘要 |
| state | text | 是 | `prepared`、`may_have_sent`、`observed`、`reconcile_required`、`failed_before_send`、`blocked` |
| external_operation_id | text | 否 | 唯一外部逻辑操作身份 |
| may_have_sent_at | timestamptz | 否 | 只能由空变非空 |
| observed_at | timestamptz | 否 | 最近观察 |
| usage | jsonb | 否 | 版本化用量或计费证据，可为空 |

唯一约束为 `(logical_request_id, purpose, attempt_generation)` 与 `external_operation_id`。`resolved_config` 只保存非秘密版本与参数，秘密正文仍由 secrets 层持有。`state` 进入 `may_have_sent` 后不得更改闭包；需要换版本必须新建逻辑请求，不能原地覆盖。本表只记录 B09 的 Manager 调用事实，与 B05 的用户测试记录 `models.tests` 身份不同、证据目的不同，不能互相替代。Manager 调用也必须核项目运行预算策略，若 B05 的项目运行额度 scope 尚未采用则保持 blocked；它不复用 `actor_model_test` 的额度数值，也不凭空假定一个额度。

本节回应共同规则中“新增提案要有出处，能被合并的就合并”的要求。保留的表都能说明唯一事实、写入者、生命周期和查询需求；合并项在此列明。

| 表 | 必要性出处 | 结论 |

## 4. 事务与恢复

### 4.1 正常流程

消息提交在一个短事务内完成原操作检查、会话与内容范围核权、序号分配、消息、答复关联、回执和投递待办。提交后才返回 201。协调器扫描待办，先确保项目会话有可用 Manager 绑定，再解析配置并登记 `manager_calls`。发送前在短事务中写 `may_have_sent_at`，外部调用在事务外，返回后按 `observation_revision` 条件更新投递观察，低修订迟到观察不覆盖当前事实。Manager 的控制工具调用核调用授权与代次，成功结果和公开回复同事务保存。

本次提案规定会话绑定的房间规则。普通会话在关联 Issue 前的准备只依赖 `manager_sessions` 自身的 `manager_instance_ref`、`transport_session_ref` 与 `state`，`issue_id` 与 `room_link_id` 保持为空。会话成为某 Issue 的主会话后，准备与观察事务新建一代次并在该代次写 `issue_id`；房间可用时把 `room_link_id` 指向该 Issue 在同项目、同会话的主房间关联。当前 Issue 上下文从空变非空、Issue 之间切换、或房间引用变更，都必须新建代次并把旧行写 `superseded_at`，同一代次不允许原地改指；校验失败返回冲突并保留原绑定，不写跨项目、跨 Issue、跨会话或 Leader 房间的引用。房间观察由 coordinator 写入 B07，本批只读该引用；探测失败不改写本表 `state`，也不清空已有引用。

### 4.2 重试分层

| 层级 | 身份 | 允许行为 | 禁止行为 |
| --- | --- | --- | --- |
| 传输重试 | 同一 `external_operation_id` | 按原身份查询或重发同一请求 | 生成新外部编号或新消息 |
| 逻辑调用重试 | 同一 `logical_request_id` 与 `purpose`，`attempt_generation` 递增 | 确认未发送后按原配置再调用 | 换配置、换 Key、换会话 |
| 修复轮次 | 业务轮次，见 B11 | 形成新计划修订和一至多个新任务 | 用传输重试冒充业务修复 |

三层分开记录。同一次网络超时不能计数为一次业务修复，也不能因为业务重试而绕过累计上限。

### 4.3 响应丢失与同键异参

消息提交的 COMMIT 回执丢失时返回 `RESULT_UNCONFIRMED`。原操作查询先按 `submissionId` 读主库，404 不证明请求不会提交，不自动换键。同键不同正文、引用或 entry 返回 409，不覆盖原记录。会话创建的响应丢失沿用同一规则，重试返回同一会话和同一条首消息。

投递发送后响应丢失时，不得直接重发。先按 `external_operation_id` 查询传输侧事实；没有可靠查询能力时停在 `reconcile_required`，保留核查责任，不生成第二条消息。模型调用响应丢失时同样先查原调用，已 `may_have_sent` 的调用不得换成新秘密版本重发。

### 4.4 并发

消息写路径使用固定锁序 `actor 本地访问版本、project、conversation、logical_request、clarification、操作槽位`。有多个同类对象时按 ID 排序。所有问题替换、接收、解决、失效和正文清理遵守同一顺序。先取得输入范围的有效观察，不持锁调用 GitHub 或模型。

两个不同操作键同时答复同一个 open 问题时按请求与问题行锁串行。首个有效事务保存答复并升修订，另一个返回 409，整笔消息不保存。即使正文相同也不按文本合并。同一 pending 请求的直接判断与提问竞争时，请求行 CAS 和 resolution 唯一约束只允许一个结果。

### 4.5 崩溃与重启

事务未提交时数据库回滚，不存在半条消息、问题或投递。提交完成但唤醒丢失时，扫描器按已提交待办重新发现，不新建消息或问题。模型处理后尚未持久控制结果时，新领取者复用原 `commandSlotId` 与输入依据，旧领取者写入因代次失效被拒绝。已 resolved 但后续待办未运行时，扫描 `TargetResolution` 产生的唯一待办，不重复确定目标。重启后普通会话按自身运行绑定恢复，不因缺少房间关联阻塞或重建绑定；已关联 Issue 的会话按原 `issue_id`、`room_link_id` 与代次恢复，不自动改写关联，也不自动推进代次。

解释时权限未知或配置不可用时，保留 `answer_saved` 与原来源，待核条件恢复后按原请求核验，不重新开放问题让用户重复回答，也不静默换模型版本。

### 4.6 迟到结果与旧代次

旧 Manager 会话代次、过期租约或已被替换的问题回写只返回内部 `STALE_PROCESSING_CONTEXT`，不追加公开已解决记录。已提交控制结果仍可在当前可信作用域按原槽位查询，但不能据此授权新的副作用。旧外部调用可能已经发出时保留核查责任，不把本地清理当作外部取消成功。

### 4.7 删除与保留

本批不新增浏览器删除路由。正文清理在同事务中清除确切输入、规范化输入、消息正文、派生公开文本和可还原正文的副本，设置 `removed_at` 并保留作用域、键、必要结果归属与内容权限范围。清理后当前有权者查询和重放返回 410，不再比较新输入，不复活旧键。配置、秘密与调用的版本身份在仍被引用时不可级联删除；秘密正文可销毁，但版本身份与不可用事实保留。未知外发结果在清理前必须先核查，保留证据与重新评估条件。

## 7. 待取舍点

| 取舍 | 选项 | 影响 | 本章默认写法 |
| --- | --- | --- | --- |
| 普通讨论的配置固定单位 | 按一次可恢复模型处理请求固定，或按整段会话固定 | 决定 `manager_calls.configuration_revision` 是否为空以及新请求能否选新配置 | 按请求固定，沿用配置绑定专题第 6 节的候选方向 |

| 完整 MCP Schema | 本次冻结首版可执行 Schema，或保留工具名与适配层契约 | 影响外部契约稳定性与后续兼容成本 | 工具名已采用，Schema 与调用身份仍为候选 |
