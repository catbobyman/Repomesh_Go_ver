# B09 真实 Manager 会话与投递（G1／G2）

本批对应施工计划中的 B09，范围是 G1 与 G2 的最小真实 Manager 往返。用户能完成的事情有三件。第一，在已建 Issue 的固定配置下或普通讨论的新请求下保存一条消息，并把这条消息可靠地交给该项目的 Manager 会话。第二，看到 Manager 的受控提问、目标判断、回复和通过工具创建的 Issue 结果，而不把聊天文本当成控制命令。第三，在响应丢失、进程重启、租约过期或旧会话回写时，按原操作身份恢复并区分本地已保存、外部已投递、Manager 已收到和实际已处理四种事实。

本批不包含 Worker 派工、Attempt 容器、跨仓执行、换图、预算编辑、更正系统和完整聊天面板。它还依赖 B06 的 Issue 固定配置绑定和 B07 的只读查询边界，但不等待它们全部实现即可评审。

2026-09-15 的物理布局复核把本章原来的 13 张候选表合并为 6 张 `repomesh_messaging` 表。合并只改物理承载，已采用的逻辑身份、唯一性、作用域、事务、恢复和清理语义不变。消息计数与独立会话创建回执移入 B06 的 `repomesh_issues.conversations`，字段由 B06 声明，本章不重复建表。B01 至 B04 的 36 张已有表（含 1 张系统表）、字段、约束与 API 保持不动。本章六张表与全部新字段仍是提案，未实现、未落库。

### 1.1 物理表布局：原 13 张降为 6 张

合表理由按用户能感受到的后果说明。

- 一次用户提交和它产生的消息本来在同一事务、一对一提交，拆成两张表只会多一种半成品形态。提交身份成为消息行的字段组，重放仍按 submissionId 查到同一条消息。
- 会话序号只是会话行上的一个计数。放进 `conversations` 后，所有消息写路径继续锁会话行并持锁到提交，分页高水位直接读该列，后台少维护一张只有两列的行。
- 一条逻辑请求首期就是一条根消息的单项解释，入口行与请求行一一对应。请求身份、来源、状态和修订作为入口行字段组保留，答复入口只引用根请求，不会伪造第二个请求。
- 授权回答的是“当前这一步能不能调用”，同一入口同一时刻只有一个当前步骤，把步骤依据与授权凭据放在入口行与这个基数一致。会话可以同时容纳多个待处理请求，把授权压回会话单槽会给讨论加一条假的串行限制，把多份授权塞进 JSON 又会失去明确键和约束。
- 一个问题的唯一答案本来按 clarificationId 定位，答案是问题行上的字段组。并发第二份答复仍被同一行约束拒绝，清理正文也不会解除唯一性。
- 目标解释只由 `decide_message_target` 的成功提交产生。把解释、依据版本和后续核验责任放在同一条控制行上，可以一次原子提交，不需要在控制结果 JSON 里再挖权威目标。
- 投递和模型调用都是“一次可能已经发出的外部动作”，共用不可变外部身份、发送前事实、租约围栏、迟到观察和正文清理规则。共用一张 `manager_executions` 表并分成两个受限子型，一次消息投递与一次模型调用各占一行，分支字段是完整的类型化列与 CHECK，不是一个通用载荷。

### 1.4 用户能完成什么

用户在一个 Issue 相关的会话里发出真实消息后，可以确认消息已经本地保存，并在后续读取中看到它是否进入投递、是否被 Manager 会话接受、是否产生问题或回复。用户不需要理解协议细节，但页面必须把四种事实分开显示。本地保存成功不等于投递成功，投递成功不等于 Manager 收到，Manager 回复也不等于计划生效或 Worker 已开始工作。

普通讨论可以先于 Issue 存在。用户发出的每一条普通消息都走同一个消息保存用例，只有新的可恢复模型处理请求才固定配置。用户随后指定某个 Issue 时，后续受控动作核对该 Issue 的固定配置，讨论记录不倒填为 Issue 的创建配置。

普通会话在关联 Issue 前没有房间关联，Manager 会话的运行绑定由 `manager_sessions` 自身通过 `manager_instance_ref`、`transport_session_ref` 与 `state` 持有。会话关联 Issue 后，当前运行上下文写入该行的 `issue_id`，绑定按同项目、同 Issue、同会话引用该 Issue 的主房间投影。同项目同 Issue 的 Leader 房间只服务仓库执行派工，不绑 Manager 会话。房间关联不是普通会话准备的前置条件。同一会话仍可先后关联多个 Issue，当前代次只表达当前运行上下文，更换上下文必须新建代次。

## 2. API 设计

### 2.1 已有会话消息五端点

以下五条路径来自[消息澄清浏览器契约](../current/conversation-message-clarification-api-contract.md)第 1 节，状态为已采用设计、未实现。本章不新增字段，只在 §2.2 至 §2.6 说明调用约束和 B09 补上的投递语义。

| 方法与路径 | 作用 | 成功 |
| --- | --- | --- |
| `POST /api/projects/{projectId}/conversations/{conversationId}/messages` | 保存普通消息或带引用答复 | 201 首次，200 同键重放 |
| `GET /api/projects/{projectId}/conversations/{conversationId}/message-submissions/{submissionId}` | 原操作者核查原提交 | 200 同一不可变回执 |
| `GET /api/projects/{projectId}/conversations/{conversationId}/messages` | 按提交序号分页历史 | 200 |
| `GET /api/projects/{projectId}/conversations/{conversationId}/messages/{messageId}` | 定位原消息、问题或答复 | 200 单一投影 |
| `GET /api/projects/{projectId}/conversations/{conversationId}/clarifications/{clarificationId}` | 读取当前问题状态、可回复性和目标 | 200 |

五条路径都以当前内容范围核权，权限未知返回 503，不以空结果掩盖未知。分页高水位、游标和失权清理沿用契约，不在 B09 重开设计。

### 2.2 POST /api/projects/{projectId}/conversations/{conversationId}/messages

这是本批唯一新增消息的业务写入口。状态为已采用设计、未实现。B09 只补两点。第一，保存事务在首次提交成功时写入本消息的处理入口行与投递行，即 `message_processing_entries` 和 `manager_executions` 的 `kind='message_delivery'` 行。第二，投递责任与消息同事务落库，但外部调用在事务外。

| 项目 | 内容 |
| --- | --- |
| 调用方 | 具备该会话发言资格且通过同源 Cookie 与 CSRF 校验的登录用户 |
| 方法与路径 | `POST /api/projects/{projectId}/conversations/{conversationId}/messages` |
| 幂等键 | `Idempotency-Key` 必须是 UUID，作用域 `(projectId, conversationId, actorUserId, entry=conversation_message, submissionId)` |
| 输入 | `content` 必填，非全空白，最多 20000 Unicode 标量。`replyTo` 可选，提供时为 `clarificationId` 与 `expectedRevision` 两个必填字段 |
| 返回 | `submissionId`、`status=committed`、`conversationId`、`messageId`、`sequence` 十进制字符串、`committedAt`、`replyTo.answeredRevision` 或 null、`links.message`、`links.operation` |
| 错误 | 400、401、403、404、409、410、413、422、429、503，业务码沿用契约第 5 节 |
| 授权与作用域 | 保存时核整个项目仓库范围并原子扩展会话内容范围，答复另核原问题、原请求和原操作者 |
| 并发与重放 | 同键同输入返回原回执，同键异输入 409，不覆盖正文。问题按行锁串行，不同键并发只有赢家整笔保存 |

设计理由。同一事务保存消息、序号、答复关联、原操作回执和投递责任，用户双击不会得到两条消息，响应丢失后重试仍返回第一次提交的消息。投递失败只影响投递观察，不把已保存消息回滚成失败。

### 2.3 GET /api/projects/{projectId}/conversations/{conversationId}/message-submissions/{submissionId}

状态为已采用设计、未实现。调用方是原操作者。返回与首次提交相同的不可变回执，回执由 `conversation_messages` 的提交字段组、messageId、conversationId、提交序号与提交时间重建。404 `MESSAGE_SUBMISSION_NOT_FOUND` 只表示此刻没有可见提交，不证明原请求不会提交。结果清理后返回 410，键在项目保留期内不复用。它不返回当前 Manager 处理状态，投递状态由 §2.9 单独读取。

设计理由。原操作查询冻结的是当次提交事实，不随问题后来被替代或目标后来改变而改写。用户可以在网络不确定时安全重试，而不会因为当前状态变化得到与第一次不同的回执。

### 2.4 GET /api/projects/{projectId}/conversations/{conversationId}/messages

状态为已采用设计、未实现。调用方是当前内容范围可读的登录用户。`limit` 默认 50，范围 1 到 100，`cursor` 为不透明字符串。返回按会话提交序号升序的 `items` 与 `nextCursor`。每个 `Message` 投影包含 `id`、`sequence`、`author`、`content`、`createdAt`、`replyTo`、`clarificationId`。分页不承诺总数，不冻结问题处理状态。

设计理由。以提交序号排序并以高水位分页，避免页码在并发提交时漏消息或重复消息。高水位读 B06 会话行的消息计数字段，处理状态另读，历史列表不会因为某条问题后来解决而改变遍历结果。序号和修订是不透明字符串，客户端不按数值解析比较。

### 2.5 GET /api/projects/{projectId}/conversations/{conversationId}/messages/{messageId}

状态为已采用设计、未实现。返回单条消息投影，形状与列表项一致。`author.kind` 只允许 `user`、`manager`、`system`，作者由服务端可信入口产生，客户端不能提交。正文按不可信展示内容处理，不执行其中 HTML 或脚本。

设计理由。问题、答复和普通消息共用一种定位方式，恢复页面可以直接打开原消息，不必遍历整个会话。作者由服务端绑定，模型或用户无法伪造系统消息。

### 2.6 GET /api/projects/{projectId}/conversations/{conversationId}/clarifications/{clarificationId}

状态为已采用设计、未实现。返回 `id`、`revision`、`state`、`sourceMessageId`、`questionMessageId`、`answerMessageId`、`candidates`、`resolution`、`supersededBy`、`actions.canReply`、`reasonCodes`。状态只允许 `open`、`answer_saved`、`resolved`、`superseded`、`invalidated`。`resolution` 只在 `resolved` 非 null，`outcome=issue_target` 必须有 `issueId`，`outcome=no_work` 必须为 null。读取不授予执行权限。

设计理由。问题有稳定身份和修订，并发答复与旧页面回写会被拒绝，用户不会覆盖别人的答复，也不会因为按钮隐藏值被解释成正式目标。

### 2.7 POST /api/projects/{projectId}/conversations

状态为本次提案，未实现。它补齐契约明确留下的首条消息创建缺口。页面可以先创建业务会话并同时提交第一条消息，不拆成三次写操作。

| 项目 | 内容 |
| --- | --- |
| 调用方 | 项目 owner 或当前具备项目访问资格的登录用户 |
| 方法与路径 | `POST /api/projects/{projectId}/conversations` |
| 幂等键 | `Idempotency-Key` 为 UUID，作用域 `(projectId, actor, entry=conversation_create, creationId)` |
| 输入 | `title` 可选，1 到 200 字符。`firstMessage` 可选，提供时为 `{content:string}`，规则同 §2.2。`issueId` 可选，必须属于同项目且当前可读 |
| 返回 | `creationId`、`conversationId`、`title`、`revision`、`createdAt`、`messageId` 或 null、`sequence` 或 null、`links.conversation`、`links.operation` |
| 错误 | 400、401、403、404、409、410、422、429、503。新增 `409 CONVERSATION_CREATION_CONFLICT` 表示同键异参 |
| 授权与作用域 | 创建不扩大内容范围。有首条消息时按项目全仓范围保存消息并登记内容范围与投递责任 |
| 并发与重放 | 同键同输入返回原回执，同键异输入 409，两个不同键创建同名会话是两个独立会话 |

创建幂等身份、原输入和原回执的物理位置是 B06 的 `repomesh_issues.conversations`：`standalone_creation_id`、`standalone_creation_actor`、`standalone_creation_schema_version`、`standalone_creation_exact_input`、`standalone_creation_canonical_input`、`standalone_creation_receipt`、`standalone_creation_committed_at`、`standalone_creation_removed_at`、`standalone_first_message_id`，部分唯一键 `(project_id, standalone_creation_actor, standalone_creation_id) WHERE standalone_creation_id IS NOT NULL`，entry 固定为 `conversation_create`。该索引覆盖 removed 行，空会话没有消息也按原键重放。字段的物理声明只在 B06 出现一次。

首条消息不新建另一套幂等作用域。它在 `conversation_messages` 中使用 `entry=conversation_create_first_message`，`submission_id` 由完整创建作用域稳定派生，不能只从裸 creationId 派生。`schemaVersion` 只用于选择比较器，不进入幂等主键。`standalone_creation_receipt` 是本节返回形状的封闭版本化回执，冻结当次 title、revision、messageId、sequence 与提交时间。原会话后来改名不回写旧回执，id 或序号不能由当前 title 重建。清理回执时清空标题副本，键、actor、时间与首消息身份保留。`standalone_first_message_id` 为空时该会话的 messageId 与 sequence 均为 null，不造消息、处理入口或投递行。有首消息时与会话同事务提交，B06 `conversations` 的本地列 `(project_id, id, standalone_first_message_id)` 按延迟复合检查引用本章 `conversation_messages(project_id, conversation_id, id)`。该外键随本章六张表落地时建立；首批 B06 的页面创建分支不因此依赖尚不存在的消息表。

本节的 title 只来自显式输入，不从头条消息正文派生。首消息被清理时，`standalone_creation_exact_input`、`standalone_creation_canonical_input` 与 `standalone_creation_receipt` 中的标题和正文副本也必须清理，会话当前标题按它自己的来源规则处理，详见 §3.8 与 §4.8。

空会话创建不登记 Manager 准备工作，只有第一条消息提交成功才登记。不带 `issueId` 的普通会话同样走本节创建流程。它先没有房间关联，Manager 会话的运行绑定由 §3.5 自身持有，会话成为某 Issue 的主会话后才引用该 Issue 的房间投影。

## 3. 数据表设计

以下表名、schema 与字段是本次提案，未实现。物理 schema 使用 `repomesh_messaging`，实施时在现有 0001 至 0006 迁移之后追加。六张物理表是 `conversation_messages`、`message_processing_entries`、`clarifications`、`control_operations`、`manager_sessions`、`manager_executions`。消息计数与独立会话创建回执不是本 schema 的表，它们的字段、唯一键与写路径见 B06 的 `repomesh_issues.conversations`，本章只在需要的语义处引用。

本章不新增通用 operation、job 或 event 表，也不把任何表写成“登记到 foundations 的共享框架”。各业务域保留自己的操作回执。后台工作复用[首批持久化设计](../current/backend-first-batch-persistence.md)第 3 节已经采用的 DurableWork 机制，消息解释使用 `message_processing_entries`，投递与模型调用使用 `manager_executions`，两者都由对应域持有。

共同类型。ID、messageId、clarificationId、resolutionId、commandSlotId、externalOperationId，以及范围、配置、profile 和 provider 版本都用 text，公开编码保持不透明字符串，客户端不按数值解析或改写原 expectedRevision 回执。内部 request 与 question 单调计数可以用 bigint，API 编码仍是十进制字符串。sequence、epoch、claim generation 和 observation revision 计数用 bigint，时间用 timestamptz。

共同约束。

- 复合外键都携带 project_id 与 conversation_id，需要时携带 logical_request_id 与 actor。不能仅凭全局 id 唯一省略归属核验。跨表外键默认 RESTRICT，正文清理不级联删除身份行。
- 未删除内容、不可变输入和原回执列，与可更新状态、租约和观察列分别规定更新权限。同一行不因此允许一起覆写。
- 提交后的完整形态依靠 CHECK、唯一约束、复合外键与明确的延迟约束触发器保证。跨行语义不能冒充单行 CHECK。公开提交没有可见半成品。
- JSON 只用于已有封闭 schema 的候选、非秘密配置快照、证据与用量摘要和不可变 API 回执。ID、类型、当前状态、修订、唯一性、授权边界、控制决定与清理标志全部使用有类型的列。JSON 必须带版本和权威来源。
- removed 后清除确切输入、规范化输入、正文、派生公开文本、候选标签、含原文的结果与证据，以及所有可还原正文的副本。保留作用域、永久业务键、必要结果归属和权限范围。无权先返回 404，当前有权且内容已清理时返回 410。410 不比较新正文，不允许旧键复活。
- 跨批引用只指向 B06 与 B07 的现行物理对象，包括 `repomesh_issues.conversations` 与 `repomesh_issues.repository_scopes`，不沿用已取消的旧 scope 表名。

本章用到的被引用唯一键如下。`conversations` 提供 `UNIQUE(project_id, id)`。`conversation_messages` 提供 `UNIQUE(project_id, conversation_id, id)`、`UNIQUE(project_id, conversation_id, id, actor)` 与 `UNIQUE(project_id, conversation_id, committed_sequence)`。`message_processing_entries` 提供 `UNIQUE(project_id, conversation_id, entry_id)`、`UNIQUE(project_id, conversation_id, logical_request_id, request_actor)` 与 `UNIQUE(project_id, conversation_id, entry_id, effective_logical_request_id)`。`clarifications` 提供 `UNIQUE(project_id, conversation_id, logical_request_id, id)`。`manager_sessions` 提供 `UNIQUE(project_id, conversation_id, id)`。`control_operations` 提供 `UNIQUE(project_id, conversation_id, logical_request_id, resolution_id)`，这是普通唯一约束，不用仅对非空值生效的部分索引充当外键目标。

### 3.1 conversation_messages

物理表：`repomesh_messaging.conversation_messages`

用途与写入者：保存不可变消息事实、会话内提交序号和用户提交幂等身份。写入者是 `messaging.Service.SubmitMessage`、会话创建用例和受控 Manager 回复入口。每行有三种形态：用户消息带提交字段组，Manager 或 system 消息没有提交字段组，正文清理后的墓碑保留身份并清空正文。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| `id` | text | 是 | 主键，即 messageId，服务端生成，永不复用。 |
| `project_id` | text | 是 | 项目归属。 |
| `conversation_id` | text | 是 | 会话归属，与 `project_id` 组成复合外键到 B06 的 `repomesh_issues.conversations`。 |
| `committed_sequence` | bigint | 是 | 会话内提交序号，正数。 |
| `author_kind` | text | 是 | `user`、`manager` 或 `system`。 |
| `actor` | text | 否 | 用户消息必填，Manager 与 system 消息为空。 |
| `service_binding_id` | text | 否 | Manager 消息必填，与 `project_id`、`conversation_id` 组成复合外键到 `manager_sessions`。 |
| `content` | text | 否 | 存活正文必填，非全空白且不超过 20000 Unicode 标量，墓碑为空。 |
| `reply_to_clarification_id` | text | 否 | 用户答复引用的问题。 |
| `clarification_id` | text | 否 | 可信问题消息引用的问题，只由可信入口写入。 |
| `submission_id` | text | 否 | 客户端提交键，作用域内幂等。 |
| `submission_entry` | text | 否 | `conversation_message` 或 `conversation_create_first_message`。 |
| `submission_schema_version` | integer | 否 | 比较器版本，不进入幂等键，墓碑保留。 |
| `submission_exact_input` | bytea | 否 | 原正文与原引用信封，removed 后清空。 |
| `submission_canonical_input` | bytea | 否 | 规范化输入，removed 后清空。 |
| `submitted_reply_revision` | bigint | 否 | 答复回执的 answeredRevision，取提交前的问题修订。 |
| `created_at` | timestamptz | 是 | 提交时间。 |
| `removed_at` | timestamptz | 否 | 正文清理时间。 |

键与约束。

1. 主键 `id`，并有 `UNIQUE(project_id, conversation_id, id)`、`UNIQUE(project_id, conversation_id, id, actor)` 与 `UNIQUE(project_id, conversation_id, committed_sequence)`，`CHECK (committed_sequence > 0)`。
2. 部分唯一 `(project_id, conversation_id, actor, submission_entry, submission_id) WHERE submission_id IS NOT NULL`。客户端 UUID 是作用域内幂等键，不增加 submission_id 全局唯一来缩小已采用的键空间。
3. 用户行要求 actor、submission_id、submission_entry、submission_schema_version 非空，且 service_binding_id 为空。submission_entry 只允许 `conversation_message` 与 `conversation_create_first_message`。Manager 行要求 service_binding_id 非空且 actor 为空。system 行由可信服务入口构造。非用户行的提交字段全部为空。
4. 存活用户行的 exact、canonical 与 content 非空。用户墓碑的三项全空，但提交 ID、schema version、actor、entry、序号、时间和必要的 reply 身份保留。Manager 与 system 行用同一个 `removed_at` 清正文。
5. `reply_to_clarification_id` 与 `submitted_reply_revision` 同时空或同时非空，非空只允许用户消息。`clarification_id` 只允许可信问题消息，不能由浏览器传入。
6. 循环引用，包括问题与答案的互相引用，用可延迟外键，在提交时检查完整关系。删除一律 RESTRICT。

写入与清理。SubmitMessage 与会话首条消息事务写用户消息，受控服务入口写 Manager 与 system 消息。普通消息的 replyTo 固定为 null。答复回执的 answeredRevision 取 `submitted_reply_revision`，永远不是问题的当前修订。处理器不能更新正文、原输入或回执字段，正文清理走受限路径统一置墓碑。`submission_exact_input` 包括原正文和原引用信封。`submission_canonical_input` 只按已采用的比较器处理 JSON 属性顺序等规则，正文不 trim，不做 Unicode 或换行归一化。身份、输入与消息一次插入提交，不需要独立可见的提交占位。

设计理由。提交与消息本来一次提交、一对一，不存在独立于消息而需要提前成功的 submission 生命周期。同一行可以保留原操作身份而清空消息内容，不需要两张表，也不会出现“提交成功但没有消息”的可见状态。

### 3.2 message_processing_entries

| `request_actor` | text | 否 | 根请求 | 原操作者。 |

| `step_input_kind` | text | 否 | 稳定步骤 | `root_message` 或 `clarification_answer`。 |

| `step_expected_question_revision` | bigint | 否 | 稳定步骤 | 步骤建立时的问题修订，无问题时为空。 |

| `authorization_generation` | bigint | 否 | 可替换凭据 | 等于签发时的 claim_generation。 |
| `authorization_expires_at` | timestamptz | 否 | 可替换凭据 | 不晚于本次 lease_until。 |
| `authorization_revoked_at` | timestamptz | 否 | 可替换凭据 | 撤销时间。 |

两种入口定位。根入口在首次可信处理时写入一次根请求字段组。答复入口的 `target_logical_request_id` 按问题查得的根请求填写，自己的 `logical_request_id` 必须为空。服务消息如需处理责任，也保留独立入口，但不因是消息就自动分配用户工作请求。按 `entry_id` 找领取与租约，按 `logical_request_id` 找根请求，按 `(message_id, handler)` 找某条消息的处理入口，按 `target_logical_request_id` 找该请求的后续答复入口。

键与外键。

1. `UNIQUE(message_id, handler)`、`UNIQUE(logical_request_id)`、`UNIQUE(project_id, conversation_id, entry_id)`、`UNIQUE(project_id, conversation_id, logical_request_id)`、`UNIQUE(project_id, conversation_id, logical_request_id, request_actor)` 与 `UNIQUE(project_id, conversation_id, entry_id, effective_logical_request_id)`。另设部分唯一 `UNIQUE(authorization_id) WHERE authorization_id IS NOT NULL`：`authorization_id` 可以为空，空表示当前没有有效凭据；非空时在本表唯一，续领不复用旧值。
2. `message_id`、`root_source_message_id` 与 `step_source_message_id` 按 `(project_id, conversation_id, id)` 引用消息行。`authorized_session_id` 按 `(project_id, conversation_id, id)` 引用 `manager_sessions`。`target_logical_request_id` 按 `(project_id, conversation_id, target_logical_request_id)` 自引用本表的 `UNIQUE(project_id, conversation_id, logical_request_id)`，只指向本会话的根请求行。
3. 根字段全空，或者基础身份字段全非空。有 `logical_request_id` 时 `source_unit=whole_message_single_request`、`root_source_message_id=message_id`，且 `target_logical_request_id` 为空。`request_actor` 与 `logical_request_id` 一起构成 `clarifications` 的复合引用目标。
4. 带 replyTo 的用户消息入口要求 `target_logical_request_id` 非空、根请求字段为空，归属与 question 和 message 的原请求一致。此跨行规则用延迟约束触发器验证。答复从对应 message 读取 `reply_to_clarification_id`，客户端不能提交 target request。
5. `current_question_id`、`step_question_id` 与 `step_accepted_answer_id` 一律按 `(project_id, conversation_id, effective_logical_request_id, 问题ID)` 引用 `clarifications(project_id, conversation_id, logical_request_id, id)`。用 effective 键后，根入口与答复入口都能指向同一个根请求的问题和答案。只按答复行为空的 `logical_request_id` 引用会因 MATCH SIMPLE 对空列放行，不能使用。`resolution_id` 按 §3.4 的显式唯一键引用控制行。该键与请求 resolved 状态的一致性用延迟触发器核验，不拿只对非空值生效的部分索引做外键目标。
6. 稳定步骤组全空，或者完整写全。根来源步骤允许 `step_accepted_answer_id` 为空，`step_expected_question_revision` 为空或非空。答复步骤要求两者都非空。合法组合按 §3.4 的动作分支判定，不写成无条件规则。credential 组在“有完整稳定步骤但当前没有有效凭据”与“有完整稳定步骤及完整凭据”两种形态下都合法，不要求整组全空，避免把稳定步骤一起擦掉。credential 组非空时 `authorization_id`、`authorized_session_id`、`authenticated_service_ref`、`authorization_generation`、`authorization_expires_at` 五列同时非空，`authorization_revoked_at` 可空。新签发的凭据撤销时间为空，撤销时才写入，凭据组全空时撤销时间也必须为空。

授权生命周期。同一入口同时只有一个当前步骤，`current_command_slot_id` 在换领取代次时保持不变。前一步已完成且请求或问题修订已推进，或者旧步骤因明确的上下文变更被失效后，才能分配新槽位并一次写全稳定步骤组。领取超时和响应丢失不构成换槽位的理由。续领只重新签发 credential 组，新的 `authorization_id` 不复用，`authorization_generation` 更新为本次 `claim_generation`，`authorization_expires_at` 不晚于本次租约。撤销把当前凭据置 `authorization_revoked_at`。代次变化可以清空 credential 组，稳定步骤组保留到该步骤完成或明确失效，避免续领丢失槽位、分支、来源与动作白名单。已过期的旧凭据不作为独立行永久保存，正式审计由已提交的 `control_operations` 行和 `manager_executions` 中的当次上下文证据持有。`manager_executions` 不对可替换的 `authorization_id` 建外键，只保存 `issued_authorization_id` 和有类型的上下文快照，作为事实证据，不是可再次使用的令牌。

授权核验不能只验签。服务调用查当前入口行、Manager 会话和根请求，核未撤销凭据、数据库时间、租约持有者和代次、当前会话代次、请求与问题修订、答案身份和动作白名单。租约更新不自动延长已签发凭据的过期时间，需要重新签发。

工作状态与逻辑状态分离。`work_state` 表示当前处理责任，`request_state` 表示解释事实。`awaiting_clarification` 的请求可以没有正在领取的模型工作，不能占住会话传输队列。保存答复使原请求进入 `answer_pending` 并创建答复入口，根请求不会变成第二个入口。权限未知把 `work_state` 置 blocked 或 retry_wait，不把问题标 invalidated，也不把 answer_saved 改回 open。

每个根入口与答复入口各自持有独立的稳定步骤与凭据。同一会话里两个不同 logicalRequest 可以同时各获自己的授权，不改成会话单槽。

首期只采用 `whole_message_single_request` 基数。未来多来源拆分协议未采用，不为它预建表。未来如一入口确需多个独立请求，应新增明确的来源单元模型和迁移，不能把请求列表放进 JSON。

设计理由。请求身份、处理责任、步骤依据和授权凭据是同一入口行上的字段组，写入者与生命周期相容：请求随入口创建，步骤依据随槽位建立，凭据随领取签发。授权留在入口行与“一个入口一个当前步骤”的基数一致，同时让同一会话中的其他请求各持自己的入口与授权，互不阻塞。

### 3.3 clarifications

物理表：`repomesh_messaging.clarifications`

用途与写入者：保存 Manager 发布的公开问题、修订和唯一答案。写入者是受控控制动作和答复提交事务。

| 字段 | 类型 | 必填 | 约束与含义 |
| --- | --- | --- | --- |
| `id` | text | 是 | 主键，即 clarificationId，服务端生成，永久不复用。 |
| `project_id` | text | 是 | 项目归属。 |
| `conversation_id` | text | 是 | 会话归属。 |
| `logical_request_id` | text | 是 | 所属根请求。 |
| `request_actor` | text | 是 | 原请求操作者，按同域复合外键核验。 |
| `source_message_id` | text | 是 | 原来源消息。 |
| `question_message_id` | text | 是 | 同事务发布的问题消息。 |
| `revision` | bigint | 是 | 问题修订。 |
| `state` | text | 是 | `open`、`answer_saved`、`resolved`、`superseded`、`invalidated`。 |
| `candidates` | jsonb | 是 | 版本化候选数组，可为空，最多 20 条，按 issueId 去重。 |
| `superseded_by` | text | 否 | 后继问题。 |
| `invalidation_reason` | text | 否 | 非敏感失效原因。 |
| `answer_message_id` | text | 否 | 唯一答复消息。 |
| `answered_revision` | bigint | 否 | 提交前的问题修订。 |
| `answered_at` | timestamptz | 否 | 答复提交时间。 |
| `created_at` | timestamptz | 是 | 创建时间。 |
| `updated_at` | timestamptz | 是 | 最近状态时间。 |
| `removed_at` | timestamptz | 否 | 正文清理时间。 |

键与约束。

1. 主键 `id`，并有 `UNIQUE(project_id, conversation_id, id)` 与 `UNIQUE(project_id, conversation_id, logical_request_id, id)`。问题的 source 与根请求、问题消息的 `clarification_id` 与本行 id 都要按复合归属核验。
2. `(project_id, conversation_id, logical_request_id, request_actor)` 按 §3.2 的同名唯一键引用根请求入口。问题与答复必须属于同一请求和同一操作者。
3. 部分唯一 `UNIQUE(answer_message_id) WHERE answer_message_id IS NOT NULL`，答案三列 `answer_message_id`、`answered_revision`、`answered_at` 全空或全非空。
4. 部分唯一索引 `(logical_request_id) WHERE state IN ('open','answer_saved')` 继续存在，保证同一请求同一时刻至多一个可答复问题。原 clarificationId 唯一答复约束由同行答案槽位直接保证。
5. 答复消息按 `(project_id, conversation_id, request_actor, answer_message_id)` 复合引用 §3.1 的用户消息。同事务触发器要求该消息的 `reply_to_clarification_id=id`、`submitted_reply_revision=answered_revision`、`created_at=answered_at`。Answer 的 submissionId 与 actor 从不可变答复消息投影取得，避免重复权威。
6. `source_message_id` 与 `question_message_id` 按 `(project_id, conversation_id, id)` 引用消息行。`superseded_by` 按 `(project_id, conversation_id, logical_request_id, id)` 引用后继问题，不得指向自身或回指祖先。

状态规则。`open` 必须无答案。`answer_saved` 与 `resolved` 必须有答案。`superseded` 与 `invalidated` 可以有或没有答案。`answered_revision` 是提交前的修订，答复保存后问题修订增加。后续替换或解决不得重写答案身份和已消费的修订。替换只能在原请求锁下新建新 ID 问题，使原问题 superseded 并设置 `superseded_by`，同时更新请求的 `current_question_id`。未答复的 open 问题允许被替换，合法的输入组合见 §3.4。已完成的问题不得重新开放。`resolved` 要求同一请求唯一的最终解释存在，且 `input_kind=clarification_answer`、`accepted_answer_id` 等于本行 id。直接判断分支不虚构问题和答案。

正文与清理。问题正文只在 question message，延迟一致性检查要求该消息是可信问题消息且正文不超过 2000 Unicode 标量。`candidates` 只接受已有的候选 schema。清理问答正文不删除问题与答案关联，同时清除 candidates 中可还原公开文本和派生内容并置 `removed_at`。清理后同一问题仍不能接受第二份答复。读取先核内容范围和清理状态。

设计理由。答案本来就按 clarificationId 定位，且同一问题只有一个答案槽位。把答案作为问题行字段组不会削弱并发拒绝、修订锁和清理后的唯一性，却少维护一张始终与问题一对一的行。

| `resolution_request_revision` | bigint | 否 | 目标解释 | 解释依据的请求修订。 |
| `resolution_created_at` | timestamptz | 否 | 目标解释 | 解释创建时间。 |
| `public_message_id` | text | 否 | 公开记录 | 同事务公开消息，按同会话复合外键引用。 |
| `continuation_kind` | text | 否 | 后续核验 | 固定为 `verify_issue_target`。 |
| `continuation_state` | text | 否 | 后续核验 | `ready`、`claimed`、`done`、`blocked`、`retry_wait`。 |
| `continuation_claim_generation` | bigint | 否 | 后续核验 | 核验领取代次。 |
| `continuation_lease_owner` | text | 否 | 后续核验 | 核验领取者。 |
| `continuation_lease_until` | timestamptz | 否 | 后续核验 | 核验租约。 |
| `continuation_next_run_at` | timestamptz | 否 | 后续核验 | 下次核验扫描时间。 |
| `continuation_blocked_reason` | text | 否 | 后续核验 | 非敏感阻塞原因。 |

键与约束。

1. `UNIQUE(resolution_id)`，部分唯一 `UNIQUE(logical_request_id) WHERE resolution_id IS NOT NULL`，以及普通唯一约束 `UNIQUE(project_id, conversation_id, logical_request_id, resolution_id)`。
2. `(project_id, conversation_id, processing_entry_id, logical_request_id)` 按 §3.2 的 `effective_logical_request_id` 唯一键引用处理入口。答复入口用该键指向旧根请求，直接四列引用自己的 `logical_request_id` 会错误拒绝合法答复。
3. `manager_session_id` 按 `(project_id, conversation_id, id)` 引用 `manager_sessions`。`source_message_id` 与 `public_message_id` 按 `(project_id, conversation_id, id)` 引用消息行。`accepted_answer_id` 按 `(project_id, conversation_id, logical_request_id, accepted_answer_id)` 引用 `clarifications(project_id, conversation_id, logical_request_id, id)`，其唯一答案、状态与修订再按动作分支核验。
4. `action=decide_message_target` 当且仅当 `resolution_id`、`outcome`、`resolution_request_revision`、`resolution_created_at` 全非空。其他动作这四个字段全空。`outcome=issue_target` 要求同项目 Issue FK 非空，`no_work` 要求 issue_id 为空，关联与读权在事务中核。
5. 成功行的 `canonical_input`、`result`、`committed_at` 完整。墓碑清空输入和含正文结果，保留 `command_slot_id`、action、schema_version、作用域、resolution_id、必要目标归属与 `committed_at`。resolution 的唯一性部分索引不按 removed_at 过滤，清理后不能插入第二个最终解释。

按动作与状态核输入分支。

- 首次 `propose_clarification`：来源是根消息，`accepted_answer_id` 与 `expected_question_revision` 为空，请求此前没有当前问题。
- `decide_message_target` 的直判：来源是根消息，请求处于 pending 且从未有问题历史，`accepted_answer_id` 与 `expected_question_revision` 为空。该分支继续禁止用根消息绕过已有问题。
- `replace_clarification` 替换当前 open 且未答复的问题：来源仍是根消息，`accepted_answer_id` 为空，`step_question_id` 与 `expected_question_revision` 非空，并匹配同一请求的 `current_question_id` 与 open 状态。原问题 superseded、新问题 open、请求修订提升与本次提交同事务，不为替换伪造答案。
- `replace_clarification` 替换已有答复的问题，或 `decide_message_target` 的答复分支：来源是答复消息，`accepted_answer_id` 是原问题 ID，当前问题、唯一答案与两个修订全部匹配。

以上组合由延迟触发器按具体动作核分支，不写成无条件的单行 CHECK，也不能把“从来没有问题”套到全部动作上。

目标解释。TargetResolution 是 decide 行的有类型业务子记录，权威目标不从 result JSON 提取。`resolution_id` 与 `command_slot_id` 不相等也不混用。下游引用 resolutionId、logicalRequestId 和依据版本，并另行核执行许可。

原子提交与查询。决策步骤的稳定槽位先保存在处理入口行。本表只保存原子提交的成功结果或墓碑，不提前提交“已受理、可能生效”的占位。重放先读已提交结果并核当前可读范围，同槽位同动作同输入返回原结果，不根据最新问题状态重新判断。旧凭据不能写新结果，但可以通过当前可信只读入口查询原槽位。`get_message_control_result` 读取本表，不创建槽位记录。

后续核验责任。最终目标的后续核验责任由本行 continuation 字段组唯一持有。只在 `outcome=issue_target` 时创建完整字段组，kind 固定为 `verify_issue_target`，`causeId` 为 `resolution_id`，`targetId` 为 `issue_id`。resolution 唯一性同时保证 `(causeId, kind, targetId)` 唯一。`no_work` 与非 decide 行的这一组全空。状态沿 `ready`、`claimed`、`done`、`blocked`、`retry_wait` 由目标核验扫描器维护，控制结果与解释列保持不可变。下游尚无实现时保持 blocked 或 `INTEGRATION_NOT_AVAILABLE`，不写执行成功。目标核验只确认后续接受条件，真正派工由 B10 的域操作去重与核权。

设计理由。目标解释、控制结果和这条决定产生的唯一后续责任属于同一次提交。放在同一行后，并发两个决定仍被 resolution 唯一约束拒绝，清理正文后唯一键仍占位，重启时扫描这组字段即可恢复原责任，不需要在结果 JSON 里寻找权威目标。

用途与写入者：把项目会话映射到当前 Manager 会话代次。写入者是 `BindingService.Ensure` 与 coordinator 观察器。

| 字段 | 类型 | 必填 | 约束与含义 |

| `issue_id` | text | 否 | 当前运行上下文的 Issue，无 Issue 的普通会话为空。 |
| `room_link_id` | text | 否 | 非空时要求 `issue_id` 非空，并与 `project_id`、`issue_id`、`conversation_id` 一起引用 B07 的 `issue_room_links(project_id, issue_id, conversation_id, room_link_id)`。该目标是主房间，Leader 房间不能绑定 Manager 会话。 |
| `manager_instance_ref` | text | 是 | 上游实例不透明引用。 |
| `manager_session_epoch` | bigint | 是 | Manager 会话代次。 |

键与约束。`UNIQUE(project_id, conversation_id, id)` 供消息行、处理入口行与执行行的复合引用使用。`UNIQUE(project_id, conversation_id, manager_session_epoch)` 与部分唯一 `(project_id, conversation_id) WHERE superseded_at IS NULL` 保留，每个会话至多一个当前代次。写路径要求本行 `superseded_at IS NULL`，旧代次保留但失去写权限。检查约束为 `room_link_id IS NULL OR issue_id IS NOT NULL`。

普通会话先于 Issue 存在，它的运行绑定由本行的 `manager_instance_ref`、`transport_session_ref` 与 `state` 承担，不等待也不伪造 B07 房间关联。会话关联 Issue 后，四列一起引用 B07 `repomesh_issues.issue_room_links` 的同名唯一键。B07 的主房间与 Leader 房间互斥检查保证非空 `conversation_id` 只能引用该会话的主房间，跨项目、跨 Issue、跨会话或 Leader 房间的引用都被拒绝。更换当前 Issue 上下文或房间引用必须新建代次并把旧行写 `superseded_at`，不允许原地改写。B07 表保持 `issue_id` 非空，只为已有 Issue 登记关联，不为无 Issue 会话造行。普通会话的 `issue_id` 与 `room_link_id` 同时为空时不触发该复合外键。

`manager_session_epoch` 表示 Manager 逻辑会话代次，与 room 观察的 `runtime_generation` 是两个事实，不能互相替代。`transport_session_ref` 必须带 schemaVersion 与来源。房间标识、裸 room_id 与房间观察不在这里复制。具体传输编码不在本批冻结。

本表不保存调用授权。授权凭据的生命周期短于会话，由 §3.2 的当前步骤字段组持有。运行权限与调用权限不能由一个 `ready` 值代替。旧会话上可能已经外发的执行记录仍保存原 session 并继续核查，会话切换不证明旧外部执行已取消。探测 unknown 不删除旧运行绑定，也不拿 B07 的 runtime_generation 替换 `manager_session_epoch`。

模型调用分支的规则。

1. `UNIQUE(logical_request_id, purpose, attempt_generation) WHERE kind='model_call'`，`(project_id, conversation_id, processing_entry_id, logical_request_id)` 引用 `message_processing_entries` 的 effective 唯一键。
2. 秘密四元组按 `(secret_version_id, secret_owner_kind, secret_owner_id, secret_purpose)` 引用 `repomesh_secrets.versions` 的既有唯一目标。`executed_source_message_id` 按 `(project_id, conversation_id, id)` 引用消息行，`manager_session_id` 按 `(project_id, conversation_id, id)` 引用会话行。
3. 模型闭包必须来自同一组来源行。除了上述外键，实施时用延迟检查核对：`profile_links(profile_id, profile_version)` 选中的发布行在 provider、revision、row、owner 与 secret 四元组上等于本行，不能只凭各列都非空就当作同一模型。
4. 会话与完整固定配置在实际出站前必须非空。可用性缺失保持 blocked，不换默认模型或秘密。Issue 调用要求 `issue_id` 非空且 `configuration_revision` 等于该 Issue 的 `initialConfigurationRevision`，该匹配在 P9 采用后可用延迟约束读取 Issue 行，P9 未采用时保持候选状态。普通讨论的 `issue_id` 与 `configuration_revision` 可以为空，但自身 model、secret 与版本闭包照样固定。
5. `resolved_config` 只保存非秘密版本和参数，不保存正文或完整 prompt。重启沿原闭包，不查 latest。首次可恢复请求选择配置后，以该请求已有最早固定的闭包为准，后续 purpose 与 attempt 通过请求锁核对相同固定版本。跨步骤确需不同 Issue 上下文时建立明确新请求，不能原地把旧请求闭包换掉。
6. 执行证据列是对该次调用的不可变来源证明，不是当前授权替代品，只凭它们存在不能重新放行。

范围版本。发送和核查按 `content_scope_revision` 重新读取 B06 `repository_scopes`：先按 `project_id` 与 `conversation_id` 读会话 owner 及其范围，`issue_id` 非空时再按 `project_id` 与 `issue_id` 读 Issue owner 及其范围，分别与 `content_scope_revision` 和 `issue_content_scope_revision` 做等值比较。任一步失败就重核完整集合。行保存的版本是登记时的观察快照，用于判断该次出站是否能继续，不是指向旧范围行的键，也不能为了让旧调用通过而原地替换已发送的依据。

分支互斥。`message_id` 与 `delivery_state` 只在投递分支非空，模型版本、配置、usage 与执行证据列只在调用分支非空。两个分支的必需列由 CHECK 与唯一约束分别约束，不使用共用状态列，也不用通用载荷容纳分支字段。

观察与未知。低 `observation_revision` 或旧 `claim_generation` 的回写不覆盖新事实，核查接管须使用新领取者身份。探测失败只把 `last_observed_state` 标为 `unknown`，`state` 保持最近已证实的推进值或进入 `reconcile_required`，并保留原关联，不删除、不降级会话绑定。`may_have_sent_at` 只能由空变非空。外部操作进入 `may_have_sent` 后，目标会话、来源与答案、配置闭包和秘密身份全部不可变。

重试。逻辑 `attempt_generation` 递增只能发生在上一尝试有证据未发，或已按协议终结且本次策略允许时。前次可能已发送且结果未知时只核查原 `external_operation_id`。不能以“模型重试”为名重新计作新用户请求或绕开预算。

费用归属。`usage` 只在模型调用分支非空，用调用 id、project、logicalRequestId、可选 issue_id 与固定 policy 和配置版本定位费用事实。投递分支的 usage 与全部模型版本字段必须为空，两种分支不会共用一笔模型费用身份。Manager 调用仍须核项目运行预算，不能拿 B05 的 `actor_model_test` 额度替代。项目运行预算范围未采用或不可用就 blocked，不补造额度。

清理范围。投递从消息的会话范围确定清理对象，模型调用从根请求、实际来源消息与答案，以及可选 Issue 的固定内容范围确定清理对象。行的 project、conversation、issue 与 source 归属不会因当前会话后来切换 Issue 而改变。删除一条源消息时，清理引用它的投递证据和调用证据中的正文副本，保留调用的版本身份、用量数值与归属，以及投递的外部身份和接收证据。不能按会话一次硬删两种全部记录，也不能因为模型调用还需要计费就保留 prompt。必须保留的非正文审计与待核责任独立于正文列。

为什么能共表。两种行都由 coordinator 与 Manager 适配层持有外发责任，生命周期都从本地准备到可能已发、证据观察和核查，再保留最小外发证据。共同的不可变外部身份、发送前事实、租约围栏、迟到观察和清理规则相同。分支状态使用不同列与 CHECK，各自的输入关系与唯一键依旧独立。本表与 B05 的用户模型测试仍不合表，测试额度、主体与协议不同。

### 3.8 由 B06 给出的存储位置

以下两项不出现在 `repomesh_messaging`，也不在本章声明物理表。它们由 B06 的 `repomesh_issues.conversations` 持有字段，整个设计集只计一次。

消息计数：`last_message_sequence bigint NOT NULL DEFAULT 0 CHECK(last_message_sequence >= 0)` 与 `message_sequence_updated_at timestamptz`。会话创建时保持 0 与 null。B09 所有真实消息写路径锁该会话行，分配序号并持锁到提交，分页高水位读该列。页面来源卡片不分配消息序号，序号允许间隙。

独立会话创建回执：§2.7 列出的九个 `standalone_*` 与 `standalone_first_message_id` 字段、部分唯一键和 `conversation_create` 入口由 B06 声明。本章只规定它们的写入、读取与清理语义。

- 空会话可创建并按原键重放。带首消息的创建在一个事务中提交，`(project_id, conversation_id, standalone_first_message_id)` 按延迟复合检查引用同一会话的消息行。
- 回执不能被当前标题重建。原会话后来改名不回写旧回执，清理回执时清空标题副本，键、actor、时间与首消息身份保留。
- §2.7 不采用“标题由首消息正文派生”的来源，title 只能显式提交或不提交，因此这一批不需要额外的标题来源标记列。清理 `standalone_first_message_id` 指向的消息时，在同一会话锁内清空该会话的 `standalone_creation_exact_input`、`standalone_creation_canonical_input` 与 `standalone_creation_receipt`，并置 `standalone_creation_removed_at`，保留创建键、actor、committed_at、时间与首消息身份。回执中的旧标题属于副本，必须一并清除。会话当前标题由 B06 按自己的标题来源规则处理，独立改名后的标题不受本次清理影响。未来若采用从首消息派生标题的来源，B06 必须先增加可判定的来源标记列，再扩展这条清理规则。
- 一般后续消息的清理不能清除与它无关的会话创建操作。
- 页面创建分支由 B06 的页面操作字段组表达，两个分支互斥，既有会话不改写创建归属。

## 4. 事务与恢复

### 4.1 正常流程

消息提交在一个短事务内完成原操作检查、会话与内容范围核权、序号分配、消息、答复关联、回执、处理入口和投递责任。提交后才返回 201。协调器扫描处理入口，先确保项目会话有可用 Manager 绑定，再解析配置并登记 `manager_executions` 的调用行。发送前在短事务中写 `may_have_sent_at`，外部调用在事务外，返回后按 `observation_revision` 条件更新观察，低修订的迟到观察不覆盖当前事实。Manager 的控制工具调用核当前步骤凭据与代次，成功结果、公开回复和后续核验责任同事务保存。

本次提案规定会话绑定的房间规则。普通会话在关联 Issue 前的准备只依赖 `manager_sessions` 自身的 `manager_instance_ref`、`transport_session_ref` 与 `state`，`issue_id` 与 `room_link_id` 保持为空。会话成为某 Issue 的主会话后，准备与观察事务新建一代次并在该代次写 `issue_id`，房间可用时把 `room_link_id` 指向该 Issue 在同项目、同会话的主房间关联。当前 Issue 上下文从空变非空、Issue 之间切换、或房间引用变更，都必须新建代次并把旧行写 `superseded_at`，同一代次不允许原地改指。校验失败返回冲突并保留原绑定，不写跨项目、跨 Issue、跨会话或 Leader 房间的引用。房间观察由 coordinator 写入 B07，本批只读该引用。探测失败不改写本表 `state`，也不清空已有引用。

### 4.2 总锁序

固定总锁序与 B06、B07 对齐：principal 的 binding、session、account，随后 project 与所需 connection，随后 conversations 按 id 排序，随后必要 Issue 按 id 排序，随后 `message_processing_entries` 按 `entry_id` 排序，包含根请求和此次答复或服务入口，随后 `clarifications` 按 id 排序，随后 `manager_sessions` 按 id 排序，随后 `control_operations` 按槽位排序，随后 `manager_executions` 按 id 排序。不需要的对象层可以跳过。普通消息没有目标 Issue 写锁时直接进入处理入口层。消息与操作的最终插入在已持有的会话与请求范围完成。计数并入 conversation 后，不再另锁计数器。

同类 processing 行先收齐根入口和当前入口的 ID，再按 entry_id 排序，不能一个路径先锁答复、另一条路径先锁根。此映射替代旧写法中“先 logicalRequest、后其他 processing 结果”的含糊说法。会话行本来就是所有消息写路径共同锁，把计数移入会话行没有新增消息级串行瓶颈。

扫描器不能持有 executions 或答复入口行锁再倒向 conversation 与 request。可以先无锁选候选 ID，再开启短事务按上述顺序领取并 CAS `next_run_at`、状态与代次。外部核权观察和模型或传输调用在事务外。准备观察器若只更新一张 session 或 execution 行，无需拿上层锁，但不得在这个事务中继续反向取得业务锁。凡核准控制或切换上下文必须按完整顺序执行。

消息提交的路径。先核当前身份与可披露性并查原作用域提交，原成功优先于新问题修订，墓碑优先于输入比较。新请求预核完整内容范围，按固定序锁后重核访问 epoch 与 range version，再插入合并消息行、递增会话计数。答复还在 question 同行写唯一答案并使 question 进入 `answer_saved`、根 request 进入 `answer_pending`，各升修订。同事务保存处理入口、投递行与必要后续责任。并发失败整笔回滚，不留孤立消息。只提交后返回 201。

控制提交的路径。先核原槽位成功结果，再核当前步骤凭据，按固定序锁后重核 source、question、answer 与 request CAS。一次提交控制行，包括可选 resolution、新问题或旧问题变化、公开消息及后续责任。槽位的 action 与 input 一旦成功不可覆盖。替换未答复的 open 问题时，原问题 superseded、新问题 open 与请求修订提升也在本次提交内完成。最终解释的后续核验责任固定由 §3.4 的 decide 行 continuation 字段组持有，唯一键语义为 `(resolution_id, verify_issue_target, issue_id)`。目标核验扫描器恢复该行，handler 未接入时 blocked 或 `INTEGRATION_NOT_AVAILABLE`，不写执行成功。

传输按同会话 `committed_sequence` 排序。前序可能已发送且结果未知时，后续投递等待其核查。纯语义等待不阻塞同会话后续独立消息。投递、模型调用与控制结果的状态分别读取，本地消息回执不随其变化。

### 4.3 重试分层

| 层级 | 身份 | 允许行为 | 禁止行为 |
| --- | --- | --- | --- |
| 传输重试 | 同一 `external_operation_id` | 按原身份查询或重发同一请求 | 生成新外部编号或新消息 |
| 逻辑调用重试 | 同一 `logical_request_id` 与 `purpose`，`attempt_generation` 递增 | 确认未发送后按原配置再调用 | 换配置、换 Key、换会话 |
| 修复轮次 | 业务轮次，见 B11 | 形成新计划修订和一至多个新任务 | 用传输重试冒充业务修复 |

三层分开记录。同一次网络超时不能计数为一次业务修复，也不能因为业务重试而绕过累计上限。

### 4.4 响应丢失与同键异参

消息提交的 COMMIT 回执丢失时返回 `RESULT_UNCONFIRMED`。原操作查询先按 submissionId 读主库，404 不证明请求不会提交，不自动换键。同键不同正文、引用或 entry 返回 409，不覆盖原记录。会话创建的响应丢失沿用同一规则，重试返回同一会话和同一条首消息。

投递发送后响应丢失时，不得直接重发。先按 `external_operation_id` 查询传输侧事实。没有可靠查询能力时停在 `reconcile_required`，保留核查责任，不生成第二条消息。模型调用响应丢失时同样先查原调用，已 `may_have_sent` 的调用不得换成新秘密版本重发。

### 4.5 并发

消息与控制写路径使用 §4.2 的固定锁序。有多个同类对象时按 ID 排序。所有问题替换、接收、解决、失效和正文清理遵守同一顺序。先取得输入范围的有效观察，不持锁调用 GitHub 或模型。

两个不同操作键同时答复同一个 open 问题时按请求与问题行锁串行。首个有效事务保存答复并升修订，另一个返回 409，整笔消息不保存。即使正文相同也不按文本合并。同一 pending 请求的直接判断与提问竞争时，请求行 CAS 和 resolution 唯一约束只允许一个结果。不同槽位的两个决定被 resolution 部分唯一约束拒绝。已清理的结果仍占唯一键，不能插入第二个终局。两个正在替换同一 open 问题的步骤按请求锁串行，只有一个能得到该问题仍是 open 的观察。

### 4.6 崩溃与重启

事务未提交时数据库回滚，不存在半条消息、问题、投递或调用。提交完成但唤醒丢失时，扫描器按已提交的处理入口、槽位、投递与调用身份重新发现，不新建消息或问题。收到模型输出但控制结果尚未提交时，新领取者沿用原 `commandSlotId` 与原稳定步骤依据，旧领取者写入因代次与凭据失效被拒绝。已 resolved 但后续核验未运行时，扫描 §3.4 decide 行的 continuation 字段组，不重复确定目标。重启后普通会话按自身运行绑定恢复，不因缺少房间关联阻塞或重建绑定。已关联 Issue 的会话按原 `issue_id`、`room_link_id` 与代次恢复，不自动改写关联，也不自动推进代次。

解释时权限未知或配置不可用时，保留 `answer_saved` 与原来源，待核条件恢复后按原请求核验，不重新开放问题让用户重复回答，也不静默换模型版本。清理或替换使旧控制许可失效，但已可能外发的记录仍须核查，不声称外部已取消。

### 4.7 迟到结果与旧代次

旧 Manager 会话代次、过期租约或已被替换的问题回写只返回内部 `STALE_PROCESSING_CONTEXT`，不追加公开已解决记录。已提交控制结果仍可在当前可信作用域按原槽位查询，但不能据此授权新的副作用。旧外部调用可能已经发出时保留核查责任，不把本地清理当作外部取消成功。

### 4.8 删除与保留

本批不新增浏览器删除路由。正文清理先取得与写入相同的范围锁，撤销当前凭据并提升业务修订，然后在同事务中清除确切输入、规范化输入、消息正文、派生公开文本、候选标签、含原文的结果与证据，以及可还原正文的副本，设置 `removed_at`。清理保留作用域、提交身份、消息身份、答案关联、resolution、槽位与外发身份的唯一性，也保留必要的权限范围和待核责任。

清理会话创建的回执副本时按 §3.8 的联动规则执行。删除 `standalone_first_message_id` 指向的消息会同时清空该会话的 standalone exact、canonical 与 receipt 三项副本并置 `standalone_creation_removed_at`。会话当前标题不是首消息的派生副本，按 B06 自己的标题来源规则处理，独立改名后的标题保留。一般消息清理不影响与它无关的创建操作。

清理后当前有权者查询和重放返回 410，不再比较新输入，不复活旧键。对外发结果未知的记录先核查再清理，保留最小审计与待核责任，不直接删除执行行丢掉可能外发的事实。配置、秘密与调用的版本身份在仍被引用时不可级联删除。秘密正文可以销毁，版本身份与不可用事实保留。

## 7. 待取舍点

| 取舍 | 选项 | 影响 | 本章默认写法 |
| --- | --- | --- | --- |
| 普通讨论的配置固定单位 | 按一次可恢复模型处理请求固定，或按整段会话固定 | 决定调用行的 `configuration_revision` 是否为空以及新请求能否选新配置 | 按请求固定，沿用配置绑定专题第 6 节的候选方向 |
| 首期传输 | 先指定某一种房间会话传输，或保持适配器无关 | 决定 `transport_session_ref` 身份与投递观察接口 | 保持适配器无关，只要求稳定外部操作编号和可核查观察 |
| 完整 MCP Schema | 本次冻结首版可执行 Schema，或保留工具名与适配层契约 | 影响外部契约稳定性与后续兼容成本 | 工具名已采用，Schema 与调用身份仍为候选 |
| 新建会话接口 | 采用本章 §2.7，或要求必须先有 Issue 才建会话 | 影响普通讨论先于 Issue 的可行性 | 按提案继续，物理承载已定在 B06 的 `conversations`，采用状态仍待确认 |
| 投递观察历史 | 合并为最新观察字段与 observation_revision，或未来另建历史表 | 影响审计粒度与表数量 | 先合并，确有逐次审计需求时再按真实查询新建 |
| 一入口多请求的来源单元 | 首期只允许 whole_message_single_request，或现在就设计多来源拆分 | 决定是否需要新的来源单元模型与迁移 | 首期只采用单请求基数，未来需求出现时新增明确模型，不把请求列表放进 JSON |
| 普通讨论的执行 profile | 按候选要求固定 execution profile，或允许普通讨论不写该组 | 决定调用行中 execution profile 三列是否允许为空 | 三列同时空或同时非空，Issue 分支按 P9 采用后的既有要求填写 |
| P9 配置绑定采用 | 先采用 P9 再实现 B09 消费者，或不启用真实消费者 | 决定 G1 能否成立 | 依赖 P9 采用，未采用前相关消费者保持 blocked |
