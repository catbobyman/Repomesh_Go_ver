# 06 · 人工监管与审核

## 监管方式

| 方式 | 用户体验 | 要求 |
| --- | --- | --- |
| AI 自己干完 | 按已配置的规则自动推进，不等待常规人工检查点 | 清楚告知自动程度；交付自身的验证与授权条件仍生效 |
| 关键处我看一眼 | 默认在仓库范围和交付处等待人工；异常时升级 | 至少一个有效审核人，异常升级必须保留 |
| 每步都由我把关 | 六类关键检查全部受人工控制 | 不允许关闭其中某一类后仍称为完整人工控制 |

六类检查点是仓库范围、规格、任务执行、验证、交付、异常升级。异常只在发生时形成待办，不能把检查点数量当成正常流程一定需要点击的次数。

## 功能需求

| 编号 | 功能 | 规则与结果 |
| --- | --- | --- |
| GOV-01 | 配置监管策略 | 在首次开工前选择三档方式，可展开检查点与审核人配置；显示预计停顿位置和次数口径 |
| GOV-02 | 审核人授权 | 选择项目或仓库监督人，配置可查看、批准、要求修改、暂停、恢复、取消、修改规格等动作，明确适用仓库与范围 |
| GOV-03 | 策略预览与撤回 | 在需求卡片和开工确认中显示同一摘要；未生效草稿可修改或撤回，生效策略与历史草稿可区分 |
| GOV-04 | 审核台待办 | 汇总当前用户可处理的待审事项，侧栏计数与列表一致；显示需求、检查点、仓库、证据版本、提出时间与等待原因 |
| GOV-05 | 审核详情与证据 | 展示原请求、关键风险、候选结果、验证状态、可用证据、可执行决定；用户可从待办返回需求上下文 |
| GOV-06 | 批准、拒绝、要求修改 | 记录真实操作人、决定、理由、时间、范围及版本；要求修改说明待补充内容，拒绝不伪装成任务已完成 |
| GOV-07 | 需求内决策夹 | 需求详情集中呈现待审批和关注事项，关联到当前轮次及完整证据；保留已经处理的历史 |
| GOV-08 | 审批有效性 | 只接受针对当前有效证据的决定；内容变化后关闭旧放行状态，产生新待办并解释失效原因 |
| GOV-09 | 暂停、恢复与取消 | 有权限者可暂停新分配与新执行、恢复暂停项目或取消后续执行；显示操作原因与当前状态 |
| GOV-10 | 运行中策略变更 | 预览新增或取消检查点对在途工作的影响，确认后形成新版策略；不得追认过去未受审的步骤 |

GOV-01 至 GOV-09 为保留；GOV-10 为补齐，现有首次开工策略不能被描述为已支持任意中途修改。

## 权限规则

- 查看权、仓库修改权与审批权分别配置，能够阅读不代表可以批准。
- 仓库监督人必须绑定参与范围内的仓库；项目监督人不得沿用无效的仓库选择。
- 同一人同一范围不能重复添加授权。非自动模式必须至少有一个真正可处理相应检查点的人。
- 管理员可查看全局待办，不意味着无需业务授权即可代替任何审核人决定。
- 智能体的职责分配不能冒充人工登录身份。

## 审核状态

待处理 → 已批准／已拒绝／要求修改。证据变化后旧单显示已过期或被新单取代，保留原决定。正在提交时防止连点；如果另一人已处理，展示已接受的决定并更新列表，不能覆盖。

审核通知中断时保留最后一次已知列表并显示“更新中断”与最后同步时间。已经接受的决定不因通知失败而丢失；恢复后不生成第二次同义决定。

## 关键业务限制

暂停只阻止后续分配和执行，不承诺撤回在途外部动作；取消不可恢复为原任务继续运行。已产生的候选、交付和部分合入要通过第 08 册的恢复或回滚处理。异常先在仓库团队内部汇总，无法处理再由组织负责人升级人工。

## 验收

1. 选择“关键处我看一眼”后，开工预览明确显示范围、交付及异常升级。
2. 走到已启用的检查点会产生对应待办，未授权用户不能处理。
3. 同一证据重复到达不会产生重复待办，两人同时处理只接受一次决定。
4. 候选更新后旧批准失效，新审核展示新的差异与证据。
5. 暂停后不能开始新任务；恢复后继续；取消后不能直接恢复执行。
6. 所有六类检查点在重写产品中均有可到达的触发场景，不能仅出现于设置项。
