## 已处理的历史分歧

1. **团队创建粒度**：早期界面设计出现“每需求每仓建团”的描述；当前 Project README 与 CONTEXT 明确仓库团队长期复用。本 PRD 采用仓库常设团队，需求只引用。
2. **两份前端**：`web/` 属早期人工审核与规划界面，`frontend/` 是当前整合控制台。按当前路由组织产品，不把两个前端变成两套用户产品。
3. **运行方式**：早期托管流程存在转交第二执行者的描述，近期设计与记录区分托管原生和本地 CLI。PRD 保留两种产品方式与共同验证规则，不延续已被替换的转交细节。
4. **真实验证边界**：2026-09-06 记录证明特定托管示例达到独立复验，并记录恢复问题；它不证明所有工作方式、仓库、交付、前端或生产场景都已通过。因此成熟度标注不使用“全部完成”。
5. **监管触发缺口**：旧监管界面说明提到规格检查点曾无完整可达路径；PRD 将六类检查点全部可触发列为重写验收，而非描述当前全部可用。
6. **数据服务验证**：本地流程、测试交接与真实 Polar 数据服务验收分开。PRD 标记外部条件未完成时必须阻塞，不宣传真实服务通过。
7. **自动交付与仓库入口**：核心工作台有受策略控制的自动推进；仓库原生入口的初期方案限制自动合入。两者适用范围分开，未合并为一个无条件全自动承诺。
8. **生产发布**：早期产品愿景提到部署、灰度和生产回滚，当前主要能力以仓库交付为主。生产发布单列扩展，不能把合入状态叫作上线成功。
9. **真实运营接入**：运营检查清单仍列出容量来源、通知渠道、备份恢复演练等未完成项。PRD 保留功能，界面缺源时显示未接入。
10. **检索隔离**：历史页面材料中出现跨组织检索叙述；产品范围采用工作区与授权规则，跨区汇总只能包含当前用户有权查看的数据。
11. **测试用需求与平台功能**：根目录“通知摘要-需求文档.md”自述为测试数据派生需求，TrainTicket 通知邮件、价格、退款等为被交付业务的样例。它们不是 RepoMesh 自身的邮件产品、票务或电商功能，未混入平台 PRD。
