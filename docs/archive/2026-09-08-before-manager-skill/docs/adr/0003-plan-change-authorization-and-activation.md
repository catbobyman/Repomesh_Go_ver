# ADR-0003：计划变更的自动化档位、许可与生效

RepoMesh 的跨仓 issue 需要根据执行证据调整计划，同时保留人工控制、执行归属和可追溯性。用户确认：Manager 随时可以提出计划变更，RepoMesh 判断是否获准，并在执行条件满足后应用；批准成功与计划生效分别记录。

本决定沿用 [ADR-0001](0001-agentteams-issue-concurrency-and-isolation.md) 的长期团队、issue 会话、独立 Attempt、容量约束和暂停语义，以及 [ADR-0002](0002-github-app-authorization-and-draft-pr-delivery.md) 的 Git 授权与人工合并边界。`accepted` 表示以下产品规则已经确认，不表示接口接入、审批强制约束或部署验证已经完成。

## 1. 已确认的六条规则

### 1.1 审批对象是明确的计划版本

- 计划变更展示新增、删除和修改的工作、原因、依赖变化、仓库范围、预算及循环上限。
- 已批准版本保持不变，后续修改产生新版本；保留变更与其所依据版本的关系。
- Manager 提出变更不自动使新版本成为当前执行依据。

### 1.2 两个自动化档位共用执行规则

| 档位 | 计划变更如何获准 | 执行边界 |
| --- | --- | --- |
| 全自动（YOLO） | RepoMesh 按既有授权范围、预算和策略自动判断。 | 获准后仍需满足应用条件，不能跳过容量、隔离和证据约束。 |
| 需要审批 | 展示具体变更，由人判断是否批准。 | 获准后采用同一套应用与执行规则。 |

扩大权限、提高预算上限或放宽已确认验收条件，在两个档位下都需要人决定。人的决定仍受其有效授权及仓库规则约束。合并继续由人和仓库规则控制。

自动化档位规定编排决定如何获得许可，不授予额外 Git 权限，也不等同于某个 coding CLI 的跳过权限检查参数。

### 1.3 已批准的 Loop 可以自动运行

- 已明确范围和上限的循环可以在许可内自动推进，无须每轮重复审批。
- 例如已批准“前端修复并重新验证，最多三轮”，可自动执行该循环；三轮仅为场景示例，不是全产品默认值。
- 循环内产生新候选时，重新判断验证证据是否适用于新的固定交付组合；许可仍适用不代表旧证据仍有效。
- 超出原循环范围或上限时，形成新请求，不无限重试或静默扩大工作。

### 1.4 变更获准后才进入应用流程

- 等待审批时，旧计划仍是有效版本；已经发现不能继续的工作明确标记为阻塞，不能因旧版本仍有效而继续不适用的工作。
- 变更获准后进入“已获准，待应用”，此时新版本尚未生效。
- 第一版在应用变更时，按受影响的上游 Project 暂停新派工，等待在途任务及已提交结果处理到可重规划状态。暂停派工不自动终止在途执行。
- 核对最新状态，应用新版本并读回确认成功后，才以新版本继续派工。处理已提交结果不能冒充业务验收通过。
- 同一上游 Project 内只暂停某个分支的能力留待技术验证，不作为首期承诺；RepoMesh issue 与上游 Project 的具体映射仍需明确。

### 1.5 失败与冲突不覆盖历史

- 审批被拒绝时保留变更和拒绝原因。
- 应用遇到冲突时读取最新计划，重新判断原变更及其许可是否仍适用，不直接覆盖最新状态。
- 写入结果不确定时先核查；只有读回确认成功，页面才显示新版本已生效。
- 保留旧版本、执行记录和验证证据。候选或计划变化后的证据适用性与许可适用性分别判断。

### 1.6 RepoMesh 实际控制执行许可

- Manager 生成和提出计划变更；RepoMesh 保存许可记录，并控制变更应用和任务启动。
- 审批状态必须与实际执行约束一致，不能只靠页面按钮、Matrix 消息或提示词保证等待审批。
- Controller、MCP 和存储写入路径如何受控、如何防止绕过，以及与上游计划及派工机制如何衔接，均须后续技术验证。

## 2. 场景与流程

frontend F1 与 backend B1 正在联调。Manager 发现还需检查导出功能，提出计划 V2；当前有效计划为 V1。

```text
[Current plan V1: frontend F1 + backend B1]
                         |
                         v
[Manager proposes V2: add export verification + reason]
                         |
               +---------+----------+
               |                    |
               v                    v
     [YOLO: policy decision]   [Human approval]
               |                    |
               +---------+----------+
                         |
                         v
             [Authorized, awaiting application]
                         |
                         v
      [Pause new dispatch for affected upstream Project]
      [Wait for in-flight work and submitted results to settle]
                         |
                         v
        [Recheck current state -> Apply V2 -> Read back]
                         |
             +-----------+-------------+
             |                         |
             v                         v
      [V2 active]              [Conflict / Failure / Uncertain]
      [Continue dispatch]      [Keep history; inspect and reassess]
```

YOLO 也经过“已获准，待应用”。自动判断不保证立即应用；因当前执行状态等待与因尚未审批等待，是两个不同原因。

## 3. 页面状态与职责

| 页面状态 | 含义及展示内容 |
| --- | --- |
| 待审批 | 等待人决定，展示计划版本、变更内容、原因、范围及预算和循环约束。 |
| 已获准，待应用 | 许可已获得，显示尚未满足的执行条件。 |
| 应用中 | 正在写入并核对新计划。 |
| 已生效 | 新版本成为当前执行依据。 |
| 已拒绝 | 保留拒绝原因和变更记录。 |
| 需重新判断 | 计划、候选或应用条件发生变化，原变更或许可的适用性需要重判。 |
| 应用失败 | 展示失败原因与下一步，保留旧版本及证据；结果不确定时先核查。 |

这些是计划变更的产品状态，不直接替换 issue、Worker、Attempt 或上游 Project 的状态。

- Manager：说明为什么改、改什么，以及依赖、范围、预算和循环的变化。
- 人：在审批档决定是否批准；两个档位下均负责上述必须由人决定的边界变化。
- RepoMesh：保存有效版本和许可，协调应用时机，核对结果并控制派工。
- 仓库 Team 与验证执行者：在当前有效计划及已有授权内执行；业务修复仍归对应仓库 Team，验证环境不向业务仓库推送修复。

### 3.1 首期仅通过自然语言调整编排

- 用户通过自然语言提出编排调整，例如“增加旧客户端兼容性检查，完成后再汇总验收证据”。
- Manager 将要求转化为明确的计划变更提案，展示差异及原因，继续按本 ADR 的自动化档位、许可和应用规则处理。自然语言请求不直接改写当前有效计划，也不额外要求 YOLO 档逐次人工审批。
- 首期不提供直接编辑节点、属性、依赖连线或拖拽编排的入口；这些能力进入后续待办设计。
- 这项范围决定不改变既有获准与生效的区分，也不证明上游已经支持运行中局部改图。

## 4. 上游依据与技术待验证项

依据本地 [AgentTeams 接口调查](../../../../agentteams-survey-2026-09-07/agentteams-api-cli-survey-2026-09-07.md)，源码基线为 `eeaab64391ccaec9118e84977f538aefd40720d6`。本次只阅读调查记录，未重新核查远端源码或调用真实服务。

| 调查记录的能力或限制 | 本决定的影响 |
| --- | --- |
| TeamHarness 本地 MCP 有 `plan_dag`、`plan_loop`、`ready_nodes`、`ready_loop_nodes`、`record_loop_iteration` 和 `accept_task_result`。 | 提供可复用的计划与循环基础，但不能据此承诺任意嵌套、条件分支或运行中局部改图。 |
| Controller `POST /api/v1/projects/{id}/replan` 重写 DAG，存在 `in-progress/submitted` 任务时拒绝。 | 获准与生效分开，应用前等待并核对可重规划状态。该 REST 操作不能直接当作 Loop 重规划契约。 |
| `pause` 暂停新调度，不打断运行中的任务。 | 单独表达派工暂停与在途执行；不把暂停响应当作进程停止确认。 |
| Project 身份包含 `(team, project_id)`；写入使用 ETag，并发冲突返回 `409`。 | 保留明确执行归属，冲突后读回并重新判断。多实例调用还需选定正确实例。 |
| Admin/Manager 有 Controller 全权限；`projectflow` 的部分角色限制依赖工具注入和提示约束。 | 必须验证真实的受控写入、派工入口及绕过路径，不能认为上游已强制实现审批档位。 |
| Project 有历史快照和产物读取；`complete` 要求任务进入终态。 | 可辅助观察与追溯；任务终态和上游完成不证明业务验收通过或获准合并。 |

实现前重点验证：许可与执行路径的强制关联；暂停后的在途任务与迟到结果处理；REST 和本地 MCP 并发写冲突及重启恢复；Loop 的控制接入；计划应用结果核查；跨仓 issue 到上游 Project 的映射与暂停范围。

Dashboard 较新版本的 HITL 与 `org.agentteams.run v1` 不能直接算作锁定 Controller 的能力，其兼容矩阵尚未验证。

## 5. 取舍与未决范围

采用版本化提案、许可判断和延后应用，接受变更获准后仍可能等待在途工作收敛的成本，以适应上游重规划限制并保留明确的执行依据。页面上的灵活编排不能超出实际执行路径能保证的语义。

本轮已确认计划变更的六条规则、上述流程与页面状态，以及首期仅支持自然语言调整的交互范围。以下仍待讨论：

- 具体测试阶段、必需证据、正式人工审查门槛，以及 draft PR 创建和更新时机。
- 人工合并顺序、部分合并失败、代码回退、部署恢复和数据恢复流程。
- 跨仓验证小组是否常设、成员与负责人配置，以及具体 Graph 节点和模板。
- 首次计划的审批入口、谁有权审批、档位默认值与覆盖方式、运行中切换档位的详细行为。
- 后续待办设计：直接编辑编排图，包括节点、属性、依赖连线和拖拽交互；不属于首期范围，具体交互后续明确，仍须沿用版本化变更、许可与生效规则。
- 审批、执行和证据记录的具体存储结构，以及上游 Project 的执行映射；本 ADR 不确认独立的 `IssueRun` 等新增实体。
