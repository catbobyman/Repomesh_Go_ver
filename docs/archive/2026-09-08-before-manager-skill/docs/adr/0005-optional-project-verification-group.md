# ADR-0005：项目级跨仓验证小组可选启用

项目可以配置专用的跨仓验证小组，并在项目设置中选择是否启用。用户确认开关控制是否使用专用小组；关闭后，Manager 仍按需安排验证。这样允许项目按需要配置专用验证成员，同时保留一致的验证要求。

## 已确认决定

- 验证小组属于项目级；项目设置提供“启用跨仓验证小组”开关。
- 启用后，优先由项目的专用验证小组执行跨仓验证节点。
- 未启用时，由 Manager 按需安排项目内具备验证能力和相应权限的 Worker 执行。
- 无论开关状态如何，已确认的验证范围、证据要求和通过门槛始终有效，见[测试与验证节点设计](../verification-node-design.md)。
- 没有合适的执行者时，显示等待原因。
- 小组及相关验证执行者承担验证工作，业务修复仍由对应仓库 Team 负责，验证环境不向业务仓库推送修复。

沿用 [ADR-0001](0001-agentteams-issue-concurrency-and-isolation.md) 的 Worker 单活跃任务、Attempt 独立副本及全局容量和项目额度约束，以及 [ADR-0002](0002-github-app-authorization-and-draft-pr-delivery.md) 的权限边界。选用其他 Worker 不扩大其有效权限，也不绕过容量和隔离要求。项目设置的配置不改变首条 issue 正式提交并持久化后才准备实例的既有规则。

## 固定验证负责人与组内协调

启用的验证小组设置一名固定验证负责人，负责组内任务安排、证据完整性核对和结果汇总，并向 Manager 回报。Manager 继续承担跨仓 issue 的整体协调。

```text
Manager：协调跨仓 issue
    |
验证负责人：组织本组验证工作
    |
    +-- Worker：页面筛选验证
    +-- Worker：接口与数据验证
```

例如 F1 + B1 同时需要页面和接口检查，Manager 交付当前有效的验证计划，验证负责人安排成员执行并汇总各项结果。涉及业务修复或计划范围变化，再由 Manager 协调相关仓库 Leader；计划变更继续遵守 ADR-0003 的许可与生效规则。

采用固定验证负责人，接受增加一个协调角色的成本，让多个专项节点的日常安排和证据汇总具有明确的责任人。正式验证执行者的独立性要求见下文；测试编写、初判及复核采纳分工见下文；本节不将固定负责人映射为已验证的上游 Leader 资源。

## 正式验证执行者与业务作者分离

- 业务作者可以编写自测、提供测试脚本和排查资料，但不担任本轮相关业务改动的正式跨仓验证执行者。
- 正式跨仓验证由未参与本轮被测业务改动的 Worker 执行；独立性判断针对本轮被测改动，不以是否曾参与该仓库开发作为判断依据。
- 验证 Worker 可以复用已有测试，但需要核对测试是否符合验收条件，并实际执行验证，提交证据和检查结论。
- 未启用专用验证小组时，Manager 也按上述要求选择执行者；没有合适成员则等待并显示原因。

```text
Worker A 编写前端改动 F1
Worker B 编写后端改动 B1
Worker C 验证 F1 + B1，提交证据和检查结论
验证负责人核对证据并汇总
```

采用这一分工，接受额外成员需求和可能的等待，以减少开发与验证沿用同一错误理解的问题。上述为正式验证执行者的独立性要求；最终结论的复核和采纳职责见下一节。

## 必检清单的编制与计划版本

| 角色 | 职责 |
| --- | --- |
| 各仓 Leader | 提供接口契约、改动范围、已知风险和已有测试。 |
| 验证负责人 | 根据已确认的验收条件编制跨仓必检清单，明确各节点的覆盖范围。 |
| Manager | 核对整个 issue 的验收覆盖、依赖和预算，将清单纳入计划版本。 |
| 验证 Worker | 根据清单编写或复用具体测试脚本并执行。 |

例如“分页后仍保持支付状态筛选”已经是验收要求，验证负责人将它落实成必检项，验证 Worker 再编写具体操作与断言。

未启用验证小组时，由 Manager 组织被指派的验证 Worker 起草清单并核对。业务含义不清仍交给人确认；涉及计划变更时沿用 ADR-0003。纳入计划版本与获得许可、实际生效保持既有区分，本节不新增首次计划审批人或入口的决定。

## 检查结果的初判、复核与采纳

| 角色 | 职责 |
| --- | --- |
| 验证 Worker | 编写或复用测试、实际执行，提交证据和单项结果初判。 |
| 验证负责人 | 核对验收依据、版本、证据和结论，复核后采纳为节点的有效检查结果。 |
| Manager | 汇总节点结果与验收覆盖情况，协调后续工作；未启用验证小组时，承担上述复核职责。 |

执行者提交初判与复核采纳分别表达。页面分别显示“执行者初判”和“复核状态”，让用户看清结果是否已经被采纳。该流程是 Agent 内部职责分工，不改变现有人工决定边界。

例如 Worker 报告“四项全部通过”，但没有分页检查的证据，复核者应指出缺口，相关检查保留为“暂无法判定”，节点尚未通过。采纳针对有依据的真实检查结果，不只针对“通过”结果。

## 问题归属与重新验证

- 验证 Worker 提交失败证据和初步归属；验证负责人核对后交给相关仓库 Leader 定位。未启用验证小组时由 Manager 承担相应组织和复核职责。
- 已经证实违反验收条件时，即使尚未定位到仓库，也保留“业务缺陷、归属待定位”，不退回为结论未知。
- frontend/backend 对归属有分歧时，由 Manager 协调补充诊断，依据证据分派修复；涉及业务含义不清时，按业务解释的决定规则处理。
- 业务仓库 Team 负责修复；新候选提交后，验证负责人组织重新验证，未启用小组时由 Manager 组织。
- 独立验证 Worker 针对新的固定组合执行，重新判断旧证据能否复用；组织重验本身不保证旧证据继续有效。
- 诊断和重验遵守当前计划及获准额度，需要调整计划时按 ADR-0003 处理；具体循环行为留在第 4 项。

以上分工经用户回复“采用”确认。同一条消息提出 Manager 统一对人沟通、YOLO 无人工门禁及 Skill 驱动动态执行的新方向，见[方向修改讨论稿](../manager-entry-and-skill-orchestration-proposal.md)。新方向对业务解释和授权边界的具体修改尚在讨论，不将 Agent 内部复核解释为逐项人工确认。

## 场景

“支付状态筛选”的 F1 + B1 需要跨仓验证。项目启用验证小组时，优先向小组安排相应验证节点；项目未启用小组时，Manager 从项目内安排具备能力和权限的 Worker。两种情况下都使用同一套固定组合、证据及通过要求。不能因未启用专用小组而省略必检项或直接判为通过。

## 运行中停用：停止接新任务，在途工作收尾

用户关闭开关后，小组停止接收新任务，页面进入“停用中”。不同阶段的工作分别处理：

| 工作状态 | 处理规则 |
| --- | --- |
| 尚未开始，包括已分配但未启动 | 停止由该小组启动，交回 Manager 按既有授权安排。 |
| 正在执行 | 当前 Attempt 继续完成，保存结果和证据。 |
| 已提交、待核对 | 继续核对结果；提交本身不算通过。 |

```text
跨仓验证小组：停用中
正在执行：1
待核对结果：1
```

上述工作处理完后显示“已停用”。新验证任务由 Manager 按关闭后的规则安排；涉及计划变更时仍沿用 [ADR-0003](0003-plan-change-authorization-and-activation.md)。

收尾和结果核对保留真实检查结论，不将业务缺陷或阻塞处理为通过。这里的停用状态属于验证小组，不替代 issue、计划版本、Task 或 Attempt 的状态。

## 仍待讨论与技术边界

第 2 项原清单剩余两组产品问题。用户同时提出统一 Manager 交互、按模式处理人工门禁及 Skill 驱动动态执行的方向修改，当前优先讨论该方向对既有规则的影响；不再预估固定的剩余确认次数。

| 组 | 待决定内容 |
| --- | --- |
| 成员配置与不可用时的安排 | Worker 数量与配置方式、负责人或执行成员不可用时的安排。 |
| 开关设置与停用异常 | 开关默认值、修改权限，以及长时间未收尾、异常和停用中重新启用的处理。 |

技术待验证项：

- 正式验证执行者与本轮业务改动作者参与关系的记录和核查。
- 项目级验证小组、固定负责人怎样映射 AgentTeams 资源、成员、房间和权限；不能将产品角色直接等同于已证明可用的上游资源。
- 成员及资源回收、启停和计划许可与生效控制路径的具体衔接。

详细 Graph/Loop 执行行为留在第 4 项，不在本项因确定职责而自动增加派工或重试许可。

本 ADR 已确认组织、开关基本含义、固定验证负责人的协调职责、正式验证执行者独立性、必检清单编制、结果初判与复核采纳、问题归属与重新验证职责，以及停用收尾规则。成员及资源的具体回收方式、开关与计划变更控制路径的技术衔接仍需细化；不将停用等同于删除成员或历史记录。

- 用户提出采用项目级小组，并在设置中提供“是否启用该团队”的选择。
