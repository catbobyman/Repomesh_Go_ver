# Manager 统一交互与 Skill 驱动执行：方向修改讨论稿

状态：用户已提出方向修改；下列架构建议和对旧规则的替代语义尚待逐项确认。不是已确认 ADR，不代表 AgentTeams 已实现或已通过运行验收。

## 用户最新提出的方向

- 人在主界面只与 Manager 对话，主要显示 Manager 的会话窗口。
- 所有需要用户同意的事项，由 Manager 汇总并反馈给用户。Manager 可以有 MCP 或工具，将“门禁”级别的问题呈现给用户。
- 按模式区分：YOLO 完全不触发人工门禁，另一模式会触发。
- 团队、测试和验证可以写成 Skill，由团队按 Skill 执行；Leader 根据 Skill 和仓库情况请求创建 Worker，测试流程也按 Skill 组织。

本次没有要求安装、编码、部署或连接真实服务。不能将这些方向表述为已实现功能，也不能将“可以用 MCP”写成已确定接口契约。

## 架构建议，待确认

| 部分 | 建议职责 |
| --- | --- |
| Skill | 描述团队职责、所需能力、执行步骤、测试方法、证据要求和升级问题的条件，允许按仓库及任务裁剪具体工作。 |
| 本次计划 | 将 Skill 和仓库情况落实成具体角色、任务、必检项、依赖及上限；记录使用的 Skill 版本，沿用版本化计划和实际生效记录。 |
| RepoMesh | 校验并执行 Worker 分配或创建、容量占用、权限与隔离、计划应用和任务启动；保存决策及证据。 |
| Manager 会话 | 汇总进度、结果及需人决定的事项；需要审批时在同一会话呈现具体提案，用户回应关联对应事项及版本。 |

Skill 更新不建议静默改写在途计划。长期 Team、Leader 与按需请求 Worker 可以并存；优先复用合适空闲 Worker、必要时申请新 Worker 属于建议，具体生命周期尚未决定。正式验证与本轮业务作者分离的既有规则仍应体现在人员选择中。

建议的流程：

```text
用户 <--> Manager 会话
                |
          当前计划与 Skill
                |
       Leader / 验证负责人
                |
       请求所需能力的 Worker
                |
       RepoMesh 检查并分配资源
                |
       Worker 执行 -> 证据与结果回流
                |
         Agent 内部复核与汇总
                |
             Manager
```

验证负责人的复核、仓库 Leader 的定位和 Manager 的汇总属于 Agent 内部工作，不等于每一步都需要用户确认。内部角色会话可继续存在；主界面由谁对人沟通与内部任务由谁主责是不同问题。

工具入口建议由 Manager 调用，携带问题、依据、受影响工作、建议和待决定版本。RepoMesh 根据模式保存决定、返回执行结果或待用户决定状态。是否采用 MCP、工具参数和恢复契约留待技术设计；避免只靠 Manager 是否记得调用工具来保证执行约束。

## YOLO 无人工门禁的建议解释，待确认

- YOLO 不弹出审批或等待人工同意；Manager 在适用授权内自行处理编排和判断，并保留决定记录。
- 建议权限、预算上限、已明确的验收条件及仓库合并规则仍由系统约束。触及边界时，给出受限或未完成结果；不自动扩大权限、增加预算或降低标准，也不借此新增等待审批节点。其他工作能否继续由后续 Graph/Loop 规则明确。
- 对尚未定义的业务规则，建议允许 Manager 在 YOLO 下选择并记录解释，继续测试；记录应注明解释由 Manager 采用，不能写成人已确认，也不能覆盖已有明确要求。
- 需要审批的模式中，由 Manager 在同一会话给出解释、建议及影响，用户决定后再用于受影响检查。
- 缺失证据、环境不可用和真实缺陷仍按事实记录。选择了业务解释不表示测试已经通过。

当前首先需要确认：YOLO 是否授权 Manager 对缺失业务规则选择并记录解释后继续执行。这会改变 ADR-0004 的原规则，不能从“不弹审批”悄悄推导为已经授权。
