# 测试与验证节点设计

本文记录七项讨论顺序中的第 1 项。用户已整体确认输入与必检清单、按类型保留附件、结果呈现与汇总方案，第 1 项在当前产品设计深度收口，进入第 2 项“跨仓验证人员职责”。以下为已确认设计，不表示已经实现或完成运行验收。交接入口见 [v3 handoff](HANDOFF-2026-09-07-v3.md)。

方向修改提示：用户最新提出主界面仅与 Manager 对话、所有人工决定经 Manager 汇总呈现、YOLO 不触发人工门禁，以及团队和测试验证流程由 Skill 指导、按任务动态请求 Worker。见[方向修改讨论稿](manager-entry-and-skill-orchestration-proposal.md)。其中 YOLO 对缺失业务规则和既有授权边界的处理仍待明确；以下保留原决定以便追溯。验证负责人复核是 Agent 内部工作，不要求用户逐项确认。

## 已确认

### 缺失业务规则的解释由人确认

Agent 可以提出业务解释和测试建议，但须经人确认，才能用该解释判定相关检查通过或失败。该决定及其适用边界见 [ADR-0004](adr/0004-acceptance-rule-clarification.md)。

### 证据不足时保留“暂无法判定”

- 对证据不足、尚不能确定检查结论的单项检查，保留“暂无法判定”这一结果，并列出缺失证据。仅未定位具体仓库或代码位置的情况见下一节。
- 该结果描述单项检查，不直接决定整个 issue 的状态。
- 缺少证据本身不能证明业务存在缺陷，也不能证明一定是环境或数据问题；分类原则与附件要求见下文。

示例：规则明确要求“已支付”筛选显示测试订单 P01，但 frontend F1 + backend B1 的页面为空。目前只有截图，尚未核实 P01 是否成功写入、是否处于当前账号可见范围，以及接口实际返回了什么。该检查可记录为“暂无法判定”，并列明缺失的证据。

以下仅为说明已确认含义的页面文字示例，完整布局、字段和交互尚未定稿：

```text
检查：支付状态筛选应显示 P01
验证组合：frontend F1 + backend B1
检查结果：暂无法判定
缺失证据：P01 写入与可见范围检查、接口请求及响应记录
```

### 业务缺陷判定不等待具体定位

- 当证据足以证明实际行为违反已明确的业务规则时，可以判定该项存在业务缺陷，无须等待定位到具体仓库或代码位置。
- “检查结果：业务缺陷”与“问题归属：待定位”可以同时成立。
- “暂无法判定”表示证据尚不足以确定检查结论；已经证实存在业务缺陷，仅未定位具体仓库或代码位置，不因此改记为“暂无法判定”。
- 缺陷判定与归属定位分别表达，不因结果标签自动触发派工；归属与重验职责见 ADR-0005，具体 Graph/Loop 执行行为仍待第 4 项讨论。

示例：已核实实际运行 F1 + B1，规则明确要求当前账号筛选“已支付”时看到订单 P01，相关数据与环境前提成立，操作记录却证明结果为空。即使尚未定位是前端参数、后端查询还是接口衔接的问题，也可以记录业务缺陷。该示例说明判定与定位的关系，不将示例证据清单设为所有检查的统一门槛。

```text
检查结果：业务缺陷
问题归属：待定位
依据：明确的预期、相关前提检查记录、实际结果
```

### 环境阻塞按证据证明的原因判定

- 分类依据是证据证明的原因，不仅是错误发生在启动、构建、数据准备还是页面操作阶段。
- 已证实验证前提缺失、导致无法检查时，判为环境阻塞，并指出未满足的前提及支持证据。
- 已证实候选违反约定要求时，判为业务缺陷；即使错误发生在服务启动或数据准备阶段，也适用这一边界。
- 证据不足以区分上述情况时，保留“暂无法判定”，列出待补证据。

| 场景示例 | 结果及依据 |
| --- | --- |
| 测试环境应提供的数据库没有启动，导致无法继续检查 | 环境阻塞；记录缺失的验证前提及证据。 |
| 数据库符合约定，但 B1 的迁移代码存在已证实的错误，导致启动失败 | 业务缺陷；记录候选违反约定要求的证据。 |
| 只有“连接失败”日志，尚未查明数据库、配置或候选代码的问题 | 暂无法判定；列出待补证据。 |

此处确认分类原则；通用最小证据记录和按检查类型保留的附件见下文。环境或测试数据准备责任，以及恢复和重新验证的流程在后续主题细化。

### 验证节点的通过门槛

- 约定的必检项全部具有适用于当前固定组合的有效通过证据，验证节点才判为通过。
- 逐项保留检查结果；跳过、受阻、需求待澄清或暂无法判定的必检项不能计为通过。
- 必检项尚未全部达到上述条件时，节点尚未通过；汇总保留各项结果和所有未通过原因，见下文。
- 沿用固定组合原则：组合变化后重新判断原证据是否有效。节点通过不直接表示整个 issue 完成。

示例：F1 + B1 的节点约定四项必检：已支付订单展示、未支付订单排除、清除筛选、分页保持筛选条件。前三项通过，第四项因测试数据未准备好受阻。保留前三项的通过结果，同时显示第四项的阻塞原因，节点尚未通过。这四项只用于说明通过门槛，不是全产品默认检查清单。

### 单项检查的最小证据记录

每项检查保留以下五组信息，具体附件要求按检查类型确定：

| 信息 | 必须保留的内容 |
| --- | --- |
| 检查归属 | issue、节点、检查项、Attempt、执行者和执行时间。 |
| 验证对象 | 实际运行的各仓 commit，以及环境、配置和测试数据的版本或可追溯记录。 |
| 判定依据 | 对应计划及验收条件版本，本项预期结果。 |
| 执行证据 | 相关前提核查、操作步骤或测试脚本版本、实际结果，以及支持结论的附件。 |
| 检查结论 | 结果分类、判断理由、缺失证据；问题归属已知则记录，未知则保留待定位。 |

以“筛选已支付后应显示 P01”为例，记录需关联实际运行的 F1/B1 commit、该项预期的依据和本次执行事实，使其他验证者能够复核结论。

页面先展示结论和预期／实际差异，详情中查看证据，并分别显示“执行者初判”和“复核状态”。验证 Worker 提交初判，验证负责人复核后采纳为节点的有效检查结果；未启用小组时由 Manager 复核。职责和例子见 [ADR-0005](adr/0005-optional-project-verification-group.md)。按检查类型保留的附件要求见下文；完整字段结构、存储方式及交互细节仍待细化。

### 专项验证节点与验收覆盖范围

- 允许一个跨仓 issue 按验收范围拆成多个专项验证节点。
- 每个节点明确关联自己负责的验收条件和必检项，并按该范围判定通过。
- issue 层汇总各节点的覆盖情况，显式呈现尚未覆盖的验收条件；单个节点通过仅证明其负责范围达到约定要求。

示例：假设 issue 已明确要求页面支持支付状态筛选，导出结果也遵循同样的筛选条件。页面验证节点检查展示、筛选、分页及清除筛选；导出验证节点检查导出请求及文件内容。页面节点通过时，若导出尚未安排检查，issue 层仍显示这一覆盖缺口。本例不将导出功能纳入所有筛选需求的默认范围，也不决定节点间的具体 Graph/Loop 行为。

### 节点输入与必检清单

每个节点执行前，应能够明确查看以下节点说明：

| 输入 | 内容 |
| --- | --- |
| 检查范围 | 负责的验收条件，以及对应必检项、操作条件和预期结果。 |
| 判定依据 | 当前生效计划版本、验收条件版本；未明确的业务规则单独标出。 |
| 固定组合 | 涉及仓库的完整 commit，以及实际运行版本的核对要求。 |
| 验证前提 | 环境入口、配置、测试账号及可见范围、测试数据要求和准备记录。 |
| 执行约束 | 当前授权范围、预算和时间限制，以及本节点需要提交的证据。 |

必检清单及其验收条件映射随计划版本保存，调整沿用 [ADR-0003](adr/0003-plan-change-authorization-and-activation.md)。具体测试脚本另行记录版本，以便复现。缺失输入明确指出，按已确认规则判断为环境阻塞、需求待澄清或暂无法判定。清单由验证负责人编制、各仓 Leader 提供依据，Manager 核对并纳入计划版本；测试由验证 Worker 编写或复用并执行，结果按复核采纳规则处理，详见 [ADR-0005](adr/0005-optional-project-verification-group.md)。未启用小组时，Manager 组织被指派的验证 Worker 起草清单并核对；本节不新增首次计划审批人或审批入口的决定。

### 按检查类型保留证据附件

通用五组最小证据信息继续适用，并按检查类型保留以下必要附件：

| 检查类型 | 附件要求 |
| --- | --- |
| 页面交互 | 操作步骤、断言结果、关键页面截图；涉及跨仓链路时关联相关请求和响应。 |
| 接口与数据 | 请求条件、响应、预期与实际差异，以及相关测试数据的前提核查。 |
| 构建、启动与集成 | 命令或脚本版本、执行结果、相关日志，以及实际运行版本记录。 |
| 环境阻塞 | 未满足的前提、核查结果及其如何阻止检查。 |
| 需求待澄清 | 存在歧义的原始要求、不同解释、受影响的检查项。 |
| 暂无法判定 | 已获得的证据，以及还缺什么才能判断。 |

附件应足以支持对应结论。例如证明订单筛选正确，需要订单与筛选条件的检查结果，仅有 HTTP 200 不足以证明这一点。具体文件格式、存储结构与采集实现仍待细化。

### 单项结果、执行进度与节点汇总

单项检查采用以下五类结果：

| 结果 | 含义 |
| --- | --- |
| 通过 | 有适用于当前固定组合的有效证据，证明该项符合明确预期。 |
| 业务缺陷 | 已证实候选违反约定要求；具体仓库或代码位置可以待定位。 |
| 环境阻塞 | 验证前提缺失导致无法检查；原因可细分为服务、配置、测试数据或验证工具等。候选自身违反约定仍归业务缺陷。 |
| 需求待澄清 | 业务预期尚不明确，需要人确认。 |
| 暂无法判定 | 现有证据不足以确定结论。 |

测试数据阻塞归入“环境阻塞”的原因分类，页面可直接显示“环境阻塞：测试数据未准备好”。

执行进度与验收结论分别显示。待执行、执行中、跳过等属于执行状态，不能充当通过证据。节点保留所有未通过原因及数量，不以一个原因覆盖其他检查结果；节点只有满足已确认的全部必检项通过门槛，才判为通过。

```text
节点：支付状态筛选验证
组合：F1 + B1
执行状态：本次执行已结束
验收结论：尚未通过

必检项：4
  通过：2
  业务缺陷：1（归属待定位）
  环境阻塞：1（测试数据未准备好）
```

issue 层继续汇总各专项节点的验收覆盖情况，显示遗漏和未通过项。以上状态示例不定义完整的执行生命周期，也不代表上游接口已实现这些产品状态。

## 后续主题与实现细化

第 1 项在当前产品设计深度已收口，用户明确要求进入第 2 项。以下关联问题在后续主题集中讨论：

- 第 2 项：组织、启停、独立性、必检清单编制、结果初判与复核、归属与重新验证职责见 [ADR-0005](adr/0005-optional-project-verification-group.md)；原清单剩余成员及不可用安排、开关设置与停用异常两组。当前优先讨论用户最新提出的 Manager 交互、模式与 Skill 动态执行方向。
- 第 3 项：环境、配置和测试数据准备，以及固定组合选择、恢复与清理。
- 第 4 项：补充证据或重新验证的触发与执行、等待澄清期间其他检查如何继续，以及历史记录的关联与保留细节。
- 第 5—7 项：人工审查与 PR 时机、人工合并及部分失败、回退与恢复。

字段与版本关联结构、证据文件格式及存储、完整执行状态机和页面交互细节仍需实现前细化。本文件不通过检查结果标签自动决定新派工、重试、审批或 issue 完成；具体 Graph/Loop 行为仍在第 4 项讨论。

## 确认记录

- 用户对缺失业务规则的解释须经人确认后用于相关检查判定，回复“同意”；详见 ADR-0004。
- 用户对保留“暂无法判定”以承接证据不足、尚不能可靠归因的检查，回复“确定”。
- 用户对“业务缺陷的判定不必等待具体仓库或代码位置定位完成”回复“同意”；同时明确“暂无法判定”针对检查结论尚不确定，不因具体归属未定位而抹去已经证实的缺陷结论。
- 用户对“验证前提缺失导致无法检查，判为环境阻塞；已证实候选违反约定要求，判为业务缺陷；证据不足则暂无法判定”回复“采用”。
- 用户对“约定的必检项全部具有适用于当前固定组合的有效通过证据，验证节点才判为通过”回复“确认”。
- 用户对以检查归属、验证对象、判定依据、执行证据、检查结论五组信息作为每项检查必须保留的最小证据记录，具体附件要求按检查类型确定，回复“确认”。
- 用户对允许一个跨仓 issue 按验收范围拆成多个专项验证节点，并要求每个节点明确自己的覆盖范围，回复“允许”，并询问剩余待决定项。
- 用户对输入与必检清单、按检查类型保留证据附件、单项结果与节点汇总三组完整建议，回复“确定，记录，进入下一项”；第 1 项收口，进入第 2 项人员职责。
