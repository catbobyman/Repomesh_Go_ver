## 2. 已确认的组织与隔离基线

- 使用 AgentScope 团队的 agentscope-ai/AgentTeams，不从零重新选型。
- 一个 RepoMesh 管理多个长期、多仓库项目，每项目对应独立 AgentTeams 实例，实例内部一个长期 Manager。
- 项目内每仓一支长期 Team，包含 Leader 和 Workers；不同 issue 复用角色身份，不重建 Manager 或团队。
- 初期 Controller、Matrix、存储和网关也按实例分开，接受重复基础开销。房间、具名 Manager 或目录前缀不能替代项目隔离。
- 当前最多一台服务器，RepoMesh 统一管理全局容量与项目额度，不能让每个实例按独占整机调度。
- 一个 Worker 同时只有一个活跃任务，领取和占用由后台原子保证。每次 Attempt 独立 clone、分支、构建目录及结果记录；worktree 不是安全边界。
- 普通容器不承诺 VM 或恶意多租户级隔离；Agent 不直接持有宿主 Docker socket，可信管理面的创建参数也要受限。
- 跨项目接入同一远端仓库时，本地隔离不隔离远端 Git 历史，仍需协调任务分支、基线变化与交付。
- 停止进程、回收副本和删除历史证据是不同动作；回收前保存必要状态，关键数据需要服务器外备份。

## 4. Issue、房间与 session：D17

跨仓或影响范围未知的 issue 默认由 Manager 主责。明确限定单仓且未发现跨仓依赖时可直达 Leader；来源仓库不能单独证明影响范围。单仓工作发现越界时升级给 Manager，保留原 issue 历史。

```text
Cross-repo Issue I101
|
+-- Main room R-I101
|     +-- Manager -> its own session
|
+-- Repo room R-I101-A
|     +-- Leader A -> its own session
|     +-- Worker A1 -> its own session -> Task / Attempt clone
|
+-- Repo room R-I101-B
      +-- Leader B -> its own session
      +-- Worker B1 -> its own session -> Task / Attempt clone

Single-repo Issue I102
|
+-- Primary repo room R-I102-A
      +-- Leader A -> its own session
      +-- Assigned Worker -> its own session
```

- RepoMesh 受控建房、邀请、设权，并维护 project / issue / repository / agent / room / session 映射。Manager 或 Leader 可以提出建房需求。
- Worker 默认加入仓库 issue 房间，普通 Task/Attempt 不逐个建房；特殊权限、超大上下文或专项验证等明确需求才考虑专用房间。
- 按此前研究的 QwenPaw 路径，建房、邀请和加入不等于创建模型 session；Agent 首次处理有效消息时按 matrix:{room_id} 查找或创建自己的本地 session。
- 同房不同 Agent 各自维护 session。共享的是可见消息，不是共同模型内存、隐藏推理或未发布工具结果；相同 session 字符串不能作为跨 Agent 的全局唯一标识。
- 私聊同样按私聊房间划分；长期 DM 不会隔离多个 issue。@ 选择/触发接收者，同房再次提及延续原会话。当前讨论的普通 reply/thread 不构成独立 session 边界。
- Manager 若也参与仓库子房间，会有该子房间自己的 session；不能假设它自动继承主房间完整上下文。具体消息桥接和结果回流需验证。
- Team Room 保留公共协作信息，其他 issue 的临时指令、审批和未完成计划不能当作共享长期记忆。
- Manager / Leader 采用短轮事件驱动协调，Worker 按容量并行。多个 issue 同时在途不等于承诺 Manager 同时多路模型推理。
- Worker 单活跃任务约束跨房间生效，不能因有两个 session 就同时接两项执行任务。
- Task/Attempt 通知和迟到结果要明确归属；独立 clone 不会自动清除同 issue session 的旧指令，重试上下文选择仍需验证。

这里的产品拓扑已确认，具体 session 时机、消息过滤、队列、上下文和重启恢复仍未做端到端验收。

## 5. 仓库范围与权限：ADR-0002

用户确认的意图：仓可以多给，权限分层收窄；Agent 改代码和开 PR，合并由人和仓库规则决定。

| 层级 | 已确认边界 |
| --- | --- |
| 选仓 | 添加仓库选择全部或指定范围，不设置逐仓只读、推送、开 PR、合并的操作菜单；App 安装范围、项目范围和任务范围分开。 |
| App | 使用固定工作权限集，目标覆盖读取代码、建/推任务分支、创建 PR、读取检查状态等主路径。 |
| 运行时 | 凭证或受控工具能力进一步收窄到相关项目、仓库、任务；不默认启用 GitHub Issues 操作、重跑 CI 或仓库管理。 |
| 发起人 | 不通过 Agent 放大用户的有效 Git 权限；App 能访问不代表当前用户有权访问，RepoMesh 要服务端核验。 |
| 交付 | 默认推自己的任务分支并开 draft PR，合并由人和仓库规则控制。读取规则不等于有权修改、绕过规则或直推主分支。 |

- “先只读接入、以后逐项启用写权限”的建议未被接受。
- 多仓共同修改仍由各仓 Team 分工，未授权单 Worker 获得所有仓库的可写共享工作区。
- GitHub App 权限名称、token 实际收窄维度、用户权限约束和分支规则强制效果尚未技术验证。不能把“产品禁止 Agent 合并”写成“已证明 GitHub 有能开 PR 但无法合并的 token”。
- RepoMesh 内部 issue 不等同于 GitHub Issues API 对象。外部 issue 同步的身份与权限另行明确。
- “全部仓库”是否动态包含后续新增仓库、授权撤销及部分失败如何呈现、项目配置完成条件尚待细化。

## 6. 计划变更决定与后续讨论

### 已确认：计划变更如何获准和生效

[ADR-0003](adr/0003-plan-change-authorization-and-activation.md) 记录用户明确确认的六条规则：

1. 审批对象是明确的计划版本，展示差异、原因、依赖、仓库范围、预算和循环上限；后续修改产生新版本。
2. 全自动（YOLO）按既有授权、预算和策略自动判断，审批档由人判断，两档共用执行规则。扩大权限、提高预算上限、放宽已确认验收条件都由人决定，合并仍由人和仓库规则控制。
3. 已批准范围和上限内的 Loop 可自动运行；新候选仍需重判固定组合的证据有效性，越出循环范围或上限形成新请求。
4. 等待审批时旧计划仍有效，不能继续的工作明确阻塞。变更获准后才进入应用流程；第一版按受影响上游 Project 暂停新派工，等待在途任务和已提交结果收敛，核对、应用并读回成功后才生效。
5. 拒绝、冲突、失败和不确定结果保留历史；冲突后读取最新状态重新判断，不确定时先核查。
6. RepoMesh 保存许可并实际控制变更应用和任务启动；Controller、MCP、存储写入路径如何受控仍需验证，不能只做页面审批。

计划变更页面分别显示待审批、已获准待应用、应用中、已生效、已拒绝、需重新判断和应用失败。这些状态不替代 issue、Worker 或 Attempt 状态。单分支暂停暂不作为首期承诺；首次计划审批入口、审批人、档位默认值及切换细节尚未敲定。

已确认首期编排调整仅支持自然语言：用户提出要求，由 Manager 形成版本化变更提案，继续按上述许可与生效流程处理。直接编辑节点、属性、依赖连线及拖拽编排进入后续待办设计，不属于首期范围。
