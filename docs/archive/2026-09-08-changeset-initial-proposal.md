## 当前建议：先确定 ChangeSet 边界

建议一个 issue 默认维护一个贯穿本次交付的主 ChangeSet。ChangeSet 使用稳定身份，多轮修复增加不可变的候选版本，保留历史，不在每次 Attempt 时新建完整 ChangeSet。

三类概念分别表达：

| 建议概念 | 记录什么 |
| --- | --- |
| ChangeSet | 本次变更的稳定归属：所属 issue、涉及仓库、关联 PR，以及交付过程记录。 |
| ChangeSet 版本 | 某次明确的变更内容与固定候选组合，例如 F1＋B1；关联当时的计划、验收、环境和验证证据。 |
| 操作记录 | 一次逻辑动作的请求、目标和结果，例如创建某仓 draft PR、更新候选、核查合并状态或开展恢复。 |

上述是待讨论的概念划分，不预先锁定表结构或新建领域实体。Plan Version 说明如何组织工作，ChangeSet 版本记录本次准备交付什么；两者不必具有相同版本号。

## 支付筛选场景

```text
Issue：支付状态筛选
    |
    +-- ChangeSet CS-01（稳定身份）
           |
           +-- 版本 1：F1 + B1 -> 验证证据 1
           |
           +-- 版本 2：F1 + B2 -> 验证证据 2
           |
           +-- frontend PR / backend PR（持续关联）
           |
           +-- 创建、更新、观察合并、恢复等操作记录
```

B1 修复为 B2 属于新候选版本，不属于重复请求；旧版本及证据保留。PR 不必因候选版本变化重新创建，这与 E2 的持续更新规则一致。实际合并状态的更新属于事实记录，不能把旧候选的证据静默改写为新组合通过。

## 幂等应落在逻辑操作上

建议为同一逻辑动作保留稳定操作标识和明确输入：

- 创建主 ChangeSet 本身也按 issue 归属去重，重复初始化不产生第二份记录。
- 同一动作的网络重试沿用同一标识，返回已有结果或核查进行中的结果，不重复创建 PR 等外部对象。
- 输入变化不能冒充原动作的重复请求；应拒绝不一致的复用，或明确形成新版本／新操作。
- 不只用 ChangeSet 身份作为所有操作的共同幂等键。创建 PR、更新候选和恢复是不同意图，应分别记录。
- 外部操作超时或结果未知时，先核查远端事实，再决定继续；不能把本地保存了操作标识当作远端已成功或只执行一次的证明。
- 回退或恢复是有自身身份的新操作，并关联被恢复的变更；重试回退与重新发起不同恢复意图分别处理。

这只是幂等设计建议。操作标识范围、并发冲突、外部对象关联、失败恢复以及不同来源事件的去重，后续逐项确定。合并继续由人和仓库规则控制，不由 ChangeSet 自行取得权限。

## 当前关键问题

是否采用“一个 issue 默认一个主 ChangeSet、修复保留同一身份并新增版本、各交付动作独立记录并处理幂等”的边界？

确定后再讨论版本冻结条件、PR 与仓库关联、状态、合并与部分失败、恢复关系和各类幂等操作。不自动采用 F／G 中此前提出的固定合并顺序、issue 完成条件或恢复执行方案。
