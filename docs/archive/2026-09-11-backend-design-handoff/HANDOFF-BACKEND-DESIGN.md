## 2. 已采用的约束

- 同一 Go 工程的 Web、后台协调和受限主机执行配套发布。Web／Agent 不持有 Docker socket；主机执行不开放任意宿主命令或挂载入口。
- 项目先保存；首次会话消息或页面建项提交后异步准备。页面与 Manager 创建共用业务命令，创建提交不等待实例、模型或房间就绪。
- 必要会话、Issue、主 ChangeSet、来源、输入快照、幂等结果及待办／事件同一个 PostgreSQL 短事务保存，外部执行在事务外；结果未知先核查原操作。
- Conversation 与 Issue 独立，一会话可关联多项；实例、Team、上游 Project、Task、Attempt 和业务对象不能互相代替。每项目独立 AgentTeams 实例，每仓长期 Team／Leader。
- Worker 单活跃 Attempt；Attempt、Worker 与容量统一预留，环境准备后启动前再核验；失联／超时不证明旧执行停止或资源释放。
- Graph 在后台进程内，仓内有限 DAG 复用上游，RepoMesh 控制跨仓、结果采纳和 Loop；不另写完整 Go DAG 引擎或拆 Graph 服务。
- 当前 YOLO 保留权限、预算、计划和验收约束，Git 合并仍由人处理。Skill、直接编辑图、后续审批、历史分析继续暂缓。

具体采用范围见 [ADR 索引](../../adr/README.md)、[创建契约](../../current/issue-page-create-api-contract.md)、[双入口机制](../../current/manager-create-issue-tool-design.md)、[架构专题](../../current/architecture-design-v1.md)和[后端专项](../../current/draft-conversation-backend-design.md)。不把整份 proposed 专项一并视为未采用，也不把 accepted 视为实现完成。

## 4. 推荐排期与每批完成边界

1. 先完成 B01—B04 中登录／权限、项目保存、手动建项、列表与详情所需的最小设计。把必要对象、持久创建和失败行为收口，不提前冻结剩余业务表。
2. 再实施该范围的真实持久化：创建事务、默认会话和 ChangeSet、来源、幂等及准备待办；刷新和重复提交基于真实记录。尚未接通运行端时保持真实未接入／未就绪状态，不发布 Manager 已接手或产品全链路完成。
3. 在 B05/B06 收口且接入范围得到实际任务授权后，实现提交后准备、运行映射、可信 MCP 和消息链路。自动准备方向已采用，这里补的是协议和实现，不另加人工开工门禁。
4. 后续分别推进 B08 的分析链路与 B07 的单仓单轮受控执行。仓库分析不依赖 AgentTeams Ready；两项各自验收，再扩展跨仓、结果采纳与循环。

这是上一轮评估建议的顺序，不是新的产品 ADR；旧 Prompt 中“先补 MCP／先做分析”的历史顺序不覆盖本文。设计就绪不等于运行验证通过，也不自动扩大本次编写交接任务的实施范围。

## 5. 必须先设计并验证的失败场景

第一批持久化设计至少交代：同键并发同输入只产生同一结果、同键不同输入拒绝、提交后响应丢失查询原操作、查询暂时 404 不盲目换键、已提交后运行失败保留业务事实、配置／权限变化重新核验、删除正文不让旧操作复活、业务记录与待办不出现一半成功、后台重启不重复制造逻辑操作。

接入前再覆盖以下实际风险，不因上游端点或 HTTP 200 而宣称能力存在：

| 已有证据或既定限制 | 设计／验证要求 |
| --- | --- |
| REST 拒绝不能覆盖 shared 写入和原生工具角色覆盖；MCP 与 REST 可出现覆盖竞争。 | 明确每条实际写路径的控制者和授权／版本约束；仅加提示词或封装 HTTP 不算控制闭环。 |
| Task cancelled 不保证进程或副作用停止，旧凭据撤销也存在不同窗口。 | 停止请求、实际停止、旧身份失效和资源释放分别取证；无法确认时不立即开替补。 |
| Matrix 已保存消息不等于 Worker 消费，thread 回复与 room session 有已测差距。 | 稳定消息／操作身份、游标及补查；明确保存、投递、接收／处理证据，多 Issue 晚到结果不改归属。 |
| 请求的资源值不保证真实容器限额生效。 | 在受限主机执行实际操作处落实并读回限额，不能从 CR 或进程名推断隔离。 |
| paused replan 为 409；in-progress／submitted 阻止换图；多目标非原子。 | 细化并选择受控衔接，逐目标读回及部分应用恢复；不把 pause→replan 两次调用当完整算法。 |
| Checkpoint 的 200 曾返回 HTML；原生 DAG ready 仅是候选。 | 验证响应类型和真实能力；就绪候选、准入预留、实际启动、业务完成分别处理。 |

这部分不能仅靠文档宣布成立，应在之后明确授权的独立验证中使用可观察的失败场景。现阶段不重跑旧实验、不操作共享卷；两轮 [remaining-preconditions](../../../validation/agentteams-2026-09-10/reports/remaining-preconditions.md) 与 [resumed-blocked-audit](../../../validation/agentteams-2026-09-10/reports/resumed-blocked-audit.md) 保持原义。

对应开发批次开始前，应具备四组一致的设计结果：

- 页面流程与状态表：由页面侧交付，后端可逐项说明权威数据和当前可用操作。

- 接口契约：调用者、输入输出、错误、幂等、并发及恢复有唯一基线；协议尚待验证的能力明确标注。
- 失败／恢复验收用例：指定观察依据、预期事实和不可宣称的成功，尤其区分队列、资源、运行与业务结果。

以上是工程条件，不新增逐项审批流程。新任务报告已采用设计、实现进度和实测证据时分别标记，不用文档 adopted、骨架构建或新 clone 代替业务验收。
