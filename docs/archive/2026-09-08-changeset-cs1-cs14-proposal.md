# ChangeSet 剩余问题与建议

更新：2026-09-08。用户要求将剩余问题及推荐一次列出。以下按产品与架构决策归为 **14 组（CS1—CS14）**；精确字段、API、插件契约等实现细节不另计数，H—K 仍延后。表中方案均未确认，不能因列入本文而视为已接受或已实现。

## 已确认基线

- 一个 issue 默认一个贯穿本次交付的主 ChangeSet；修复保留同一身份和多轮历史。
- issue 正式提交并持久化时建立主 ChangeSet，允许暂时没有 Candidate、Delivery Combination 或 PR。实例准备时机不变；重复事件和恢复复用既有归属。
- ChangeSet 关联 issue、仓库、PR、Candidate、Delivery Combination 和交付历史，也是 Agent 查看与溯源的入口。
- Agent 先读带来源引用的摘要，再按需查询关联的结构化记录及原始证据；摘要结论能定位到来源，证据缺失如实显示。
- 沿用现有候选结果和交付组合表达各轮产物及验证对象，不另定义一套“ChangeSet 候选版本”。
- Candidate 提交不等于已交付；各仓单独成功不等于组合通过。组合变化后重新判断证据有效性。
- 各逻辑操作独立记录并处理幂等。重试核查既有结果，真正的新变更另行记录；外部结果未知不等于成功。

- Candidate 正式提交即收录到所属 ChangeSet，保留产物版本和来源 Task／Attempt；未被接受也保留结果、原因、证据及历史，修复产生新候选而不覆盖旧记录。收录不自动等于接受、入选组合或交付。
- 已确认设计见 [ADR-0008](../adr/0008-changeset-attribution-and-history.md)。

## Issue 含义：现有定义澄清

这里的 Issue 是 RepoMesh 内部的一条统一需求事项，有自己的目标、范围、计划和验收条件，由 Manager 统筹，可以涉及一个或多个仓库。这沿用[术语表](../../CONTEXT.md)和 [ADR-0002](../adr/0002-github-app-authorization-and-draft-pr-delivery.md)，不是重新提出的对象边界。

GitHub issue 是某个仓库中的外部事项记录。RepoMesh Issue 不要求先在每仓创建一个 GitHub issue；也没有已经确认的“必须由多条 GitHub issue 拼成集合”的规则。是否关联、如何导入或同步，属于下表 CS1 的建议。

```text
RepoMesh 项目
    |
    +-- RepoMesh Issue：支付状态筛选
           +-- Manager 主房间、计划、验收条件
           |
           +-- 主 ChangeSet
                  +-- frontend / backend 的 Candidate 与 PR
                  +-- Delivery Combination、证据和交付历史

GitHub issue 的外部关联规则：CS1，尚待确认
```

## 剩余 14 组决策

| 编号 | 待决定的问题 | 推荐方案（尚未确认） |
| --- | --- | --- |
| CS1 | RepoMesh Issue 与 GitHub issue 怎样关联 | 一条 RepoMesh Issue 可关联零到多条 GitHub issue，标明来源或跟踪关系；重复导入同一来源先查已有映射，不自动合并需求。首期先支持关联，创建、评论、状态同步及关闭外部 issue 不默认启用，权限与接入单独确定。 |
| CS2 | 交付完成后新增工作、重开或拆分怎样归属 | 本轮未完成的修复继续原 ChangeSet。完成后新增范围建立关联的新 RepoMesh Issue 和 ChangeSet；误标完成可追加更正并恢复处理。跨 issue 记录依赖，首期不引入自动合并或嵌套 ChangeSet。 |
| CS3 | 哪些 Candidate 可以选入正式交付组合 | 业务仓候选经 Leader 内部初审接受后成为可选输入，Manager 按该次检查的范围、前提和有效计划选定固定组合；未修改的参与仓库固定基线。未接受候选可用于明确的诊断，但不冒充已接受候选；新候选到来不替换已启动验证的组合。 |
| CS4 | 代码、判据或环境变化时，究竟新增什么记录 | 任一仓库版本变化建立新 Delivery Combination。代码组合不变，但验收依据、Skill、配置或 mock 数据变化时，新增绑定相应上下文的验证记录并重新判断证据；单纯补充证据不强制新建组合，历史记录保留。 |
| CS5 | Candidate、分支、PR 和真实 commit 怎样关联 | 使用固定 commit 和实际产物关联，分支名或 PR 编号不能单独代表被验证版本。沿用 E 的同仓持续更新 PR；rebase、外部追加提交等导致实际 head 变化时重新匹配候选及证据。PR 无法继续复用时记录替代 PR 与旧 PR 的关系，不抹去旧记录。 |
| CS6 | ChangeSet 的总体状态怎样表达 | 分别记录执行进展、验证结论和交付进展，摘要可同时显示“执行已结束、验证未通过、部分仓库已合并”，并列出阻塞原因。整体结论根据相关记录汇总，不让一个笼统成功状态掩盖未完成部分。 |
| CS7 | 谁记录事实，谁作出判断，怎样更正 | 执行 Agent 提交产物、陈述及证据，沿用 Leader／验证负责人／Manager 的检查和协调职责。RepoMesh 保存来源、操作者、时间及可核查的执行结果，外部状态以实际观察为依据；判断和更正追加记录，摘要引用来源，不覆盖原始历史或把建议写成已发生事实。 |
| CS8 | 幂等标识、并发更新和重启恢复怎样处理 | 本地 Issue 与主 ChangeSet 推荐作为一次原子登记。每个逻辑操作有独立标识，绑定目标和输入摘要；同标识不同输入拒绝。并发更新校验目标版本，对同一目标的冲突操作串行处理；重启和超时先核查本地及远端结果再恢复，不承诺跨系统只执行一次。 |
| CS9 | 什么时候算本次变更完成 | 约定交付物和适用验收完成，必做事项已处理；涉及代码时，所有必需 PR 已由人合并，最终实际组合具有适用的有效证据。无需修改的仓库不制造 PR；无代码变更按对应交付约定判断。代码交付与部署上线分别记录，关闭 GitHub issue 不是必需完成依据。 |
| CS10 | 跨仓 PR 按什么顺序合并 | 按兼容性选顺序，由 Manager 给出依据，人执行合并。支付筛选若 F0＋B1 已验证可用，可先 backend 再 frontend；若其他顺序更安全则选其他顺序。不存在安全过渡组合时，先形成兼容改造或协调发布方案，不声称多仓 Git 合并具有原子性。 |
| CS11 | 基线变化或一仓已合并、另一仓受阻怎么办 | 记录各仓真实状态，明确显示部分合并。将实际已合并版本作为后续组合输入，重新判断受影响证据；在已有授权和计划内继续处理剩余工作，不自动撤销已成功部分。出现需要恢复的影响时，转入明确的恢复处理，不能把部分成功标成整体完成。 |
| CS12 | 关闭 PR、撤销代码、恢复部署和恢复数据怎样区分 | 未合并 PR 的取消记录在原 ChangeSet；已合并代码的撤销建议由人发起关联恢复 Issue／ChangeSet，相关仓 Team 产出撤销 PR，人合并。首期部署与数据恢复由相应有权限的人执行，RepoMesh 记录方案、对象、结果和证据。恢复关联原变更，不删除原历史；这属于交付处理，不给 YOLO 插入逐项执行审批。 |
| CS13 | Agent 可以查哪些 ChangeSet，怎样定位 | 默认读取当前 ChangeSet；允许在既有有效权限内，按 RepoMesh Issue、仓库、commit、PR 查找相关历史，再按需读取明细。读取结果标明所属组合、记录时间和来源；跨项目查询首期不默认开放，不因有关联就放大查看权限。 |
| CS14 | 哪些历史和证据保留，哪些可以清理 | 项目存续期保留归属、版本关联、决定和操作结果；必要验收证据随交付档案保存，临时运行材料按项目清理策略处理。明确标注附件已归档、过期或缺失；历史结论保留，但缺失正文不冒充当前仍可复核的证据。具体容量和保留期限作为实现配置细化。 |

## 边界及细化顺序

上述表格提出剩余选项的推荐，不变更已确认的 Manager 唯一对人窗口、模式规则、固定组合证据、有效权限、计划许可与生效、E 的 PR 时机或人工合并职责。CS12 的恢复处理也不把 YOLO 改成等待逐项同意的运行模式。

可按 CS1—CS14 分别采用、修改或暂缓。确认后再展开其字段、状态和异常；不把外部同步、并发控制、查询或恢复的建议描述成现有 AgentTeams 能力。F／G 的旧建议未整体采用，由本清单继续讨论；H／I／J／K 暂不展开。
