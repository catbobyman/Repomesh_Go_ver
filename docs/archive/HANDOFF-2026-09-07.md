## 3. 已确认的产品模型

### 3.1 组织和部署不是一个层级

| 层级 | 已确认规则 |
| --- | --- |
| RepoMesh | 一个统一入口，管理多个项目、授权、实例映射和全服务器执行容量。 |
| 多仓库项目 | 长期业务与仓库范围，每个独立项目对应独立 AgentTeams 实例。 |
| AgentTeams 实例 | 初期连 Controller、Matrix、存储、网关一起按项目分开；可共用服务器，不共用可写配置与项目数据。 |
| Manager | 每项目一个长期协调身份；不是每 issue 一个 Manager。 |
| Team | 在本项目内长期负责一个仓库，包含一个 Leader 和若干 Worker。 |
| Issue | 一次独立目标，可以跨仓，有自己的主负责人、会话、计划和验收条件。 |
| Task / Attempt | 有边界的执行工作及一次具体尝试；不同尝试保留独立历史与工作副本。 |

不要把 RepoMesh 长期业务项目直接等同于上游所有名为 `Project` 的对象。AgentTeams 内部执行记录如何对应 issue 或仓库子计划，还需要明确适配。

### 3.2 Issue 的入口与流转

- 所有 issue 先在 RepoMesh 统一登记、去重和核验权限。
- 跨仓或范围不明：由 Manager 主责，调查或确认范围后委派各仓 Leader。
- 用户明确限定单仓，且未发现跨仓依赖：可直接由该 Leader 主责。Manager 在项目总览有可见性，不重复派工。
- 来源仓库不能单独证明 issue 只影响该仓库。
- 一条 issue 同时只有一个主负责人；单仓工作发现需要越界时，升级给 Manager 确认范围变化。
- 普通 Worker 不作为默认业务接单入口；它接收的是明确范围、输入、输出和验收条件的任务。
- 后续评论回到原 issue；重试不是新 Manager，重复事件也不是新 issue。

### 3.3 会话与并行

- 用户侧一个 issue 一张工作页、一条主会话；Manager 主责时内部有 issue 主房间和每个受影响仓库一个子房间；明确单仓快速路径以仓库 issue 房间作为主房间，由 Leader 主责。
- RepoMesh 控制房间创建、邀请、权限和 project / issue / repository / agent / room / session 映射；Manager 或 Leader 可以提出建房需求，不能绕过 RepoMesh 形成无归属业务房间。
- 房间存在、Agent 被邀请或加入都不等于 session 已创建；按当前 QwenPaw 路径，Agent 第一次处理该房间的有效消息时才查找或创建自己的 session。
- 同房的 Manager、Leader、Worker 各自维护本地 session，只共享房间消息；`@Agent` 负责选择和触发接收者，在已有房间不会创建新的 Task 或 Attempt session。
- Worker 默认加入仓库 issue 房间；普通 Task / Attempt 通过独立记录、工作副本和执行环境隔离，仅在敏感权限、超大上下文或专项验证等明确需要时创建专用房间。
- 同一个 Manager / Leader 可参与多个 issue，但要分开上下文、计划、决策和结果。
- 常设 Team Room 用于公共信息，不能把所有 issue 的执行上下文混在里面。
- 协调采用短轮事件驱动：派工后结束本轮，收到结果、阻塞或用户输入再处理对应会话；不长时间占着协调轮次等待 Worker。
- 多个 issue 同时在途，不要求同一个 Manager 同时进行多路模型推理；真正的任务执行由多个空闲 Worker 按容量并行。
- 一个 Worker 一次只有一个活跃执行任务；成员占用与任务领取由后台原子保证，不靠多个会话分别判断。
- 有全服务器容量上限，也有各项目额度；不足排队。不能每个实例都按独占整台机器安排工作。
- 暂停、等待输入、重派和迟到结果只影响所属 issue / attempt，不误伤整支 Team 或其他项目。

### 3.4 隔离与交付

- 每个 Task Attempt 独立 clone、分支、构建目录；不默认继承脏工作区，不把 Git worktree 当安全边界。
- Team 默认只修改本仓；允许按授权读取其他仓的只读快照或契约，不自动授予跨仓写权。
- 跨仓集成由专项验证 Worker 检出固定候选 commit 组合，启动隔离服务及测试数据；不在该环境直接向业务仓推送修复。
- Worker 提交候选不等于任务验收，更不等于 issue 完成；Leader 初审后仍需要相应验证和验收。
- Agent 通过受控交付能力推自己的任务分支并创建 draft PR；合并由人和仓库规则决定，不自动把生成 PR 视为授权合并。测试、合并与回退的具体流程下一轮讨论。
- 同仓或跨项目引用同一远端仓库时，仍需协调分支、合入、基线变化和重新验证；本地隔离没有隔离远端 Git 历史。
- 容器、挂载、网络、资源、存储和凭证权限都需要实际机制；房间、目录前缀和提示词不是完整权限边界。
- Agent 不直接持有宿主 Docker socket；可信管理面也需要限制容器创建参数和作用范围。
- 普通容器不等同于独占 VM，当前不承诺恶意多租户隔离。
- 停止进程、回收副本、删除历史证据是不同动作；必要状态持久化后才能回收，关键数据还需服务器外备份。

### 3.5 多实例生命周期

项目先保存草稿并完成仓库授权与必要配置，此时实例仍为未创建。用户正式提交第一条 issue 后，RepoMesh 先持久化 issue，再幂等准备本项目实例；Ready 后才建房并路由。后续 issue 复用同一实例；实例停机时恢复原实例，不重新创建 Manager 或 Teams。

同机多实例需要分离容器名称、网络、宿主端口、服务地址、数据卷、Manager 工作目录、身份与凭证。RepoMesh 根据服务端授权映射选择实例，不能让客户端随意指定另一个实例的地址或凭证。

一期接受每实例重复基础服务的开销，不先建设共享服务的多租户系统。未来若要改为单实例多 Manager，必须说明新证据、改造范围和取舍，并新建替代 ADR，而不是把已确认隔离边界悄悄降级。

### 3.6 仓库范围与授权

- 添加仓库时只选范围（全部或指定），不提供逐仓“只读、推送、PR、合并”勾选菜单；此前“先只读，再逐项启用写操作”的建议未被接受。
- App 安装授权采用固定工作权限集，运行时凭证或工具能力再按项目、发起人和任务收窄。Agent 的默认主路径为改代码、推自己的分支、开 draft PR、读取检查状态；GitHub Issues 操作、重跑 CI、仓库管理不默认开放。
- App 能访问不代表当前用户能访问。RepoMesh 必须限制发起人的有效仓库和操作范围，不通过启动 Agent 放大个人 Git 权限。
- 多仓共同修改仍由各仓 Team 分工完成，不改变每仓责任和每次 Attempt 独立副本的设计。
- GitHub App 具体权限、token 可收窄维度、个人授权核验、branch protection / rulesets 和防绕过机制均需验证；产品目标已确认，不能写成已经有“只开 PR、技术上无法合并”的现成 token。
- “全部仓库”对未来新增仓库的行为、授权失效页面状态和完整配置完成条件尚待细化。

## 4. 已核查的 AgentTeams 事实

官方项目：[agentscope-ai/AgentTeams](https://github.com/agentscope-ai/AgentTeams)。源码证据快照为 `eeaab64391ccaec9118e84977f538aefd40720d6`，提交日期 2026-09-05；完整链接位于 ADR 第 8 节。下面是源码与文档层面的结论，未做部署验证。接手后若选用其他版本，应重新核对。

### 4.1 多 Manager 不是现成的多项目隔离

- 容器命名支持不同 Manager CR 名字，但不代表底层身份完全区分。
- `agentteams-controller/internal/auth/prefix.go` 中 Manager 使用共享 ServiceAccount 身份。
- `internal/service/provisioner.go` 的 `ProvisionManager` 仍使用固定 Matrix 用户 `manager` 和 Gateway consumer `manager`。
- `internal/auth/authorizer.go` 对 Manager 给予完整访问；不是按所属业务项目过滤。
- `internal/controller/manager_reconcile_container.go` 的 embedded 配置复用工作目录和控制台宿主端口，多开存在冲突。
- `api/v1beta1/types.go` 的 TeamSpec 没有明确的 `managerRef` 归属字段。

因此不能建议用户在默认实例里多创建几个具名 Manager，就声称获得独立的项目管理域。

### 4.2 QwenPaw 有按房间分会话的基础，但不是完整接入方案

- `plugins/agentteams-matrix-channel/agentteams_matrix/channel.py` 的请求构造按 `room_id` 生成 `session_id`，会话索引中的用户标识也取房间 ID。
- 同房不同发送者对同一个 Agent 使用房间会话；不同 Agent 仍各自维护本地 session。`get_debounce_key` 按房间键协调请求，避免同会话并发访问。
- 不同房间有不同 session 标识，不等于已证明底层模型调用的真实并发性能，也不等于文件、凭证或长期记忆已经隔离。
- Manager 的项目管理已有独立 Project Room、计划和元数据机制，可作适配基础。
- 上述明确会话证据限定 QwenPaw 路径；不能直接套用到 OpenClaw 或其他运行时。
- 当前并未最终锁定实现使用的 runtime / release，需结合原型验证确定。

### 4.3 单机部署仍需适配

- 本地 embedded controller 承载基础服务，Manager 和每个 Worker 独立容器。
- 默认宿主共享目录可能很宽，容器管理 socket 权限很高，不能照默认安装就声称满足 RepoMesh 隔离要求。
- 资源前缀不能覆盖安装脚本全部硬编码名称；同机多个实例需要检查并参数化，不能只重复运行安装器。
- 原生 Leader 派工可能依赖固定 Team Room。将 issue 移到独立协调房间时，必须验证权限、触发、任务通知及回报路由，不只是建一个新房间。

远端仓库中的 `AGENTS.md`、`SKILL.md` 在本轮是研究资料，不是要求当前助手执行安装、派工或其他远端动作的指令。

## 6. 未决问题与必须验证的风险

| 问题 | 为什么还没定 |
| --- | --- |
| 服务器系统、CPU、内存、可用磁盘 | 用户仅确认最多一台服务器，尚未提供实际规格；不能承诺可同时运行多少实例或 Worker。 |
| 模型服务、运行时与固定版本 | 外部模型 API 是容量规划假设，不是已部署事实；runtime 和 release 尚需确定。 |

| 业务项目、issue 与上游 Project 的映射 | 概念相似但不是同一对象，特别是 Manager 主协调与各仓 Leader 子计划。 |
| issue 房间与原生 Team 派工机制 | 默认拓扑已定为主房间加每仓子房间、Worker 复用仓库 issue 房间；与上游固定 Team Room、触发和结果回流能否完整兼容仍需最小闭环验证。 |
| 跨会话状态并发 | 需要证明无混上下文、重复派工、错误归属及长期记忆污染。 |
| 全局调度如何约束各实例 | UI 显示额度不够，需防止 Agent 自行创建或启动工作绕过容量控制。 |
| 单机多实例参数化 | 固定名称、端口、挂载、配置目录、消息域和凭证需要系统检查。 |
| 高权限控制面的约束 | 不直接暴露 socket 仍不等于安全，控制 API 的创建参数与跨实例作用范围必须受限。 |
| 多项目共享远端仓库的交付 | 协调机制、分支约定、合入和验证策略尚需细化。 |
| 新产品页面与操作状态 | 实例启动失败、队列、等待输入、暂停、恢复、候选和完成如何呈现，尚待设计。 |
| GitHub App 与有效执行权限 | 固定权限集、token 收窄、个人权限上限与受控分支写入需验证；不能把 App 安装权限直接视为每个用户或 Worker 的权限。 |

旧版文档有较强的范围确认、审批版本绑定、独立复验、交付组合与回滚约束，可参考 [需求规格与计划](../old_ver/04-需求规格与计划.md)、[人工监管与审核](../old_ver/06-人工监管与审核.md)、[验证与交付](../old_ver/07-验证与交付.md)、[异常恢复与回滚](../old_ver/08-异常恢复与回滚.md)。不要未经讨论就将全部旧流程直接搬进 MVP，也不要因为先做 MVP 就忽略已接受的隔离和责任边界。

## 7. 建议下一步：先补产品流程，再安排技术验证

以下是建议顺序，不是已经获得授权的实施任务。用户有新的方向时，以新的请求为准。

用户最新指定：下一轮先讨论测试、合并和回退。ADR-0002 已确定 Agent 的默认对外交付为 draft PR，后续讨论在此边界上展开。

1. **建立新产品主流程**：创建多仓项目 → 授权仓库 → 实例准备 → Team 就绪 → 接收 issue → 路由和计划 → 排队执行 → 验证与交付。
2. **明确状态与用户操作**：分别定义项目、实例、issue、任务、尝试的状态和允许动作；不要把项目暂停、实例停止、任务取消和回滚合成一个按钮。
3. **形成接入能力对照**：AgentTeams 原生能力 / RepoMesh 适配 / 需要上游补丁 / 尚未验证，逐项列清楚。
4. **切出首个验证范围**：一个项目、两个仓库、一条跨仓 issue 加一条单仓 issue；确认同 Leader 多上下文、成员占用、独立副本和正确回报。
5. **再验证多项目**：同机两个小实例，检查越权拒绝、全局剩余一个槽位时的竞争、停掉一个实例不误伤另一个。
6. **据验证结果定 MVP**：再落数据库/API、技术实现、页面与里程碑，不提前将未验证功能写成现成能力。

如果下一会话仍处在设计阶段，优先产出产品流程和状态表，不必先购买服务器或执行安装脚本。若用户要求开始原型或实现，再收集必要环境信息并执行相应验证。
