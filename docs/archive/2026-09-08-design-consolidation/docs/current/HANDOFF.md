## 3. 项目、Issue、Manager 与运行资源

使用 agentscope-ai/AgentTeams。每个长期多仓项目独立实例、一个 Manager，每仓长期 Team／Leader。首期最多一台服务器，多实例配置及资源需隔离，实际容量未测量。

项目填写名称与用途；用户关联 GitHub 账号，选择自己的仓库及实际有权参与的受邀仓库。账号关联不代替 App 安装授权，执行仍核验发起人有效权限。接入时不用选分支，Manager 按 Issue 与已有明确要求确定目标分支和固定基线，Team 在独立 Attempt 副本中执行。模型 API Key 在设置中配置，项目使用可用配置；执行环境、预算与时限可继承明确默认值并显示实际值，Worker 并发默认 1，验证小组默认关闭。管理面必要配置检查通过后才允许正式提交 Issue，不提前准备实例。部分仓库不可用时按 J3 保持项目部分可用，按实际权限及依赖处理；授权检测、拦截和恢复触发方式仍需细化。

Issue 是 **RepoMesh 内部的一条统一需求事项**，具有目标、范围、计划和验收条件，可以涉及一仓或多仓。它与 GitHub 单仓 issue 分开，可关联零到多条外部 issue 并注明来源／跟踪关系；重复导入先查映射，不自动合并需求。首期不默认启用外部 issue 创建、评论、同步或关闭操作。

```text
保存项目配置（不创建实例）
    |
正式提交 RepoMesh Issue + 主 ChangeSet，原子持久化
    |
首条 Issue：准备项目实例；后续：复用或恢复
    |
实例 Ready -> 为新 Issue 建立独立 Manager 主房间
    |
项目现有 Manager 以独立 Issue session 接收并承担总责
    |
按范围委派仓库 Leader，建立所需仓库子房间
```

所有新 issue，包括明确单仓，都先进入 Manager。Leader 负责被委派仓库工作，Manager 始终负责整条 issue；各 Agent 有自己的 session。追加消息、重试和重复事件复用原事项归属与房间。准备实例或建房失败保留已登记 Issue／ChangeSet，核查后幂等重试。

Worker 单活跃任务，每次 Attempt 独立 clone、分支、构建目录和执行记录。团队 Worker 并发数量可配置，**默认 1**，不包含 Manager、Leader 或固定验证负责人，也不要求预先创建等量常驻进程。执行共同受全局容量、项目额度、权限及独立性要求约束。

Leader／验证负责人按 Skill 和工作需要请求能力匹配的 Worker，优先复用合适空闲成员，必要时申请创建；RepoMesh 实际分配、创建和启动。优先完成已有候选的验证、必要诊断和收尾，同级按等待顺序安排。

Worker 失联时先核查旧 Attempt 已停止或失去写入能力，再开替补 Attempt；不确定时保留状态不明。验证负责人不可用时 Manager 代行协调；Manager／Leader 故障优先恢复原身份和保存的上下文，停止相关新增派工，在途按已有约束收尾。

身份、配置和整理后的知识可保留，空闲时释放执行资源，证据及必要产物保存后回收副本。Agent 不直接持有宿主 Docker socket；普通容器不承诺 VM 级或恶意多租户隔离，关键数据需要服务器外备份。

## 4. 对人窗口、模式、权限和计划控制

人只在主界面与 Manager 对话。Manager 通过 MCP 或工具呈现需要决定的事项，RepoMesh 留记录并控制执行；Agent 内部初审和复核不形成逐项人工门禁。

| 内容 | 已确认规则 |
| --- | --- |
| YOLO | 不弹人工审批、不等待人同意，在当前许可和约束内自主处理。 |
| 需要审批 | 需要用户决定的事项统一经 Manager 呈现，回应绑定具体事项及版本。 |
| 缺失业务规则 | YOLO 由 Manager 选择并记录解释；审批模式经 Manager 请人决定。解释不覆盖已有明确要求，也不冒充人已确认。 |
| 权限、预算上限、既定验收边界 | Agent 不自行扩大权限、提高上限或放宽条件。YOLO 返回受限／未完成结果，不因此增加人工等待；审批模式改变边界由人决定。 |
| GitHub App | 固定工作权限集，运行时收窄，执行范围不放大发起人的有效 Git 权限。 |
| Git 交付 | Agent 推自己的分支、开 draft PR；人和仓库规则决定合并。YOLO 不授予合并权。 |

I 本轮主要规则已确认，见 ADR-0003 第 1.7—1.11 节。当前项目及 Issue 仍统一 YOLO，首次计划及后续调整在既有授权和约束内自动判断许可；审批能力后续开发。此前默认审批模式的建议未采用。

| 后续审批能力 | 已确认规则 |
| --- | --- |
| 首版计划 | Manager 在已有权限及预算内准备并展示计划；有权的人统一批准一次，RepoMesh 应用并核对生效后启动执行，范围与上限内不逐项或逐轮审批。 |
| 审批资格 | 发起人在仍具备相应项目权限时可审批自己的计划；项目管理员或获授计划审批权限的人可代审。一名有权查看完整计划且符合资格的人批准即可；记录人及版本，代审不扩大原发起人的 Git 权限。 |
| 项目默认与 Issue 覆盖 | 项目管理员或有配置权限的人设默认模式及允许范围；新 Issue 继承默认，发起人可在允许范围内另选。项目只允许审批时不能选择 YOLO；修改默认值只影响后续新 Issue。 |
| 运行中切换 | 符合该 Issue 计划审批资格的人可在允许范围内发起；停止新派工，在途收尾并核对已提交结果后切换。YOLO 转审批时批准剩余计划，反向切换保留原待审批记录并重新判断许可，不冒充人工批准。 |
| 允许范围变化 | 新 Issue 按新范围选择；不再符合策略的已有 Issue 停止新派工、在途收尾并报告受限，保留原模式与历史，由有资格的人明确切换后继续。放宽只增加可选项，不自动切换已有 Issue。 |

成果、明确要求、拒绝决定和累计消耗保留，不重新开始整条 Issue。实际暂停按受影响上游 Project，GitHub 人工交付职责、权限、预算及验收边界继续有效。

计划必须版本化。提出变更、获准、应用和读回确认分别记录；批准不等于生效。两个模式共用实际执行约束，许可范围及上限内的 Loop 自动运行，冲突、拒绝、失败和不确定结果保留历史。RepoMesh 实际控制计划应用及任务启动，Skill 或聊天文本不能代替执行约束。

应用变更时暂停受影响的上游 Project 的新派工，等待在途及 submitted 结果处理到可重规划状态，再核对、应用并读回。不能假设首期上游支持只暂停单个分支。Skill 版本记录在计划和验证依据中，更新不静默改变在途计划或验收条件。

## 5. Graph／Loop 与测试验证

Graph／Loop 采用插件形式，首期支持顺序、并行、汇合、有界 Loop。用户通过 Manager 的自然语言请求形成版本化编排提案；直接编辑节点、属性、连线和拖拽编排为后续待办。插件接口、部署形式和上游映射仍待细化。

| 上限或处理 | 已确认规则 |
| --- | --- |
| 默认修复 Loop | 3 轮。 |
| 默认诊断补证 | 2 轮。 |
| 默认环境自动恢复 | 2 次。 |
| 提前停止 | 连续两轮同一失败且无新增有效证据，结束当前循环；新策略走版本化变更。 |
| 共同约束 | 上限写入具体计划，预算或时限先到先停，换计划不清零累计消耗。 |
| 分支与迟到结果 | 无依赖且已获准的工作可继续；旧结果保留历史，核对计划、Attempt 和组合后判断证据适用性。 |

首次计划记录各仓目标分支的固定基线。验证绑定完整仓库版本组合，未改动但参与联调的仓库也固定版本；每个验证 Attempt 有独立环境、配置及数据。各仓 Leader 提供运行说明、mock 数据及使用说明，验证侧组织准备，核对实际运行源码／构建、配置和数据，保留环境清单。

mock 数据不自动证明未实际运行的真实链路；依赖 mock 的范围要明确。业务仓脚本或代码修复交回对应 Team，专项验证环境不向业务仓推送修复。失败先保存日志与现场再重建，完成并保存证据后释放资源。

### 验证职责与结果

项目验证小组**默认不启用**，开关由项目管理员或获授配置权限的人修改并留记录。启用时有固定验证负责人；未启用时 Manager 组织具备能力和有效权限的 Worker。正式验证执行者未参与本轮被测业务改动，作者可以自测和提供脚本。

Leader 提供契约、范围、风险和已有测试；验证负责人编制必检清单，Manager 核对覆盖、依赖和预算并纳入计划；Worker 执行并初判，负责人复核采纳，Manager 汇总。小组关闭时由 Manager 承担相应组织及复核职责。业务归属按证据由 Leader 定位、Manager 协调分歧，修复归业务 Team，验证侧组织独立重验。

| 单项结果 | 判定含义 |
| --- | --- |
| 通过 | 当前检查在适用组合与前提下有有效通过证据。 |
| 业务缺陷 | 已证实违反适用要求，具体仓库归属可以待定位。 |
| 环境阻塞 | 环境、测试数据、账号等必要前提未满足。 |
| 需求待澄清 | 缺少业务解释，按当前模式处理。 |
| 暂无法判定 | 证据不足以得出可靠结论，补充诊断。 |

支付筛选示例：已确认 F1＋B1 实际运行、当前账号应看到已支付订单、mock 数据与环境前提成立，而页面为空，可以判业务缺陷；数据未准备好则属环境阻塞；应显示哪些支付状态未明确则需业务解释；缺少必要运行证据时保留暂无法判定。

最小证据包括检查归属、实际对象、判定依据、执行证据和结论。全部约定必检项具有适用于当前组合的有效通过证据，节点才通过；提交、执行结束或跳过不表示通过。多个专项节点明确覆盖范围，整条 Issue 汇总覆盖和缺口。

停用小组时停止接新工作，未启动任务交回 Manager，在途收尾、submitted 继续核对，完成后显示已停用。超时或卡住显示停用受阻，处理和保存结果后完成停用；重新启用不抢回已交出的任务或复活已终止 Attempt。

## 6. PR 与 ChangeSet：已收口的交付设计

E1—E5：Leader 初审形成有明确范围和自测记录的候选后创建 draft PR，跨仓验证可随后继续。同一 RepoMesh Issue 在同仓默认持续更新一个 PR。必检证据对当前组合有效通过、内部复核完成且必需仓库检查满足后，Manager 推荐正式审查；首期由人将 GitHub draft 转为正式 PR。反馈回原 Issue，按模式及有效计划处理。

ChangeSet 确定一次变更的归属，串联 RepoMesh Issue、仓库、PR、Candidate、Delivery Combination、依据与交付历史，也是 Agent 查看和溯源的入口。它默认随 Issue 原子登记，可以暂时没有候选、组合或 PR。

Candidate 正式提交即收录并关联 Task／Attempt，未被接受也保留检查与原因，修复产生新候选。业务候选经 Leader 内部初审接受后，Manager 按检查范围、前提和有效计划选定正式组合；未接受候选可用于明确诊断。新候选不替换在途组合。

CS1—CS14 的完整决定见[现行设计](changeset-design.md)。接手时尤其保留：

- **版本与证据**：仓库版本变化建立新组合；代码不变而验收、Skill、配置或 mock 数据上下文变化，新增相应验证记录并重新判断证据。PR 依据实际 commit／产物关联，head 或合并结果变化需要核对。各仓成功不等于整体成功。
- **状态与幂等**：执行、验证、交付进展分别汇总；事实、判断及更正保留来源和历史。每个逻辑操作有独立 ID、目标和输入摘要，同 ID 不同输入拒绝；并发校验目标版本、同目标冲突串行处理，超时和重启先核查结果。
- **完成与合并**：约定交付物、验收和必做事项完成；代码变更所有必需 PR 已人工合并，最终实际组合证据有效，才满足对应完成条件。无代码改动按相应交付约定判断；部署另记。按兼容性选合并顺序，例如验证 F0＋B1 可用后才考虑 backend 先合。
- **部分失败与恢复**：部分合并保留各仓真实状态，用实际已合并版本形成后续组合、重判证据并推进剩余工作，不自动撤销成功部分。未合并 PR 的取消留原 ChangeSet；已合并代码撤销由人发起关联恢复 Issue／ChangeSet，仓库 Team 出撤销 PR、人合并；首期部署及数据恢复由相应有权限的人执行并记录。
- **后续归属与查询保留**：本轮修复沿用原 ChangeSet，完成后新增范围建立关联的新 Issue／ChangeSet；误标完成追加更正，首期无嵌套 ChangeSet。Agent 先读带引用的摘要，再查明细与证据；默认当前记录，可在既有权限内查询同项目相关历史，首期不默认跨项目查询。项目存续期保留归属、版本关联、决定和操作结果，必要验收证据随交付档案保存，临时材料按策略清理并标明可用性。

恢复和人工交付处理不为 YOLO 插入逐项执行审批；ChangeSet 不扩大任何权限。具体运行机制尚未实现。

[结构说明](changeset-structure.md)使用“稳定主记录＋关联明细＋摘要视图”解释这些关系。记录修订信息用于并发校验，Candidate／组合表达产物版本，Plan Version 表达工作安排；不能把这些版本混为一套。字段名、数据拆分、示例 YAML 和接口均未冻结。
